## 2026-08-16(5) 「明細だけ畳む」を測ろうとして、盤面が用途を通していないことが分かった

**問い**(外部評価4人目・Apple マップの乗換案内): 「ft_snapshot の出力が非常に長い。重複ID・
曖昧ラベル・scroll-leftover の note が大量に付き、必要な要素を探すのが難しい」。
2026-08-16(1) の宿題 —— **注記を落とすのではなく明細だけ畳んだらどうか** —— をやる回。

**先に盤面を採った**(`Tests/Fixtures/RealAppSnapshots/ios-maps_transit_steps{,_expanded}`)。
評価者の画面そのものを固定コーパスへ入れて実数を出した:

| | 注記 | 木 | 比 |
|---|---|---|---|
| 経路詳細(展開) | **3,621B** | 5,658B | **64%** |
| 参考: `ios-news_feed` | 3,070B | 13,155B | 23% |

内訳は `duplicateIDsNote` 1,810B + `ambiguousLabelsNote` 880B = **74%**(評価者の名指しと一致)。
**どれも誤検知ではない** —— `#DetailButton`×10 `#PrimaryLabel`×8 が実在し、素の `#id` では
1つも選べない。つまり下げ道は「対象を減らす」ではなく文面側にしか無い。

**短縮形(2回目以降)は答えにならない**と分かった: 3,621B → 2,894B(80%)にしか下がらない。
畳んでいるのは**凡例だけ**で、列挙本体は毎回出る。当初の候補「同じ画面の再掲を止める」は
これで没(再掲は主因ではない)。

**作った物**: `FT_MCP_NOTES_BRIEF=<鍵>`(注記は出したまま**明細だけ**畳む)と
`Scripts/mcp-bench.sh --variant <名>=brief:<鍵>`。`FT_MCP_NOTES_OFF` は本ごと落とすので、
A/B が測るのは「事実が要るか」になってしまう —— その答えは 2026-08-16(1) で出ている
(落とすとセレクタを書くタスクで ft_* が 17→28)。残る問いは**明細まで要るか**だった。

**回して止めた**: `and-browser-dupgrid-selector` を full/brief × 5 で投げ、**2 run 目で中止**。
記録を読んだら、**この盤面では明細がそもそも出ていない** —— 全群が既存の
`compactGroupLine` で1行に畳まれており(`— none of these have a selector on this screen;
tap by ref instead.`)、brief が畳む対象が1つも無い。残り8 run は定型文 200B の差を
測るだけだった。**陽性対照を「注記が出ているか」で取っていたら気付かない** ——
注記(ヘッダ)は両側で出る。見るべきは**明細の有無**(`grep " >> \."` = full で 0 だった)。

**代わりに固定コーパス 40 枚で brief の効き目を全数測った**(offline・数秒):

| 画面 | full | brief | 差 |
|---|---|---|---|
| `ios-maps_transit_steps_expanded` | 2,690 | 1,459 | **−1,231** |
| `ios-maps_suggest_keyboard` | 2,135 | 1,356 | −779 |
| `sutec-home` | 1,909 | 1,277 | −632 |
| `and-settings_root` | 1,399 | 823 | −576 |
| (合計 40 枚) | 41,608 | 32,123 | −9,485 |

**この表が実装の欠陥を1つ出した**: 10 枚で brief のほうが**長かった**(既に畳まれている
画面へ末尾の総括を足していた)。brief は full の**厳密な部分集合**でなければ、A/B が
「明細の有無」ではなく定型文の差を測る。修正後は残り 2,045B。

**ついでに試して撤回した設計変更**: 最大の塊 `#DetailButton ×10` は全員索引形なのに
畳まれていない —— `compactGroupLine` が**スコープ一致**を要求しているため。緩めると
40 枚で 1,555B 減った(最悪画面 2,690→2,290)。**が、撤回した** ——
`MCPNoteCompactionTests` が witness を持っており(Google マップのタブ帯は
**どのタブの子かが祖先名にしか乗っていない**)、畳んだ瞬間に5件が区別できなくなる。
**1,555B と識別情報は釣り合わない。再提案しない**。

**次にやること**: 「明細まで要るか」は**まだ測れていない**。要るのは
**⑴ 明細が実際に出る盤面**(上の表の上位 = 地図の経路詳細 / 設定ツリー)で
**⑵ セレクタを書く用途のタスク**(操作タスクでは 2026-08-13 以降つねに ±0)。
`and-settings-keyboard` は ⑴ を満たすが操作タスク、`and-browser-dupgrid-selector` は
⑵ を満たすが ⑴ を満たさない —— **今の盤面表には両方を満たすものが1つも無い**。

**盤面を作ろうとして分かった制約**(同日・続き):

- **web ページには id 付きの容器を作れない**。`<p id="issued">` を置いた既存盤面を
  Android Chrome で実際に読むと、木では id を持たない `staticText` になる
  (id を持つのは `#url_bar` 等**ブラウザ自身の chrome だけ**)。
  「重複値が id 付き容器の中にある」形は **web 盤面では再現できない**
- **Android 設定ツリーは判別に使えない**。`#title ×7` の明細は `.staticText&&ストレージ` を
  出すが、行 clickable と title は**単鎖**なので `isSingleChain` により
  `ambiguousLabelsNote` は発火せず、**素のラベルで足りてしまう** ——
  明細が無くても同じ答えに着く盤面では、この問いを分離できない

**削減を2つ試して2つとも撤回した**(どちらも同じ砦に当たった):

| 試した削減 | コーパス 40 枚での効果 | 撤回した理由 |
|---|---|---|
| `compactGroupLine` のスコープ一致要求を外して畳む | −1,555B | Google マップのタブ帯は**どのタブの子かが祖先名にしか乗っていない**(`MCPNoteCompactionTests` が witness を持つ)。畳むと5件が区別不能 |
| 索引形は ref だけにして文字列を出さない | −3,401B(明細の 42%) | 同上 —— **長さの元凶であるスコープ接頭辞が識別情報そのもの**。同じテストが同じ理由で落ちた |

**明細の中身を全数で分類した**(302 項目・8,013B。畳まれた群 72 行 / 明細を出した群 78 行):

| 形 | 件数 | バイト | 削れるか |
|---|---|---|---|
| 素のラベル / `#id` | 147 | 3,137B | 文字列は木にあるが、**一意である保証**が情報 |
| `.型&&ラベル` | 53 | 1,457B | 木からは導けない |
| スコープ付き索引 | 96 | 3,401B | **識別情報を運ぶ**(上の撤回2件) |
| 書けない(—) | 6 | 18B | — |

**現時点の結論**: この2本の注記が長いのは**画面が実際に曖昧だから**で、機械的に削れる部分は
既に削ってある(全員索引形かつ同一スコープの群は 72 行ぶん畳み済み)。外部評価への回答は
**「測った。削れる部分は残っていない」**。`FT_MCP_NOTES_BRIEF` は**問いを開いたまま残すための道具**
として置いておく —— ⑴⑵ を同時に満たす盤面が現れたら、その日に測れる。

## 2026-08-16(4) ref 失効の税は存在しなかった —— 設計変更を見送る

**問い**(外部評価3人目 + 私の「最も重い」評価): 「ref がスナップショットをまたいで変わるので、
複数ステップの操作では毎回撮り直す必要があり、ターン数が増える」。私はこれを**設計の穴**と
呼び、`RefGuard.relocate` を世代跨ぎへ広げる案まで書いた。**測ってから決めることにした**。

**先に機構を読んだ**: ref は消えない —— `maxRefGenerations = 5` の窓の内側なら受け付けて
現在の木へ引き直す(`verifiedRef` の `isStale` 経路)。つまり争点は「本当に撮り直しているか」。

**測った物**: `and-browser-dupgrid-multitap`(書けるセレクタが1つも無い画面で
札幌→東京→大阪 の降水確率を3回タップ)。**A/B ではなく絶対値** —— 見るのは
「タップ1回あたり何枚撮ったか」。`--repeat 5`。

| n | ok | 合計 taps | 合計 snaps | タップあたり |
|---|---|---|---|---|
| 5 | 5/5 | 15 | **5** | **0.33 枚** |

内訳(5 run):

    #1  snaps=0 taps=3   open_url > tap > tap > tap
    #2  snaps=2 taps=3   (唯一の撮り直し。古い ref の再利用 2 回 = 引き直しが効いている)
    #3  snaps=1 taps=3   open_url > snapshot > tap > tap > tap
    #4  snaps=1 taps=3
    #5  snaps=1 taps=3

**判定: 設計変更は不要**。エージェントは**1枚撮って3回叩く**のが既定の振る舞いで、
撮り直していない。撮り直した1 run も、古い ref がそのまま通っている(引き直しの陽性対照)。
**「ref が失効するから往復が増える」は、この盤面では起きていない。**

**#1 が 0 枚なのは同日の別修正の効果**: `ft_open_url` の `snapshotAfter` が着地を待って
木を返すようになった(0e8939c)ので、開いた直後に ref が手に入る。**別々に入れた2つの変更が
同じ税を削っていた**。

**残る本物の問題は別の場所にある**: 同じ苦情の後半「セレクタが書けない画面では逃げ場が無い」は
**操作するエージェントの問題ではなくシナリオを書く側の問題**(実ページで 53% が書けない)。
そちらは ref では解けない —— シナリオに ref は書けないので。手を入れるならこの穴であって、
ref の寿命ではない。

## 2026-08-16(続々) シナリオを書く側で測ると差が出た(初)

**測る読者を変えた**: 前2節は「操作するエージェント」で、どちらも手数 ±0 だった。
理由の仮説は「エージェントは常に ref で叩くので、素のラベルが一意かを知る必要がない」。
そこで**触らずに検証を書く側**を測る `and-browser-dupgrid-selector` を足した ——
問いは「素のラベル `20%` はこの1要素を指せるか / 一意に指せる式は書けるか」。
**件数は聞かない**(Chrome は可視部分しか a11y に出さないのでスクロール位置で変わる)。

| variant | task | n | ok | ft_* 呼び出し | 拒否 | wall s | out tok |
|---|---|---|---|---|---|---|---|
| full | and-browser-dupgrid-selector | 5 | 5/5 | 17 | 5 | 135.6 | 8704 |
| no-ambiguous | and-browser-dupgrid-selector | 5 | 5/5 | **28** | **12** | 161.4 | 9919 |

**陽性対照**: 注記を含む run は full 5/5・no-ambiguous 0/5。

**差**: ft_* の呼び出しが **17 → 28(+65%)**、wall +25.8s、出力トークン +14%。
**答えは両方とも 10/10 正しい**(`unique=no selector=none`)—— 注記は正解率ではなく
**そこへ至る手間**を買っている。

**いちばん解釈しやすい指標**: **MCP の外へ答えを探しに出た run**
(`Bash` / `Read` で ftester のソースや docs を読もうとした)が **full 2/5 → no-ambiguous 4/5**。
注記が無いと、エージェントは「一意に指せるかの規則」を**自分でソースに探しに行く**。

**割り引くべき点(実験系)**: それらの `Bash`/`Read` は `--allowedTools mcp__ftester` で
**全部拒否されている**(拒否 5 → 12)。拒否された呼び出しもターンとトークンを食うので、
`tools` 列の差 3 → 5 には**サンドボックス固有の水増しが混じる**。上の表を ft_* だけで
数え直したのはそのため。**それでも ft_* だけで 17 → 28 なので、差の向きは変わらない**。

**判定**: `ambiguousLabelsNote` は**残す**。操作するエージェントには効かないが、
**セレクタを書く側では手間を買っている**(初の実測)。外部評価の「長すぎる」への回答は
「測った。操作中は効かないが、シナリオを書くときには効いている。よって既定では消さない」。

**次に詰めるなら**: 差の実体は「規則を探し回る手間」なので、注記そのものを削るのではなく
**"none of these have a selector on this screen" の1行だけ残して明細を畳む**形が候補。
それを測るには variant を「注記を落とす」ではなく「明細だけ落とす」にする必要がある
(いまの `FT_MCP_NOTES_OFF` は本単位でしか落とせない)。

## 2026-08-16(続) 用途を通すタスクで測り直した —— やはり手数 ±0

**前節の宿題**: 読み取りタスクでは注記の用途(重複する値から1つを選んで**操作する**)を
通っていなかった。盤面にタップの観測可能な効果を足し(`tap_result=<地点>-<項目>`)、
`and-browser-dupgrid-tap`(大阪の降水確率をタップさせる)を足して測り直した。
`20%` は4地点にあるので、当てずっぽうは別のトークンになって落ちる = **成否が信号になる**。

| variant | task | n | ok | tools | snaps | err | wall s |
|---|---|---|---|---|---|---|---|
| full | and-browser-dupgrid-tap | 5 | 5/5 | 4 | 1 | 0 | 49.6 |
| no-ambiguous | and-browser-dupgrid-tap | 5 | 5/5 | 4 | 1 | 0 | 42.7 |

**差: tools ±0・ok ±0**。10 run すべてが**正しいセル**(大阪の降水確率)を叩いた。

**陽性対照**: 注記を含む run は full 5/5・no-ambiguous 0/5。

**採点をやり直している**(重要): 最初の集計は full 5/5・no-ambiguous 3/5 と出たが、**これは
実験系の欠陥**だった。`completed` は**エージェントの最終テキストに expect を当てる**だけなのに、
`expect` を `tap_result=osaka-precip` と書き、プロンプトでは「`RESULT: <tap_result の値>`」と
指示していた。つまり**散文に `tap_result=` と書いたかどうか**で割れていただけで、
10 run とも答えは `RESULT: osaka-precip`(正解)。**トランスクリプトは残っているので
expect を直して再集計した**(デバイスの再実行は不要)。task の expect も直してある。
**「差が出た」と読んだら、まず実験系を疑うこと** —— この節はその実例。

**判定**: 読み取りタスク・操作タスクのどちらでも、この注記は手数も成否も動かさない。

**なぜ動かないかの仮説(次に測るべきもの)**: エージェントは**常に ref で叩く**ので、
「素のラベルでは一意に指せない」という情報を必要としない —— ref は構造的に一意だから。
この注記の本当の読者は **⒝ シナリオを書く側**(セレクタを書かねばならない)で、
**それは手数では原理的に測れない**(この README の「ここで測れないもの」に既に書いてある)。
測るなら `draft: true` のタスク(`and-form-wifi` と同じ形)にして `sel ok/weak` を見る。
**それまで注記に手を入れない** —— いま消すと、測っていない読者のために効いている可能性を壊す。

## 2026-08-16 `ambiguousLabelsNote` は手数を動かすか(browser・重複ラベルの格子)

**問い**(外部評価2名から独立に): 曖昧ラベル警告が長すぎて実用情報が埋もれる。既定で畳むべきか。
バイト比は測ってあった(実ページでツリー比 19〜22%)が、**バイトは読み手のコストではない**ので
手数で決める必要があった。

**盤面を先に作った**: この注記の最大の発生源は `browser` アーキタイプ(固定コーパス14枚の
平均 682B)なのに、**ベンチに browser 盤面が1つも無かった**(最も近い `cmp-webview-grid` は
自前アプリの WebView で、値が全部ユニークなのでこの注記がほとんど出ない)。
`and-browser-dupgrid`(実ブラウザ + `Bench/boards/weather-dupgrid.html`)を足して埋めた。
忠実さの確認: この盤面の注記 944B / ツリー比 20% は、実ページ(831B/21%・943B/22%・1163B/19%)の
真ん中に入る。

**回した物**: `and-browser-dupgrid` を `--repeat 3`、variant は `full` と
`no-ambiguous`(= この注記だけ落とす)。

| variant | task | n | ok | tools | snaps | err | wall s | out tok |
|---|---|---|---|---|---|---|---|---|
| full | and-browser-dupgrid | 3 | 3/3 | 4 | 1 | 0 | 61.7 | 4229 |
| no-ambiguous | and-browser-dupgrid | 3 | 3/3 | 4 | 1 | 0 | 66.4 | 4627 |

**差: tools ±0**。しかも **6 run すべてが完全に同一**だった —— 同じデバイス・同じ5手
(`ToolSearch > list_devices > open_url > snapshot > screenshot`)・同じ正解。
wall の +4.7s と out tok の +398 は n=3 のばらつき(手順が1手も違わない以上、注記の効果ではない)。

**陽性対照**: 注記を含む run は `full` 3/3・`no-ambiguous` 0/3
(`grep -l "match multiple elements" <variant>/*.jsonl`)。落とす操作は効いていた。

**判定できたこと**: この盤面・このタスクでは、注記は 1 run あたり約 328B を払って**手数を
1手も買っていない**。

**判定できないこと(重要)**: タスクが**読み取りだけ**で、しかも1スナップショットで解ける。
この注記の目的は「重複するラベルの中から**1つを選んで操作する / セレクタに書く**」ときの
手当てなので、**その用途は一度も試されていない**。ここから「注記を消してよい」とは言えない。
**タスク設計の欠陥はこちらにある**(盤面は形を再現したが、タスクが注記の用途を通っていない)。

**副次で分かったこと(こちらのほうが示唆的)**: 6/6 の run が**スクリーンショットを撮って**
レイアウトを確認していた("masonry/floating grid" と自分で述べ、木の並び順を信用しなかった)。
**重複ラベルの曖昧さを、エージェントは注記ではなく `ft_screenshot` で解いている**。
注記の有無で行動が1手も変わらなかったのは、この代替手段が先に成立しているからかもしれない。

**この盤面で最も大きい注記は曖昧ラベルではない**: `missingPageContentNote` が 457B/run、
「操作直後に読んだ」注記が 239B/run で、どちらも **6/6 の run で発火**している。
出力バイトを減らすのが目的なら、狙うべきはこちら。

**次にやること**: 重複するセルの**1つを操作させる**タスク(例:「大阪の降水確率のリンクをタップ」)を
足して測り直す。盤面にはタップ結果の表示が要る(現在のセルは `javascript:void(0)` で
観測可能な効果が無い)。それまで**この注記に手を入れない**。

## 2026-08-13 `unlabeledClickablesNote` は手数を動かすか

**問い**(docs/mcp-audit-rounds.md の未修正の持ち越し): この注記は Android メッセージの
「新しい会話」画面で偽の主張をする —— `[16] clickable (12,85 126x126)` を
「安定したセレクタで指せない」と言うが、**その内側に一意ラベル「戻る」があり `tap '戻る'` は成功する**。
矩形の**包含**を拾う幾何規則を足すべきか。台帳は「足すなら手数を測ってから」と保留していた。

**回した物**: `and-chat-newconv`(この注記が発火する盤面)/ `and-settings-keyboard`(対照。
Android 設定にこの注記は出ない)。`--repeat 5`・variant は `full` と `no-unlabeled`(= この注記だけ落とす)。

| variant | task | n | ok | tools | snaps | err | wall s |
|---|---|---|---|---|---|---|---|
| full | and-chat-newconv | 5 | 5/5 | 6 | 1 | 0 | 31.1 |
| full | and-settings-keyboard | 5 | 5/5 | 7 | 1 | 0 | 39.0 |
| no-unlabeled | and-chat-newconv | 5 | 5/5 | 6 | 1 | 0 | 33.1 |
| no-unlabeled | and-settings-keyboard | 5 | 5/5 | 7 | 1 | 0 | 35.8 |

**差: tools ±0(両タスク)**。wall の ±2〜3s は n=5 のばらつきの中。

**陽性対照**: `full` の chat の記録には注記が **1 run あたり4回**出ており、`no-unlabeled` では

## 2026-08-13 「セレクタの品質」の軸を足した(手数では測れない側)

**動機**: 注記には読者が2種類いる —— ⒜ いま作業しているエージェント(タスクを終えるための情報)と

`duplicateIDsNote` をこの軸で A/B するという当初の狙いは**成立しない**。

## 2026-08-13 実際の run で「どの注記が何バイト出ているか」を測った

**動機**: カタログを縮めたいのに、**削る候補を「実際に出ている量」で並べられなかった**。
`NoteCoverageTests` は固定コーパスに対する**満額**のバイト数で、実運用の頻度を含まない。
`bench-summary.mjs` に `noteCost()` を足し、記録に残っている tool_result から
注記行(`note:` / `caution:` / `⚠️`)を拾って**署名ごとにバイトを畳む**ようにした
(鍵との写像は持たない —— 二重管理は必ずズレる)。**デバイス時間はゼロ**で、
既に取ってある記録に後から流せる。

**`and-form-wifi`(5 run・合計 15,870 B)**:

| バイト | 回数 | 注記 |
|---|---|---|
| 3255 | 31 | `long labels are shown cut off with "…"`(**短縮形が 6回/run**) |
| 2480 | 20 | `2 scroll areas on screen: #content_parent …` |
| 1795 | 5 | `this tree was read immediately after the action …` |
| 1760 | 22 | `the soft keyboard covers (0,1541 1080x883) …` |
| 1655 | 5 | `these ids are shared by multiple elements …`(初回の満額) |

**`and-chat-newconv` + `and-settings-keyboard`(20 run・合計 19,481 B)**:

| バイト | 回数 | 注記 |
|---|---|---|
| 7180 | 20 | `this tree was read immediately after the action …`(**359 B × 1回/run**) |
| 3471 | 39 | `duplicate ids — write one of these instead …` |
| 3310 | 10 | `these ids are shared by multiple elements …` |

**分かったこと**: **実現コストの順位は、固定コーパスの満額バイトの順位と違う**。
カタログのコメントは主因を `duplicateIDsNote`(15.1KB)/ `ambiguousLabelsNote`(10.0KB)と
書いているが、実際の run で最も多く出ているのは:

1. **`this tree was read immediately after the action`** —— `snapshotAfter` を使うたびに
   **359 B を毎 run 満額で**払う静的な但し書き
2. **`long labels are shown cut off`の短縮形** —— 1回 105 B が **6回/run** 繰り返される
   (`once()` で短くはなっているが、**短縮形でも 100 B 級**で、しかも毎回出る)

どちらも**画面の中身に依らない定型文**で、**削る/短くする判断が手数と独立に立てられる**
(「この但し書きが無いと手詰まりになる」形が想像しにくい)。

**同日に削って測り直した**(`and-form-wifi`・`--repeat 5`):

| 注記 | 1回あたり | 変化 |
|---|---|---|
| `this tree was read immediately after the action …` | 359 B → **239 B** | **−33%** |
| `long labels …` の短縮形 | 105 B → **67 B** | **−36%** |

**合計は 15,870 B → 14,890 B(−6.2%)**。ただし合計は run ごとの経路のばらつきを含む
(同じ注記の発火回数が 31→33、20→23 と動いている)ので、**1回あたりのバイトのほうが
きれいな指標**。**挙動は変わっていない**: 完了 5/5、`sel ok/weak` は 8/0 のまま、
手数は 13 → 14(この task は 12〜14 で揺れており n=5 の範囲内)。

**落としたもの**: ⒜ 「不変に見えたら1回だけ待って撮り直した(上の注記を見よ)」——
**それが実際に起きた回には settle-lite の注記そのものが出る**ので二重だった
⒝ 短縮形の「最初の注記を見よ」—— 短縮形なのに満額の指示を繰り返していた。
**残したのは行動に要る部分だけ**(「操作直後の木である」「`waitFor` で確かめてから無いと言え」
「`*prefix*` で書け」)。

**次の候補**(同じ理由で削れる可能性): `2 scroll areas on screen …`(2,852 B / 23回)と
`the soft keyboard covers …`(1,920 B / 24回)。どちらも**毎回同じ形**で出る。
ただし前者は**代替手段が無い盤面がある**(容器の中でしかスクロールできない画面)ので、
消すのではなく**短くする**側で測ること。

## 2026-08-13 代替手段の無い盤面で A/B したら、それでも手数は動かなかった

**この日いちばん重い結果。** 今日の A/B が2件とも ±0 だった理由を「代替手段があるから」と
説明してきた(`ft_navigate back` で回復できる等)。**その説明が使えない盤面を作って測った**。

**盤面**: `cmp-webview-grid`(WebView 画面の格子。見出し行は `aria-hidden` なので
**ツリーからは原理的に取れず、`ft_screenshot` でしか読めない**)。
**タスク**: 3つの列見出しをすべて読む + 8/15 の気温を読む。

| variant | ok | 各 run の手数 | 中央値 | note B |
|---|---|---|---|---|
| full | 5/5 | 7, 8, 10, 11, 12 | 10 | 1907 |
| no-grid | 5/5 | 7, 9, 11, 13, 15 | 11 | 1180 |

**陽性対照は有効**(`full` は 4/5 の run で発火・`no-grid` は 0/5)。
**それでも差は誤差の中** —— 範囲が 7〜12 と 7〜15 で大きく重なる。
**両方とも 5/5 完了**し、注記が無くてもエージェントは自力で `ft_screenshot` へ到達した
(スクショ回数は full 7回 / no-grid 9回)。注記のコストは **727 B/run**。

**結論**: **「まっさらなエージェントの手数」は、注記の価値を測る指標として弱い**。
エージェントは資源が豊富で、案内が無くても別の道で目的を達する。
**手数で正当化できる注記は、ほとんど無いかもしれない**。

**この評価軸を捨てるという意味ではない** —— 手数は「注記が**害**になっていないか」
(読ませすぎて遠回りさせていないか)の検出には引き続き効く。
**足す/消すの判断材料としては、`note B`(実現バイト)のほうが決定的**に使える。

**盤面自体は残す価値がある**: offline で `gridWithoutHeaderNote` を発火させられる唯一の場所で、
**バイトの回帰**と**検知の回帰**には引き続き使える(実 web を叩くタスクは盤面が毎日変わる)。

## この計測で見つかった bench 側の欠陥(修正済み)

- **`--out` に相対パスを渡すと 20 run すべてが起動しない**。run は `cd "$CWD"` してから
  `claude` を起動するので、相対の `--mcp-config` は cwd 側で解決されて必ず見つからない。
  それでも `claude` は 1 イベントも出さずに終わるので、集計は `0/5` = **タスク失敗と
  見分けが付かなかった**。`--out` を絶対パスへ正規化し、**記録が空の run はその場で名指し**して
  集計の前に「台本の失敗」だと言うようにした
- **README が書いていた陽性対照が届かない**。「サーバが起動時に `FT_MCP_NOTES_OFF: silencing …` を
  stderr へ出すので `bench.log` で確かめる」とあるが、**MCP サーバの stderr は `claude` が
  抱えるので `bench.log` には出ない**(実測 0 件)。効く対照は**記録の中の注記そのもの**を
  数えること(上の陽性対照)。README を直した
