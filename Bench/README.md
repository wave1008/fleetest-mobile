# MCP の使い勝手を測る(まっさらなエージェントのタスク完了)

**評価者を替えるための道具**(2026-08-12)。それまでの評価は「フルコンテキストの私が応答を読んで
違和感があるか」だった。バグは有限なので監査を重ねれば減衰するが、**「もっと分かりやすく
言えたはず」は無限に出る**ので、その評価軸では注記も分岐も単調に増え続ける(実際そうなった)。

ここで測るのは**そのアプリを初めて触るエージェントが、タスクを終えられたか・何手かかったか**。
注記を1本足すか消すかは、この手数が動いたかどうかで決める。

```
Scripts/mcp-bench.sh --list
Scripts/mcp-bench.sh --task cmp-scroll-find --repeat 3
# A/B: duplicateIDsNote を落とした版と比べる
Scripts/mcp-bench.sh --task cmp-scroll-find --repeat 5 \
  --variant full= --variant no-dupids=duplicateIDsNote
```

生の記録は `.ftester/bench/<日時>/`(stream-json・`summary.json`・`bench.log`)。そこは
`.gitignore` されているので、**回したら結論を Bench/measurements.md へ1節書く**
(判定に使った陽性対照まで)。

## 読み方

| 列 | 意味 |
|---|---|
| `ok` | 完了した run / 総 run。**最終行の `RESULT:` を `expect` で照合**した結果(自己申告ではない) |
| `tools` | ft_* の呼び出し回数の中央値。**これが主指標** |
| `snaps` | `ft_snapshot` + `ft_batch` の回数。注記が減らすべきは主にここ(木の読み直し) |
| `err` | `isError` で返った回数 |
| `sel ok/weak` | **セレクタの品質**(`"draft": true` のタスクだけ。下書きの安定セレクタ数 / 索引 + TODO の数)。**手数と独立の軸** —— エージェントは常に ref で叩けるので、書き手向けの注記は手数に出ない。`-` は下書きを採っていない task |

差分は**両方が全 run 完了した task だけ**を比べる(手数が少ないのは早々に諦めたからかもしれない)。
`tools +3` は「その注記を落としたら手数が3増えた = 注記は効いていた」と読む。

## 判定の規律

- **1回のグリーンで判定しない**。`--repeat` は最低3、差が小さいなら5以上
- **陽性対照は記録の中で数える**: 落としたはずの注記の文言を
  `grep -c "<注記の一部>" <variant>/<task>-*.jsonl` で数え、
  **base では出ていて variant では 0 になっている**ことを確かめる。両方 0 なら
  「そもそもこの盤面では発火しない」= その A/B は注記について何も言っていない。
  **`bench.log` を見ても分からない**(2026-08-13 実測): サーバは起動時に
  `FT_MCP_NOTES_OFF: silencing …` を stderr へ出すが、**その stderr は `claude` が抱える**ので
  `bench.log` には1件も残らない。綴りを間違えた鍵の `NOT a note key (ignored)` も同じ
- **記録が空の run(`!! 記録が空`)が出たら、その回の集計は読まない**。それは
  タスクの失敗ではなく台本の失敗(claude が起動していない)なので、`bench.log` の
  `Error:` を先に潰す
- **差が出ないときは実験系を疑う**。ビルドは毎回 `swift build --product ftester-mcp` を通すが、
  タスク・盤面・デバイスが変わっていれば手数は簡単に動く
- **CLAUDE.md の無い作業ディレクトリで走らせている**(`<out>/cwd`)。保守者向けの指示を
  読んだエージェントは「まっさらな読み手」ではない

## タスク

| id | archetype | 何を代表するか |
|---|---|---|
| `cmp-scroll-find` | dense-list | スクロール容器の中の探索(縦リスト + 横カルーセルが同居する画面) |
| `cmp-text-input` | form | 入力とソフトキーボードの遮蔽 |
| `cmp-noid-directional` | no-id | id を公開しないアプリ(方向セレクタしか使えない) |
| `cmp-webview-aria` | webview | `#id` が効かない画面・`aria-label` 由来のラベル(内蔵 HTML なので通信に依存しない) |
| `maps-route` | map | 実アプリ・高密度・システムアプリ(xcuitest ブリッジが要る) |
| `ios-settings-about` | settings | 実アプリ・深い設定ツリー(2階層たどって値を読む) |
| `and-settings-keyboard` | settings | **Android の**設定ツリー(3階層 + 根のスクロール。行の状態=スイッチも読む) |
| `and-chat-newconv` | chat | **Android の**チャット。入力 + ソフトキーボード遮蔽 + **`unlabeledClickablesNote` が偽の主張をする戻るボタン**を実際に押させる |
| `and-form-wifi` | form | 通常欄 + **伏せ字欄** + 有効化条件つきボタン。**フォームが伸びると操作ボタンがツリーから消える**状態を必ず通るので、そこからの回復の手数が測れる |
| `cmp-webview-grid` | webview-grid | 見出し行が `aria-hidden` の表。**列見出しはツリーから原理的に取れず `ft_screenshot` でしか読めない** = 代替手段の無い盤面(`gridWithoutHeaderNote` の offline witness) |
| `and-browser-dupgrid` / `-tap` / `-multitap` / `-selector` | browser | **実ブラウザ + 中身の変わらないページ**(`boards/weather-dupgrid.html`)。同じ値が何度も出る格子で、読み取り・操作・ref 再利用・セレクタ品質を別々に問う。詳細は下の「browser 盤面」 |
| `and-browser-grid-noheader` | browser | 実ブラウザ側の**見出しが落ちる格子**(`boards/grid-noheader.html`)。`cmp-webview-grid` と同じ形を、注記が実際に生まれる経路(Chrome + DOM)で測る |

自前 SUT の4つは**対照**(盤面が契約で固定されているので手数のブレが小さい)。
`maps-route` だけが実アプリで、**自前 SUT は実アプリの形を代表しない**(遮蔽・積み重なり・
中身外しは実アプリでだけ出る。`Tests/Fixtures/RealAppSnapshots/README.md` 参照)。
**両方を見ること** —— 対照だけだと実アプリの難しさが測れず、実アプリだけだと盤面のブレを
注記の効果と取り違える。

**`"draft": true`** を書いたタスクは、台本がプロンプトへ「最後に `ft_draft_scenario` で書き戻せ」を
足す(**指示は台本に1本だけ持つ** —— タスクごとに書くと A/B の両側で頼み方が変わり、
品質の差が文言の差に化ける)。**この軸で注記は A/B できない** —— 下書きのセレクタは
エージェントではなく**サーバが選ぶ**ので、注記を落としても下書きは変わらない(2026-08-13 に判明。
Bench/measurements.md)。使い道は**探索が「再生できるシナリオ」を産んでいるかの回帰ゲート**。

`expect` は**契約から決めた値**(`E2EAppCMP/docs/ui-contract.md`)。SUT の契約を変えたら
ここも変えること。

## アーキタイプを足すとき

**足すならアプリ名ではなくアーキタイプで足す**。スナップショットのコーパスは 2026-08-12 に
19 枚(地図 14)→ 25 枚(地図 14 + settings 2 + chat/keypad/media/webview 各1)へ広げ、
それだけで**「地図でしか出ない」と見えていた注記5本のうち3本が他アーキタイプでも出た**
(`Tests/Fixtures/RealAppSnapshots/README.md`)。1アプリを深く掘るより、初見のアーキタイプを
1つ足すほうが1件あたり安い。

タスク側は 2026-08-12 に settings と webview を足し、2026-08-13 に **Android の settings / chat / form**
を足して **実アプリ5 + 自前 SUT 4**。コーパスにあってタスクに無いアーキタイプは
**media / keypad / dense-list**。

**2026-08-13 まで全タスクが iOS だった。** Android を足したのは、注記の未解決の witness
(`unlabeledClickablesNote` の包含形)が Android メッセージにしか無かったため —— **測れない盤面の
上で設計判断を保留し続けていた**。盤面は両方とも `ft_launch` で根まで戻るので run 間の後始末が要らない
(chat は**送信しない**ので会話一覧は0件のまま)。

**監査ラウンドとの関係**: 監査(docs/mcp-audit-rounds.md)で初見のアプリを触ったら、
フィクスチャを1枚採るのと同じ流れでここへタスクを1本足す。そうすると
「そのアーキタイプで手数が減ったか」を次の変更のときに測れる。

## この穴がいま制約になっている(2026-08-13)

下の「測れないもの」は 2026-08-12 には周辺の話だったが、**その後この穴がボトルネックになった**。
ブラウザ(= 実 web ページ)を5ラウンド回した結果、新しい注記はほぼ全部この形から生まれており、
**注記を最も産む形に、注記を止める機構が無い**状態が続いている。実際、ブラウザ5ラウンドの
実バグは 3→3→4→4→4 と減衰せず、**その 3/4 は前のラウンドで入れた注記の手直し**だった
(docs/mcp-audit-rounds.md §「自作の機構を監査しているとき、それは収穫ではない」)。

**当面の代用**: `NoteBudgetTests` が注記の**本数と鍵の集合を等号で固定**する。手数で消せない
以上、せめて増やすことを意識的な操作にして、根拠を台帳へ書かせる。**これは計測の代わりでは
ない** —— 効いていない注記を**消す**根拠は、いまも手数以外に作れない。

**埋めた**(2026-08-13 に E2E-CMP ほか 5 SUT の内蔵 HTML へ「見出しを a11y へ出さない表」を入れ、
`cmp-webview-grid` として A/B 済み。結果は measurements.md「代替手段の無い盤面で A/B したら、
それでも手数は動かなかった」= 陽性対照は有効・手数は誤差の中・判断材料は note B)。
2026-08-24 に**実ブラウザ側の同じ形**を `boards/grid-noheader.html` として足した(下記)。
**ライブの web を叩くタスクでは代用しない**(盤面が毎日変わり、手数の差が注記の効果と混ざる)。

**やり方**(使い捨てページで確かめてから 5 SUT へ展開した手順。盤面を足すときはこの順で):

- **`aria-hidden="true"` を見出し行に付けると、描画は残したまま a11y から消える** ——
  値のセルはそのまま木に出るので、**実 web ページで観測した「見出しだけ落ちる格子」を
  オフラインで決定的に再現できる**(iOS Safari / WKWebView で実測)
- **同じ手で `webViewGapNote` の帯も作れる**(`aria-hidden` の段落を置くと「要素が1つも無い帯」になる)
- **閾値に届かせる調整が要る**: `gridWithoutHeaderNote` は「直上の空き ÷ 行間の中央値 ≥ 2.0」。
  素直に組むと 91/48 = **1.9 で発火しない**。見出し行に厚み(`padding: 34px`)を与えて
  空きを 139 まで広げたら発火した。**発火しない盤面を 5 SUT へ展開しても A/B で黙らせる
  対象が無い**ので、**移植の前にプロトタイプで発火を確認すること**
- 動く雛形はリポジトリ内に2つ: `boards/grid-noheader.html`(実ブラウザ用)と
  各 SUT の `webview.html`(アプリ内 WebView 用)

## browser 盤面(2026-08-16 に追加)

**穴の特定**: 曖昧ラベル注記の最大の発生源は `browser` アーキタイプ(固定コーパス14枚の
平均 682B。次点 ec 646B / map 421B)なのに、**盤面10個に browser が1つも無かった**。
最も近い `cmp-webview-grid` は自前アプリの WebView で、しかも表の値がすべて異なるので
この注記がほとんど出ない。**測れない形について「その注記が効いているか」は決められない**。

**埋め方**: ライブの web は叩かない(下記)まま、**実ブラウザ + 中身の変わらないページ**にする。
盤面は `Bench/boards/weather-dupgrid.html`(リポジトリ内)で、ホストで配信して
エミュレータから 10.0.2.2 で引く:

```
cd Bench/boards && python3 -m http.server 8791 --bind 127.0.0.1
```

**10.0.2.2 が届かないことがある**(2026-08-24 実測): この Mac では Chrome が別の何かに当たって
503 を表示し、次の試行ではページ内容が木に1つも出なかった(サーバのログには要求が1件も
来ていない)。**確実なのは `adb reverse`** —— エミュレータごとに1回張り、URL は `localhost` で書く:

```
adb -s <serial> reverse tcp:8791 tcp:8791   # 以後 http://localhost:8791/<盤面>.html
```

`and-browser-dupgrid` 系4本のプロンプトは 10.0.2.2 を直書きしているので、届かない機械で
回すときは**そのままでは解けない**(URL を書き換えると A/B の基線が変わるため、書き換えは
計測をやり直す覚悟で行うこと)。

再現しているのは実ページ(`ios-browser_yahoo_top`)の形そのもの ——
同じ値が地点をまたいで何度も出る / セルが**ラベルを持たないアンカー**で入れ子になる。
**忠実さは実測で確かめてある**(Android Chrome で読んだ値):

| 盤面 | 曖昧ラベル注記 | ツリー比 |
|---|---|---|
| 実: Yahoo 天気トップ(iOS) | 831B | 21% |
| 実: tenki.jp 週間(Android) | 943B | 22% |
| 実: J1順位表(iOS) | 1163B | 19% |
| **`and-browser-dupgrid`(盤面)** | **926B** | **21%** |

**タスクは2つある**。`and-browser-dupgrid` は**読み取りだけ**(1スナップショットで解ける)で、
2026-08-16 の計測では注記の有無で手数が1手も動かなかった —— ただし**この注記の用途
(重複する値から1つを選んで操作する)を通っていない**。用途を通すのは
`and-browser-dupgrid-tap`(大阪の降水確率をタップさせる。`20%` は4地点にあるので、
当てずっぽうは別のトークンになって失敗する = 成否そのものが信号になる)。

**Chrome の初回ダイアログは先に消しておく**(通知の許可・プライバシーサンドボックス)。
消し忘れると手数がその始末に食われ、注記の差が埋もれる(実際に踏んだ)。

## ここで測れないもの(2026-08-12 時点の穴 / 08-13・08-16・08-24 に解消したぶんを差し引いた残り)

**格子の見出し行の欠落は測れる** —— アプリ内 WebView が `cmp-webview-grid`(2026-08-13)、
実ブラウザが `and-browser-grid-noheader`(2026-08-24)。どちらも `gridWithoutHeaderNote` の
発火を実測で確かめてある。

**残っているのはアドレスバーのリダイレクト**(要求した URL と別のページを表示する形)。
offline の盤面では**飛ばす側**を用意できるが、それは「ブラウザが黙って別ページを出す」
という**実ページ側の性質**を再現したことにはならない。`addressBarNote` はこのため
**手数の差ではなく「実機の witness + 固定コーパス 33 枚で誤検知0」を根拠に入れたまま**。
**ライブの web を叩くタスクは足さない**(盤面が毎日変わり、手数の差が注記の効果と混ざる)。
