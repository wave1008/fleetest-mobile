# 壊れにくいシナリオの書き方

シナリオが flaky になったり、何も検証していないのに緑になったりするのを防ぐための規約です。
コマンドの詳細は [DSL コマンドリファレンス](../../commands.md) を参照してください。

## 要素の出現待ちに `wait` を置かない

要素の出現は暗黙で待たれます。操作は約0.7秒までロケータ解決を再試行し(`timeout:` で変更可)、
検証コマンドはタイムアウト(既定5秒)までポーリングして再判定します。`exist(...)` の前に
`wait(1)` を置くのは冗長です —— 待ちが足りなければ、そのコマンド自身の `timeout:` を上げてください。
`wait` に本当に出番があるのは、要素は既に在るのにタップ座標がまだアニメーション中でずれている場合
(メニュー展開・シート表示直後など)だけです。

## セレクタは記憶ではなく実スクリーンショットから採る

id やラベルを想像で書かないでください。実画面を撮り(`ft_snapshot`、または VSCode 拡張の
ライブ操作パネル)、実際に返ってきた id・ラベル・型をそのまま使います。`#id` を第一候補にする
のが最も頑健です。id が無い要素には `||` で予備のラベルを添えます。

```swift
tap("#login_btn||ログイン")   // #login_btn を優先し、無ければラベルへ
```

`||` は候補の和集合です —— `tap` は最初に見つかった候補に着地するので、この書き方は
そのまま自己修復のフォールバック連鎖としても働きます。

## 座標タップをシナリオに残さない

`tap(x:y:)` は操作可能な要素を1つも公開しない稀な画面のためのものです。セレクタが見つかって
いるなら必ずそちらを使ってください —— 座標はレイアウトが動いた瞬間に壊れますが、セレクタは
多少の UI 変更を吸収します。座標は(MCP での探索など)その場限りの操作なら問題ありませんが、
シナリオは何度も繰り返し実行されるため、ここでの違いが最も効いてきます。

## 出るか不定のものは `ifCanSelect` と `irregularHandler` で包む

どのコマンドにも「出ないかもしれない」を表す引数はありません —— 解決できないセレクタは必ず
シナリオを失敗させます。出るか不定のダイアログやバナーはこう包みます。

```swift
ifCanSelect("今はしない", waitSeconds: 2) {
    tap("今はしない")
}
```

scene の途中いつ出るか分からないアプリ内メッセージ(プロモモーダル等)には、各ステップを
ガードする代わりに `setUp()` で `irregularHandler` を1回宣言してください —— 出た時点で
自動的に閉じます(iOS の権限確認のような OS 側のシステムダイアログは、アプリの木の外に
居るため別扱いです。`iosAlertHandler` を参照してください)。

## `expectation` に必ずアサーションを置く

アサーションの無い `expectation { }` はコンパイルも実行も通りますが、何も証明していません
—— アプリがどう壊れても緑のままです。`ftester run --dry-run` はデバイスに触れる前にこれを
検知します: アサーション0個の `expectation` と、実際に `ft_snapshot` で撮った画面に無い `#id`
を警告します。シナリオを書いたら、デバイス実行の前に必ず一度 dry-run を実行してください。

## 失敗はシナリオ全体を中断する(`tearDown` は走る)

コマンドが失敗するとシナリオは即座に停止し、以降のすべてのステップ(後続の scene も含む)が
スキップされます。唯一の例外は `tearDown()` で、失敗後でも必ず実行されます。後始末
(シナリオが作ったデータの削除等)はここに置いてください —— そうしないと、失敗した実行の
残留が次回実行に影響します。

## 両 OS で回すなら `app:` / `platform:` を書かない

`@TestClass(app:)` と `platform:` を書かなければ、同じシナリオが `--profile ios` /
`--profile android` の両方で走り、対象アプリはその時点の実行プロファイルから解決されます。
これらを書くのは、そのシナリオが本当に特定 OS 専用のとき(その OS だけの設定画面など)だけに
してください —— そうでなければ OS ごとにクラスを複製することになります。

## 値を読むときは先に確定させる

要素から読んだ値(`exist("#total").text`・`.value`・`.id`)は読んだ時点の値で、後から
再取得されません。画面がまだ更新中なら、`textIs` 等で値が確定したことを確かめてから読んで
ください。そうしないと更新途中の値を掴んでしまいます。

## 不可逆な操作は再試行を書かない

操作を送ってから効果が出るまでの間に割り込みが湧いたとき、ツールは撃ち直しません ——
そのタップが既に着弾していたかどうかは観測から言えず、撃ち直すと二重実行になり得るためです。
着地画面を確認したうえでシナリオ側が撃ち直す(`ifCanSelect` で結果画面を確かめてから叩き直す)
ことは可能ですが、**もう一度実行しても安全な操作にだけ**行ってください。送信・購入の確定の
ような不可逆な操作の周りに再試行を書いてはいけません。
