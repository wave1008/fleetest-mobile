# Creating a Test Project

A test project (`TestProjects/<name>/`) bundles scenarios, profiles and reports for one app.
This page covers the project layout and the commands that manage it.

## Layout

```
TestProjects/SampleApp/
├── profiles/
│   ├── apps/sampleapp_ios.json    # app profiles
│   ├── machines/M2Ultra.json      # per-machine device definitions (file name = machine name)
│   └── runs/ios.json              # run profiles (app + device list + run-time settings)
├── scenarios/                     # Swift DSL
│   ├── _Main.swift                # delegates to the runner (do not edit)
│   ├── Generated/                 # scenarios generated from Live Control recordings
│   └── _disabled/                 # excluded from compilation (parking spot for generation
│                                   # failures and anything you want to keep out of the build)
├── reports/                       # per-scenario Markdown reports
├── results/                       # run-results JSON database (see results_analysis.md)
└── .fleetest/                      # heal cache and other per-project state
```

Each project maps to its own SPM target `fleetest-scenarios-<name>`, so a compile error in one
project does not stop the others. `_Main.swift` wires the target to the scenario runner and
normally does not need editing.

## Two package configurations

There are two ways this project's Package.swift can reference foundation-tester:

- **External package configuration** (the default for `/fleetest:fleetest-setup`): your work
  folder has its own `Package.swift` that depends on the foundation-tester clone via SPM
  (`fleetest init`). Your `TestProjects/` assets live in your work folder, separate from the
  tool's clone, so tool updates never touch your scenarios or profiles.
- **Clone configuration**: you work directly inside the foundation-tester clone, and
  `TestProjects/` sits inside it. Used mainly for developing the tool itself.

`fleetest init` scaffolds the external configuration (a `Package.swift` plus a first test
project). `--fleetest-path` points at a local clone (`.package(path:)`); `--fleetest-url` depends
on a git URL instead (`--fleetest-version` pins a minimum tag, `--fleetest-branch` tracks a branch
for testing before a tag exists).

## Managing projects

| Command | Description |
|---|---|
| `fleetest project create <name> [--app <bundleID>] [--platform ios\|android\|both]` | Scaffold a new test project and register it in `Package.swift` |
| `fleetest project list` | List test projects and whether they are registered in `Package.swift` |
| `fleetest project sync` | Regenerate the `Package.swift` marker section from a scan of `TestProjects/` (run this after a manual copy or a `git pull`) |

`Package.swift`'s marker section (between `// === fleetest projects begin/end ===`) is fully
regenerated by `create`/`sync`; do not hand-edit it.

## Project name rules

A project name becomes an SPM target name, so it must match `^[A-Za-z0-9_][A-Za-z0-9_-]*$`
(no Japanese). This restriction is on the project name only — `@TestClass` class names inside
scenarios can be Japanese, as in the examples throughout this documentation.

## Resolving `--project`

Most commands accept `--project <name>`. When it is omitted, the tool resolves it as follows:

1. If `TestProjects/` contains exactly one project, use it.
2. Otherwise, fall back to the configured default project.
3. Otherwise, fail with a list of candidate project names.
