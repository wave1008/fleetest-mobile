リモート実行の基本設計。用語の定義(RR-0)は [spec.md](spec.md)。

## RR-1 前提と目的

- **マシンは Mac に統一**(ユーザー決定 2026-07-30。クライアント・実行側とも)。
  非 Mac クライアントからの実行という要件は存在しない
- CI は self-hosted Jenkins / EC2 Mac([ci.md](../ci.md))。**ジョブ粒度のリモート実行は
  CI が既に担っている**ため、本構想の固有価値は CI を経由しない対話的用途に限られる:
  1. **Mac フリートへのシナリオ並列分散**(夜間回帰のスループット。FM はホスト単位で
     許可枠に制限される共有資源(PT-3.5)のため、1台に集約すると枠で
     頭打ちになる。台数分に分散すれば機械ごとに別の枠が使え、screenLooksLike 多用スイートは
     台数分の実質短縮になる)
  2. **デバイス/実機ラボの共有**(iOS 実機は元々 LAN/iproxy の2択で相性は悪くない)

## RR-2 却下済みの代替案(再提案しない)

| 案 | 内容 | 却下理由 |
|---|---|---|
| A. ブリッジ層で切る | `BridgeClient` の HTTP を遠隔ホストへ向ける | ステップ毎 snapshot の chatty なプロトコルに LAN RTT が乗り、ms 級チューニング(stale-guard 350ms・LPT 等)が崩れる。プロビジョニング(ブート・ランナービルド・インストール・ゾンビ掃除・凍結復旧)は全部ローカルプロセス制御前提で、遠隔化には常駐エージェント=第二プロダクトが要る |
| B. 独自プロトコルの常駐デーモン | fleetestd を立ててクライアントが接続 | 全マシン Mac なのでどのマシンもフルスタックが動き、役割分離の動機が無い。ジョブ粒度なら Jenkins の再発明。認証/TLS の自前実装が必要 |
| FM 分離構成 | デバイスは VM ファーム・FM は手元物理 Mac(案A の副産物) | 全 Mac(物理)前提で動機消滅 |

## RR-3 採用方針: ジョブ(run)単位の SSH ディスパッチ

**対等ピアモデル**。どの Mac も clone + `Scripts/install.sh` で同一状態になれるので、
リモート実行=「向こうの Mac で普通にローカル実行し、結果を手元へストリームする」だけにする。
新プロトコル・認証・常駐デーモンは作らない(トランスポートは SSH)。

`fleetest run --runner <mac>` の流れ(アプリは転送しない。ランナー側の配置は RR-14・RR-18.6):

1. 適合チェック(RR-7。不一致は fail fast)
2. 転送(rsync: シナリオ・プロファイル)。**リモートは外部構成(WORK_DIR 分離)前提・
   rsync 先はリモートの WORK_DIR**(実装は RR-18.6 の `<base>/users/<issuer>/work`)。
   **相手のローカルインストールと同じ場所に置かない** — `--delete` が相手の資産を消し、
   クローン共用は SPM ビルドロック競合を起こす(実害3件は [records.md](records.md) の RR-12)
3. リモートで実行(`install.sh` は `remote setup` が済ませる。RR-14)。転送後はリモートで scenario ターゲットの
   swift build が走る(コールドは数分。`clean -fd` に `-x` を付けない= .build 温存の
   既存設計が増分ビルドを効かせる)
4. **ストリームバックの実体は用途で分ける**: CLI/CI は `fleetest run --quiet --junit` の
   出力中継、拡張(レーン表示)連携は `fleetest api run` の NDJSON 中継
   (`fleetest run` は人間向け出力で NDJSON を喋らない。ApiRunCommand が唯一の機械可読契約)
5. 成果物回収(reports/・JUnit・results DB・録画)。**JUnit 内 `report:` 行は
   リモートの絶対パス**なので回収後のローカルパスへ書き換える。
   回収物は**リモートが生成した外部入力**として扱う(RR-15)

**禁止事項(実装者向け・摩擦が出ても回避しない)**:

- **`StrictHostKeyChecking` を無効化しない**(`-o StrictHostKeyChecking=no` を足さない)。
  ホスト鍵検証は MITM に対する唯一の防御であり、同時に「設定の乗っ取りで未知ホストへ
  ディスパッチされる」経路を実際に塞いでいる(RR-15)。初回接続の TOFU は
  `ssh-copy-id` の手動ステップ(RR-14 ステップ0)で人間が1回だけ行う
- **`--remote-dir` を実行ごとの自由入力にしない**。転送は `--delete` 付きでリモートの
  ディレクトリを上書きするため、宛先は**登録簿(RR-13)に登録された値のみ**を使う

**ホスト混在プロファイル(devices に `host: "local"` と `host: "M1Max"` 等が並ぶ形)を
`--runner <名前>` で単一ホストへ送るときは、そのホスト担当のデバイスだけが
`--device`/`--device-machine` として自動で付く**(丸ごと送ると受け側の「local」枠が発行元の
Mac のデバイスに解決され、存在しないデバイスの起動を試みるため)。担当が1台も無いプロファイルは
ディスパッチ前にエラーで止まる。

## RR-4 全体アーキテクチャ

```
┌─ ローカル Mac(発行側)────────────────────────────┐
│ fleetest run --runner mac2 --profile …              │
│  ├─ 適合チェック(rev / Toolchain)                │
│  ├─ dispatch.lock の取得(待機列。RR-13・RR-18)   │
│  ├─ 転送(rsync: シナリオ・プロファイル)          │
│  ├─ NDJSON 受信 → 進捗表示・拡張へ中継            │
│  └─ 成果物回収(reports/ ・junit.xml・録画・run ログ)│
└───────────────┬────────────────────────────────────┘
                │ SSH
┌───────────────▼─ リモート Mac(実行側)────────────┐
│ sshd のプロセスが fleetest run --runner local を   │
│ 直接実行(Aqua セッションが存在することが前提。RR-5) │
│  └─ シミュレータ・XCUITest・FM・エミュレータ        │
└────────────────────────────────────────────────────┘
```

## RR-5 Aqua セッションの前提と実行の置き場(GUI セッション制約への回答)

GUI 依存は fleetest のコードではなく **macOS のセッション意味論**に由来する
(launchd のセッション種別が Background[SSH 直・LaunchDaemon]か Aqua かで
WindowServer・ユーザー空間サービスへのアクセスが変わる。
「ログインなしで Aqua を作る」公式手段は macOS に無い)。よってコード分離では消せず、
**Aqua セッションが存在すること**を前提に置く。

| コンポーネント | Aqua セッション | 備考 |
|---|---|---|
| iOS シミュレータ + XCUITest | 存在が必須 | レンダリング・スクリーンショット・XCUITest はユーザーの launchd ドメインのサービスに依存する。本ツールはスナップショット・録画多用で回避不能 |
| FM(FTFoundationModels) | 存在が必須 | Apple Intelligence のデーモン群はユーザーセッション側 |
| Android エミュレータ | 存在が前提 | `-no-window` で起動し、SSH セッションから動く(RR-6) |
| コンパイル・オーケストレーション・results・align | 不要 | 純粋にプロセスとファイル |

- **常駐エージェントは持たない**。発行側が rsync で転送したあと、ssh でランナー機の
  `fleetest run --runner local` を直接実行する(`--runner local` はランナー側での再ディスパッチを止める)。
  判断・プロビジョニングは fleetest 本体にあり、ランナー側に加える機構は無い
  (.claude/rules/installer-agents.md「機械作業はスクリプト/CLI に寄せ、スキルには判断だけ残す」と同じ方針)
- **1マシン1 run は `dispatch.lock`(RR-13)で守る**。同一リモートへの同時ディスパッチはデバイス割当と
  loopback のポートが競合するため、FIFO の待機列(RR-18)に並べて1本ずつ通す。**その機械で直接打った run
  (`fleetest run` / `fleetest api run`・fan-out の local エントリ)も同じロックを取る**
  (`Sources/fleetest/LocalDispatchLock.swift`)ので、他人のディスパッチと手元の run も重ならない
### 運用前提(Aqua セッションの寿命と2モード)

**自動ログインを無条件必須にはしない**(モード B 限定の選択肢。下記)。macOS は
FileVault 有効時に自動ログインを無効化するため、「自動ログイン必須」はランナー機の
FileVault を捨てることと同義になる。ランナーには SSH 鍵・ソース・シナリオ(テスト資格情報を
含み得る)・録画が載るので、既定は FileVault 有効(モード A)とし、
**Aqua セッションの寿命**に着目して要件を組み直す:

| 事象 | Aqua セッションへの影響 | 対処 |
|---|---|---|
| 画面ロック | **消えない**(セッションは生きたまま) | ロックは**有効のままでよい**(RR-9 で XCUITest/録画の可否を実測) |
| ディスプレイスリープ | 消えない | 可 |
| **システムスリープ** | 実質停止 | `pmset` で**無効必須**(`sudo pmset -a sleep 0`) |
| **再起動・電源断** | **消える**(loginwindow で停止) | 人が1回ログインして復帰(下記) |

つまり**セッションを失うのは再起動だけ**で、それ以外は無人で回り続ける。再起動は OS 更新
程度の頻度なので、「再起動のたびに人が1回だけ解錠・ログインする」運用は成立する:

- **計画再起動**: `sudo fdesetup authrestart` で再起動すると、次回起動時の
  FileVault 事前認証をスキップしてボリュームが解錠される(遠隔管理用の標準機構)。
  ただし**解錠 ≠ ログイン**なので、その後に画面共有(またはコンソール)で1回ログインして
  Aqua セッションを立てる。
  **実行は人が対話 ssh(または画面共有)で行う手作業** — ディスパッチ経路は
  `BatchMode=yes` で sudo プロンプトに応答できず、NOPASSWD 設定は攻撃面を広げるので
  作らない(再起動は稀なので手作業に倒す。2026-07-31 決定)
- **不意の電源断**: 事前認証から人手で解錠+ログイン。**画面共有(Screen Sharing)を
  有効にしておく**と手元から実施できる(ステップ0 の必須項目)
- **「ログインしていない」を機械で検出する**: `stat -f%Su /dev/console` がランナー
  ユーザーと一致するかを preflight とディスパッチ前チェックに入れ、不一致なら
  **「ランナーが loginwindow で待機中 — 解錠が必要」と明示して落とす**。入れないと
  シミュレータ側の不可解な失敗として現れて切り分けに時間を溶かす

### サポートする2モード(どちらも正式構成)

再起動後の復帰手段だけが違う。**どちらを採るかはランナー機の設置環境で決める**。

| | モード A: FileVault 有効(既定) | モード B: FileVault 無効 + 自動ログイン |
|---|---|---|
| 再起動後 | 人が1回**解錠+ログイン**(画面共有可) | **ゼロタッチ**で Aqua が立つ |
| 平常時 | 無人 | 無人 |
| 向く設置 | 共用オフィス・持ち出し得る機械 | 施錠されたラボ・EC2 Mac 等の専用機 |
| 受容するリスク | — | 起動できる人がデータに到達。自動ログインは `/etc/kcpassword` にログインパスワードを可逆保存(RR-15.4) |
| 設定 | `fdesetup` 有効・自動ログインなし | `fdesetup` 無効・`autoLoginUser` 設定 |

- **Apple silicon ではモード B でもディスクは常時暗号化されている**(ハードウェア鍵)。
  FileVault の有無は「起動時に鍵が自動で使えるか/資格情報を要求するか」の差であり、
  「平文で置かれる」わけではない。ただし**その機械を起動できる人はデータに到達できる**
- 画面ロックの扱いは**両モード共通**(ロックはセッションを消さないので有効のままでよい。
  実測は [records.md](records.md) の RR-9 実験②が未実施)。システムスリープ無効も共通
- **準備状態の判定は両モード共通で `stat -f%Su /dev/console`**(Aqua セッションが
  立っているか)。モードが変えるのは**失われたときの復帰手段だけ**なので、ディスパッチ側の
  チェックはモードを知る必要がない。モード判定(`fdesetup status` + `autoLoginUser`)は
  **preflight が「復帰手順の案内文」を出し分けるためだけに使う**
  (モード A: 「解錠+ログインが必要」/ モード B: 「自動ログインが効いていない — 設定を確認」)
- **到達経路は「SSH の Background セッションでそのまま実行する」1つだけ**(2026-07-31 実測)。
  コンソールに誰かがログインしていれば、SSH 側のプロセスからでもユーザーの launchd ドメインの
  サービス(CoreSimulator 等)に到達でき、シミュレータ・XCUITest・in-app ブリッジまで動く。
  したがって上表の「Aqua 必須?」は正確には**「Aqua セッションが存在すること」が必須**で、
  実行プロセスがその中にいる必要はない
- **`launchctl asuser` 経由の注入は使わない(ユーザー決定 2026-07-31)**。`asuser` は **root を
  要求**し(`Could not switch to audit session`)、sudo を作らない方針では使えないため。
  セッションモードの選択肢自体を持たない(`--remote-session` は無い)。**再提案しない**

## RR-6 Android の SSH 実行

**エミュレータは `-no-window` で起動している**(`DeviceBooter.startEmulator` が
`-no-snapshot -no-window -no-boot-anim -no-audio -gpu host` を渡す。プロセスの実体も
`qemu-system-aarch64-headless`)。したがって既知の凍結知見(複数台同時描画がトリガ・
sleep/wake で修復)は**すべてヘッドレス環境で得られたもの**で、「窓あり前提」ではない。
`-no-window` 採用の条件だった2項目は検証済み。

実測(SSH の Background セッションから):

| 項目 | 結果 |
|---|---|
| エミュレータの起動 | ✅ 16秒で起動(`-no-window -gpu host`。**Metal も SSH セッションから使える**) |
| Android シナリオの実行 | ✅ 完走(ディスパッチ経由・exit 0) |
| gRPC 制御(`EmulatorControl.shutdown`) | ✅ 動作(2秒で停止。gRPC ポートは `[::1]` に listen し、同一マシンの SSH セッションから到達できる) |

**残る本当の論点は「Aqua セッションが無い(loginwindow のまま)状態で動くか」**で、これは
RR-5 のログイン検出(RR-16.3)が塞いでいる領域。iOS と同様、**Android も「Aqua セッションが
存在すること」を前提にする**(未ログイン状態での検証は未実施)。よって
「Android だけログイン不要のレーンに振り分ける」最適化は**現時点では成立が確認できていない**。

**ディスパッチ前にエミュレータを起こす必要は無い**: プロファイル実行(`ProfileSupplyLanes`)が
未起動の AVD を起こす(`AndroidLaneRecovery.bootMissingDevices`)

## RR-7 版整合・更新

- リモート側も clone + ソースビルド(配布方針どおり)。更新は `fleetest remote align <runner>`
  (全機は `Scripts/align.sh`)
- ディスパッチ前の適合チェックは**2項目**: **git revision・ToolchainFingerprint
  (Xcode の版 + iOS Simulator SDK のビルド。**macOS の版は含まない**)**。
  **machineName は照合しない** —— 「送り先が想定の機械か」は ssh の宛先(とホスト鍵)が
  保証するので、リモートの登録名は見ない(`RemoteCompat.verdict`)。
  git revision の不一致は**黙って走らせず fail fast**(このリポジトリの
  「片方だけ変えない」規律をマシン間に広げると、スキューは恒常的なバグ族になるため
  入口で遮断する)。**ToolchainFingerprint だけは仕分けが1段深い**(ユーザー決定): 製品版
  (`Xcode X.Y`)が同じで build 番号だけ違う = ベータの seed 違いはディスパッチを**止めない
  advisory**、製品版が違う(26 vs 27 等)は従来どおり fail-closed。根拠は、リモートへ渡るのが
  TestProjects のソースだけで、fleetest 本体・XCUITest ランナー・in-app dylib は**ランナー機が
  自分の Xcode でビルドする**ため機械的な依存が無く、止める理由が「結果の比較可能性」だけに
  縮むこと(実質的な結合は `appPath` のアプリが手元ビルドのままワークスペース経由でランナーへ
  入る1点だけ)。仕分けは `fleetest api remote-compat` / `fleetest remote status --json` の
  `toolchainAdvisory: String?` が持ち、`toolchainCompatible` は「blocking で止まるか」の意味になる
  (advisory のときも true)
- **ランナーに複数の Xcode が入っているときは、発行側の Xcode に一致するものへディスパッチが
  自動で選ぶ**(ユーザー決定)。選ぶのは **`DEVELOPER_DIR`**(プロセス単位・sudo 不要)——
  **`xcode-select -s` は使わない**: 機械全体に効き sudo が要るので、共有ランナーでは自分の選択が
  他の利用者の run を壊す。候補はランナーの **`/Applications` 直下**の `Xcode*.app` だけ
  (`CFBundleShortVersionString` / `ProductBuildVersion` を読む)。**別の場所に置いた Xcode は
  見つからないので登録簿の pin(`RemoteHostEntry.developerDir`)で指定する**。選択規則
  (この順): ①pin があればそれ ②build 番号まで一致する候補がちょうど1つならそれ ③製品版
  (`Xcode X.Y`)が一致する候補がちょうど1つならそれ ④候補が空(列挙できない・Xcode が無い)なら
  何もしない(従来どおり ambient = `xcode-select -p` の結果)⑤一致0個・複数なら**候補一覧を出して
  ディスパッチを拒否**する(手近な Xcode へ黙って倒さない)。**適合チェック(probe)と実行(run)は
  必ず同じ `DEVELOPER_DIR` の解決を通る** —— 食い違うと「照合した Xcode と違う Xcode で走る」
  沈黙した退行になる。**`remote align`(`Scripts/align.sh`)のビルドも同じ解決を通す**
  (`alignRevisionCommand(developerDir:)`。一致しない・列挙できないときは ambient で、一致しないときは1行警告する)
  —— 通さないとランナーの `xcode-select -p` の結果でビルドし、それがコマンドラインツールだと FoundationModels の
  マクロが無くてビルドが落ちる(M1mini で実測)。**モニター(デバイスの状態・ライブ映像)には効かせない** —— 観測は
  dispatch.lock の外で常時走るので、版の違う simctl を同じ CoreSimulatorService に当てる危険を
  増やさない。効果として、**Xcode の製品版が違うランナーも、その製品版の Xcode さえ入っていれば
  フリートに混ぜられる**(この選択が無ければ製品版違い = 常にディスパッチが止まる)。
  **iOS シミュレータのランタイムは Xcode に付いてこない**(CoreSimulator のランタイムは機械共有)
  ので、選んだ Xcode の製品版に対応するランタイムが無ければ起動できない —— `remote status` の
  RUNTIME 欄が既にこれを警告する。**製品版をまたいでフリートを混ぜると、OCR・FM は OS 付属**
  なので結果が機械で変わりうる(既存の macOS 混在の注意と同じ)。赤の帰属は run.json の
  `toolchain` 欄(docs/results-json.md)で追える
- **照会そのものが失敗したときは理由まで出す**(2026-09-09)。`RemoteCompat.ProbeOutcome` が
  「値が無い」と「なぜ取れなかったか」を別に持ち、ssh の exit status とリモートの出力を
  reasons へ載せる。**照会系は1回だけ引き直す**(待ち時間は置かない) —— ssh の単発失敗は
  そのレーンのシナリオを丸ごと捨てるのに対し、引き直しは ssh 1往復で済む。
  **判定は緩めない**: 2回とも失敗すれば fail-closed のまま非互換で落ちる
- **rev 一致の意味 = 両者が同一 upstream コミットにいること**。ローカルの未コミットの
  ツール変更はリモートに載らない(ツール開発中の変更をリモートで試す用途はスコープ外)
- **照合するのは「rev に包含されないもの」だけ**という原則で照合項目が決まる —
  Toolchain(マシンごとの Xcode/SDK)と machineName(リポジトリ管理外のローカル設定)は
  rev では担保されない。**`ProtocolVersion` は照合しない**(リポジトリ管理下なので
  rev 一致に包含される。RR-12 の結論)
- リモートの **TOOL_ROOT 解決は既存4箇所の規則を再利用**する(preflight.sh / update.sh /
  toolRootResolve.ts / Package.swift 宣言。`toolRootContract.test.mjs` の対象)。
  ディスパッチ用の独自解決を新設しない
- **実行前に版ズレだけを問い合わせる口は `fleetest api remote-compat --project <P> --profile <X>`**
  (JSON。人が読む表は `fleetest remote status`)。拡張はこれで実行プロファイルのリモートホスト
  全部の rev/toolchain 適合を見て、ズレていれば「更新して実行 / キャンセル」をダイアログで聞く
  (**「そのまま実行」は置かない** —— ズレたまま走らせるとリモート担当分は必ず
  checkCompatibility に弾かれ、部分失敗の run にしかならない。align で直せないズレ
  = 未 push・到達不能・製品版の違う toolchain 不一致は実行を止めて理由を出す(ベータ seed 違いの
  toolchain advisory は止めない)。チェック自体を外すのは
  設定 `fleetest.remoteCompatCheck`)。ズレの解消(揃えるだけ)は `fleetest remote align <runner>` —
  `remote setup` の align ステップだけを単独で実行する軽量版(preflight/install は通さない)

  **手元を更新したあと全機を揃えるときは `Scripts/align.sh`**(push → 登録簿の全機へ
  `remote align` を**並列で**投げる → `remote status` の REV が手元の HEAD と一致するまで確かめる)。
  `remote align` は1機ずつしか受け取らないので、素で使うと**人の手では必ず直列になる**
  (前の機の出力を読んでから次を送る形になる)。台数ぶん待ちが伸びるだけの誤りなので、判断の余地を機械へ移してある。
  **汚れた作業ツリーでは何もせずに落ちる** —— ランナーは push 済みのコミットを取りに行く

## RR-8 マルチマシン分散(`run --fleet --split`)

- `RunOrchestrator` の worker 抽象はマシン跨ぎへ拡張しない。
  分散は**ディスパッチの手前**(発行側)で行う: シナリオ一覧をローカルで解決 → LPT で
  エントリへ割り当て → 確定した `--scenario` を各エントリへ渡す。各ホストの中では
  従来どおり `RunOrchestrator` が自分のデバイスへ割り当てるので、**2階層が独立**に働く
  (マシン跨ぎの worker 抽象を作ると、ホスト内のデバイス割当と二重管理になる)
- 見積りは既存の `LPTScheduler`(results の中央値)を再利用する。**新しい実績の仕組みを作らない**
- **platform 適合を守る**(iOS 専用シナリオは iOS を走らせられるエントリへ)。どこにも
  入らないシナリオがあれば**throw して止める** —— 黙って落とすと「走ったつもりで
  走っていない」を作る。エントリの platform は実行プロファイルの devices が直接持つ
  (実行プロファイルはプロジェクト資産なので ssh 無しで解決できる)
- **割り当ては決定的**(同着はシナリオ ID、負荷同着はエントリ順)。前回と同じ割り当てを
  再現できないと flake の切り分けにならない
- **実績が1件も無いとき**は全シナリオが同じ重みになり、LPT は本数の均等割りに退化する。
  このとき重みの絶対値は割り当てに影響しないので、**根拠のある秒数を選ぶ問題自体が無い**
  (テストで「値を変えても同じ割り当て」を固定)。秒と誤読されないよう推定列は出さない
- `--split` のときだけローカルビルドが要る(一覧の解決)。プレーンな `--fleet` の経路は変えない

**実測(2026-08-16。E2E-iOS 23本 / M1Ultra + M1Max)**: 11 + 12 本に分かれ、
推定 133.4s / 135.7s に対し実測のテスト時間 130.5s / 128.9s(**誤差 2〜5%**)。
壁時計は 2分56秒(1台で23本走らせるとテスト時間だけで約 259s)。
- results DB のマージは不要(集計は results/ を走査するファイルベースで、回収した時点で載る。
  RR-13 末尾)。レポート内パスの書き換えは `RemoteReportLink`(記録側)/
  `RemotePathRewrite`(JUnit・NDJSON)。
  **JUnit の集約**: `run --fleet --junit <path>` が1ファイルにまとめる。
  各エントリには一時パスの `--junit` を渡し、完了後に `FTCore.JUnitMerge` で結合する)。
  **読めないエントリを黙って省かない**のが要点 —— 出力が無い/壊れているエントリは
  合成した失敗スイート(`fleet-entry-missing` / `fleet-entry-unreadable`)として結果に残す。
  省くと CI からは「そのホストのぶんは全部通った」に見え、throw して1件も書かないと
  「JUnit が無い」= 設定次第で緑にも見える。**赤いテストが1件あるほうが確実に伝わる**。
  同じスイート名が複数ホストで出るので `hostname` を付け、合計は結合後に数え直す
  (各エントリの外側の合計を信用しない)
- デバイス選定は**実行プロファイルの devices が持つ `machine` で解決**する(devices 自体が
  すでにマシン単位の概念を持つ)

**machine 別見積りとディスパッチ固定費(2026-08-18)**: 機械ごとの速度差(手元と各リモート機で
異なる)とディスパッチ経路の固定費(SSH 接続・転送・増分ビルド)を割り当てに織り込む
(`FleetSplit.MachineContext`)。`RemoteHostFactsStore`(`.fleetest/remote-hosts/<host>.json`)は
machine 識別子・実測固定費に加え **CPU モデル・論理コア数・直近 run の同時起動デバイス数**も
持つ。CPU 情報はディスパッチの到達性プローブ(`RemoteRunDispatcher.resolveLayout`)に相乗りした
`sysctl` の実測、machine とデバイス数は回収した実績レコード(`machine`/`worker`)由来 ——
書き手が違う(前者はプローブ、後者はレコード)ので、片方だけ取れなかったときも他方は上書きで
消さない。ローカル機の facts も同じ鍵("local")で `FleetRunner.buildMachineContext` /
`DeviceMachineRunner.assign` が毎回書く(こちらは SSH プローブを経由しないので `MachineHardware.current()`
を直接使う)。

見積りは**同一機の実績 > 混合中央値 × 速度係数(共通観測シナリオの比の中央値)>
コア数の逆比(ローカル基準の事前係数)> 1.0** の順で決める。実績の無い機械には、
共通観測が貯まるまでの間 `entryFallbackFactors`(ローカルのコア数 ÷ 相手のコア数)を暫定係数として
使う ―― 観測が増えて速度係数が求まり次第、そちらへ自然に置き換わる(FleetSplit の優先順が
決める。facts に coreCount が無ければ 1.0 = 従来どおり均等)。**初回(キャッシュ無し)は
従来と同一の混合見積り**に退化する —— facts が無いエントリは machine=nil・offset=0・factor=1.0
として扱われる。**実績が1件も無い run は ms の固定費だけを落とす**(見積りが単位重みへ
退化するので、ms の固定費を同じ比較に載せると単位重みを支配してしまう)が、**コア数の逆比の
係数は効いたまま**にする(単位重み自体に掛かる比率なので単位を汚さない。
`FleetSplit.machineContext(_:ifHistoryExists:)` が offsets だけ 0 化して返す)。
**見積りはそのエントリが実際に回す platform の実績だけで作る**。同じ scenarioID を
ios と android の両方で走らせるプロジェクトでは、機械別の実績が片 platform に偏る —— ある機械が
直近 android でしか回していなければ、その機械の中央値は android のものになる。全 platform の
max を採ると、それが「同一機の実績」として ios の run へ入り、**速い platform の値で遅い
platform を見積もって、一番遅く終わる機械に最も多く配る**。実データ(受け手の iOS 98 本・3機・
18 レーン)では M1Ultra だけが android 由来の見積りを 9 本ぶん掴み、レーン当たり実績 552 秒に
対して推定 448 秒(−19%)で最後まで走る極になっていた(local +1% / M1Max +8%)。scope を掛けると
同じ入力で −7% まで縮む。**両 platform を回すエントリでは scope が両方 = 従来の max と同一**
なので、狭まるのは「そちらの platform を回せないエントリ」だけ。速度係数(`speedFactors`)も
**比の分子と分母を同じ platform で取る** —— platform を潰して割ると、速度差ではなく platform 差を
係数として掛けることになる。

ディスパッチのログは推定に続けて**その推定が何に基づいたか**を出す(`FleetSplit.EstimateBasis`。
`local: 43 scenario(s) on 8 device(s) [est. 485s; 36 from <machine> history, 7 scaled x1.00 (measured)]`)。
`--split` の割り当て表は BASIS 列。係数だけでは由来が分からず、遅い機に偏った run を後から
検証できない(2026-08-24 受け手要望)。

実行後の集計表には **IDLE 列**(そのエントリの最長 duration との差)がある —
静的割り当ての偏り(ストラグラー)を再配分機構を作る前に実測で貯めるためで、割り当てそのものは
実行後にフィードバックしない。効果の実測(3機械12台での収束データと、初回 run を効果の
基線にしない理由)は PT-3.7 の 7。

### RR-8.1 マシン間でシナリオを1本ずつ配る(動的な割り振り)

**実装と実測(2026-10-27)**: `DynamicSplit`(判定)・`FleetSplit.Estimator`(見込みの共有)・`WorkQueueProtocol` / `StdioPullSource`
(子の口)・`DynamicDispatcher`(親の配り手。`run` / `api run` が共有)。E2E-Flutter の ios-inapp-boost(28 本・手元 8 台 + M1Max 4 台 +
M1Ultra 6 台・実績あり)で静的と交互に 2 回ずつ: **全体 51.0 / 50.5 秒(動的)・51.8 / 53.8 秒(静的)**。実績がたまった run では
見込みどおり数%。初回(実績なし)・ばらつきの大きい run での効果は未計測。実地で踏んだ罠: ssh を包む sh(`ParentBoundCommand`)が
`&` のコマンドの stdin を /dev/null に付け替え、返事がリモートへ届かずリモートのデバイスが止まった(fd 3 へ退避して渡す。
`ParentBoundCommandTests.testStdinReachesTheWrappedCommand`)。stdin の横取り: stdin を指定せずに起こす子プロセス(adb・ssh など)が親の返事を読み、レーンがシナリオを受け取れず止まった(子の `WorkQueueStdin.claim()`)。その修正の直後、中継役が fd 0 を ssh へ渡していたためリモートへ返事が届かない退行が出た(中継は claim の fd を渡す)。いずれも本節の「親と子の間の口」と中継の記述を参照

**目的**: 1つの実行プロファイルのデバイスが複数のマシンにまたがる run(RR-13 の `DeviceMachineRunner` と、`api run` の対
`ApiRunMachineFanout`)で、最初に決め打ちする割り振り(上の LPT)をやめ、**空いたデバイスが親から次のシナリオを1本ずつもらう**。
初回(記録なし = 均等割りで最大 134 秒遊んだ)・短い run(最大 23〜32 秒)・所要のばらつきが大きい run の遊びを消す。
マシンの中のデバイスへの割り当て(`RunOrchestrator`)と同じ考え方を、マシンの間へ1段上げる。ユーザー決定(2026-10-27): 案 A。

**割り振りの規則(ユーザー指示)**: あるマシンのデバイスが空いたら、待っているシナリオごとに
「**今このデバイスに渡したときの終わる時刻**(今 + このマシンでの見込み)」と「**同じ platform の他のレーン(他のマシン + 同じマシンの他のデバイス)に回したときの一番早く終わる時刻**
(そのデバイスが空く見込みの時刻 + そのマシンでの見込み)」を比べ、前者が後者以下のシナリオだけを渡す(複数あれば見込みの長い順 = LPT。`--no-lpt` は親の候補の順を ID 順にする —— 子のカタログの並びは配る順に効かない)。
渡せるものが無ければ**何も渡さず待たせる**(遅いマシンが終わり際に長いシナリオを取って全体を引き延ばさない)。
- 見込みは今の静的な割り振りと同じ材料(`FleetSplit.MachineContext`: 同一機の実績 > 混合中央値 × 速度係数 > コア数の逆比)。
  **新しい記録の仕組みを作らない**。送りの固定費は run の開始で1回払い済みなので、ここでは足さない
- 比べる相手は要求を1度でも出したレーンだけ(供給中のレーンは空きと数えない)
- 「空く見込みの時刻」= そのデバイスが今回しているシナリオの開始時刻 + そのマシンでの見込み。空いて待っているデバイスは「今」
- **安全弁**: 比べた相手のデバイスが見込みの時刻を過ぎても空かなければ、相手の空く時刻を `今 + 超過した時間` とみなす(超過した分だけ後ろへ倒す)。比べ直す時刻は `reconsiderAt` で返し、要求・終わりの知らせ・その時刻のタイマーで判定し直す
- **端の条件**: 待っているシナリオがそのデバイスの OS で回せないものだけなら「もう無い」を返す(そのデバイスは終わる)。全部配り終えたら
  全デバイスへ「もう無い」

**親と子の間の口**: 子の run の標準入出力を使う。**子は run の入口で `WorkQueueStdin.claim()` を最初に呼ぶ**(stdin を close-on-exec の fd へ移し、fd 0 を /dev/null にする)。移さないと、stdin を指定せずに起こす子プロセス(adb・ssh など)が親の返事を読んで横取りし、渡したはずのシナリオをレーンが受け取れずに止まる(2026-10-27 実測: 手元で 28 本中 4 本・リモートで 5 本が結果なし)。`WorkQueueStdinWiringTests`:
- 子は新しい内部の口(`--work-queue`。利用者向けではない)で起こし、**全候補のシナリオを知った上で、配られた分だけ回す**
  (ビルドと一覧はふだんどおり)。デバイスが空くと **`{"ftWork":…}` の1行 JSON**(要求 `want` のみ。`WorkQueueProtocol`)を stdout に出し、
  stdin から1行の JSON(渡す/もう無い)を読む。待たせる = 親が返事を遅らせる
- 親(`DeviceMachineRunner` / `ApiRunMachineFanout`)が全マシンの要求を1か所で受け、上の規則で答える。`{"ftWork"` で始まる行は表示・NDJSON の
  中継から抜く(利用者には見せない)
- リモートの子は `ssh -tt` の先にいる: 中継役の `fleetest run --runner M --work-queue` は **`WorkQueueStdin.claim()` の fd** を ssh の stdin に渡し(fd 0 は入口で /dev/null に差し替え済みなので、fd 0 を渡すとリモートに返事が1本も届かず、リモートのレーンが全部止まる。それ以外の ssh(結果の回収など)は /dev/null のまま)、リモートの
  fleetest は stdin が端末なら**エコーを切る**(`tcsetattr`。切らないと送った行が出力へ折り返す)。行は端末の1行の上限(MAX_CANON)より
  十分短い(シナリオ ID 1つ)。**`-tt` はやめない**(手元の中断をリモートへ SIGHUP で届ける役 = RR-3)
- 却下した口: ssh の逆向きのポート転送(リモートの loopback に待ち受けが増え、同じ機械の他の利用者から届く = 認証が要る)/
  何回かに分けて run を送る(1回ごとに送りの固定費を払う = 案 B。記録がたまった run ではむしろ遅い)/ 常駐の中継デーモン(RR-2 の B)

**変えないもの**: `--broadcast`(全デバイスで全シナリオ)・`--fleet`(エントリごとに別のプロファイル。`--split` は今の静的な割り振りのまま)・
マシンの中のデバイスへの割り当てと再キュー(`RunOrchestrator` の `requeue`)・dispatch.lock の取り方(`DispatchPrelock`)・
結果の回収と JUnit の結合・`api run` の利用者向けの NDJSON(イベントの種類と形。`fleetestProtocolVersion` は上げない =
親子の口は同じ版の fleetest 同士の内部の約束で、リモートは適合チェックで同じコミットに揃っている)。

**中断**: 親は配るのをやめ、保留中の要求にも以後の要求にもすべて none で答える。子も中断を受けたら親の返事を待たず、待っている要求を全部 nil で終える(`ScenarioPullSource.stopWaiting`。`RunOrchestrator.requestInterrupt`)—— 親の返事が届かないレーンは、これが無いと中断しても解けない。
配っていない分は「中断で渡さなかった」と1行出し、失敗にはしない。

**落ちたマシン**: 子が途中で終わったら、そのマシンへ渡して終わりの知らせが来ていないシナリオは**回し直さない**(途中まで走ったかもしれない
= サーバーの状態を変えたかもしれない。届いたか分からない操作を撃ち直さないのと同じ規律)。今と同じく `reportMissingResults` の
「結果の無いシナリオ」として赤で残す。まだ誰にも渡していないシナリオは、残ったマシンへふつうに配る。

**既定と殺しスイッチ**: マシンをまたぐ run は既定でこの方式。保守者の殺しスイッチ環境変数 `FT_STATIC_SPLIT=1`(`DeviceMachineRunner.dynamicSplitEnabled`)で今の静的な割り振りへ戻す
(`FT_EMPTY_DRAG=off` と同じ位置づけ・利用者向けの口ではない)。

確かめ方: 純粋関数のテスト(`DynamicSplit` / `JobSchedule`)・偽の源のテスト(`StdioPullSourceTests`・`PulledDispatchTests`)・配り手のテスト(`DynamicDispatcherTests`・`MultiTargetRunnerTests`)

### RR-8.2 複数の対象を1回で回す(run を丸ごと配る段とシナリオを配る段の統合)

**目的**: 回帰のまとめ役(`Scripts/regress.py`。PT-8.1)の良いところ —— **複数の run を1つの待ち行列で配り、run ごとの固定費を
マシンが並列に払う** —— を製品へ取り込み、RR-8.1(シナリオを1本ずつ配る)と1つの配り手にまとめる。ユーザー決定(2026-10-27):
口は `--profile` の繰り返し・終わり際はシナリオ単位へ切り替える・regress.py は薄い包みにする。

**口**: `fleetest run --project A --profile ios --profile android` / 複数のプロジェクトは `--target A:ios --target B:android`
(`--project` / `--profile` と併用しない)。**対象が1つなら今までと同じ経路**(RR-8.1 を含む)。2つ以上の対象は `--broadcast` `--fleet` `--runner` `--dry-run` `--scenario` `--folder` `--failed` `--port` `--platform` `--serial` `--app-id` `--device` `--device-machine` `--all-machines` と併用しない(一覧は `MultiTargetRunner.firstRejection` の呼び手 = `Fleetest.swift` の validate)。`--runner local` で絞れないので、regress.py は各プロファイルに載っている全マシンを使う。
`api run` には入れない(拡張は1プロファイルずつ起こす。理由は `RunCommandFlagParityTests` の表へ書く)。

**仕事と粒度**: 仕事(job)= 対象1つ。どのマシンで回せるかはそのプロファイルのデバイスの `machine` で決まる。**マシンは同時に1つの子 run だけ**
(1台1本 = dispatch.lock)。子 run は最初から `--work-queue`(RR-8.1 の口)で起こし、その仕事の候補を全部知った上で1本ずつもらう。
- 空いたマシンの次の仕事(`JobSchedule.decide`。純粋関数):
  1. **まだ誰も始めていない仕事**: 見込みの長い順に「今このマシンで始めたときの終わる時刻(固定費 + そのマシンで全部回す見込み)」と
     「他のマシンに回したときの一番早い終わる時刻(そのマシンが空く見込み + 固定費 + 見込み)」を比べ、前者が以下なら始める
     (RR-8.1 と同じ規則を仕事の単位へ上げたもの = 遅いマシンが終わり際に長い仕事を取らない)。どれも当てはまらなければ待つ
  2. **このマシンで回せる**未着手の仕事が無いとき(終わり際)だけ、走っている仕事に2台目以降として**加わる**(固定費のあいだに今の担当だけで終わるなら加わらない): 加わると、その仕事の残りが終わる見込みが
     早まる(加わる固定費のあいだも他のマシンは進む)仕事のうち、早まる量が一番大きいもの。早まらなければ待つ
  3. 始めていない仕事も、残りのシナリオがある走っている仕事も無ければ、そのマシンは終わり
- 仕事の中のシナリオは RR-8.1 のまま(仕事ごとに `DynamicDispatcher`。加わったマシンのレーンも同じ規則で比べる)。子は自分の仕事の
  残りが無くなると終わり、そのマシンは空いて次を選ぶ
- 「空く見込み」= min(始めた・加わったときに覚えた終わる時刻, 今 + 残りの見込み)。見込みを過ぎても空かなければ RR-8.1 と同じ安全弁
  (超過したぶん後ろへ倒す)。**「今 + 残り」だけにしない** —— 毎回いまから作り直すと遅れても期限を過ぎた側へ倒れず安全弁が効かない
  (2026-10-27 の実測: FM が落ちて遅くなった手元を空いた2台が10分以上待ち、未着手の対象を取らなかった)。残り = まだ誰にも渡していないシナリオの見込みの和 ÷ レーン数を、担当マシンの速さで合算したもの(走っているシナリオは数えない)。配っていない分が無ければ「今」。記憶した時刻は仕事ごとに1つで、始める・加わるたびに小さいほうへだけ更新し、担当が0台になって未着手へ戻した仕事は消す

**見込み**: シナリオは `FleetSplit.Estimator`(RR-8.1 と同じ)。仕事 × マシンは「そのマシンのその仕事のデバイスだけで、残りのシナリオを
全部回す時間」= 見込みの和 ÷ レーン数。固定費は `RemoteHostFacts.dispatchOverheadSeconds`(RR-8 の固定費)。新しい記録の仕組みは作らない。

**準備**: 対象のプロジェクトを手元で1回ずつビルドして一覧を出す(今の分割経路と同じ)。dispatch.lock は、残った仕事が使う全マシンぶんを(一覧が空で飛ばした対象だけが使うマシンは取らない = `MultiTargetRunner.labelsInUse`)
`DispatchPrelock` で最初に取り、全部の仕事が終わるまで持つ(途中で手放すと他人の run が割り込み、配り手の見込みが崩れる)。

**落ちたマシン・中断**: RR-8.1 と同じ(渡したシナリオは回し直さない・中断は待っている要求へ none)。落ちた = 子の終了コードが 0・1 以外。落ちたマシンには以後仕事を配らない。同じ (仕事, マシン) の子は1回しか起こさない(配り手は抜けたエントリの要求に答えないので、起こし直しても返事が来ない)。**担当が0台になった仕事に誰にも渡していないシナリオが残っていれば未着手へ戻し、ほかのマシンが始める**(戻さないと落ちた1台の残りが誰にも配られなかった)。中断以外で配られなかったシナリオや、どのマシンでも始まらなかった対象は赤。中断で残った分は失敗として記録しないが、親の終了コードは 130(子が全員 0 でも 0 にしない = 未実行を含む回帰を検証済みにさせない。3経路が `DeviceMachineRunner.parentExitCode` を共有)。「残った分」には**渡したのに結果が無いシナリオ**も入る(配り手は返事を送る前に pending から外すので、子が受け取る前の中断では未配布にも子の失敗にも数えられない)= run は結果 JSON の走査(`reportMissingResults` の戻り値)、api run は多重化の `unfinishedTotal` で数え、中断なら 130・中断でなければ 1。窓なしの照合し直し(全月の run.json を読む = 数千件で数秒)は、1つのプロセスの中で (結果フォルダ, runGroup) ごとに1回だけ読む。中断時の子の `stopWaiting` は RR-8.1 と同じ。**中断のあとは子を起こさない**: 起動の予約はロックの中・起動は外なので、起こす直前に中断を見て予約を戻す。起動から中断の登録(`FleetRunner.runEntry` の `InterruptRelay.forwarding(…, catchUp: true)`)までの間に来た中断は、登録と同じ臨界区間で「登録より前に中断を受けていたか」を見て、その子へ1回だけ伝える(登録の後で印を見ると forwardToAll と二重に送り、子の2回目の中断は後始末を飛ばして即終了する)。**配り手の購読も同じ**: ロックの取得中の中断は DispatchPrelock の購読が受けて終わるので、3経路の配り手(複数対象・run の機械分担・api run の機械分担)は `InterruptRelay.observing(catchUp: true)` で登録し、登録より前の中断を登録の直後に1回受ける。api run は自前のシグナルソースを持たない(過去の中断を知らない)。**3経路の親は入口(チケットの発行・手元のロックの先取りより前)で中断の印 `DeviceMachineRunner.ParentInterrupt` を立てて最後まで持つ** —— 先取りの `acquire()` は自前の購読を外すと既定動作へ戻すので、無いとビルドの間の SIGTERM で親が後始末なしに死ぬ。手元のロックの待ち・ビルド・一覧取得・配り手の登録の直前の中断は子を1つも起こさずに 130 で抜ける(`interruptedBeforeAnySubRun`。ビルド中の中断はビルドが終わってから拾う)。`DispatchPrelock.acquireInOrder` は全部取り終えた直後にも中断を見る(最後の1台の取得の最中の中断を見ずに true を返すと、子を起こしてから止めた)。

**一覧と対象外**: 対象ごとの一覧は通常の入口と同じ `ScenarioSelection.resolve`(`@Draft` / `@Deleted` を外す)を通す —— 子へは完全一致の ID で渡すので子の側では外れない。外して空になった対象は飛ばす(通常の入口も外して空なら成功で終わる。全部の対象が空なら「nothing to run」)。**レスポンス計測のプロファイルは複数対象と併用しない・単一対象でも動的に配らない**(反復 `responseRepeat` は子だけが展開し、親は同じ ID を1回しか配らない = 指定の回数を回さずに成功する。`--device` でリモートの1台に絞ると1グループでも機械分担の経路に入る。`dynamicSplitEnabled(measuresResponse:)`)。子も `--work-queue` と計測の併用を断る(run / api run の入口で stdin を移した直後 = 供給より前。`RunCommonOptions.rejectWorkQueueMeasurement`)。返事を待つ間に別のレーンが再キューした分は、返事が none でもそのレーンが拾う(`ScenarioQueue.next`)。

**regress.py の行方(実装済み)**: SUT の鮮度確認とビルドの段・回帰の対象の一覧(スイート × SUT × OS/モードの `--target`)・検証済みの印と推奨・
陽性対照・証人の run(`e2e.sh` の in-app の証人)・画像分類器の劣化の検査だけを残し、配る部分は `fleetest run --target …` へ任せる。
E2EX / E2EY のプロファイルにもリモートのデバイスを足す(E2E のプロファイルと同じ形)。

## RR-11 GUI(vscode-fleetest モニター)への影響

リモートデバイスをローカルと混在表示するときの契約。実装地点は RR-13「デバイスモニタータブの多ホスト監視」。

- **デバイスの識別に machine を含める**。デバイス名は全 Mac で衝突する(どのマシンにも「iPhone 17」がいる)ので、
  タイルは machine 別にグルーピングしてバッジを付ける。負荷チャートも machine 別の行に分ける
- **版ズレは実行前に聞く**: ランナーの更新は実行前の版ズレダイアログの「更新して実行」(= `fleetest remote align`。
  `vscode-fleetest/src/runHandler.ts`)。設定タブに「このホストを更新」の UI は無い
- **帯域**: リモートタイルの既定は低 FPS/静止サムネイル、**選択時のみライブ化**(可視タイルのみ配信)。
  H.264 全タイル常時配信は LAN 帯域で成立しない
- **フレーム経過秒をタイルに表示**する。「古いフレーム」の原因がデバイス凍結とネットワーク遅延の2値になり、
  表示なしでは切り分け不能
- **watchdog の分界**: 凍結検知は「フレーム不変=デバイス凍結」前提だが、リモートではリンク切れでも同じ見え方になる。
  **ホスト到達性を先に判定してからデバイス凍結と診断する**(入れないとネットワーク瞬断のたびに sleep/wake 修復が誤発火する)
- **run レーンにホスト帰属を表示**する(NDJSON にホストを乗せて流す)。罠: runLaneModel/runReducer は両バンドル共有 →
  新規表示文字列は `i18n/strings/lane.ts` のランタイム側(既存の i18n 制約)
- **占有の表示は「どの run が使用中か」まで**。「誰の」は出さない(RR-15.3 で同一信頼グループ限定を既定とした)
- **リモートへの `devices down` 相当は他人の run を殺し得る** → ホスト側 `showWarningMessage({modal:true})` で確認
  (webview の `window.confirm` は効かない)
- **レポート・録画リンクはクリック時に回収してから開く**(録画は大きいのでオンデマンド+withProgress)。
  実行ログは OUTPUT へ(ホスト別チャンネル or 行プレフィクス)
- **プロセスタブ・orphanSweep はローカルプロセス走査前提**でリモートに適用できない。リモート分は状態表示だけにし、
  効かない kill ボタンを出さない。掃除はリモート側 fleetest の責務
- **ライブ操作は他の機械のデバイスも開ける**(serve を向こうで起こす。`.claude/rules/live-control.md`)。
  watchdog の自動修復は発行側の拡張が ssh で撃つ(RR-13)
