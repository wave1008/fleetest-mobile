## RM-2 試作の方法(Android Emulator・API 35)

情報源。時刻はすべてデバイスの単調時計。

| 情報源 | 取り方 | 性質 |
|---|---|---|
| t0 | `dumpsys input` の RecentQueue にある ACTION_DOWN の `eventTime` | ms 精度。ブリッジの変更は不要 |
| **SF** | `dumpsys SurfaceFlinger --latency-clear` → 操作 → `--latency <layer>` の actualPresentTime | アプリのレイヤーがフレームを出した時刻。観測による負荷はほぼ無い。**1レイヤー最大128フレーム**(60fps で約2秒分。動き続ける画面では溢れる) |
| **撮影** | デバイス内のシェルで `screencap \| md5sum` を回し、前後の `/proc/uptime` を記録する | 撮影の間隔は約 80ms(emulator)。全画面のハッシュを取る。1回の撮影は取得・転送・md5 を含むので、絵を取った瞬間は区間の中で特定できず、撮影の間に出て消えた変化は見えない |
| **木** | ブリッジの `/snapshot?refresh=1` を回し、次の対象が2回続けて同じ枠になった回 | ホストの時計で測り、`/proc/uptime` との往復(最短 RTT 約 25ms)でデバイスの時計へ写す。t0 との食い違いは −2〜−10ms。**見ているのは対象の有無と枠だけ**(遮蔽・可視性は見ていない)なので t2 ではなく「対象と枠を観測できた」の観測窓 |

条件: 4 SUT(View=`e2e.android`・CMP=`e2e`・Flutter・RN)× 4遷移 × 撮影あり(B)/なし(A)を交互に各4回(計128回・エラー0件)。
emulator-5556 の1台。この Mac の他の Emulator 5台と実機2台は接続したまま。load1 は 7.4〜30.7(24コア)。
**モニターの一時停止は前半約20分だけ効いていた**(`monitor pause --for 20` の単位は分で、計測は約30分)。

遷移:
- `nav_selector`(ホーム → セレクタ画面。次の対象は `#btn_back`)/ `btn_back`(逆向き)
- `btn_delay_1`(1秒後に `#txt_delayed` が木に現れる)
- `btn_freeze_3s`(3秒のフリーズ = 陽性対照。View/CMP/Flutter はメインスレッド、**RN は JS スレッド**のビジーループ)

## RM-4 分かったこと

1. **観測による負荷は、この条件では測れる大きさではなかった**: 撮影あり/なしの SF の中央値の差は全組で ±13ms 以内。
   ただし画面が軽い SUT・emulator 1台・前半だけ一時停止という条件での値で、重い画面や撮影の頻度を上げたときは未確認
2. **SF のフレーム ≠ 見た目の変化**: View と RN の画面遷移の後、約 1.65〜1.93 秒にスクロールバーのフェードの17フレームが続く
   (`SF 最後` が 1.9 秒になる原因)。さらに View の `btn_back` では、**フレームが出ているのに、取得した画像の間では差が無かった**
   (撮影は約 80ms おきなので、その間に出て消えた変化までは否定できない)。SF の「最後のフレーム」をそのまま t2 にすると大きく誤る
3. **「最初の塊の終わり」で装飾を切る方法も使えない**: 遷移は 76〜88ms で正しく切れるが、遅延表示(`btn_delay_1`)では
   中身が 1 秒後に別の塊として来るので、押した反応の 113ms を t2 にしてしまう。**装飾と本体を時刻だけで分ける方法は無い** →
   t2 は「次の対象」で決める(定義のとおり)
4. **画面の静止だけでは「操作可能」と言えない(陽性対照で確認)**: メインスレッドのフリーズ中は画面が止まる。CMP / Flutter は
   フリーズの前後で**取得した画像の間に差が無かった**(同じ限定つき)。「0.5秒静止したら操作可能」とその場で判定すると、フリーズ中に誤って操作可能と言う
5. **メインスレッドのフリーズは、アプリが応答するかで捕まる**: View / CMP / Flutter では木の取得(と /tap 自体)がフリーズの終わりまで返らない。
   SF もフリーズの終わりで描画が再開する(3.03〜3.11 秒)
6. **JS スレッドのフリーズ(RN)は、その操作のどの情報源にも出ない**: UI スレッドは空いているので、木は 230ms で答え、フレームも出ない。
   **次の操作の反応時間に出た**(2842ms = フリーズの残り + 通常の反応)。ただし**言えるのは「今回の確認ダイアログの表示では出た」まで**。
   ネイティブで完結する操作(スクロール等)は JS が止まっていても反応でき、JS を要する操作でも最初の画面変化がネイティブ側で先に起きる
   もの(TextInput の文字表示が先に変わり、`onChangeText` の処理だけが遅れる等)では t1 は短く出る。どちらでも t1・t2 とも
   正常に見えうる(陽性対照の追加は RM-6)。
   報告は「このステップの反応が遅い」という事実だけ(前のステップへ帰属しない)
7. **木で測った t2 には、ブリッジの待ちの下限がある**: 木の観測は `/tap` が戻ってから始まり、`/tap` は a11y の静穏 200ms
   (`QuietWaiter.QUIET_MS`)を待つ。そのため木の値は 230〜350ms より小さくならない。実際の遷移は 80ms 前後で終わっている(SF)。
   **製品では、判定をブリッジの中に置き、注入の直後から観測する必要がある**(ホストからのポーリングでは測れない)
8. **撮影の値は SF より 60〜70ms 遅く、分解能は約 80ms**。全画面のハッシュなので、ステータスバーの変化を拾う
   (フリーズの撮影ありの回の 32 回中 2 回に、4.3〜4.4 秒の孤立した変化。SF には無い)。使うなら `waitForSettle` と同じく端を除く
9. **時計**: `input` の eventTime と SF は同じ MONOTONIC(`uptimeMillis` と同じ、スリープ中は止まる時計)。`/proc/uptime` は
   BOOTTIME(スリープ中も進む)で、**差は起動以来のスリープの合計**。emulator-5556 は `dumpsys gfxinfo` の見出しの Uptime(MONOTONIC)と
   Realtime(BOOTTIME)が一致(28716768ms)= 差 0 なので、この写像は t0 と −2〜−10ms で合った。スクリプトは毎回この差を読んで
   引き、試行の前後で差が動いたらその回を無効にする形に直した

## RM-6 残り

製品に入っていない設計と、試作で未確認のこと。現行の設計は [design/response.md](design/response.md)(RM-1・RM-5・RM-8)。

**未実装の設計**

- **t2 の条件④(対象の領域で画素が変わらなくなる)と、シナリオの最後のステップの t2(画面全体の静止 ③+④)**。今は t2 を木の履歴だけで決め(`readyDecidedBy` = `tree`)、
  最後の計測ステップは判定しない。フレームが出ていることを応答の根拠にしない(RM-7)
- **t1 を名乗る `reactionMs`**: 最初のフレームを注入前の絵との差で確かめる(Android はアプリのレイヤーの範囲、iOS はステータスバー等を除いた範囲)。今は `firstFrameMs` だけを出す
- **要素の同一性の照合(`readyIdentity: element`)**: 今は全構成が `locator`(同じ位置に別の要素が来ても見分けない)。試した結果(2026-10-15・`Scripts/poc/identity-probe/`):
  Android は a11y ノードの同一性(ウィンドウ ID + `AccessibilityNodeInfo`)で、画面の入り直しは Compose・Flutter・RN・View とも新しい印・衝突 0 だが、
  **View の `RecyclerView` / `ListView` は行の View を使い回し、リストの上下 8 回送りで別の行が同じ印になった(91 件)**。iOS in-app は要素に通し番号を載せた形で、
  アドレスは解放後に再利用されるので印に使えない。入り直しは SwiftUI・CMP・Flutter が衝突 0、**RN は画面をまたいでネイティブの View を使い回す(25 件)**。リストは UIKit の
  `UITableView`(E2EAppIOS の `RowTableView`)が 106 件・RN が 63 件・CMP と Flutter が 0 件(Flutter は in-app のスクロールが途中から効かず往復を完遂していない)。
  帰結: `element` にできる見込みは Android の Compose・Flutter・RN と iOS の CMP、使い回す容器の外の要素(Android View・UIKit)。iOS の RN は全部 `locator`。
  残り: SwiftUI の `List` 自体・iOS の Flutter のリスト往復・使い回す容器の中かの木からの判定(Android は親の `className`、iOS はセル)・ほかの作り(遅延リストの別の実装・横スクロール・
  ナビゲーションの別のライブラリ)。XCUITest のブリッジは要素のオブジェクトを持たないので `locator` のまま
- **`stepKey`・`occurrences`・`ambiguous`(run をまたぐステップの同定)**: 今の鍵は (scene, section, command, description, 出現順) で、同じ経路の操作が別々の箇所から呼ばれたものを区別しない。
  案は、操作を呼んだ時点の呼び出しスタックを**ソースの位置(ファイル・行・列)の列**に直した鍵(試作 `Scripts/poc/call-stack-key-poc.swift`。sut-ec-mobile 21 本 264 操作・E2E-CMP 56 本 649 操作で
  2 回の dry-run の鍵が 100% 一致 = `Scripts/poc/dryrun-stack-keys/`)。前提は「学習と計測が同じ実行ファイル」「最適化しないビルド」。位置への解決は run の終わりに鍵ごと 1 回、
  一意性はバイナリの全部の呼び出し(arm64 の `bl` / `blr`)の戻り先を行表で位置に直して確かめ、同じ位置へ戻り先が 2 つ以上・列が 0・マクロ展開の中のどれかに当たる鍵は
  `ambiguous: true` で run をまたぐ比較から外す(行だけでは `helper(); helper()` が、`@_transparent` の展開では戻り先が 1 つの行に重なる)。字句で測れる箇所を表にする案は不採用
  (AI が書いた sut-ec-mobile は 252 件の 57.9% が測れない)。集計は `occurrences`(標本の回数)を並べる
- **観測の寿命の厳密化**: 観測 ID・ブリッジの起動世代・所有するシナリオ実行に結び付け、次の注入と一体で前の観測を締める形(`nextStepMismatch` / `observationAborted` / `bridgeRestarted` /
  `superseded` / `resolvedTargetChanged` / `contextUnidentified` の欠測理由)。今は直近 2 件の締めた観測を持ち、欠測の理由は 6 値(`notReadyBeforeNextAction` / `observationTimeout` /
  `observationTruncated` / `observationLost` / `noTarget` / `bridgeError`)。シナリオの失敗・アプリの終了・ブリッジの再起動で観測が残った場合の理由の区別は無い
- **ホストの報告の拡張表示**(拡張のモニター・結果画面に `firstFrameMs` / `readyMs` を出す)。今は md の報告と CLI(`fleetest results response`)だけ
- **`occurrences` の集約・`measure("名前") { }` ブロック・閾値で落とす機能**(いずれも未決定)
- xctrace の生の記録(約 3MB/秒)を既存の保持容量の掃除(`.claude/rules/results-retention.md`)へ接続すること(今は `--time-limit 2h` の安全弁と一時フォルダの後始末だけ)

## RM-7 実機での試作(2026-10-15)

### Android(Pixel 4a・Android 13・アニメーションあり)

条件: 方法は RM-2 と同じ(4 SUT × 4遷移 × 撮影あり/なし各4回・計128回・エラー0件)。アニメーション倍率を 1 に戻して測った
(ブリッジの既定は 0)。t0 はブリッジの所要時間ログ(`FT_BRIDGE_TIMING=1`)の行の時刻 − (inject + settle) で逆算した
(Emulator で `dumpsys input` と突き合わせて食い違い 0ms)。**この逆算には誤差が残る**: 引いている区間の始点はブリッジの `handleTap` の
座標解決の前で、ACTION_DOWN の瞬間ではない。所要時間の読み取りからログの時刻までの遅れも入る。さらに `logcat -v monotonic` の時刻は、
ログが記録した REALTIME を表示のときに変換したもの。数 ms 程度と見込むが測っていない(製品では入力イベント自身の時刻を返す = RM-5)。
**時計**: 計測の後(16:31)に `dumpsys gfxinfo` の見出しで Uptime(MONOTONIC)と Realtime(BOOTTIME)が一致(2737337419ms)。
差は起動以来のスリープの合計で減ることは無いので、計測中も差は 0 だった(= `/proc/uptime` で写した撮影・木の時刻も SF・t0 と同じ時計に
乗っていた)。※ 当初は logcat の時刻と `/proc/uptime` の一致を根拠にしていたが、logcat の時刻は変換して表示したものなので根拠にならない
(Codex レビューの指摘)。モニターは全体を通して一時停止。load1 は 9〜28(24コア)。

1. **アニメーションを残すと遷移が伸びる**: View の遷移は 3 フレーム(Emulator・倍率0)→ 8 フレーム(71〜188ms)
2. **View の SUT は操作のたびに約3秒、見た目の変わらないフレームを 60fps で描き続けることがある**(6回中5回。手で遷移させた1回は

   **次の操作の時点でも描画が続いていて、「操作後の最初のフレーム」が 1〜2ms と出る**(View の btn_delay_1・btn_freeze_3s)

5. **木の上限が 450〜1000ms**(木の取得1回に数百 ms)→ ホストからのポーリングでは t2 の分解能が足りない
6. **Android 13 の `dumpsys input` は eventTime を出さない**(`MotionEvent, age=…ms` だけ)→ t0 はブリッジから返すしかない

### iOS(iPhone SE3・iOS 26.6.2・XCUITest ブリッジ)

方法: `xcrun xctrace record --template 'Animation Hitches' --all-processes` で記録しながら、ブリッジの `/tap` で1回撃つ
(`Scripts/poc/ios-trace-poc.py`・表の読み出しは `Scripts/poc/xctrace_table.py`)。E2E-iOS の遷移とフリーズを各2回。
時刻は記録の開始から(t0 は取れない = 下の6)。

| 遷移 | 画面に出たフレーム(ms) | アプリのメインスレッドの停止 | /tap が戻る | 次の木の取得 |
|---|---|---|---:|---:|
| btn_freeze_3s | 3087〜3320 に15枚 → 6154〜6637 | **3116 から 3029ms** / **3162 から 3031ms** | 486〜489 | **2883〜2885** |
| nav_selector | 3091〜3325 に15枚 → 5225〜5775・6175〜6392 | 35ms / なし | 489〜514 | 294〜310 |

分かったこと:
1. **`displayed-surfaces-interval` が Android の SF に当たる**(画面全体で、変化があったときだけ行が出る。起動の6秒で20行)
2. **`potential-hangs` がメインスレッドの停止をそのまま出す**(3秒フリーズを 3029 / 3031ms)。木をポーリングせずに応答停止が分かる
3. **停止中もフレームは出る**: 停止の開始をまたいで押下のアニメーションが描かれる(render server 側で進む)
4. **遷移の約2〜3秒後に装飾の塊**(スクロールインジケータと思われる)。Android のスクロールバーと同じ
5. **XCUITest の tap はフリーズ中でも約 490ms で戻り、次の木の取得が停止の終わりまで待たされる**
6. **t0 は外から取れない**: 記録の開始時刻は秒単位、os-log は空、os-signpost は計測機器の定期記録だけ、アプリの run loop は
   XCTest のタップ前の問い合わせで起き続けていて、タップを受けた瞬間を区別できない。ランナーが端末の `mach_absolute_time` を返せば、`time-info` の
   `mabs-epoch` と換算係数(`timebase-info`)で記録上の時刻へ正確に写せる

### ブリッジの中での観測(Android・Pixel 4a・2026-10-15)

方法: 使い捨てのブリッジ(`Scripts/poc/observe-probe/bridge-poc-observe.patch`。同じ versionCode で Pixel 4a にだけ入れ、終了後に
正規の APK へ戻して dex の一致を確認)に `/pocObserve` を足した。タップを注入したらすぐ返し、裏のスレッドが木を連続して読んで、各読みの
開始・終了(`uptimeMillis`)と次の対象の枠を記録する。窓 = 「対象が読めて枠が2回続けて同じ」になった読みの終わり(上限)と、それより前で
条件を満たさなかった最後の読みの開始(下限)。アニメーション倍率は 1(元の 0 に戻した)。遮蔽・画素の静止(①の遮蔽・④)は見ていない。
4 SUT × 4 遷移 × 4 回(`observe_probe.py`)。t0 は注入の直前に読んだ `uptimeMillis`。**読みは素の取得(`forceRefresh=false`)で、
Android 13 の取得はノードのキャッシュを返しうる** —— 子の枠が最新かは確かめていないので、下の値は「木の条件(対象が読めて枠が2回同じ)を
確認した候補時刻」であって、①②が実際に成り立った時刻の保証ではない(Codex の指摘)。**下限は出さない** —— 測ったときの定義(枠の変化を
見た読みの開始を下限にした)は、変化が前の読みとの間に起きた場合に停止の時刻を含まない誤りだった(スクリプトは直した。直した定義では
測り直していない)。

| SUT | nav_selector→btn_back | btn_back→nav_selector | btn_delay_1→txt_delayed | btn_freeze_3s | 取得1回の所要(中央値) |
|---|---|---|---|---|---:|
| View | 60〜72 | 69〜74 | 1056〜1070 | 3056〜3068 | 4〜6ms |
| CMP | 169〜286 | 132〜187 | 1059〜1064 | 3039〜3066 | 4〜8ms |
| Flutter | 164〜410 | 136〜167 | 1090〜1114 | 3044〜3051 | 4〜5ms |
| RN | 107〜121 | 104〜121 | 1073〜1090 | **41〜56** | 4〜7ms |

(候補時刻 = 条件を確認した読みの終わりの、4回の範囲。単位は t0 からの ms)

分かったこと:
1. **取得1回の所要は 4〜8ms**(ホストからの読み直しは1回数百 ms = RM-7 の Android の表)。ただし素の取得なので、**最新の状態を見る分解能が
   これだとは言えない**(キャッシュを避けた対照と、枠を動かす陽性対照が要る = RM-6)
2. **Flutter の遷移は、最初の読みが遷移の間 UI スレッドに待たされ**、戻ったときには対象の条件がもう揃っていた(測ったときの定義でも下限が
   出なかった)。根の応答が返ったことは③(アプリが応答する)の材料になるが、子の枠の鮮度は別なので、これだけで t2 を決めない
3. **CMP のフリーズでは注入そのものが約 3 秒止まる**(注入の所要 3033〜3052ms。ほかは 19〜54ms で、Flutter の1回だけ 148ms)= t0 を「注入の直前」で取ると、
   反応・t2 にフリーズの全体が入る。入力イベントの時刻(RM-5 の ACTION_DOWN の `downTime`)を t0 にするのはこのため
4. **RN の JS の停止は、今回の木の条件の候補時刻に出なかった**(41〜56ms = UI スレッドは空いていて、対象は木に揃っている)。RM-4 の6と同じ
5. **観測の負荷**(`observe_load.py`。同じタップを観測あり(1500ms)/なし(0ms)で交互に4回ずつ。**注入前は固定で待つだけで描画の
   停止を確かめず、注入の後 約1.8秒で SurfaceFlinger を1回読んだ** = 比べたのは「採取した範囲の中の最初・最後のフレーム」で、前の操作の
   描画を拾う・描画の途中で切れることがある。View は操作のたびに約3秒描画を続けることがある = 上の Android の節): 最初のフレームの中央値は観測ありが View +8.5・CMP +3・Flutter +14.5・RN +5ms(Flutter は観測ありで 349ms の外れが
   1回)。採取範囲の最後のフレームの中央値も観測ありが +1.5〜+7ms(描画の終わりの比較ではない)。**全部「観測ありが遅い」側だが、4回ずつではばらつきと区別できない**。製品では
   読みの間隔を空ける(連続読みにしない)か、負荷を測る対照を多くの回数で取ってから決める

### ブリッジの中での観測の測り直し(第2版・同日・Pixel 4a)

使い捨てのブリッジ(第2版 = `bridge-poc-observe.patch`)は観測のスレッドを注入の前に起こし、読み方(素 = `forceRefresh=false` /
取り直し = 全ノード `refresh()`。API 34+ は `clearCache` も = Pixel 4a は API 33 なので `refresh()` だけ)・読みの間隔・スワイプの注入を
指定できる。端末は終了後に正規の APK(dex 一致)・アニメーション倍率 0・verifier 設定の未設定へ戻した。

**鮮度**(`freshness_probe.py`。同じ観測の中で素と取り直しを交互に読み、素の取得が「それより前に終わった取り直しの列で、最新より
前に出ていた枠」を返した回 = **逆行の候補**を数える。4 SUT × 2 ケース × 4 回):

| SUT | スワイプ中の `#row_05`(陽性対照) | 遷移 nav_selector→btn_back | 取得1回の中央値(素 / 取り直し) |
|---|---|---|---|
| View | 素 29 回中 **逆行の候補 1 回** | 素 90 回中 0 | 6〜73ms / 59〜178ms |
| CMP | 素 20 回中 0 | 素 23 回中 0 | 10ms / 268〜317ms |
| Flutter | 素 24 回中 0 | 素 66 回中 0 | 7〜33ms / 97〜214ms |
| RN | 素 26 回中 0 | 素 48 回中 0 | 9〜80ms / 137〜177ms |

- 陽性対照では、素・取り直しとも1回の観測で枠の変化を 2〜8 回見ている(枠が動いたことは観測できている)。**ただし逆行の候補は古い
  取得と確定しない** —— 実際の枠が A→B→A と戻っても同じ形になる(Codex の指摘)。View の1件は、取り直しの列が一方向に進む中
  (y = 1179→1165→1137→…→625)で素の1回だけが前の値 1179 に戻ったもので、一方向のスワイプなので古い取得と読むのが自然だが、
  実際の戻りを否定はできない。また、素と取り直しが同じだけ遅れていれば見えないので、**0 件は「古い枠を返さない」ことの証明でもない**
- **取り直しは遷移では素の約 10〜30 倍遅い**(スワイプ中は素も 33〜80ms に伸びるので約 2〜30 倍 = View 2.4 倍・RN 1.7 倍もある)。交互に読むと素の2回の間に取り直しが
  挟まるので、遷移の窓の上限は View で 242〜274ms(素だけの第1版は 60〜74ms)に広がった = 取り直しを混ぜると分解能が落ちる
  (アプリが遅くなったのか読みが遅れたのかは、この測り方では分けられない)

**負荷**(`observe_load2.py`。注入の前に 500ms フレームが出ないことを確かめ、`SFPoller` で継ぎ足して注入の後 4 秒を採る。観測なし /
連続読み / 16ms 間隔を交互に 8 回ずつ。除いた回は 0。反応 = t0 の後の最初のフレーム、中央値 ms):

| SUT | 観測なし | 連続読み | 16ms 間隔 |
|---|---:|---:|---:|
| View | 57.0 | 55.0 | 61.5 |
| CMP | 156.5 | 147.5 | 137.0 |
| Flutter | 131.5 | 141.5 | 141.0 |
| RN | 87.0 | 91.0 | 96.0 |

- 差は ±20ms 以内で向きもそろわない(CMP は観測ありが速い)。**8 回ずつでは観測による一貫した遅れは見えない**。10〜20ms 程度の差が
  無いとは言えない。**描画の終わりは比べない** —— 測ったときの判定は、採取の終わり(注入の後 4 秒)まで描画が続いた回も「終わり」と
  数えていた(View は約 4.2 秒描画が続き、ほぼ全回がこれ = Codex の指摘)。スクリプトは「採取の終わりまで 500ms 残らない最後のフレームは
  終わりを確かめられなかった」に直した(直した判定では測り直していない。生のフレームは保存していない)
- 第1版(4 回ずつ・採取範囲 1.8 秒)で「全部観測ありが遅い」側に出たのは、この回数では再現しなかった
