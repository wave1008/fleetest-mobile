# レスポンス計測(試作の記録と設計の方針)

**状態: 試作(2026-10-15・ブランチ `poc/response-measurement`)。製品コードとブリッジには何も入れていない。**
試作のスクリプトは `Scripts/poc/response-poc.py`(計測)と `Scripts/poc/response-poc-summary.py`(集計)。

**用語**

| 語 | 意味 |
|---|---|
| t0 / t1 / t2 | 操作の注入 / 最初の画面変化(反応)/ 次の操作ができるようになった時刻(§1) |
| SF | SurfaceFlinger。Android の画面合成サービス。アプリのフレームが画面に出た時刻を記録している |
| SUT | System Under Test。ここでは fleetest 自身の E2E 用アプリ(View・CMP・Flutter・RN の4種) |
| View | Android の View/XML で書いた SUT(`E2EAppAndroid`) |
| CMP / RN | Compose Multiplatform / React Native |
| 木 | アクセシビリティ(a11y)の要素ツリー。ブリッジの `/snapshot` が返す |
| 観測窓 | ポーリングで「成り立った」と分かった時刻の幅。真の時刻はこの中にあるとは限らない(下限は「まだ成り立っていなかった最後の観測」が無いと決まらない) |
| p90 | 90パーセンタイル |
| RTT | Round Trip Time(往復時間) |
| load1 | ホスト(macOS)の1分平均のロードアベレージ |
| 撮影あり(B)/ なし(A) | デバイス内で画面を撮り続けながら測った回 / 撮らずに測った回(観測による負荷の比較用) |

## 1. 何を測るか(ユーザーと合意した定義)

「レスポンス計測モード」で、並列なしで回す。**対象は実機(ユーザー決定 2026-10-15)**。Simulator / Emulator は対象外
(§2〜§4 の Emulator の実測は方法の検証として残す。実機の実測は §7)。1回の操作について、次の3つの時刻を取る。

```
操作の注入 ──▶ 最初の画面変化 ──▶ 操作可能になった時刻
   t0              t1(反応)            t2(操作可能)
```

- **t2 は次のステップで決める**: 次のステップの対象が木で解決でき、覆われておらず、枠が止まっていて、**かつアプリが応答する**。
  次のステップが無いとき(シナリオの最後)は画面の静止だけで決める
- 時刻は**デバイスの時計**で打つ(ホストで打つとブリッジとの往復が混ざる)
- 1回の値で語らない(N 回の中央値・p90)。比べるのは**同じデバイス・同じ機械での前回比だけ**。帰属(「アプリが遅い」)は書かない

## 2. 試作の方法(Android Emulator・API 35)

情報源。時刻はすべてデバイスの単調時計。

| 情報源 | 取り方 | 性質 |
|---|---|---|
| t0 | `dumpsys input` の RecentQueue にある ACTION_DOWN の `eventTime` | ms 精度。ブリッジの変更は不要 |
| **SF** | `dumpsys SurfaceFlinger --latency-clear` → 操作 → `--latency <layer>` の actualPresentTime | アプリのレイヤーがフレームを出した時刻。観測による負荷はほぼ無い。**1レイヤー最大128フレーム**(60fps で約2秒分。動き続ける画面では溢れる) |
| **撮影** | デバイス内のシェルで `screencap \| md5sum` を回し、前後の `/proc/uptime` を記録する | 撮影の間隔は約 80ms(emulator)。全画面のハッシュを取る。1回の撮影は取得・転送・md5 を含むので、絵を取った瞬間は区間の中で特定できず、撮影の間に出て消えた変化は見えない |
| **木** | ブリッジの `/snapshot?refresh=1` を回し、次の対象が2回続けて同じ枠になった回 | ホストの時計で測り、`/proc/uptime` との往復(最短 RTT 約 25ms)でデバイスの時計へ写す。t0 との食い違いは −2〜−10ms。**見ているのは対象の有無と枠だけ**(遮蔽・可視性は見ていない)なので t2 ではなく「対象と枠を観測できた」の観測窓 |

条件: 4 SUT(View=`e2e.android`・CMP=`e2e`・Flutter・RN)× 4遷移 × 撮影あり(B)/なし(A)を交互に各4回(計128回・エラー0件)。
emulator-5556 の1台。この Mac の他の Emulator 5台と実機2台は接続したまま。load1 は 7.4〜30.7(24コア)。
**モニターの一時停止は前半約20分だけ効いていた**(`monitor pause --for 20` の単位は分で、計測は約30分)。

遷移:
- `nav_selector`(ホーム → セレクタ画面。次の対象は `#btn_back`)/ `btn_back`(逆向き)
- `btn_delay_1`(1秒後に `#txt_delayed` が木に現れる)
- `btn_freeze_3s`(3秒のフリーズ = 陽性対照。View/CMP/Flutter はメインスレッド、**RN は JS スレッド**のビジーループ)

## 4. 分かったこと

1. **観測による負荷は、この条件では測れる大きさではなかった**: 撮影あり/なしの SF の中央値の差は全組で ±13ms 以内。
   ただし画面が軽い SUT・emulator 1台・前半だけ一時停止という条件での値で、重い画面や撮影の頻度を上げたときは未確認
2. **SF のフレーム ≠ 見た目の変化**: View と RN の画面遷移の後、約 1.65〜1.93 秒にスクロールバーのフェードの17フレームが続く
   (`SF 最後` が 1.9 秒になる原因)。さらに View の `btn_back` では、**フレームが出ているのに、取得した画像の間では差が無かった**
   (撮影は約 80ms おきなので、その間に出て消えた変化までは否定できない)。SF の「最後のフレーム」をそのまま t2 にすると大きく誤る
3. **「最初の塊の終わり」で装飾を切る方法も使えない**: 遷移は 76〜88ms で正しく切れるが、遅延表示(`btn_delay_1`)では
   中身が 1 秒後に別の塊として来るので、押した反応の 113ms を t2 にしてしまう。**装飾と本体を時刻だけで分ける方法は無い** →
   t2 は「次の対象」で決める(定義のとおり)
4. **画面の静止だけでは「操作可能」と言えない(陽性対照で確認)**: メインスレッドのフリーズ中は画面が止まる。CMP / Flutter は
   フリーズの前後で**取得した画像の間に差が無かった**(同じ限定つき)。「0.5秒静止したら操作可能」とその場で判定すると、フリーズ中に誤って操作可能と言う
5. **メインスレッドのフリーズは、アプリが応答するかで捕まる**: View / CMP / Flutter では木の取得(と /tap 自体)がフリーズの終わりまで返らない。
   SF もフリーズの終わりで描画が再開する(3.03〜3.11 秒)
6. **JS スレッドのフリーズ(RN)は、その操作のどの情報源にも出ない**: UI スレッドは空いているので、木は 230ms で答え、フレームも出ない。
   **次の操作の反応時間に出た**(2842ms = フリーズの残り + 通常の反応)。ただし**言えるのは「今回の確認ダイアログの表示では出た」まで**。
   ネイティブで完結する操作(スクロール等)は JS が止まっていても反応でき、JS を要する操作でも最初の画面変化がネイティブ側で先に起きる
   もの(TextInput の文字表示が先に変わり、`onChangeText` の処理だけが遅れる等)では t1 は短く出る。どちらでも t1・t2 とも
   正常に見えうる(陽性対照の追加は §6)。
   報告は「このステップの反応が遅い」という事実だけ(前のステップへ帰属しない)
7. **木で測った t2 には、ブリッジの待ちの下限がある**: 木の観測は `/tap` が戻ってから始まり、`/tap` は a11y の静穏 200ms
   (`QuietWaiter.QUIET_MS`)を待つ。そのため木の値は 230〜350ms より小さくならない。実際の遷移は 80ms 前後で終わっている(SF)。
   **製品では、判定をブリッジの中に置き、注入の直後から観測する必要がある**(ホストからのポーリングでは測れない)
8. **撮影の値は SF より 60〜70ms 遅く、分解能は約 80ms**。全画面のハッシュなので、ステータスバーの変化を拾う
   (フリーズの撮影ありの回の 32 回中 2 回に、4.3〜4.4 秒の孤立した変化。SF には無い)。使うなら `waitForSettle` と同じく端を除く
9. **時計**: `input` の eventTime と SF は同じ MONOTONIC(`uptimeMillis` と同じ、スリープ中は止まる時計)。`/proc/uptime` は
   BOOTTIME(スリープ中も進む)で、**差は起動以来のスリープの合計**。emulator-5556 は `dumpsys gfxinfo` の見出しの Uptime(MONOTONIC)と
   Realtime(BOOTTIME)が一致(28716768ms)= 差 0 なので、この写像は t0 と −2〜−10ms で合った。スクリプトは毎回この差を読んで
   引き、試行の前後で差が動いたらその回を無効にする形に直した

## 5. 設計への帰結(案。§7 の実機の結果を反映済み)

- **計測モードはアニメーションを必ず残す**: ブリッジは起動時に Android のアニメーション倍率を 0 にし、iOS は Reduce Motion を入れる
  (`AnimationPolicy`。既定 = 無効)。止めた状態の応答時間はユーザーの体験を表さない(§7: 遷移が 3 → 8 フレームに伸びる)。
  計測モードでは `enableAnimations` を強制する(段階1で実装。既存の `enableAnimations` と同じく **run の開始時に合わせるだけで、終了時には
  戻さない** —— 次の run は開始時に既定の 0 へ合わせ直すが、run を経ない MCP のセッションは倍率 1 のまま動きうる。終了時に戻すのは段階2の残件)
- **t0 はブリッジが端末の時計で返す**(Android は ACTION_DOWN の `downTime` = `SystemClock.uptimeMillis`、iOS はランナーが合成を
  撃った瞬間の `mach_absolute_time`)。外から読む方法は残らなかった: Android 13 の `dumpsys input` は eventTime を出さず、
  iOS は記録の開始時刻が秒単位で、run loop は XCTest の事前問い合わせで起き続ける(§7)
- **t1(反応)= 最初の画面変化**(合意した定義のまま)。**最初のフレームは t1 そのものではない** —— 同じ中身のバッファを
  出し直しても1枚になり(§4 の2)、iOS の `displayed-surfaces-interval` は画面全体なので時計表示や通知の更新も拾う。
  フレームの時刻は**候補**として使い、注入前の絵との差で確かめる(Android はアプリのレイヤーの範囲、iOS はステータスバー等を除いた範囲)。
  確かめられない構成では `firstFrameMs` という別の量として記録し、t1 を名乗らない。
  全ステップで取る(前のステップが残した JS の停止が次の操作の値に出ることがある。出ない操作もある = §4 の6)。
  **さらに操作の前に描画が止まっていることを確かめる** —— 実機では前の操作の描画(約3秒)が続いていることがあり、そのまま
  「最初のフレーム」を取ると 1〜2ms と出る(§7)。計測モードは各ステップの前に「フレームが出ていない」を待ち、待っても止まらなければ
  「操作の前から描画が続いていた」を事実として残して t1 を出さない
- **t2(操作可能)= 次のステップの対象について、次の条件がすべて揃った最初の時刻**。
  **注入の時点では次の対象は分からない** —— `FTRuntime.perform` はステップを1つずつ同期で実行し、次に何をするかはシナリオの
  Swift のコード(操作の後に読んだ値での分岐など)が決める。
  **次の操作ステップが始まってから判定する方式は採れない** —— フレームと停止の区間の履歴だけでは、対象の木・枠・遮蔽・画素が
  過去にどうだったかを復元できない。例: 対象が 100ms で操作可能になり、150〜400ms は別の要素に覆われ、次のステップの観測が
  200ms から始まると、400ms を t2 と取り違える(Codex の再レビュー)。
  **採る方式 = 繰り返しの1回目で次の対象を覚え、2回目以降は注入の直後から判定する**: 計測モードは各シナリオを `responseRepeat` 回
  続けて回す(§8.1)。1回目は各操作ステップについて「次の操作ステップの対象」(ロケータ)を記録するだけにし(t2 は出さない)、
  2回目以降は注入と同時にその対象をブリッジへ渡して、注入の直後から条件を判定する。実際の次のステップが記録と食い違った回
  (分岐・座標の操作で対象が無い等)はその標本を欠測にする(食い違いは次のステップが始まった時点で分かる)。
  **観測は操作の完了と切り離す(実行を妨げない)**: ブリッジは注入した操作を通常どおり完了して返し、t2 の観測は裏で続ける
  (準備完了を待って操作の応答を遅らせない)。次の操作ステップが始まった時点でホストが学習との対応を照合し、一致すれば観測の結果を
  受け取って確定、食い違えば観測を取り消して欠測にする。観測には独自の上限を置き、次のステップの解決・操作より先に走らない
  (学習した対象が存在しない回 = 1回目だけ確認ダイアログが出た等 でも、余計な待ちが実行に乗らない)。結果の確定は照合の後。
  **論理ステップと注入を分ける**: 1つの操作ステップが複数回注入することがある(`scrollDown(repeat: 2)`・スクロールで探してから撃つ
  操作・`type(replace: true)` 等)。観測は**論理ステップに1つ**で、注入ごとには作らない。ホストは注入の要求ごとに
  (ステップの印・ステップ内で何回目の注入か)を渡し、ブリッジはステップの印が変わった最初の注入で観測を作る。
  t0 と反応(t1)は**ステップの最初の注入**から測る(利用者の操作が始まった瞬間)。t2 の条件は**ステップの最後の注入より後で**成り立った
  ものだけを数える(途中の注入はまだ画面を動かす。同じステップの次の注入が来たら、それまでに成り立った条件は捨てて判定し直す)。
  `readyMs` は §1 の定義どおり**最初の注入(t0)から**測り、`readyAfterLastInjectionMs`(最後の注入から)と `injectionSpanMs`(最初から
  最後の注入まで)・`injections`(注入の回数)を並べる(最後の注入からの値だけだと、注入 0ms・2000ms で準備 2100ms の回と、注入 0ms・200ms
  で準備 300ms の回が同じ 100ms になり、操作全体の遅れが比較に出ない)。ステップの最後の注入がどれかはホストしか知らないので、確定は
  次の論理ステップの最初の注入の時点で行う(下の「受け渡し」)。
  **観測の上限は判定を止めるだけで、観測を締めない**: 上限の起点は**そのステップの直近の注入**。上限に達したら判定(標本の取得)を
  止めて「上限で止まった」状態にする。同じステップの次の注入が来たら、候補を捨て、起点をその注入に移して判定を再開する(反復フリックの
  間隔が上限より長くても、ステップの途中で終わり方が確定しない)。**終わり方は締めたときに1回だけ決まる**: 締めた時点で判定が上限で
  止まっていれば `observationTimeout`。締めた後に同じステップの印の注入が来ることは無い(締めるのは次のステップの最初の注入か
  「締める」要求なので)
  **観測の寿命**: 観測は「受け取り」か「取消」が来る前提に頼らない(操作の後にシナリオが失敗する・アプリが落ちると、どちらも来ない)。
  - 最初の注入の応答でブリッジが**観測 ID** を返す。観測は (観測 ID・所有するシナリオ実行 = run とシナリオの試行・**ブリッジの起動世代**)
    に結び付ける。起動世代はブリッジが起動ごとに新しく作る値で、応答のたびに返す
  - **受け渡しは次の注入と一体にする**: 次の論理ステップの最初の注入の要求に「前の観測 ID・起動世代・照合の結果(一致 / 食い違い)」を
    載せ、ブリッジは**前の観測を締めてから**注入し、締めた結果をその応答で返す(別の取得の呼び出しを挟まない = 取得と注入のあいだに
    結果が失効する窓が無い)。締めた時点で t2 の条件が成り立っていなければ `notReadyBeforeNextAction`(次の操作がそれより先に撃たれた
    という事実)。シナリオの最後の操作は、ホストが画面の静止(③+④)を待ってから、注入を伴わない「締める」要求で同じ結果を受け取る
  - 終わり方と結果: 照合が一致 = 確定 / 食い違い = `nextStepMismatch` / 締めた時点で判定が上限で止まっていた = `observationTimeout`
    (上限は捨てる時刻でも締める時刻でもない)/ シナリオの失敗・中断・接続断・アプリの終了 = `observationAborted`(ホストが
    締める要求に理由を載せる。届かなければ下の「所有者が変わった」で捨てる。どれだったかは `notes` に事実として書き、言えなければ
    書かない)/ ブリッジの起動世代が変わった(再起動で観測が消えた)= `bridgeRestarted`。再起動の前の観測は欠測で、新しい世代の観測と混ぜない
  - **`superseded` は正常な流れでは起きない**: ブリッジは**別の論理ステップの**注入が、前の観測を締める指示を持たずに来たときだけ、
    前の観測を `superseded` で締めてから注入する(同じステップ内の注入は上のとおり観測を続けるので該当しない)。受け渡しを注入と
    一体にしたので、起きたらホスト側の配線漏れ
  - **保持**: 時刻による失効は置かない。締めた結果(と締めた理由)は、同じ所有者のあいだ観測 ID ごとに残し、**所有者が変わった**
    (別のシナリオ実行の最初の注入が来た)ときにまとめて捨てる。保持するのは1シナリオ実行のステップ数ぶんだけなので溜まらない
  - 取得は観測 ID と起動世代を指定し、**保持しているあいだは何度でも同じ結果(終わり方を含む)を返し、別の観測には作用しない**。
    捨てた後・別の世代の ID には「無い」と答え、ホストは `bridgeRestarted`(世代が違う)か `observationLost`(同じ世代で無い =
    所有者が変わった後に聞いた)にする。最新の観測を暗黙に指す口は置かない(遅れた要求が次の観測を締める)
  **値の正しさは鍵に頼らない**: 次の操作ステップが始まった時点で、**実際の次のステップの (コマンド名・実効的な対象指定) が、観測した
  対象と同じか**を照合し、違えば `nextStepMismatch` で欠測にする(実効的な対象指定 = フォールバック `a||b` やスコープ指定を解決に
  使う形のまま)。**指定が同じでも解決先が同じとは限らない** —— `tap("#new||#old")` は 100ms でフォールバックの旧要素、700ms で
  プライマリの新要素に解決しうる(Codex の6回目のレビュー)。そこで観測は、条件が揃った時点の**解決先**(`a||b` のどの枝で解決したか・
  要素の枠・**要素の同一性の印**)を記録し、次のステップが実際に解決した先と比べる。違えば `resolvedTargetChanged` で欠測にする
  (枠が違う = 揃った後に対象が動いた、も含む)。**枝と枠だけでは足りない** —— 旧画面の `#next` が 100ms で揃い、同じ位置に新画面の
  別の `#next` が現れて 700ms で操作可能になると、枝も枠も同じまま 100ms を採ってしまう(Codex の7回目のレビュー)。同一性の印は
  ブリッジが木の要素に載せる: Android は a11y ノードの同一性(`AccessibilityNodeInfo.equals` が比べるウィンドウとノードの ID)、
  iOS の in-app はその要素のオブジェクトの同一性。**印は要素の入れ替えで変わるとは限らない** —— Android で試した結果(下)、
  View の `RecyclerView` は行の View を使い回すので、別の行が前の行の印を引き継ぐ。確かめられた構成だけ `readyIdentity: element` とし、印を持てない・確かめられていない
  構成(XCUITest のブリッジ等)は `readyIdentity: locator` として、保証を「同じ指定・枝・枠で条件が初めて揃うまで」に限る
  (値は出すが、要素の入れ替えを見分けていないことを欄で示す)。

  ASLR を消す)・コマンド名・実効的な対象指定。予測はさらに**そのスタックで何回目か**で引く(1回目の繰り返しで (鍵・k 回目) →
  次のステップの (コマンド名・実効的な対象指定) を記録し、2回目以降は同じ (鍵・k 回目) の記録を観測の対象にする)。
  関数の呼び出しはその戻り先がスタックに残るので、列はテストの入口から操作までの**実際の経路**になる。実行順の位置や、ソースの
  位置だけを鍵にすると、同じ `tap("#next")` が別々の箇所・別々の呼び出し元から実行されたものを区別できない(Codex の差し替えと
  再レビュー)が、呼び出しスタックはヘルパーをどこから呼んだか・クロージャをその場でどこから呼んだかを区別する。
  - **テストの入口まで届かないスタックは使わない**: 入口(テストメソッドを呼ぶ直前)のスタックを採っておき、操作のスタックの末尾が
    それと一致しなければ `contextUnidentified`。外部の画像(Foundation 等)のフレームで打ち切らない —— 打ち切ると、ヘルパーの中で
    `enumerateObjects` のコールバックから呼んだ操作の呼び出し元が消え、別の経路が同じ鍵になる(Codex の5回目のレビュー)。別スレッドへ
    乗り換えた操作も入口まで届かないのでここで落ちる。製品で採る場所は、DSL スレッドで同期に動いている間(`FTSync.run` が
    `Task.detached` へ渡す前)
  - **集計の単位は「同じ経路で同じ操作」**: 同じ鍵の標本は、何回目かを問わず1つのステップとして集計し、`occurrences`(標本の回数)を
    並べる。ループの各回はここで1つにまとまる。**保存した呼び出し可能な値**(工場で作ったクロージャ・メソッド参照・`lazy.map` のような
    遅延評価)を共通の箇所から呼ぶと、作った場所はスタックに残らないので、作成元が違っても同じ経路・同じ操作なら1つにまとまる
    (Codex の5・6回目のレビューの反例。試作で再現)。これは誤った値ではなく「画面の段階が違う同じ操作をまとめて集計する」ことで、
    利用者のレポートでも同じ経路の操作は区別できない(区別したいときはシナリオ側で別の呼び出し箇所に書く)。予測の (鍵・k 回目) が
    ずれて別の対象を観測した回は、上の照合で欠測になる。**作成元を字句で除外する走査は採らない** —— 保存したクロージャの中から
    呼んだヘルパー・メソッド参照・遅延評価するコレクションと、除外を潜る形が際限なく出る(Codex の6回目のレビュー)うえ、除外しても
    値の正しさは上の照合がすでに守っている
  - 試作(`Scripts/poc/call-stack-key-poc.swift`・`swiftc -Onone`): 学習 = A・B を通る / 計測 = B だけ。計測のヘルパー・保存した
    クロージャ・`enumerateObjects` 経由の操作は学習の B と同じ鍵・A とは別の鍵。工場で作ったクロージャは計測の B が学習の A と同じ鍵
    (= 同じ経路として集計される側)。別スレッドへ乗り換えた操作は `contextUnidentified`。プロセスを変えても鍵は同じ
  - 前提: **学習と計測が同じ実行ファイル**(同じ run の中で繰り返すので満たす。ビルドし直すと位置が変わる)・**最適化しないビルド**

    回によって変わるなら、予測の食い違いとして欠測に出る)

  標本(ブリッジへの受け渡しが間に合わない等)は「観測を始めてから最初に成り立った時刻」と「観測の開始時刻」を別の欄に記録して、

  二重に持たない。条件は次のとおり:

  「応答しなかった」と言えるだけ)。**XCTest の操作後の待ち(`QuiescenceWait`)が明けた時刻は材料にしない** —— tap では既定で待ちを
  飛ばし、残す操作でも上限(6秒)で打ち切って続行し、差し替え自体が効かない環境もある(§7 でも3秒の停止中に tap が約 490ms で戻った)
- 次のステップが無いとき(シナリオの最後)は ③+④ を画面全体(端を除く)で見る

  取得1回の所要は 4〜8ms(中央値。§7 の「ブリッジの中での観測」)。ただしこれはキャッシュを返しうる素の取得の所要で、最新の状態を
  見る分解能はまだ確かめていない(§6)

- SF の128フレームの上限は実機で実際に超える(アニメーションありで連続描画)→ 計測中に読んで継ぎ足す(試作で実装済み)。
  **継ぎ足しても取りこぼしはありうる**(読みの間隔は「待ち + 層の一覧と各層の読み出しの所要」で、120Hz なら128枚は約1.07秒。読みの間に
  生まれて消えた層は一覧にも出ない)→ 間隔はリフレッシュレートと読み出しの所要から決め、**欠けを検出したらその回を無効にする**
  (試作は「履歴が上限まで埋まっていて(未確定の行も数える)、前回の読みの最新のフレームを含まない」読みを「履歴の連続性を確認できない」
  として、観測スレッドの例外とあわせて結果に `invalid` を立てる。欠けたとは限らない読みも保守的に無効になる)。
  **判定は緩めず、読む間隔を詰める**: 間隔を固定(1秒 + 読み出しの所要)にすると、120Hz で実際の間隔が 1.1 秒の入力では4回すべて
  連続性不明になった(Codex の差し替え)。試作は「履歴が埋まるまでの時間の半分」から直前の読み出しの所要を引いた残りを待つ形にした。
  **最初の1回は待たずに読む**(直前に `--latency-clear` するので履歴はほぼ空。周期もこの読みで分かる。既定の 60Hz の周期で約 1.07 秒
  待ってから読むと、120Hz の連続描画では周期を知る前に128枚を超え、その試行は最初から連続性不明になる = Codex の差し替え。
  120Hz・読み出し 20ms の模擬で、直す前は無効・直した後は有効を確かめた)。
  アニメーションの多い標本ほど除外されうるので、**条件ごとの総数・有効数・無効数を必ず並べる**(集計スクリプトが出す)
- iOS の xctrace は記録した表を全部書き出すと数分かかる(`kdebug` だけで 137 万行)→ 書き出すのは `displayed-surfaces-interval` /
  `potential-hangs` / `time-info` だけにする

- 実機が計測の途中でスリープしうる条件(画面点灯の維持をしていない端末)での時計の扱い。iOS で記録がスリープをまたぐときの
  `time-info` の更新行と連続時計の対応(要確認)
- xctrace の記録そのものの観測による負荷(未測定)
- 重い画面(長いリスト・WebView)での観測による負荷
- View の SUT が操作のたびに約3秒、見た目の変わらないフレームを描き続ける原因(未特定。§7)

### ブリッジの中での観測(Android・Pixel 4a・2026-10-15)

方法: 使い捨てのブリッジ(`Scripts/poc/observe-probe/bridge-poc-observe.patch`。同じ versionCode で Pixel 4a にだけ入れ、終了後に
正規の APK へ戻して dex の一致を確認)に `/pocObserve` を足した。タップを注入したらすぐ返し、裏のスレッドが木を連続して読んで、各読みの
開始・終了(`uptimeMillis`)と次の対象の枠を記録する。窓 = 「対象が読めて枠が2回続けて同じ」になった読みの終わり(上限)と、それより前で
条件を満たさなかった最後の読みの開始(下限)。アニメーション倍率は 1(元の 0 に戻した)。遮蔽・画素の静止(①の遮蔽・④)は見ていない。
4 SUT × 4 遷移 × 4 回(`observe_probe.py`)。t0 は注入の直前に読んだ `uptimeMillis`。**読みは素の取得(`forceRefresh=false`)で、
Android 13 の取得はノードのキャッシュを返しうる** —— 子の枠が最新かは確かめていないので、下の値は「木の条件(対象が読めて枠が2回同じ)を
確認した候補時刻」であって、①②が実際に成り立った時刻の保証ではない(Codex の指摘)。**下限は出さない** —— 測ったときの定義(枠の変化を
見た読みの開始を下限にした)は、変化が前の読みとの間に起きた場合に停止の時刻を含まない誤りだった(スクリプトは直した。直した定義では
測り直していない)。

| SUT | nav_selector→btn_back | btn_back→nav_selector | btn_delay_1→txt_delayed | btn_freeze_3s | 取得1回の所要(中央値) |
|---|---|---|---|---|---:|
| View | 60〜72 | 69〜74 | 1056〜1070 | 3056〜3068 | 4〜6ms |

分かったこと:
1. **取得1回の所要は 4〜8ms**(ホストからの読み直しは1回数百 ms = §7 の Android の表)。ただし素の取得なので、**最新の状態を見る分解能が
   これだとは言えない**(キャッシュを避けた対照と、枠を動かす陽性対照が要る = §6)
2. **Flutter の遷移は、最初の読みが遷移の間 UI スレッドに待たされ**、戻ったときには対象の条件がもう揃っていた(測ったときの定義でも下限が
   出なかった)。根の応答が返ったことは③(アプリが応答する)の材料になるが、子の枠の鮮度は別なので、これだけで t2 を決めない
3. **CMP のフリーズでは注入そのものが約 3 秒止まる**(注入の所要 3033〜3052ms。ほかは 19〜54ms で、Flutter の1回だけ 148ms)= t0 を「注入の直前」で取ると、
   反応・t2 にフリーズの全体が入る。入力イベントの時刻(§5 の ACTION_DOWN の `downTime`)を t0 にするのはこのため
4. **RN の JS の停止は、今回の木の条件の候補時刻に出なかった**(41〜56ms = UI スレッドは空いていて、対象は木に揃っている)。§4 の6と同じ
5. **観測の負荷**(`observe_load.py`。同じタップを観測あり(1500ms)/なし(0ms)で交互に4回ずつ。**注入前は固定で待つだけで描画の
   停止を確かめず、注入の後 約1.8秒で SurfaceFlinger を1回読んだ** = 比べたのは「採取した範囲の中の最初・最後のフレーム」で、前の操作の
   描画を拾う・描画の途中で切れることがある。View は操作のたびに約3秒描画を続けることがある = 上の Android の節): 最初のフレームの中央値は観測ありが View +8.5・CMP +3・Flutter +14.5・RN +5ms(Flutter は観測ありで 349ms の外れが
   1回)。採取範囲の最後のフレームの中央値も観測ありが +1.5〜+7ms(描画の終わりの比較ではない)。**全部「観測ありが遅い」側だが、4回ずつではばらつきと区別できない**。製品では
   読みの間隔を空ける(連続読みにしない)か、負荷を測る対照を多くの回数で取ってから決める

## 8. 製品化の形(案・未決定)

参考にした慣用: Android Macrobenchmark(回数を指定して中央値・最小・最大を出す。Emulator やデバッグ版では警告する)/
XCTest の `measure(metrics:)`(**基準値をデバイスごとに持ち**、前回との差で見る)。Shirates にはこの機能が無いので踏襲元は無い。
この repo の慣用: 利用者向けの切り替えはプロファイルのキーで持ち、上書きは `--set` だけ(キーごとの専用フラグを足さない
= `.claude/rules/profile.md`)。既存の `--performance` は「レーンを厳格に扱う」意味なので流用しない。

### 8.1 有効化 = プロファイルのキー

- **`responseMeasurement: true`**(既定 false)。`--set responseMeasurement=true` で上書きできる(`run` / `api run` の両方。専用フラグは
  足さない = `RunCommandFlagParityTests` は変えずに済む)
- **`responseRepeat: N`**(**段階 2a で実装済み**: 2〜50 の整数・`responseMeasurement` 無しの指定はエラー・`RunMetaRecord.responseMeasurement.repeatCount` に記録。既定 5。各シナリオを続けて N 回回し、ステップごとに中央値・p90 を出す)。**1回目は次の対象を覚える回**で
  t2 を出さない(§5)ので、t2 の標本の数は「2回目以降の各回で、そのステップ(§5 の集計の単位)が有効に測れた回数の合計」(ループ等で
  同じ単位が1回の実行に何度も出れば N − 1 を超える。食い違い・観測の遅れの回は欠測になる)。N は 2 以上でなければエラー
- 実行時設定は `ScenarioExecutionSettings` に欄を足して運ぶ(既定は init の1箇所・プロファイルからの写像は変換 init だけ・
  子プロセスへの境界は走査テストで縛る = `.claude/rules/executor.md`)。**専用フラグを足さないことでは `run` / `api run` の配線漏れは
  防げない**(`RunCommandFlagParityTests` が見るのはフラグの集合だけ)→ 両方の入口で、有効化・下の拒否条件・結果の出力・
  モニターの停止を確かめるテストを置く
- 有効なときの強制と検査(**「指定したが黙って効かない」を作らない** = 名前の付いたエラーにする):
  - プロファイルの `devices` が**全部 `kind: physical`** でなければエラー(実機だけのプロファイルを確かめる検査は今は無いので足す)
  - **アニメーションを残す**(`enableAnimations` を強制。`enableAnimations: false` と併用したらエラー)
  - **並列なし**: レーンを1本にする(複数の実機があっても1台ずつ順に回す)。`--broadcast` / `--split` / `--fleet` との併用はエラー
  - テキストの可視性検証(FM・OCR)とホスト負荷による減速を止める。モニターは run が pause して終わったら戻す
    (`e2e.sh --performance` と同じ持ち方)

### 8.2 測る範囲 = 全ての操作ステップ(自動)

- tap / type / swipe / scroll / launchApp 等、**画面を動かす操作の全ステップ**で t1・t2 を取る。検証・待ちのステップは測らない
- シナリオ側に専用の DSL は足さない(範囲は `--scenario` / `--folder` で絞る)。後から欲しくなったら `measure("名前") { }` の
  ブロックで区間をまとめる形を検討する(XCTest の慣用)

### 8.3 結果 JSON

- **段階1で実装した形**: `TimelineStepRecord` に省略可の `command` / `response` を足した。`response` は計測モードの run の
  **画面を動かす操作のステップだけ**(判定は `FlowStep.isScreenMovingOperation` = 減速 `HostLoadPacing` と共有)に付く。欄は
  `busyBeforeAction` / `quietWaitMs` / `firstFrameMs` / `firstFrameMissing`(`busyBeforeAction` / `noInjectedInput` / `noFrame` /
  `frameHistoryIncomplete` / `noSessionApp` / `bridgeError`)/ `reactionMs` / `readyMs` / `readyAfterObservationStartMs` /
  `observationStartMs` / `readyDecidedBy` / `readyMissing`。**この版で値が入るのは前の4欄だけ**で、`reactionMs` と t2 の欄は
  常に省略、`readyMissing` は常に `notMeasuredInThisVersion`(`reactionMs` に `firstFrameMs` を写さない = §5)。
  記録する入力は「ステップの最初の注入」。**欄は省略可**(下の「欄の扱い」= ユーザー決定)。`RunRecordPack.trimmedForStorage` は未変更。型は `Sources/FTCore/ResponseMeasurementRecord.swift`、結果 JSON の説明は
  docs/results-json.md §TimelineStepRecord。下の列は最終形の案
- `TimelineStepRecord` に `command`(コマンド名。今は失敗時の `FailedStepRecord` にしか無い)と `response` を足す:
  `response = { stepKey, reactionMs, firstFrameMs, readyMs, readyIdentity, readyAfterLastInjectionMs, injectionSpanMs, injections, readyAfterObservationStartMs, observationStartMs, readyDecidedBy, readyMissing,
  busyBeforeAction, notes }`
  - `firstFrameMs`: 最初のフレーム(t1 を画面の差で確かめられなかった構成ではこちらだけを出す = §5)
  - `readyMs`: t2(ステップの最初の注入から)。注入と同時に観測を始められた標本だけ
  - `readyIdentity`: `element`(要素の同一性まで照合した)/ `locator`(同じ指定・枝・枠までしか照合できない構成。§5)
  - `readyAfterObservationStartMs` / `observationStartMs`: 観測の開始が遅れた標本(t2 を名乗らない)
  - `readyMissing`: t2 が無い理由(`learningIteration` = 1回目 / `nextStepMismatch` = 次のステップが記録と食い違った /
    `contextUnidentified` = 呼び出しスタックがテストの入口まで届かない(別スレッドへ乗り換えた経路)/ `noTarget` = 次の操作に対象が無い /
    `observationLate` = 観測の開始が遅れた / `notReadyBeforeNextAction` = 条件が揃う前に次の操作が撃たれた /
    `observationTimeout` = 締めた時点で判定が上限で止まっていた / `observationAborted` = シナリオの失敗・中断・接続断・アプリの終了 /
    `bridgeRestarted` = ブリッジの起動世代が変わった / `observationLost` = 結果を受け取る前に捨てられた /
    `resolvedTargetChanged` = 指定は同じだが、観測で揃った時点の解決先(枝・枠)と次のステップが実際に解決した先が違う /
    `superseded` = 前の観測を締めずに次のステップが注入された(配線漏れ)。§5 の「観測の寿命」)
  - `stepKey`: 集計の単位(§5 の呼び出しスタックの各フレームを**ソースの位置(ファイル・行・列)に直した列**・コマンド名・実効的な
    対象指定。アドレスはビルドし直すと変わるので run をまたぐ比較に使えない。位置へ直すのは run の終わりに、出てきた鍵ごとに1回だけ
    (debug ビルドのデバッグ情報の行表から。ソースを変えれば位置が変わり、別のステップとして扱われる)。DSL の内部のフレームは除いて
    シナリオのフレームだけを並べる。**行だけでは足りない** —— 同じ行の `helper(); helper(); helper()` は別々の戻りアドレスだが、ファイル・行に
    直すと3つとも同じになる(Codex の6回目のレビュー・`-g -Onone` の最小例)ので列まで含める(同じ最小例で、行表は列 29・39・49 を
    返した = `dsymutil` → `dwarfdump --lookup`)。**run の中で別の鍵だったのに位置の列が
    同じになったもの**だけを見るのでは足りない —— 位置が重なる別の経路が別々の run にしか出なければ、どちらの run でも衝突は見えない
    (Codex の7回目のレビュー)。そこで**一意性は実行された鍵ではなく、バイナリの全部の呼び出しの戻り先で確かめる**: 実行ファイルの
    呼び出し命令(arm64 の `bl` / `blr`)を全部逆アセンブルし、その命令のアドレスを行表で (ファイル・行・列) に直す(スタックの各フレームも
    戻り先から1を引いた = 呼び出し命令のアドレスで直すので、同じ規則で数える)。
    **同じ位置へ対応する戻り先が2つ以上ある位置**・列が無い(0)・マクロの展開の中、のどれかに当たるフレームを含む `stepKey` は、run の
    中の衝突の有無によらず `ambiguous: true` を立てて run をまたぐ比較から外す。行表の行の数では足りない —— `-Onone` でも
    `@_transparent` の関数は呼び出し元に展開され、その中の3回の呼び出しの戻り先が1つの行の範囲に入り、全部同じ位置になる
    (Codex の8回目のレビュー)。同じ形の最小例(`thrice { op() }; op(); op()`・`otool -tvV` → `dwarfdump --lookup`)で、`thrice` の位置には
    呼び出しが3つ対応し、`op(); op()` は列ごとに1つだった。戻り先の数え方は、命令の種類や行表を読めないなど一意性を確かめられないときも `ambiguous` に倒す
    (外しすぎる側。run の中の集計は鍵のまま分ける))
  - `injections` / `injectionSpanMs` / `readyAfterLastInjectionMs`: そのステップの注入の回数・最初から最後の注入まで・最後の注入から
    操作可能まで(`readyMs` と `reactionMs` は最初の注入から)
  - `readyDecidedBy`: t2 を決めた条件(`target` = 次の対象が操作可能になった / `screenStill` = シナリオの最後で画面の静止)
  - `busyBeforeAction`: 操作の前から描画が止まらなかった(このとき `reactionMs` は出さない = §5)
  - 帰属・分類の欄は置かない(失敗の記録と同じ規律)
- `RunMetaRecord` に `responseMeasurement: true` と、各デバイスの識別(udid / serial・機種・OS)と機械名
- **結果 JSON の契約を変えるので `ProtocolVersion` を +1**(Swift と `vscode-fleetest/src/protocolVersion.ts` の両方)。契約の文書
  `docs/results-json.md` も同時に直す
- **欄の扱い = 省略可・`ProtocolVersion` は上げない・保存記録は移行しない**(ユーザー決定 2026-10-18。Codex の再レビューで出した
  「必須 + null・版 +1・保存記録の移行」の案は採らない)。理由:
  - 結果のファイルは読めないと**黙って飛ばされる**(`RunResultsStore` の decodeFailure)。必須にすると、移行しそこねた保存記録が
    履歴からまるごと消える = CLAUDE.md が避けたい「沈黙する縮退」をこちらが作る
  - `response` が無いことは「計測モードの回ではない(= 測っていない)」という**正しい意味**を持ち、古い記録でも同じ意味になる。
    読むときに既定値で埋めて古い形を吸う(CLAUDE.md が禁じる読み替え)には当たらない。`command` も無ければ「不明」のまま
    (description から切り出して埋めない)
  - 足した欄は後方互換(既存の読み手は無視する)なので、版を上げる条件(後方非互換)に当たらない
  - 段階を進めて欄の意味を後方非互換に変えるときは、そのときに版を上げる

### 8.5 ブリッジの変更(版を上げる)

- Android(`AndroidRunner`)と iOS の XCUITest ランナーに、計測モードのときだけ通る経路を足す:
  ①注入の時刻(端末の時計)を返す ②注入と同時に渡された次の対象(繰り返しの1回目で覚えたもの = §5)について、注入の直後から
  t2 の条件をブリッジの中で判定する。**操作の応答はそれを待たずに返し**、観測は裏で続けて、ホストが次の操作ステップの開始時に照合して
  受け取るか取り消す(§5)。観測の開始時刻も返す(遅れた標本を t2 と区別するため)
  ③操作の前の「描画が止まっている」の待ち(Android = SF のフレームが出ていない / iOS = 画面に出たフレームが途切れた。
  XCTest の待ちは打ち切り・省略・差し替え不可がありうるので、使うならそれぞれを型で区別し、描画の停止は別に観測する)
- iOS のフレームと停止は xctrace で取る(計測モードの run の間だけ記録し、書き出すのは3つの表だけ)。記録そのものの観測による負荷は
  最初に測る(§6)
- **xctrace の生の記録は大きい**(試作の9秒の記録で約 97〜101MiB。3つの表だけ書き出しても `.trace` は縮まない)→ 保存先・
  run の終了と中断(SIGINT 等)のときに記録を必ず止める・書き出した後に `.trace` を消すか容量の上限を置く・既存の保持容量の掃除
  (`.claude/rules/results-retention.md`)への接続、を製品化の条件にする
- 計測モードの経路は**リクエスト単位で適用して戻す**(例外のときも戻す)。計測の後の通常の操作へ待ち方が漏れないことを回帰で確かめる
- in-app エンジンは実機で使えないので対象外(xcuitest だけ)
