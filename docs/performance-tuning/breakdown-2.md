## 現在の時間の内訳(PT-3 の続き)

### PT-3.18 iOS のスクロール慣性は何で制御できるか(2026-08-02・**実測のみ。施策は未実施**)

スクロール領域制御(`scrollFrame`)の設計判断のために、**production の注入経路**(ブリッジの
`/swipe` と `/drag`)で 3 SUT を横断計測した。幾何スパンは全画面の 0.7→0.3(349.6pt)、
移動量はスクロール画面の可視 `#row_NN` から `n*行高 − frame.y` で推定(**Compose iOS は
画面外要素の frame がクランプされるので、ビューポートに完全に収まる行だけを使う**)。

**(a) `swipeUp(velocity:)` と `press-drag(withVelocity:)` は同じ物理**: 同スパン・同 velocity で
984.3pt 対 985.3pt(差 0.1%・ばらつきも同等)。**座標経路へ移しても慣性の挙動は変わらない**。

**(b) 終端ドウェル(`thenHoldForDuration`)は効かない**: v1500 で hold 0 / 0.05 / 0.10 / 0.20 を
振っても 2.85 / 2.85 / 2.82 / 2.82 倍で、慣性は消えず**所要だけ +200ms**。XCUITest の hold は
指を保持するだけでイベントを出さないため `UIPanGestureRecognizer` の速度計算が更新されない
(Android の `VelocityTracker` は同一座標の MOVE を送れば速度が 0 になるのと対照的)。
→ PT-6 の不採用表に登録。**iOS で慣性を消す手段は速度を落とすことだけ**。

**(c) 慣性が消える速度はフレームワークで違う**(スパン比 = 実移動量 ÷ 幾何スパン):

| velocity | SwiftUI(E2E-iOS) | Compose(E2E-CMP) | Flutter(E2E-Flutter) |
|---:|---:|---:|---:|
| 1500 | 2.85 | 1.46 | 2.76 |
| 700 | 1.67 | 1.14 | 1.61 |
| 500 | 1.43 | 1.10 | 1.37 |
| 350 | **0.97** | **0.97** | 1.21 |
| 250 | 0.97 | 0.97 | **1.11** |

**Flutter は v250 でも 11% 残る**。「速度を下げれば幾何スパンどおりに動く」は SwiftUI/Compose だけ。

**(d) 慣性除去のコストは SUT で逆向き**(v1500 → v350 のジェスチャ所要):
SwiftUI 2,970→1,507ms(**−49%**)/ Compose 595→1,367ms(**+130%**)/ Flutter 594→1,369ms(**+130%**)。
**SwiftUI だけが「慣性あり = quiescence 待ちが長い」構造**で、CMP/Flutter は素直に
「遅いジェスチャ = 遅い」。1 SUT の計測から「慣性除去は速い」と一般化してはいけない。

**(e) 遅いドラッグはジェスチャの意味を変える**: v350 / v150 の上方向ドラッグを **Flutter の
検出パッドが `swipe=down` と誤判定**する(SwiftUI/Compose は正しく `up`)。
**DSL の `swipe`(ジェスチャ目的)に慣性除去を適用してはいけない**。

**(f) 現状の取りこぼしリスク**(1 スワイプの移動量 対 リストのビューポート高):
SwiftUI 681/492 = **1.38 倍超過** / Compose 509/546 = 0.93 倍 / Flutter 963/550 = **1.75 倍超過**。
スクロール探索は行き過ぎた要素を拾い直さないので、**SwiftUI と Flutter では原理的に取りこぼし得る**
(E2E で顕在化しないのは目標が端の `#row_40` だから)。

### PT-3.19 スクロール探索の座標化を「未指定」まで広げる案(2026-08-02・**撤回**)

`scrollFrame` を明示したときの座標経路(PT-3.18 の実測に基づく実装)を、**未指定のスクロールにも
広げる**案。面積最大のスクロール容器(`ElementInfo.scrollable`)を暗黙の対象にし、慣性を消す
速度(iOS v350)と大きめの刻み(スパン 0.8)で「刻み = 実移動量」にして**要素の飛び越しを
構造的に無くす**狙いだった。実装して 4 SUT × 3 ブリッジ(Android / XCUITest / in-app)で実測し、**3つの理由で撤回した**。

- **iOS xcuitest には対象を特定できない画面がある**。E2E-iOS のセレクタ画面はスクロール容器に
  identifier が無く、snapshot のフィルタ(Other/ScrollView は identifier 付きのみ)で落ちるため
  申告が出ない。画面全体を対象にすると始点が画面の 90% = **タブバーの上**に乗り、
  **実移動量 0.0pt**(従来の `swipeUp()` は XCTest が要素の中で始点を決めるので効く)
- **Android には速度のノブが無い**。距離とストローク時間でしか決まらず、iOS と同じ設計にできない。
  既定 300ms のままだと Flutter が負荷時に `maxSwipes` を使い切って到達し損ね、200ms に速めると
  今度は Compose で**探索直後のタップが 9 行ずれた**(row_30 を狙って row_39)。
  どちらかに倒せるだけの較正が無い。
  **ずれを「慣性」と書いていたが未検証の推定**だった —— 同じ症状の真因は a11y ツリーの公開遅れで、
  2026-08-03 に snapshot のキャッシュ迂回で解決している(docs/verification/judgment.md「Compose の探索直後タップ」)。**この撤回理由を再検討するなら、まず 200ms を今のコードで測り直すこと**
- 明示指定の経路は既に価値を出している(領域を決めるのは利用者の意図で、そこでは容器が分かる)

**残したもの**(いずれも撤回とは独立に正しいと確認できた):
`ElementInfo.scrollable` の申告と `implicitScrollTarget` の規則 / 見切れ判定を**容器基準**にする修正
(下記)/ 座標スワイプが 1 ミリも動かなかったときに従来経路へ戻す自己補正 / 実移動量が
ビューポートを超えたら刻みを詰める自己補正。

**⚠️ 「残した」3つのうち2つは production で動いていなかった**(2026-08-05 に経路を追って確認)。
**同日に棚卸し済み** —— 現在の状態は次のとおり:

| 残したつもりのもの | 判明した実体 | 2026-08-05 の処置 |
|---|---|---|
| 実移動量がビューポートを超えたら刻みを詰める | `spanScale` は **`scrollPath` の中でしか読まれない**。`scrollPath` は `scrollFrame` 未指定なら nil を返すので、**既定の `scrollTo` では計算されるだけで効かない**。さらに閾値の基準が**画面の高さ**で、容器は定義上それより小さいため**指定時もほぼ発火しなかった** | **基準を容器へ直した**(下記) |
| 座標スワイプが動かなかったら従来経路へ戻す | `coordinateSwipeIneffective` は書き込みとリセットだけで**読み取り箇所が無い**。しかも立てる条件が `scrollFrame == nil`(= 座標を撃っていない場面)で、**用途と条件が噛み合っていない**撤回の遺物だった | **削除** |
| `implicitScrollTarget` の規則 | production からの呼び出し無し(単体テストのみ) | **削除**(規則はこの節に残る = 必要になったら書き直す) |

**閾値の基準を画面 → 容器へ**(`StepExecutor` の探索ループ)。PT-3.18(f) の実測を当てると、旧実装では
SwiftUI が 1 スワイプ 681pt に対し閾値 0.8×874=699pt で**素通り**していた(リストの可視高は 492pt =
**1.38 倍の超過**)= いちばん取りこぼす SUT でガードが無効だった。

**修正の実測は「差なし」= 現状の SUT では発火しない**(2026-08-05・同セッション A/B)。
E2E-CMP `S0060/S0080/S0090` を fix 3 周 / base 3 周、E2E-iOS `S0060/S0090` を 2 周 / 2 周:
スクロール系ステップの合計は**全シナリオで ±25ms 以内**(S0090 は 23.3s / 43.1s の規模)、
26/26 緑。つまり**ブリッジ既定の速度で座標スワイプする限り、実移動量は容器の 0.8 倍に届かない**。
→ この修正は**コストゼロの保険**であって高速化でも遅延でもない。**「効かないから戻す」ではなく
「発火条件を満たす SUT が現れたときに初めて効く」**と読むこと(単体テストが発火側を固定している)。

**効くのは `scrollFrame` を書いた経路だけ**で、これは仕様上の限界である(バグではない):
刻みを縮める唯一の口が `spanScale` → `scrollPath` で、あちらは領域未指定ならブリッジ既定に委ねるため。
**既定経路の飛び越しをホスト側で塞ぐには座標スワイプの常用が必要で、それがこの節の撤回対象**。
既定経路をどうしても救うなら、刻みを縮めるのではなく**行き過ぎを検出して1回戻す**(座標化を
復活させない唯一の道)。現状の失敗率は ios-xcuitest の `scrollTo` で 25/2,971 ≒ 0.8% と低く、
**凍結デバイス由来のノイズを除いた母数を取ってから**判断すること(docs/verification/triage.md「iOS シミュレータも「画面だけ死ぬ」」)。

**この過程で見つけて直した実バグ**:
- **見切れ判定が容器でなく画面基準だった**。リストの下端で見切れた行を「可視」とみなし、
  その中心をタップして**容器の外(タブバー)に当たり別画面へ遷移**していた
- **`isClippedByViewport` の大きさガードが `<` だった**。リストの行は容器と同じ幅を持つのが普通で、
  幅一致の行が丸ごと判定から漏れていた(`<=` が正しい)

**2度目の撤回(2026-08-03)**: 条件を変えて再投入した —— 保守的な刻み(スパン 0.5・速度は
ブリッジ既定のまま)で、**容器を特定できたときだけ**座標化する形。狙いは Compose の飛び越しを
塞ぐことだったが、**2つの理由で再び撤回した**:
- **Compose には効かない**。Compose の容器は xcuitest で `other` として出るため
  `ElementInfo.scrollable` を申告できず、そもそも暗黙の対象に選べない(実測: `#list_rows` も
  `#carousel_tags` も申告なし)。Compose の回避策は**利用者が `scrollFrame` を書くこと**
- **in-app で到達距離が縮む**。刻みが 0.85 ページ送り → スパン 0.5 になり、既定 `maxSwipes`(8)で
  `#row_40` に届かなくなった。「未指定ならブリッジ既定を尊重する」という決定にも反する

**再検討する条件**: (a) iOS xcuitest が identifier の無い容器も snapshot に載せられるようになる
(= 要素集合が変わるので `.型[n]` の意味に影響する)か、(b) Android で 1 スワイプの実移動量を
狙って出せる注入経路が見つかったとき。**どちらも無いまま再提案しない**(2回撤回済み)。

### PT-3.20 `hintDrag` と `ScrollGeometry` の統合(2026-08-03・**部分採用**)

WebView のヒント跳躍(`offscreenJump` / `dragGesture` / `hintDrag`)と、スクロール領域指定の
座標計算(`ScrollGeometry`)は「容器の中でマージンを避けて直線を引く」点が同じなので、
1箇所に寄せられないかを検討した。**完全統合はしない**。

- **距離の意味が違う**: ヒントは「目標まであと何 px か」で決まる**跳躍**、`ScrollGeometry` は
  「容器の何割か」で決まる**刻み**。同じ関数に押し込むと、どちらの意図も読めなくなる
- **注入経路と較正が違う**: ヒントは `/drag` を使い、`min(max(|Δy|/2500, 0.3), 0.7)` という
  **較正済みのジェスチャ時間**を持つ(PT-6 の分析どおり `scrollToEdge` の支配項)。
  `ScrollGeometry` は `/swipe` の座標で、速度はブリッジ既定に任せる。混ぜると較正値が壊れる

**採ったのは1つだけ** —— **容器を画面と交差させる規則**(`ScrollGeometry.intersection`)を
`dragGesture` でも使うようにした。従来は生の容器矩形を使っており、**画面からはみ出した容器では
画面外の座標を撃つ**(WebView が画面より高いときに起き得た)。交差を取れば scrollFrame 側と
規則が揃い、容器が画面内に収まる通常ケースでは**挙動は変わらない**(no-op)。単体テストつき。

### PT-3.22 端送りは in-app では1回で寄せる(2026-08-19・**改善**)

長文(利用規約のように「一番下まで送ってから同意」する画面)の `scrollToBottom` が遅い、が発端。
調べると **iOS の in-app ブリッジのスクロールはジェスチャではなく `UIScrollView.contentOffset` の
直接操作**(`InAppBridge.scroll` = ビューポートの 85% 固定)で、**慣性はそもそも存在しない**。
端が目的なら刻む理由が無いので、`SwipeRequest.edge`(ホストは `intent == .edge` のときだけ立てる)
で**コンテンツの端まで一度に寄せる**ようにした(bridgeProtocolVersion 70 → 71)。

**実測(E2E-iOS / ios-inapp・`スクロールで折り返し下の要素に到達できること.S0010`・base/fix を
交互に3周)**。40 行のリストなので送りは高々数ページだが、それでも:

| ステップ | base | fix |
|---|---|---|
| `scrollToTop`(末尾から先頭 = 長い方) | 1,998 / 2,034 / 1,936 ms | 811 / 820 / 797 ms(**−60%**) |
| `scrollToTop`(2ページぶん = 短い方) | 1,047 / 1,060 / 1,057 ms | 783 / 827 / 825 ms(−23%) |
| `scrollToBottom`(既に末尾付近) | 573 / 589 / 584 ms | 578 / 602 / 588 ms(±0) |
| `scrollTo "#row_40"`(探索。**edge を立てない経路**) | 947 / 929 / 967 ms | 942 / 943 / 917 ms(±0) |

(A/B の fix 側には PT-3.23 のバーストも入っていたが、この画面では**加速の条件に達しない**
= 差はすべて端寄せによるもの。バーストを外した最終形で再確認済み: 792 / 809ms)

**fix 側は長い方も短い方も約 800ms に揃う** = 所要が**文書の長さに依存しなくなった**
(残っているのは端の確定に要る読み2回ぶん)。探索が動いていないことも同時に確認できている
(`edge` を `intent: .search` へ広げると1回で端まで飛んで途中の要素を全部飛び越すので、
**この列が動いていないことが安全側の対照**になる)。

**Compose/Flutter(in-app)は UIAccessibility の scroll 経路なので 1回 = 1ページのまま**
(刻み幅を選べる API が無い)。**Android と iOS xcuitest は実ジェスチャ**なので従来どおり
(速さのノブは PT-3.16 / PT-3.17)。

### PT-3.23 端送りでスワイプを束ねて木の読みを減らす案(2026-08-19・**不採用**)

`scrollToEdge` は1本振るごとに `settledSignature()`(キャッシュを捨てた木2枚+整定待ち)を払う。
「まだ動いている間の読みは何も決めていない」ので、**3回続けて動いたら以降は最大4本まとめて振り、
読みを 1/4 にする**案を実装して A/B した。**実測で得が無く、外した**。

| witness | base | fix(バースト) |
|---|---|---|
| E2E-Android / android `scrollToTop`(n=6) | 3,185ms | 3,359ms(**+5%**) |
| E2E-Android / android `scrollToBottom`(n=3) | 1,465ms | 1,474ms(+1%) |

理由は**端の手前でバーストに入ると、端に着いた後のスワイプが最大 cap 本ぶん空振りする**こと。
実ジェスチャのブリッジでは1本が読み1回と同じかそれ以上に高いので、節約と相殺する
(iOS xcuitest は PT-3.18(d) の実測 2,970ms/本 と読み約 860ms から、**計算上も負け**)。

**2026-08-20 に決着(再検討の条件が満たされ、結論は変わらなかった)**。受け手から
**展開後の実文書**(15章すべて展開・この画面で最長)の実測が届いた:
`scrollToBottom` 19.23〜19.53s / `scrollToTop` 21.85〜22.16s(3往復・ばらつき 0.3s 以内。
折りたたみ時の 4.6〜4.8 倍 = スワイプ本数もほぼ比例)。**バーストが最も効くはずの画面**。

そこで手元の Android で**1周の内訳**を測った(`api run` の NDJSON の phase 値。
E2E-Android / android の `scrollToTop`):

| 内訳 | 値 | 割合 |
|---|---:|---:|
| **ジェスチャ(action)** | 3,479ms | **81%** |
| 木の読み(snapshot) | 585ms | 14% |
| 待ち(wait) | 227ms | 5% |

**読みは 14% しか無い**ので、束ねて 1/4 にしても上限 10%、しかも端の手前で束ねた分が
空振り(1本 ≒ 385ms)になって相殺する。受け手の 19.2s に当てはめても差は 0.5s 前後 =
**測定のばらつき(±0.3s)と同程度**。実装は入れない。**この節はもう再検討しない**
(条件だった witness が揃い、結論が確認された)。

### PT-3.24 動かさなかったスクロールで整定を待たない(2026-08-20・**改善**)

受け手の実測報告(**常時アニメーションする WebView の長文画面**)で、`scrollToBottom`/`scrollToTop`
が **距離にも画面にも依存せず 8.0s 固定**(3回・計12測定が 8.00〜8.05s)になっていた。
原因は 8 という定数ではなく **in-app ブリッジが1リクエストごとに払う整定の上限 2,500ms**
(`InAppBridge.performWithSettle(capMs: 2500)`)× 端送りのリクエスト数:

- 端送りは「動かす1回 + **端を確認する数回**」の構成(PT-3.22 で回数は一定になった)
- 確認の回は**何も動かさない**のに、収束しない画面では毎回 cap を丸ごと使い切る
- 自分が起こしていない画面の収束を待っても意味は無い → **動かさなかったら待たない**
  (`performSettlingIfMoved`。bridgeProtocolVersion 71 → 72)

**再現と実測**: 手元の SUT は素直に整定するので witness にならない。`InAppSettle` の
「静穏になった」判定を**絶対に成立しない**よう注入して、報告と同じ条件を作って計測した
(E2E-iOS / ios-inapp・base/fix を交互に2周):

| ステップ | base | fix |
|---|---|---|
| `scrollToTop` | 7,983 / 7,982 / 7,993 / 8,013 ms | 2,968 / 2,944 / 2,984 / 2,982 ms(**−63%**) |
| `scrollToBottom`(既に末尾付近 = 全部 no-op) | 5,369 / 5,377 ms | 341 / 347 ms(**−94%**) |

**base が報告の 8.0s を3桁まで再現**した = 診断が正しいことの確認になっている。
fix に残る約 2.9s は「実際に動かした1回ぶんの cap + 木の読み」。ここも消すなら
**動かした側も待たない**(xcuitest ブリッジが 2026-07-30 に `/swipe` を整定対象から外したのと
同じ判断)が、影響範囲が探索経路まで及ぶので分けてある。

### PT-3.25 in-app ブリッジの再利用は「版」ではなく「dylib の出所」で判定する(2026-08-20・**改善**)

上の計測の途中で、**ブリッジのソースを変えても稼働中の in-app ブリッジが再利用され、
dylib が作り直されない**ことが分かった(実測: ソースを書き換えて run しても dylib の mtime が
動かない / 版を下げて run しても稼働中の新しいブリッジがそのまま応答する)。
**A/B の両腕が同じ dylib を実行していて、測定そのものが無効になっていた**。

版一致だけでは掛からない理由は2つ: **①版を上げ忘れた変更は素通りする** /
**②再利用を決めるプロセスは run 内の `swift build` より前に起動している**ので、比較に使う
`bridgeProtocolVersion` 自体が1ビルド古いことがある。

直しは **`.inapp` 状態ファイルに `BridgeSourceSet.inApp` の digest を残し、再利用は出所一致のときだけ**
許す(`InAppBridgeState` / `BridgeProvisioner.planBridge`)。digest は**その場のソースから計算する**
ので上の2つとも掛かる。記録の無い旧形式は「出所不明」= 起動し直す(更新直後の1回だけ余分に起動し直す)。
**変化が無ければ再ビルドも再注入も起きない**ことはデバイス実行で確認済み(ソース編集 → 作り直す /
無変更 → 作り直さない)。

### PT-3.26 Android の端送りは gesture が弱く、しかも1本ごとに待っている(2026-08-20・**調査。実装は PT-3.27**)

上の内訳で **81% がジェスチャ**と分かったので、その中身を測った(`FT_BRIDGE_TIMING=1` +
logcat の `settleTiming`)。ブリッジは `/swipe` の処理内で静穏待ち(`quietWait`)をしており、
**中央値 233ms・最大 1,232ms**(1シナリオ 32 回で合計 8.8s)。ジェスチャ所要のおよそ半分。

**ホストも同じ整定を待っている**(`StepExecutor.settledSignature` が「署名が2回続けて一致」を
見る)。**iOS の XCUITest ブリッジは 2026-07-30 にこの二重待ちを外している**
(PT-3.8 の `mutatingPaths` に `/swipe` と `/drag` を入れない判断。「スクロール慣性は budget 内で
収束しないので、ここで待っても整定したツリーにはならず待ち時間だけ捨てる」)。
**Android には同じ判断がまだ入っていない**。

**やるなら**: `SwipeRequest` に省略可の `settle`(既定 = 今日の挙動)を足し、端送りのときだけ
false を送って A/B する。**Android ブリッジの版上げは引き下げインストールができない**ので
(2026-08-14 の実害。フリート全滅から `adb uninstall` で復旧)、**追加は必ず省略可フィールドで**、
負けたら「送るのをやめる」だけで戻せる形にすること。
**見込みは怪しい(先に読むこと)**: 受け手の 19.2s のうち 40 本 × 約 230ms ≒ 9s に見えるが、
**iOS で外した理由がここには当てはまらない**。あちらは「budget 内に収束しないので待つだけ無駄」
だったのに対し、Android の `quietWait` は**収束している**(中央値 233ms)。しかも**待つ場所が
プロセス内で安い**。外すとホストが同じ待ちを**高い単位**(HTTP + キャッシュを捨てた snapshot)で
肩代わりするので、**合計は同じか悪化しうる**。

**先に試すべきは「1本で進む距離」**(ホストだけで変えられる = ブリッジの版を上げない)。

**実測(2026-08-20・E2E-Android / android・40 行リストの先頭から `flickCenterToTop`)**。
「連続で撃つと慣性が積み上がって速く進む」(Shirates の turbo の発想。保守側の指摘)を確かめた:

| 撃ち方 | 進んだ行数 | 所要 | 1本あたり | **行/秒** |
|---|---:|---:|---:|---:|
| 間隔 0.6s × 2本 | 28 行 | 2,578ms | 14.0 行 | 10.9 |
| 間隔 0.02s × 2本 | 23 行 | 1,418ms | 11.5 行 | **16.2** |
| (参考)現在の `scrollToEdge` の /swipe | — | — | **約 6 行** | 約 9.3 |

**慣性は積み上がらない**(詰めると1本あたり 14.0 → 11.5 行に**減る** = 2本目がフリングの
停止に食われる。2026-08-02 の注記と整合)。**しかし時間あたりは 1.5 倍速い** ——
待たないぶんが距離の目減りを上回る。

**さらに大きいのは gesture の形の差**: `flick`(drag 経路・中央→上端・0.25s)は1本 14 行
進むのに、`scrollToEdge` の `/swipe`(画面比 0.4・fling)は**約 6 行**しか進まない。
**端送りが弱い方の gesture を使っている**。

→ **やること2つ(どちらもホスト側だけ)**: ①端送りの gesture を flick 相当(長いスパン)にする
②端の判定に要る読みの回数はそのままに、gesture を待たずに撃つ。見込みは 1.7 倍前後
(9.3 → 16.2 行/秒)だった。**実際にはこの節の想定を超えた** —— WebView は PT-3.27 の
CDP 一発で **19.2s → 1.6s**(受け手の実文書で確認)。この節の較正が効くのは**ネイティブの
長いリスト**だけ。
**5本で測ると末尾に着いて差が消える**(40 行リストは 5 本で端)ので、較正は 2 本で測ること。

### PT-3.27 Android の端送りを「飛ばす/強く撃つ」へ(2026-08-20・**改善**)

PT-3.26 の較正を実装した。**発端は保守側の指摘**(Shirates で turbo = 短時間に連続で撃つ実装を
したとき長いコンテンツを高速に送れた、という経験)で、
測ってみると原因は慣性の積み上がりではなく**待たないこと**と**1本で進む距離**だった。

**① WebView は CDP で一発**(スワイプを1本も撃たない)。ページの中身は DOM を持っているので
`scrollingElement.scrollTop` を代入すればよい —— iOS の in-app が `contentOffset` で
既にやっているのと同じ判断(PT-3.22)。**代入そのものは 28ms**(実測)。
対象が独自のスクロール容器のときは**面積最大でスクロール余地のある要素**へ落ちる。
使えなければ従来のジェスチャへ落ち、**使えないと分かったアプリでは以後試さない**
(ネイティブ画面で毎回 adb のソケット探索を払わないため)。

| E2E-Android の WebView 画面 | 従来(ジェスチャ) | CDP |
|---|---:|---:|
| `scrollToBottom` | 6,061ms | **2,324ms(−62%)** |
| `scrollToTop` | 7,781ms | **2,530ms(−67%)** |

**残る 2.3〜2.5s はスクロールではなくホストの端判定**(署名が2回続けて不変になるまで読む)。
つまり**所要が文書の長さに依存しなくなった**ので、長い文書ほど効く。
**受け手の実文書で確認済み(2026-08-20)**: 展開後 `scrollToBottom` **19.2s → 1.6s**で、
**折りたたみ時と同値**(= 長さ非依存が実測で成立)。

**② ネイティブは強いストロークで撃つ**。端送りをブリッジの `/swipe`(画面比 0.4 + fling)から
**drag(中央→端・0.25s)**へ変えた。理由は2つ: **1本で進む距離が 6 行 → 14 行**(PT-3.26 の実測)、
**`/swipe` はブリッジ内でも静穏を待つ**(中央値 233ms)ので二重待ちが消える。

| E2E-Android の 40 行リスト | 従来 | 強いストローク |
|---|---:|---:|
| `scrollToBottom` | 4,062ms | 3,803ms(−6%) |
| `scrollToTop` | 6,060ms | 4,606ms(−24%) |

**探索(search)は据え置き**(1回の移動量がビューポートを超えると要素を飛び越すため。PT-3.16 と同じ線引き)。
1本あたりの距離が 2.3 倍になったのに所要が半分にならないのは、**待ちがホスト側へ移った**ぶん
(整定ポーリングが cap に当たる)を払っているから。

**③ iOS の端送りは動かした後も待たない**(bridgeProtocolVersion 73)。PT-3.24 で「動かさなかった
要求では待たない」ようにしたが、**動かした側も待つ必要が無い** —— 端送りの後にホストは必ず
`settledSignature` で整定を待つので二重になる。常にアニメーションする画面では cap(2.5s)が
そのまま所要になり、受け手の実文書で端送りが 3.0s 固定になっていた残りがこれ。
**探索と単発の swipe では従来どおり待つ**(あちらは待たないと次の解決が動いている木を掴む)。

### PT-3.28 端の判定はドライバの申告で切り上げる(2026-08-20・**改善**)

### PT-3.29 端の確定に「最後に動いてから 1.0 秒」の猶予を置く(2026-09-19・**正しさのための費用**)

PT-3.28 の「申告 + 確認の読み1回」は、**窓の外に続きを非同期で描き足すリスト**(RN の `FlatList`)で誤る。
in-app は端まで一度に飛ぶので、描き足し(実測 0.4〜0.7 秒)より前の送りが「余地が無い」になる。しかも
飛ぶたびにセルが同じ座標に並ぶので、型と座標の署名(`edgeSignature`)では動いたと読めない。E2E-RN の
S0091(開いた直後の `scrollToRightEdge`)が `#tag_13` で止まった(3/3)。

直し: ①端の確定(「不変」の判定・申告の両方)は、見えている中身が最後に変わってから
`StepExecutor.edgeClaimGraceAfterMove`(1.0 秒 = 0.7 + 余裕)経った後だけ。待った後は必ず1本送る。
送る前から端なら待たない ②in-app ブリッジは `contentOffset` を動かしたら `atEdge: false`(v116)を返し、
ホストはそれを「動いた」と数える(Android の CDP と同じ意味)。**AX の scroll の受理は含めない**
(Compose は端でも受理する。v115 で含めたら CMP の端送りが毎回 `maxSwipes` = 20 まで回った)。

**費用(ios-inapp・S0091・1台・1回の実測。場面 = 往復2回ぶんの合計)**:

| SUT | 横(右端→左端) 前 → 後 | 縦(末尾→先頭) 前 → 後 |
|---|---|---|
| CMP | 4.1s → 5.5s | 3.1s → 4.6s |
| Flutter | 5.3s → 7.1s | 4.2s → 6.2s |
| RN | 0.9s(**届いていなかった**)→ 3.7s | 1.3s → 3.2s |

1回の端送りあたり約 +0.7〜1.0 秒。**実スワイプの経路(XCUITest / Android ネイティブ)は1本で1秒近く
かかるので猶予はふつう切れていて払わない**。「前」は 9/18 の性能計測の場面別所要(S0090 の場面 6・7)。

**再検討の条件**: 描き足しが 1.0 秒を超える画面(ネットワークでページを足すリスト等)で途中止まりが出たら、
定数を上げるのではなく「描き足しが起きたこと」を観測する口(ブリッジが contentSize の変化を申告する等)を先に考える。

通ったものなので確かめ済みとして扱う。**プロセスで初めて使う見本を毎回測り直す形だと効かなかった**
(シナリオは1本ごとに別プロセスで、1本で1回しか呼ばない findImages は見本を全部測り直していた =
`[Radio]` 91 → 90ms)。③の後と比べて(全体 / 照合の中央値、ms): `findImages("[Radio]")` 219/91 → 192/63・
`findImages("[Switch]")` 349/119 → 314/86。**見本を1枚しか使わなかった元の実装(199/78・399/171)より速い**。
スクリーンショットを木と一緒に取る口(ブリッジ側)は、他の用途でも効く場面が出てから考える。

### PT-3.32 XCUITest の木の取得が焦点の問い合わせで毎回 2 秒待っていた(2026-10-08・**改善**)

- **症状**: キーボードの出ていない画面で `/snapshot` が毎回約 2.05 秒(Simulator・Xcode 27。キーボードが出ている = 焦点のある画面だけ 0.06 秒)。
  MCP の `ft_snapshot` も DSL の各ステップも同じだけ払っていた
- **原因**: `withFocusedFlag` の `firstMatch.snapshot()`。一致する要素が無いと約 2 秒待ってから失敗する。先に `exists` を聞いて 0.02 秒
  (ブリッジ iOS v156。`focusMark` も同じ形。`RunnerQuerySnapshotGuardTests` が再発を落とす)
- **表に出たもの**: E2EX-Flutter のツールチップ(表示 2 秒の間に `exist` → `textIs` が終わらない)が緑に。E2EX-RN の sticky は 28s → 11s
- **代償(直した)**: 2 秒の取得が隠していた「整定の早すぎる静止判定」が出た。XCUITest の木は慣性で動いている間も 100〜170ms おきにしか
  更新されない(払った直後に 20〜40ms おきに取得: CMP 最大 134ms・RN 174ms・SwiftUI 125ms)ので、100ms 周期の 2 枚が途中で一致する。
  `AppDriver.treeLagsBehindMotion` が true のドライバ(XCUITest)だけ、整定の周期を `laggingTreeSettlePeriodMs`(350ms)以上にした

### PT-3.35 ステップの減速(hostLoadPacing)の値の決め方(2026-10-10〜11・**計測。既定 90%→200ms・95%→1000ms を採用**)

目的(ユーザー方針): ホストの CPU が 100% に張り付かないようにする。条件は特記なき限り

平均が run の平均に寄る)・**区間の最大で取ると長い(=失敗しがちな)ステップほど高く出る**ので、開始時点で取る。
`at` は**終了**時刻(`StepOutcome` を作った時点)なので、開始は `at − durationMs`。

| 条件 | 97% 以上の時間 | 90% 以上 | 中央値 | run の所要 |

| 減速なし | 13.1% | 33.8% | 86% | 119 秒 |

| 記録を読む方式 400/1000ms | 6.9% | 24.3% | 81% | 132 秒 |

- **中央値を 90% に保つことは減速ではできない**(負荷を下げることしかできない)。8 台で中央値は 87〜88% になるが、
  97% 以上が 7〜10% に増える = 揺れの大きい負荷で中央値を 90% に置くと山が 97% を超える

  10 台では `findImage` 系の赤が 2 run とも出た。ユーザー決定でこの Mac の Android は最大 6 台
- **山の正体は `launchApp` の重なり**(8 台・97% 以上のサンプル 62 個): 平均 2.8 レーンが起動の最中(90% 未満では 1.7)。
  検証・`select` はむしろ少ない(比 0.4〜0.55)= 待たない側のステップが山を作っているのではない。
  CPU 90% 以上の瞬間の起動を機械全体で1本にする門は、8 台で山を半分(約 9% → 4.2%)にしたが、
  6 台では効かず所要 +15% → 不採用(PT-6)
- 何もしていないとき(Emulator 8 台 + 配信 8 本)の CPU は約 35%。山はテストの実行そのものが作っている
- **精度への効果は未確認**: 赤は条件を問わず数件で、差を判定できる件数に届かない。上の O/E から見積もると
  全体の失敗の減り方は1割程度。確かめるなら導入前後の通常 run を `Scripts/flake-ledger.py` と O/E の集計で比べる

### PT-3.38 受け手の最初のシナリオのビルド(2026-10-23・**計測。クローンの Package.resolved を写して固定した版で解決するを採用**)

条件: M2 Ultra・`fleetest init` 直後の作業フォルダ・SwiftPM の共有キャッシュは温まっている(取得はネットに出ない)。
クイックスタート手順6・Android でも、最初の `ft_list_scenarios` が 103〜110 秒 = テストを作るセッションで最大のツール時間だった。

- **内訳**(103 秒): 版の解決と取り出し 約 52 秒 + コンパイル 約 50 秒。受け手の作業フォルダは Package.resolved を持たず、
  **依存 25 件の版を毎回計算し直していた**(しかも fleetest がテストした組と違う版になる: swift-syntax 603.0.2 → 604.0.0)

  ドラッグ・長押しに gRPC を使う(`EmulatorControl`)ので、シナリオの製品から外せない。swift-syntax はコンパイルされない(既製品が使われる)
- **解決**: 素の `swift package resolve` 42.3s / クローンの Package.resolved を置いて素の resolve 36.2s(SPM は固定があっても版を計算し直す)/
  **置いて `--only-use-versions-from-resolved-file` 15.1s**。その後のビルド 54.3s → 合計 **約 69〜72 秒**(`fleetest run --dry-run` 経由で 72.4s)
