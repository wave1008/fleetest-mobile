# リモート実行

`fleetest run --host <ホスト>` は、別の Mac へ SSH でジョブを投げ、向こうで普通にローカル実行し、
出力と成果物を手元へ持ち帰る機能です。このページはできることとセットアップの流れの要点で、
詳細な手順は [docs/remote-runner-setup.md](../../remote-runner-setup.md) を参照してください
(ここでは手順を複製しません)。

## できること

| | 状態 |
|---|---|
| 1台のリモートへジョブ単位でディスパッチ(CLI・VSCode 拡張の両方) | ✅ |
| 実行中の進行表示・キャンセル・タイムアウト | ✅ |
| レポート・JUnit・録画・run ログの回収 | ✅ |
| ランナー機の導入・撤去を手元から1コマンド(`remote setup`) | ✅ |
| 複数ホストの一括診断・掃除(`remote status` / `remote clean`) | ✅ |
| リモートで単発の `fleetest` を走らせる(`remote exec`) | ✅ |
| 複数ホストへの同時実行(フリート。`run --fleet`) | ✅ |
| 1つのシナリオ集合を台数で分散する(`run --fleet <名前> --split`) | ✅ |
| リモート実行分が `fleetest results` の集計(flaky 検出など)に載る | ✅(既定で回収) |
| モニターのデバイスタブでリモートデバイスの状態・映像を表示 | ✅ |

シナリオとプロファイルは実行のたびに自動転送されるため、編集は常に手元だけで行います
(ランナー機を直接編集することはありません)。

## 全体像

```
発行側の Mac(手元)                     ランナー機
fleetest run --host mac2 …               ~/fleetest-runner/               ← 専用ベースディレクトリ
  ├ 適合チェック(rev・Xcode)   ssh     ├── foundation-tester/          ← ツール本体のクローン(名前固定・共有)
  ├ 転送(rsync: シナリオ・設定) ────>  └── users/<issuerId>/work/      ← あなたの作業場所(発行者ごと)
  ├ 出力を受け取って表示                     ├── TestProjects/<プロジェクト>/
  └ 成果物を回収 <───────────────────      └── .build/
```

ランナー機がそのマシン自身のために持っている foundation-tester(あれば)には一切触りません ——
リモートランナーは `~/fleetest-runner/` 配下だけで完結します。

## ランナー機の前提

| 前提 | 確認方法 |
|---|---|
| Apple silicon の Mac | `sysctl -n hw.optional.arm64` が `1` |
| 発行側と同じ Xcode・同じ macOS | `xcodebuild -version` |
| コンソールにログイン済み(GUI セッションが立っている) | `stat -f%Su /dev/console` がランナーのユーザー名 |
| システムスリープ無効(ディスプレイスリープ・画面ロックは可) | `pmset -g \| grep " sleep"` |
| リモートログイン ON・鍵で入れる | 下のステップ1 |
| その macOS を知っている版の Homebrew | `brew --version` が動くこと |
| git が GitHub へ直接出られる(古いプロキシ設定が残っていない) | `git config --global --get-regexp '^https?\.'` が空 |
| Android SDK と AVD(Android を回すときだけ) | `fleetest doctor` |
| システム言語が英語 + Apple Intelligence 有効(`screenLooksLike`・自己修復を使うときだけ) | `fleetest doctor --fm-only` |

## セットアップの流れ

1. **ステップ0(ランナー機で1回だけ・手作業)** — リモートログインと(推奨)画面共有を ON、
   システムスリープを無効化、Xcode を導入してライセンスに同意、Homebrew を最新化、git の
   プロキシ設定の残留を確認、ログインしたままにする。
2. **ステップ1(発行側)— 鍵で入れるようにする**(`ssh-copy-id` の後、
   `ssh -o BatchMode=yes` が通ることを確認)。
3. **ステップ2(発行側)— ランナー機を手元から1コマンドで用意する**:
   `fleetest remote setup <ユーザー>@<ホスト> --project <プロジェクト名>`。
4. **ステップ3 — 版を揃える。** git のコミットと Xcode/macOS の指紋が一致しないとディスパッチは
   止まります。`remote setup` の align ステップが揃えます。
5. **ステップ4 — マシン名とプロファイル。** 実行プロファイルはマシンプロファイル経由で
   デバイス構成を解決します。
6. **ステップ5 — 疎通を確認する**: `fleetest remote status --host <ユーザー>@<ホスト>`。
7. **ステップ6 — 最初のディスパッチ**: `fleetest run --host <ユーザー>@<ホスト> --profile
   <実行プロファイル> --scenario <ID>`(初回は数分、以降は数秒で始まります)。

**`/fleetest:fleetest-remote-setup` は機械作業を `fleetest remote setup` に委ねます** ——
必要なことを聞き、人手が要ることは人へ渡し、結果を報告します。ステップ0の sudo/GUI が要る
手作業自体は代行しません。

## 用語: machine(マシン名)と host(ホスト名 / IP)

- **host** = ホスト名または IP アドレス(`user@192.168.20.101` など。ネットワーク上の実体)
- **machine** = その host に付ける**この Mac だけの名前(エイリアス)**。設定タブの「マシン」列で
  付ける名前で、プロファイルに書くのはこちらです

エイリアスはいつでも変えられます。**変えて困らないように、結果 JSON などの記録はホスト名で残り、
リモートへ送るファイルにも引数にもエイリアスは出ません**。

## どのマシンで走るかはマシンプロファイルが決める

デバイスのマシンプロファイルは `machine` に登録済みのマシン名を書けます。

```jsonc
// profiles/machines/M1Max.json
{ "machine": "M1Max",
  "ios": { "devices": [ { "machine": "M1Max", "name": "simulator1", "simulator": "iPhone 17 Pro" } ] } }
```

実行プロファイルはマシンプロファイル名でそれを指すため、**実行プロファイルを選べば
どの機械で走るかも一緒に決まります** —— 通常の利用に `--machine` は要りません。手元のデバイスは
`"machine": "local"` と明示します(省略すると「プロファイルの既定を継ぐ」意味になり、
1つのプロファイルに手元とリモートが混在するときに影響します)。コマンドラインの
`--machine <マシン名>` はプロファイルより優先されます(ホスト名や IP を直接指定するときは
`--host`)。**旧キー `"host"` のプロファイルもそのまま読めます**(2026-08-26 に `machine` へ改名)。

## `run --machine` と `--fleet`

```bash
fleetest run --machine <マシン名> --profile <実行プロファイル>   # この回だけ特定のマシンへ送る
fleetest run --project <プロジェクト> --fleet <名前>             # フリートの全ホストで同じシナリオを回す
fleetest run --project <プロジェクト> --fleet <名前> --split      # 全ホストで回す代わりに台数で分散する
```

フリートは `TestProjects/<プロジェクト>/profiles/fleets/<名前>.json` に `host`/`profile` の組を
列挙して定義します(`"local"` は発行側自身、それ以外は登録済みホスト名)。`--split` は
全ホストに複製する代わりに、過去の実測から見積もった所要時間で台数へ分散します。
`--junit <パス>` は全ホストの結果を1ファイルに集約し、各 `<testsuite>` の `hostname` で
どの機体の結果か分かります。

## VSCode 拡張からの利用

「実行先のホストを選ぶ」UI はありません —— 実行プロファイルを選ぶこと自体が、その
マシンプロファイルの `host` を通じてホストの選択になります。拡張が担うのは次の2つです。

- **デバイスモニターの「設定」タブでホストを登録する**(名前・ホスト・作業ベースディレクトリ)。
  CLI と同じホスト登録簿(`~/.config/fleetest/config.json`)を読み書きします。
- **マシンプロファイルの編集ダイアログでホストとデバイスを追加する** —— ホストを切り替えると
  その機械に実在するデバイスの一覧に切り替わり、その場でデバイスを新規作成することもできます。

登録済みのリモートデバイスは、デバイスモニターで手元の台と同じように表示・操作できます
(状態・ライブ映像・タイル個別の起動/停止も同じ。違いはホスト名のバッジだけです)。ただし
ブリッジ/健全性の自動修復は手元のデバイスにしか効きません。

## 1台のランナーを複数人で使うとき

同じランナー機には**同時に1つの実行しか走れません**(デバイスはその機械のものなので、
2つの実行が同じ台を取り合わないようにするためです)。埋まっているときは「誰がいつから
使っているか」が表示されます。

- **待って実行する**: CLI は `--wait-lock <秒>`、VSCode 拡張は設定 `fleetest.remoteWaitLock`
  に秒数(既定 0 = 待たずに失敗)。奪う操作は拡張にはありません
- **誰が使っているか**: `fleetest remote status --host <マシン名>` の LOCK 欄
  (`-` は「判定できなかった」で、空きという意味ではありません)。デバイスモニターでは
  ツールバーの機械の行に 🔒 が出ます
- **ライブ映像は実行中だけ自動で止まります** —— 誰かの実行が始まると、その機械のタイルは
  ライブ映像から2秒ごとの静止画に切り替わり、終わると戻ります(映像の配信はテスト実行と
  干渉するためで、自分の実行のときも同じです)。同じ台を2人が同時に眺めたときも、
  後から開いた側が静止画になります
- **他人の実行を壊す操作は止まります** —— `fleetest remote clean` は実行中の run があると
  中止し、拡張の一括停止やデバイス削除の確認には「誰の run が実行中か」が出ます

自分を名乗る設定(`~/.config/fleetest/config.json` の `issuerId`)を入れておくと、これらの
表示に自分の名前が出ます。詳しい手順は保守者向けの `docs/remote-runner-setup.md` にあります。
