# Troubleshooting

[in Japanese(日本語)](troubleshooting_ja.md)

Common problems and how to resolve them. Some areas also have their own troubleshooting section:

- Sandbox (permission errors, `403`) → "When things do not work" in [Notes and limitations](../security/limitations.md)
- Remote runs → "Troubleshooting" in [Adding a Mac](../fleet/adding_mac.md)
- Physical devices → "Troubleshooting" in [Adding physical devices](../fleet/adding_physical_devices.md)
- Servers the app depends on (won't start, no products shown) → "When a run dies halfway" in [Services the app depends on](../reference/writing/services.md)

| Symptom | Check | Fix |
|---|---|---|
| The sample app shows no products / `services up` fails | `fleetest services status`, `results/runs/<month>/<runID>/services/<service>.log` | `container system status` → if it is stopped, `container system start`. If prepare.sh stops with `run this in your fleetest work folder`, run it in the work folder (the one with Package.swift) |
| On-device model unavailable | Is Apple Intelligence enabled in System Settings? | Enable it (on macOS 27+, turn Siri on in System Settings → Siri (Siri uses Apple Intelligence). `fleetest doctor` shows the reason it's unavailable). Every call can fail while `availability` still says available (seen right after an OS update, for example) — confirm with `fleetest doctor --fm-only`, which really infers. A stopped FM sometimes comes back within a few minutes; restart the Mac if `--fm-only` keeps failing ([Maintenance for long-term use](maintenance.md)). FM is experimental. This only blocks `screenLooksLike` and [text visibility check](../reference/testclass/text_visibility_check.md) — everything else, including self-healing (locator fingerprint matching, which does not use FM), runs without it |
| OCR (Vision) has stopped | `fleetest doctor` also really calls OCR (Vision) and prints "read nothing from the built-in test image" | While it stays so, link-text taps, reading typed text back from the screen, and the OCR stage of the text visibility check fail. Rebooting the Mac has cleared this state before |
| `fleetest api fm-serve` is still running after a run | Activity Monitor / `ps` | This is expected. All on-device model calls go through this one process, which keeps the model loaded between calls (reloading it on every use is when the model can stop working). It exits by itself after 30 minutes without use, and the next run starts it again. To stop it now, run `pkill -f "fleetest api fm-serve"` (harmless — the next run just starts it again). While the VSCode extension's monitor is open it checks the model every minute, so the process stays |
| Cannot connect to the driver | iOS: is a bridge running? Android: is the device visible to `adb devices`? | iOS: run `fleetest bridge up` first (its log is `.fleetest/bridge-<port>.log`). Android: reconnect the device/Emulator so it shows up in `adb devices` |
| An iOS Simulator boots again right after you shut it down (it may stop again after about a minute) | Did you shut it down from the Simulator app's menu or with `xcrun simctl shutdown`? | The XCUITest bridge stays on the device after a run (so the next run can reuse it), and when the Simulator is shut down from outside fleetest, that bridge boots it again. Stop it with "Stop" / "Stop All" in the Device Monitor or with `fleetest devices down --profile <run profile>`, which stops the bridges first and then the Simulator |
| fleetest crashes right after it starts with `dyld[…]: Symbol not found` / `Library not loaded` | Did you update macOS but keep an older Xcode? (If `fleetest doctor` still starts, it shows the macOS and SDK versions) | Update Xcode to the same generation as macOS, delete `.build` in the fleetest clone and in your work folder, and run `bash <TOOL_ROOT>/Scripts/update.sh --force` ([Maintenance for long-term use](maintenance.md)) |
| Scenario fails to run due to a compile error | Run `swift build --product fleetest-scenarios-<project>` and read the error | Fix the reported error. A draft generated by `fleetest draft-scenario` that fails to compile is automatically quarantined into `scenarios/_disabled/` rather than blocking the rest of the project |
| Compile error `var '…' is not concurrency-safe because it is nonisolated global shared mutable state` | Is there a `var` at file level (outside the class)? | Scenarios are built with Swift 6, so a file-level `var` is an error. Make a value that does not change a `let`. **A `var` cannot pass a value between tests** (each `@Test` runs in its own process, so values do not carry over). To pass a value between tests of the same run on the same device, use `writeMemo` / `readMemo`; for fixed test data, use `data()` ([Test data and accounts](../reference/commands/dataset.md)). A value used only within one test goes in a `var` inside the function |
| Project isn't recognized (after a manual copy or `git pull`) | Does `fleetest project list` warn about an unregistered project? | Run `fleetest project sync` to regenerate the marker section in `Package.swift` |
| "Device not found" / a device is silently skipped | Is the device listed in the run profile's `devices` (right `machine`/`name`)? | Run `fleetest profile list` to see how it resolves, or `fleetest profile setup --auto-device` to register it |
| Android snapshot is slow | Check `fleetest bridge status --platform android` and `fleetest doctor` for the bridge's install/running state | Run `fleetest bridge up --platform android` to force a re-setup of the resident bridge |
| Japanese (or other non-ASCII) text doesn't get typed on Android | The bridge normally types via `ACTION_SET_TEXT`, so no IME switching is needed | Check the bridge's install state with `fleetest doctor`; reinstalling the bridge (`fleetest bridge up --platform android`) usually resolves it |

If none of this resolves the issue, ask your AI assistant to investigate — it can read bridge/run logs
and the failure report directly.

### Reporting a problem

Run `fleetest doctor --bundle fleetest-diag.zip` and attach the resulting zip when you report a
problem to the fleetest developers. It collects bridge/install/cleanup/Emulator logs, the most recent run
results (`--runs`, default 3, from `--project` or the default project) including each scenario's
run log, tool/OS versions, and the output of `fleetest doctor --roots-only` / `--fm-only` into one
file. It does not stop or restart any bridge, and nothing is sent anywhere by the command itself.
**The bundle can contain on-screen text from your app** (step labels, element lists) — review it
before sharing.

Report problems on GitHub Issues: <https://github.com/wave1008/fleetest-mobile/issues>.
