# 結果を読み、失敗を調べる

[in English](investigating_failures.md)

テストを実行するたびに、成否を問わず結果が残ります。読むのも AIアシスタントに任せられます。

## 結果を要約してもらう

### AIへの指示文

```text
fleetest の直近の実行結果を要約し、失敗があれば、失敗したシナリオと落ちた手順を一覧にして。
```

<details>
<summary><b>手動で実行する場合(クリックで詳細表示)</b></summary>

- `TestProjects/<プロジェクト>/reports/` にシナリオごとの Markdown レポートがあります。
- VSCode では Test Explorer が成否を直接表示し、そこからレポートを開けます。
  コマンド「fleetest: 結果ダッシュボードを開く」で、実行の履歴と成功率も見られます。

</details>

## 失敗の原因を調べてもらう

レポートには、失敗した手順・失敗メッセージ・**失敗した瞬間の画面の要素一覧とスクリーンショット**が
載っています。AIアシスタントはそれを読んで、何が起きたかを説明できます。

下は実際のレポートの抜粋です(サンプルアプリで、カートに追加したときの一瞬だけ出る表示を待って落ちた例)。

<img src="../images/tutorial/ja/report_failure.png" width="600" alt="失敗したレポートの抜粋。落ちた手順と失敗メッセージ、失敗した瞬間の要素一覧(折りたたみ)とスクリーンショットが載っている">

### AIへの指示文

```text
fleetest の直近の実行で落ちたシナリオについて、レポートから原因を調べて。
アプリの不具合らしいのか、テストの書き方の問題らしいのかも分けて報告して。シナリオはまだ直さないで。
```

**「直さないで」を添えるのが大事です**。AIアシスタントへ調査と修正を同時に指示すると、
アプリの不具合で落ちたテストを「期待値をアプリに合わせる」形で通してしまうことがあります。
それはテストが不具合を見逃すようになることを意味します。報告を読んでから、直すかどうかをあなたが決めてください。

### 原因の見当がついたら

| 見当 | 次の指示の仕方 |
|---|---|
| アプリの不具合 | テストはそのまま。アプリを直したら「前回落ちたシナリオだけを実行し直して」 |
| 画面が変わってテストが古くなった | 「〜の画面が変わったので、このシナリオを今の画面に合わせて直して」([追従させる](keeping_up_with_app_changes_ja.md)) |
| 出たり出なかったりするダイアログが割り込んだ | 「起動直後に〜のダイアログが出ることがある。出たら閉じてから進むように直して」 |
| よく分からない | 「このシナリオを5回実行して、落ちる回と通る回で何が違うかを調べて」 |

## fleetest は原因を決めつけない

fleetest の記録に残るのは、**どの段階で・どの操作が・どう失敗したか**という事実だけです。
「アプリが重かった」「Mac が混んでいた」のような原因の推測は記録しません —— ツールにはそれを
区別する手段が無く、推測で書くと誤った判断を生むからです。AIアシスタントの説明も、レポートに
書かれた事実を根拠にしているかを確かめながら読んでください。

## 不安定なテストを見つける

何度も回していると、通ったり落ちたりするテストが見えてきます。

### AIへの指示文

```text
fleetest の過去の実行結果から、通ったり落ちたりする不安定なシナリオと、遅くなってきたシナリオを洗い出して。
```

<details>
<summary><b>手動で実行する場合(クリックで詳細表示)</b></summary>

```bash
../foundation-tester/.build/debug/fleetest results flaky      # 成功も失敗もするシナリオ
../foundation-tester/.build/debug/fleetest results insights   # 退行・連続失敗・遅くなったシナリオ・特定デバイスへの偏り など
../foundation-tester/.build/debug/fleetest results slow       # 平均所要時間が長い順
```

</details>

### 見つけた後にすること

1. **書き方を直す。** 待ちの置き方・セレクタ・出るか不定のものの扱いは、書き方で直せます。
   [壊れにくいシナリオの書き方](../reference/writing/writing_robust_scenarios_ja.md)に沿って直すよう、AIアシスタントに指示します。
2. **Mac が重くないか疑う。** Mac が重いときは、デバイスモニターの配信を疑ってください
   ([VSCode で見る](watching_in_vscode_ja.md)の「Mac が重いとき」)。
3. **直したら、同じシナリオを数回続けて回して確かめる。** 1回通っただけでは直ったと言えません。
4. **CI での扱いを決める。** リトライで隠さず、見つけて直す方針です([CI で回す](../in_action/ci_ja.md)の「flaky シナリオの扱い(リトライ機構は意図的に無い)」)。

### AIへの指示文

```text
ログインのテストを iOS で 5 回続けて実行して、全部通ることを確かめて。落ちた回があれば、何回目に何で落ちたかを報告して。
```

<details>
<summary><b>手動で実行する場合(クリックで詳細表示)</b></summary>

回数を指定するオプションはありません。シェルのループで、同じシナリオを続けて回します。

```bash
for i in 1 2 3 4 5; do
  ../foundation-tester/.build/debug/fleetest run --profile ios-run --scenario <クラス名> --quiet || echo "失敗: $i 回目"
done
```

`<クラス名>` は、シナリオのファイル名(拡張子なし)です。各回の末尾にまとめの行が出て、落ちた回だけ続けて `失敗: N 回目` と出ます。

</details>

## 実行の様子を見返す

シナリオごとの実行ログ(各手順の成否と、実行中に出た出力)と録画が残っています。

### AIへの指示文

```text
直近の実行のログインのテストの実行ログを見せて。どの手順で何が出たかを順に説明して。
```

- 録画は既定で有効で、シナリオごとの動画が残ります。VSCode 拡張の「テストセッション」タブで見られます
  ([VSCode で見る](watching_in_vscode_ja.md))。容量を抑えたいときは、そう指示します。

```text
fleetest の iOS の実行で、失敗したシナリオの録画だけ残すようにして。
```

## fleetest 自体の不具合かもしれないとき

AIアシスタントに調べてもらっても原因がツールの側にありそうなら、fleetest の開発者へ報告してください。
添える診断情報は zip にまとめられます(どこへも送信しません)。

### AIへの指示文

```text
fleetest doctor --bundle fleetest-diag.zip で診断の zip を作って、中身を一覧にして。アプリの画面の文字が入っていないかも確かめて。
```

報告先と、zip を共有する前の注意は[トラブルシューティング](../in_action/troubleshooting_ja.md)の「不具合を報告するとき」にあります。
