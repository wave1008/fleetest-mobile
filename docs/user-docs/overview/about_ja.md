# Fleetest とは

Fleetest は iOS / Android アプリの E2E テストツールです。macOS 上で動き、Claude Code などの
コーディングエージェントと組み合わせて使うことを前提に設計されています。

## 名前に込めた3つの特徴

**fleetest** は `fleet` + `test`。同時に、*fleet*(すばやい)の最上級形でもあります。

- **fleet** —— デバイスの**フリート**で並列にテストします。シミュレータ・エミュレータ・実機、
  SSH 越しの別の Mac まで束ねられます。シナリオは複数デバイスへ自動で分配され、
  実行時間を短縮できます(ホストとデバイスが支えられる範囲で)。
- **fleetest** —— 通常の再生に LLM を挟まないので、モデルの推論待ちが発生しません。
  実行時間を決めるのはモデルではなくデバイスです。
- **free** —— クラウドのデバイスファームも、実行ごとの API 利用料も必要ありません
  (無償なのはツールで、Mac・Xcode・デバイスはお手元のものを使います)。

## AI がテストを作り、コードが決定的に再生する

テストの「作成」と「実行」で、役割をはっきり分けています。

**作るのは AI(または人)です。** 作り方は3通りあり、どれも同じ Swift シナリオになります。

- VSCode 拡張のライブ操作パネルで、アプリの操作を録画する
- エージェントに書かせる —— 実画面を探索しながらセレクタを採取します
- 手書きする —— イレギュラー処理やテストデータ投入も Swift でそのまま書けます

**再生するのはコードです。** シナリオは決定的に実行され、通常の操作再生には LLM を使いません。
速く、安定していて、CI 向きです。

**AI を使うのは限定された機能だけです。** `screenLooksLike` による画面の視覚検証と、
occlusion-guard によるテキストの視覚検証。これらはすべて Apple の
オンデバイスモデル(Foundation Models)で動くので、アプリの画面情報が Mac の外に出ることは
ありません。**Apple のクラウド(Private Cloud Compute)は使いません**
([必要環境](environments_ja.md))。壊れたセレクタの自己修復(ロケータの指紋照合)は決定的で、
FM を使いません。

## 4つの入口

用途に応じて入口は4つありますが、中身は同じコアです。どの入口で作ったテストも同じ `.swift`
ファイルになり、どの入口からでも実行できます。

| 入口 | 向いている用途 |
|---|---|
| **VSCode 拡張** | 人間の対話操作。デバイスモニター・ライブ操作(録画 → 生成)・実行・結果ダッシュボード |
| **MCP サーバ** | エージェント連携。AI によるテスト作成・デバッグ・探索的テスト |
| **CLI** `fleetest` | CI・回帰テストの定期実行 |
| **Swift DSL** | テスト資産そのもの。`TestProjects/<name>/scenarios/*.swift` |

## iOS はハイブリッドエンジンで動く

iOS シミュレータでは2本のブリッジを同時に張り、操作ごとに使い分けます。

- **in-app ブリッジ(主経路)** —— アプリの起動時にアプリのプロセスへ注入され、アプリの中から
  画面を読み、タップ・文字入力を行います。プロセスをまたぐ往復が無いぶん速く、Fleetest 自身の
  E2E(Compose Multiplatform のアプリ・40 シナリオ・8 台並列)での実測では、シナリオの所要時間の
  合計が XCUITest だけのときの 394 秒から 254 秒へ、約 36% 短くなりました。
- **XCUITest ブリッジ(補助)** —— アプリの外で動く OS の自動化です。in-app からは原理的に
  届かない操作だけを、こちらへ回します。

| こんなとき | 動く経路 |
|---|---|
| タップ・文字入力・画面の読み取り | in-app |
| ホーム画面・アプリスイッチャー | XCUITest |
| 別のアプリ(ホーム画面・設定など)を開いたとき | XCUITest(自分のアプリへ戻れば in-app) |
| OS のシステムアラート(`iosAlertHandler`) | XCUITest |
| Compose / Flutter の画面で、長押しなど in-app では撃てないジェスチャ | XCUITest |
| Compose / Flutter の中の WebView | 読むのは in-app、タップは XCUITest の実タッチ |

### ここがポイント

- **シナリオに経路を書かなくてよい** —— アプリの内側と外側の2つの経路を持つテストツールでも、
  どちらを使うかはテストの作者が API やコンテキストの切り替えで書き分けるのが一般的です。
  Fleetest では、その操作が in-app でできるかどうかをツールが実行時に判断します。回すのは、
  ブリッジが「このアプリではできない」と申告した操作と、実際に「できない」と応答した操作だけです。
  アプリの UI フレームワーク(SwiftUI・UIKit・Compose Multiplatform・Flutter・React Native)に
  よって in-app で撃てる操作は変わりますが、その差をシナリオに書く必要はありません。
- **アプリを改変しなくてよい** —— in-app ブリッジは起動時に注入されるので、テスト用の
  ライブラリをアプリへ組み込んだり、テスト専用のビルドを作ったりする必要はありません。
  いつものシミュレータ向けビルド(`.app`)をそのまま使えます。
- **経路を替えて二重に撃たない** —— 回すのは「in-app では原理的にできない」と分かっている
  操作だけです。届いたかどうか分からない操作を、経路を替えて撃ち直すことはしません
  (送信や購入が二度実行されるのを防ぐため)。
- **探索とテストで同じものが見える** —— MCP サーバ(エージェントによる探索)も実行プロファイルと
  同じエンジン構成で動くので、「探索では動いたのにシナリオでは落ちる」が起きにくくなっています。

### 適用範囲

- ハイブリッドエンジンが使われるのは iOS シミュレータだけです。iOS 実機にはブリッジを
  注入できないため、XCUITest だけで動きます。
- Android にはエンジンの選択肢はありません(adb 越しのブリッジ1本で動きます)。
- XCUITest だけで動かしたいときは、実行プロファイルの `iosInappEngine` を `false` にします
  ([実行プロファイルの設定項目](../project/run_profile_ja.md))。

## しくみ

デバイスの操作は自作の常駐ブリッジで行います。iOS はアプリに注入した in-app ブリッジと
シミュレータ内の XCUITest プロセスの2本(上記のハイブリッドエンジン)と HTTP で、Android は
adb 越しのブリッジと通信します。Appium などの外部ドライバには
依存しません。

プラットフォームの違いはドライバ層で吸収され、再生エンジンと Foundation Models の呼び出しは
iOS / Android で完全に共通です。
