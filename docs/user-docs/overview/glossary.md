# Glossary

[in Japanese(日本語)](glossary_ja.md)

The terms specific to fleetest, in alphabetical order. At the end of each entry is a link to the page that explains it in detail.

## Terms

- **App profile** — The settings that describe the app under test (bundle ID / package name and the path of the build artifact), kept in `profiles/apps/<name>.json`. See [Profiles (app / run)](../reference/project/profiles.md).
- **Bridge** — The resident part on the device side that connects fleetest to the device. On iOS there are two kinds, the XCUITest runner and the in-app one injected into the app; on Android it is a resident on-device server. Handled with `fleetest bridge up` / `down` / `status`. See [CLI reference](../reference/tools/cli.md).
- **Container** — The scroll area around an element (a list, a scroll view and so on). fleetest infers it from the screen's tree and uses it to detect clipping and to correct the coordinates it taps (container inference). On a screen where the corrections misfire, turn them off with `containerInference: false` and similar. See [scroll](../reference/commands/scroll.md).
- **Device Monitor** — The VSCode extension tab where you watch the screens and states of devices. From the top it has three permanent panes: the Line View (the row of device tiles), the Grid View (an enlarged view of the selected devices) and the Run Log View (the execution log of the selected devices). The Grid View and the Run Log View show only the devices selected in the Line View. See [VSCode extension](../reference/tools/vscode_extension.md).
- **dry-run** — A run that touches neither a device nor FM and only enumerates and validates the steps of a scenario (`fleetest run --dry-run`). It finds selector syntax errors, an `expectation` with no assertions and the like within seconds. See [dry-run](../reference/running/dry_run.md).
- **Fingerprint matching (locator fingerprint)** — When a selector no longer finds its element, looking for it again on the current screen by the type and label of the element it last resolved to (the locator fingerprint). The element is used only when exactly one matches. This is all self-healing does; it does not use FM. See [Self-healing](../reference/running/self_healing.md).
- **Fleet** — The collection of devices (virtual devices and physical devices) that run the tests. You grow it by adding devices on your Mac and other Macs (runner machines). A "fleet definition" (`profiles/fleets/<name>.json`) that lists pairs of a machine and a run profile can be given with `--fleet`. See [Fleet concepts](../fleet/concepts.md).
- **FM (Foundation Models)** — Apple's on-device language model, available on macOS 26 and later when Apple Intelligence is turned on. The features that pass an image to it (`screenLooksLike` and the FM stage of the text visibility check) need macOS 27 and later; the structuring in `draft-scenario` is text-only and works on macOS 26. Only the on-device model is used, so screen information does not leave the Mac. See [Environment](environments.md).
- **Hooks (run-setup.sh / run-teardown.sh)** — Scripts that run before and after a run. They are kept in `scripts/` of the workspace: `run-setup.sh` runs after the services have finished starting and `run-teardown.sh` runs after the run. `fleetest hooks reap` cleans up what a run that died left behind. See [Services the app depends on (compose.yaml)](../reference/writing/services.md).
- **JUnit** — The report in JUnit XML format that `fleetest run --junit <path>` writes in addition. It lets a CI system that reads JUnit XML handle the test results. See [Running on CI](../in_action/ci.md).
- **Lane** — Within a run, the flow of execution that corresponds to one device of the run profile (the same unit as a worker). See [Parallel execution](../reference/running/parallel_execution.md).
- **Live Control** — Operating the device screen directly with the mouse in the Device Monitor's Grid View, which shows when you select just one device (click to tap, drag to swipe). See [Watching in VSCode](../tutorial/watching_in_vscode.md).
- **Machine name** — A name you give a runner machine on your Mac (for example `M1Max`). Profiles use this name instead of a host name or an IP address. Your own Mac is `local`. Register one with `fleetest remote machines add`. See [Adding a Mac](../fleet/adding_mac.md).
- **Machine settings** — The settings in `~/.config/fleetest/config.json` on a Mac. They hold what the person who uses that Mac decides, such as sandbox permissions, the services runtime and the retention limits. A project or a run profile cannot loosen them. See [Machine settings (config.json)](../reference/project/machine_settings.md).
- **Mode** — The configuration by which iOS screens are read and operated: `inapp` (the default; the in-app bridge, injected into the app and fast, first, with the XCUITest bridge as the fallback) or `xcuitest` (the XCUITest bridge only, general purpose). A physical iOS device uses inapp mode **when the app is development-signed** (debuggable); otherwise it falls back to xcuitest mode automatically. Android has no choice. See [Run profile settings](../reference/project/run_profile.md).
- **MCP server (ft_*)** — The stdio MCP server (`fleetest-mcp`) that exposes device operation, scenario execution and scenario creation as `ft_*` tools. An AI assistant can call the same functions as the CLI and the extension on a person's behalf. See [MCP server](../reference/tools/mcp_server.md).
- **Physical device** — Only a real iPhone or Android handset. Simulators and Emulators are not included (they are "virtual devices"). In a run profile you write `"kind": "physical"` and the device identifier. See [Adding physical devices](../fleet/adding_physical_devices.md).
- **Relative selector** — A selector that points at a candidate by its position relative to a base element (for example `Notifications:rightSwitch`). It is used on screens where the target has no id or reliable label. The base comes first. See [Relative selector and scope](../reference/selector/relative_selector.md).
- **Report** — The Markdown written to `reports/scenario-*.md` for each scenario execution, whether it passes or fails. It has the hierarchy `scene → condition/action/expectation → step`, the element list and screenshot at a failure, and selector fix proposals. See [Test result files](../reference/testclass/test_result_files.md).
- **Response measurement** — A feature that, while running an existing scenario on a physical device, measures for each screen-changing action the "time to first frame" (from injecting the input to the first frame the app presents) and the "time until ready" (from the injection until the element operated next can be found, is enabled, is not covered and has stopped moving). It is turned on with `responseMeasurement: true` in the run profile. See [Response measurement](../reference/running/response_measurement.md).
- **Result JSON** — The machine-readable record kept in `results/runs/<YYYY-MM>/<runID>/`: `run.json` for the whole run and `scenarios/<scenario ID>.json` for each scenario. It is the source for CI gating and dashboards. See [Test result files](../reference/testclass/test_result_files.md).
- **Retention limits** — The upper limit on how much each category (recordings, reports, logs and so on) may accumulate. A category that reaches 90% of its limit is swept back down to 90%, oldest first. The result JSON is never deleted. The limits are machine settings, and `fleetest clean` can sweep too. See [Maintenance for long-term use](../in_action/maintenance.md).
- **Run** — One execution of scenarios as a whole, started with `fleetest run` or the like. It gets a run ID and its result is recorded under `results/`. See [Running scenarios (fleetest run)](../reference/running/running_scenarios.md).
- **Run profile** — The settings that decide which app runs on which devices (each device names the machine it lives on) with which run-time options. Kept in `profiles/runs/<name>.json`. See [Run profile settings](../reference/project/run_profile.md).
- **Runner machine** — Another Mac that runs tests for you. It does not need to be on the same LAN as long as your Mac can log in to it over SSH. Keep it logged in. See [Fleet concepts](../fleet/concepts.md).
- **Sandbox (Seatbelt)** — The macOS sandbox (Seatbelt) in which scenarios always run. The OS refuses reading secrets, arbitrary writes, communication with destinations that are not allowed and so on. Device operation and external communication are carried out or relayed by fleetest itself, outside the sandbox. See [Checking the sandbox and opening the holes you need](../security/sandbox.md).
- **Scenario** — A Swift file written by an AI assistant (one file holds several tests). It can also mean an individual test (a `@Test` method), whose ID at run time is `ClassName.method`. See [Creating a test class](../reference/testclass/creating_testclass.md).
- **Scene (CAE)** — A unit of a scenario, `scene(n, "title")`. Inside it you write three layers: `condition` (precondition), `action` (operation) and `expectation` (verification), abbreviated CAE. The number and the title become headings in the report. See [Test code structure](../reference/testclass/testcode_structure.md).
- **Selector** — The notation that points at a screen element with a single string: `#login_btn` (accessibility id), `Log in` (label) or `.button[2]` (type and order), combined with `&&` (and), `||` (or) and `>>` (scope). See [Selector expression](../reference/selector/selector_expression.md).
- **Self-healing** — The mechanism that, when a selector can no longer be resolved, uses the element whose type and label (the "locator fingerprint") of the last resolved element match exactly one element on the current screen. It does not use FM, and at the end of the run it writes the fixed selectors back to the scenario source automatically (review the git diff and commit). See [Self-healing](../reference/running/self_healing.md).
- **Services (compose.yaml)** — The DBs, APIs, stub servers and the like that the app under test depends on. Declared in `scripts/compose.yaml`, they are started by fleetest for each run and stopped when it ends. For exploration you bring them up by hand with `fleetest services up`. See [Services the app depends on (compose.yaml)](../reference/writing/services.md).
- **Settle** — Waiting for a screen transition to calm down after an action. The driver does it automatically, so a fixed `wait()` is not needed. There is also an explicit `waitForSettle`. See [wait, waitForDisplay, waitForClose, waitForSettle](../reference/commands/wait.md).
- **Skill** — A Claude Code skill that automates installation, profile setup, scenario creation and so on. The installer copies them into `.claude/skills/` in your work folder and you call one by name, such as `/fleetest-scenario`. See [Claude Code skills](../reference/tools/claude_code_skills.md).
- **Snapshot** — The accessibility tree of the current screen. When writing a scenario you take the real ids and labels from a snapshot and use them in selectors (`ft_snapshot` in MCP, `fleetest snapshot` in the CLI). See [MCP server](../reference/tools/mcp_server.md).
- **Test base** — Markdown that holds the specification, test viewpoints or source material that scenarios are based on. It is kept in `TestProjects/<project>/docs/testbases/`, and `fleetest draft-scenario` turns it into a scenario draft (marked `@Draft`). See [Test bases and scenario drafts](../reference/running/testbases.md).
- **Test class** — A class marked with `@TestClass` that has one or more `@Test` methods. A scenario file is a file that defines test classes. See [Creating a test class](../reference/testclass/creating_testclass.md).
- **Test project** — The container that holds the scenarios, profiles and reports for one app, kept in `TestProjects/<name>/`. See [Creating a test project](../reference/project/creating_project.md).
- **Text visibility check** — A check that confirms, for an element matched in the tree, that its text is really drawn on the screen by looking at a screenshot, and fails when it is not visible. It decides by combining OCR and FM. See [How the text visibility check decides](../reference/testclass/text_visibility_check.md).
- **Typed selector (Sel)** — The selector notation written with types (for example `.id("login_btn").or(.text("Log in"))`). It sits beside the string form, and the compiler catches spelling mistakes. See [Typed Selector (`Sel`)](../reference/selector/typed_selector.md).
- **Virtual device** — The collective name for Simulators (iOS) and Emulators (Android). It is distinguished from a physical device. See [Fleet concepts](../fleet/concepts.md).
- **Work folder** — The folder that contains `TestProjects/`. It is your own folder for using fleetest; by default the foundation-tester clone sits next to it. See [Quick start](../quick-start.md).
- **Worker** — The unit that takes scenarios within a run. Each device of the run profile becomes one worker and the scenarios are distributed among them. The degree of parallelism is the number of workers (the number of devices after resolution). See [Parallel execution](../reference/running/parallel_execution.md).
- **Workspace** — The `workspace/` folder of a test project (the staging place for app bundles, `compose.yaml` and data). Not the same thing as a VSCode workspace.

## Command options

Options of the [CLI reference](../reference/tools/cli.md) that concern where a run is sent and how it is distributed.

- **`--broadcast`** — Runs the selected scenarios once on every device of the run profile instead of distributing them (for uses such as warm-up). `--profile` is required. See [Parallel execution](../reference/running/parallel_execution.md).
- **`--fleet`** — Names a fleet definition (a list of machine and run profile pairs) and runs on several machines at the same time. With `--split`, the scenarios are distributed instead of every machine running the same ones. See [Remote Runners](../fleet/remote_runners.md).
- **`--runner`** — Dispatches a `fleetest run` to a runner machine given by a registered machine name (or `user@host`). A run profile is required. See [Remote Runners](../fleet/remote_runners.md).
