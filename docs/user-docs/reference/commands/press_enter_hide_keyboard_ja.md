# pressEnter, hideKeyboard

[in English](press_enter_hide_keyboard.md)

キーボードの確定アクションを発火する、またはソフトキーボードを閉じます。

## 関数

| 関数 | 説明 |
|---|---|
| `pressEnter(settle:)` | フォーカス中の入力欄へ Enter/IME アクション(検索・完了・送信・改行など)を発火します。 |
| `hideKeyboard(settle:)` | ソフトキーボードを閉じます。出ていないときは何もしないので、常に呼んでも安全です。**Android** は戻るキーを撃ちます。**iOS** はキーボードの上の何もない点(どの要素にも載らない点、または操作できない画面幅の容器だけに載る点。文字・画像・ボタン・入力欄・トースト・ステータスバーの上は避けます)をタップし、それでも閉じなければ Enter を送ります。閉じた後の次の操作(`tap` など)は、画面の情報からキーボードが消えるまで待ってから要素を探します(Android。端末によっては、閉じた後も数秒キーボードが残って見え、画面下端の要素が見つからないため)。 |

## 例

```swift
type("#search_box", "腕時計")
pressEnter()               // 欄の確定アクションを発火

android {
    hideKeyboard()
}
```

## 注意点

- `pressEnter(settle:)` が改行を入れるか確定アクションを発火するかはフィールド側が決めます(コマンド
  側では選べません)。`type` の末尾 `\n` についても同じ話が当てはまります。詳細は
  [type](./type_ja.md) 参照。
- **iOS の `hideKeyboard()`**: 背景のタップで閉じるかはフレームワークで違います。iOS Simulator での実測では、Compose Multiplatform は背景のタップで閉じ、SwiftUI と Flutter は続けて送る Enter で閉じます。どちらでも閉じなければステップは失敗します。ステップの注記に撃った点が出ます。タップでは閉じず Enter を送ったときは、Enter が欄のリターンキーの動作(検索・送信・次の欄)も発火させることが注記に書かれます。タップの後にキーボードより上の要素が消えていたときは、何も発火していないか確かめるよう注記が促します。
- **キーボードの下にある対象**: `tap` / `type` / `clearInput` が、対象の中心がキーボードの下にあると気付いたときは、まず容器をスクロールし、それでも覆われていれば副作用のない手段(iOS は上の背景タップ・Android は戻るキー)でキーボードを閉じてから操作します。その手段で閉じられないときは、何も触らずにステップを失敗にします —— リターンキーなら閉じられますが、欄の動作も発火してしまうので自動では押しません。そうしたいときはステップの前に `pressEnter()` を呼んでください。Android では、キーボードが出ている間に対象が見つからないとき(窓がキーボードの上まで縮み、下の要素が木から消えます)、戻るキーでキーボードを閉じてもう一度だけ探します。
- キーボードが表示されているかどうかの検証は別の検証コマンドです。
  [キーボードの検証](./keyboard_assertion_ja.md)を参照してください。
- **`settle: false`** を渡すと、このコマンドの操作後の「画面が落ち着くまでの待ち」を省きます(次のステップは動いている最中の画面を見ることがあります)。詳細は [tap](./tap_ja.md) 参照。
