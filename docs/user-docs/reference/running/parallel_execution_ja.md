# 並列実行

[in English](parallel_execution.md)

## 実行プロファイルを使う場合

**並列数 = 解決後のデバイス数**です。実行プロファイルの各デバイスが1ワーカーになり、シナリオは
その間で分配されます。回す本数が少ないときは、用意する台数を「本数 + 予備 1 台」に絞ります(`--broadcast` は絞りません)。iOS は稼働中のブリッジを再利用し、不足分だけ起動します。実行プロファイルの
`devices` に iOS/Android を混在させれば、1回の実行で iOS と Android のデバイスを同時に使えます
(各シナリオが走るのは片方の OS だけです。下記。[profiles_ja.md](../project/profiles_ja.md)参照)。

```bash
fleetest run --project SampleApp --profile all
```

`platform:` を宣言していないシナリオは、その実行の既定 OS(ワーカーが居る最初のプラットフォーム。
通常 iOS デバイスがあれば `ios`)で走ります。**`platform:` を明示していて、その OS が実行の
デバイスに含まれていないシナリオは、キューに入らずスキップされます** —— 同じプロファイルの
もう一方の OS のデバイスは、そのシナリオぶんは空回りするだけです。選んだシナリオが全部対象外なら、1本も走らずに成功(exit code `0`)で終わります。プラットフォーム非依存の
シナリオを両 OS で回すには、`--profile ios-run` と `--profile android-run` を別々に実行してください。

## 実行プロファイルを使わない場合(手動 `--port`)

Simulator ごとに別ポートでブリッジを起動し、ポート一覧を `run` に渡します。

```bash
fleetest bridge up --device "iPhone 17 Pro"                          # port 8123
fleetest bridge up --device "iPhone 17 Pro Max" --port 8124
xcrun simctl install "iPhone 17 Pro Max" <対象アプリ.app>            # 各デバイスにアプリを入れる

fleetest run --port 8123 --port 8124    # シナリオをワーカーに自動分配
fleetest bridge down --all              # 全ブリッジ停止
```

同じ実行に Android シナリオがあれば専用ワーカーが自動で立ちます(1シナリオ=1サブプロセスで
分離されるため、プラットフォームは混ざりません)。

## 目安

- **デバイスを増やせば速くなるとは限りません。** Mac が飽和した先では、1本ずつのシナリオが遅くなるだけで
  全体の時間は縮まらず、画像を使う手(`findImage` / `existImage`)やテキストの可視性検証の失敗が増えます。
- 台数はお使いの Mac で決めてください。数台ずつ足し、実行全体の時間が縮まらなくなったところで止めます。
  台数を増やしたときだけ赤が出るなら、減らした台数に戻します。
- コールドブート直後の Simulator はアクセシビリティ IPC がタイムアウトしやすいです。ワーカーは
  開始時に snapshot ウォームアップを自動で行いますが、それでも落ちる場合は `bridge up` の後に
  MCP の `ft_launch` と `ft_snapshot` でアプリを一度起動して画面を取ってから([MCP サーバー](../tools/mcp_server_ja.md)参照)実行してください。

## Mac が混んでいるときの減速

**Mac の CPU 使用率が高い瞬間は、ステップの実行を少し遅らせます**(既定で有効)。CPU が 100% 近くに
張り付くと、画像やテキストの判定を誤りやすくなるためです。

- 画面を変える操作(`tap`・`type`・スクロール・`launchApp` など)の直前に、その瞬間の Mac 全体の CPU
  使用率を測り、**90% 以上なら 0.2 秒、95% 以上なら 1 秒**待ってから実行します。待つのは1ステップにつき
  1回だけで、負荷が下がるまで待ち続けることはありません。
- 検証(`exist`・`textIs` など)と `select` の前では待ちません。操作の直後に消える表示(Snackbar など)を
  見逃さないためです。`hold { }` で押している間と、`findImage` などの画像で見つけた要素の `tap()`(見つけた位置を叩くので、待つと位置が古くなる)の前も待ちません。セレクタで指定した操作は、待ったあとに画面を取り直してから対象を探します。
- `settle: false` を付けた操作の前でも待ちません。消える表示を叩く・素早く続けて操作するなど、速さが要る操作には
  `settle: false` を付けてください。
- 待った時間は、ステップの待ち上限(`waitSeconds`)にもシナリオ全体の制限時間(`scenarioTimeout`)にも数えないので、
  待ちのせいでステップやシナリオが時間切れになることはありません。Mac が空いていれば待ちは入りません。
- 物理デバイスでも仮想デバイスでも、iOS でも Android でも、同じように効きます(測るのは Mac の負荷です)。

待った時間は結果 JSON に残ります(ステップごとの `pacingMs`、シナリオごとの `steps.paced` /
`steps.pacedMs`。[results_analysis_ja.md](./results_analysis_ja.md)参照)。

段の値を変える・止めるには、そのマシンの `~/.config/fleetest/config.json` に書きます
(リモートのランナー機では、ランナー機の設定が使われます)。

```json
{
  "hostLoadPacing": {
    "tiers": [
      { "cpuPercentAtLeast": 90, "delayMs": 200 },
      { "cpuPercentAtLeast": 95, "delayMs": 1000 }
    ]
  }
}
```

止めるときは `"hostLoadPacing": { "disabled": true }` にします。値が正しくないとき(0 以下や 100 を超える
使用率・負の待ち時間・同じ使用率の重複)は既定の値で動き、実行の開始時に1回警告が出ます。

## `--broadcast`

`--broadcast` はシナリオを分配**しない**唯一の例外です。選んだシナリオを、分配ではなく実行
プロファイルの**全デバイス**で1回ずつ実行します(warmup 等の用途)。`--profile` は必須で、
`--device` で対象デバイスを絞れます(同じ名前のデバイスが複数のマシンにあるときは、`--runner` か
`--all-machines` でどのマシンかを明示します。`--device` の名前が 1 台のランナー機だけに絞れたときは、`--runner` 無しでもそのランナー機へ配ります。[リモート実行](../../fleet/remote_runners_ja.md)参照)。同じ `scenarioID` が台数ぶん並ぶため、結果は `worker` 欄で
区別します([results_analysis_ja.md](./results_analysis_ja.md)参照)。

## 1台のマシンで同時に走る実行は1本

**1台の Mac で同時に走る実行は1本だけです。** 同じマシンで2つの実行が走ると、同じ Simulator と
同じループバックポートを取り合い、その負荷でテストが不安定になるため、2本目は開始しません。
これは回避すべき制限ではなく、意図して守っていることです。

そもそも2本目が要る場面はほとんどありません。並列は**1回の実行の中**で効きます。実行プロファイルに
デバイスを足せばシナリオはその間で分配されるので(上の節)、`run` を2回起動する必要はありません。

それでも2本目を起動したときは、次のようになります。

- **CLI** では `another fleetest run is already running on this Mac` ですぐに止まります。実行中の
  run を誰がいつから走らせているかも表示されます。失敗させずに順番待ちに並ぶには
  `--wait-lock <秒>` を付けます。並んだ順に実行されます。
- **VSCode 拡張**は既定で待ちます(上限 1 時間)。秒数はデバイスモニターの「**設定**」タブ →
  「**マシン**」→「**ランナー競合時の最大待機時間**」で変えられます(0 にすると待たずに失敗します)。
  並んでいる間は、実行ログに自分の順番が出ます。

ランナー機も同じ規則です。ディスパッチした実行がそのマシンの1本ぶんを使うので、終わるまで
そのランナー機は誰にとっても使用中になります
([リモート実行](../../fleet/remote_runners_ja.md)参照)。

## 並列実行が関わる他の場所

- VSCode 拡張も `fleetest.profile` 設定を通じて同じ並列実行を行います
  ([VSCode 拡張](../tools/vscode_extension_ja.md)の「デバイスモニター」参照)。
- LPT 順序付け(実績時間の長い順に投入)は直近の実行履歴でワーカー間の負荷を均します。
  `--no-lpt`/`--lpt-history-runs` で制御できます([running_scenarios_ja.md](./running_scenarios_ja.md)参照)。
- 決定的再生は FM を呼ばないため並列にスケールします。自己修復(ロケータの指紋照合)も FM を
  呼ばないため同様にスケールします。`screenLooksLike` はオンデバイス FM(マシンに1本)を呼ぶため、
  デバイス台数に関わらずそこで律速されます。
