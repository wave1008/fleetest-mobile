# テストベースとシナリオの下書き(draft-scenario)

[in English](testbases.md)

**テストベース**は、シナリオの根拠にする仕様・テスト観点・元ネタを Markdown で置いたものです。
`fleetest draft-scenario` はテストベースを読み、`scene`(条件・操作・期待)の骨組みを持つ Swift シナリオの**下書き**を作ります。
セレクタだけは決められないので、すべて `#TODO` のプレースホルダで出ます。人か AIアシスタントが実画面からセレクタを採って
置き換え、出来たら `@Draft` を外します。

## テストベースを置く

置き場所は `TestProjects/<プロジェクト>/docs/testbases/` です([テストプロジェクトの作成](../project/creating_project_ja.md)で作られるフォルダです)。
そこに SC / TC などの仕様書、テスト観点表、元になった要件のメモを Markdown で置き、AIアシスタントにシナリオを書かせるときの根拠にします。
フォルダ内の `README.md` は置き場の説明で、テストベースとしては数えません。

`draft-scenario` が読めるファイルは次のとおりです。

- 拡張子が `.md`・`.markdown`・`.txt` のファイル。`--testbase <パス>` で、フォルダの外のファイルも直接指せます。
- `--testbase` を省くと、`docs/testbases/` にテストベースが**ちょうど 1 つ**のときだけそれを使います。0 個ならエラー、
  複数あれば候補を並べてエラーになるので、`--testbase` で選びます。

## 書式

見出しと箇条書きだけで読み取れる形に書きます。決まりはこれだけです。

| 書くもの | 読み取られ方 |
|---|---|
| 最初の `#` 見出し | シナリオ(`@Test`)の説明。クラス名の元にもなる。無ければファイル名 |
| `##` 見出し | 1 つの `scene`。`##` が 1 つも無ければ、全体で 1 つの `scene` |
| `###` 以下の見出し | 条件・操作・期待のどれに入れるかの切り替え(下のキーワードに当たらない見出しは、今の区分のまま) |
| 箇条書き・連番・チェックボックスの行 | 手順の 1 項目(行頭の `-` `*` `+` `>`・`1.` `1)`・`[ ]` `[x]` は外される) |
| `前提:` `操作:` `期待:` のような行頭ラベル | その行の区分を指定する(`:` は全角の `：` でも可) |
| ラベルが無い行 | 今の区分に入れる(初期値は操作)。ただし**「〜こと」で終わる行は期待**に入れる |

区分(条件・操作・期待)は、見出しや行頭ラベルに次のキーワードが含まれるかで決まります(英字は大文字小文字を区別しません)。

| 区分 | キーワード |
|---|---|
| 条件(`condition`) | 前提・条件・事前・given・setup・準備 |
| 操作(`action`) | 操作・手順・実行・when・action・ステップ |
| 期待(`expectation`) | 期待・確認・結果・検証・then・expect・観点 |

行頭ラベルは、12 文字以内でこのキーワードに当たるときだけラベルとして外します。「エラー: 通信失敗」のような
本文中のコロンは、キーワードに当たらないのでそのまま残ります。強調(`**` `__`)とインラインコードの記号は取り除かれます。

```markdown
# ログイン機能

## 正しい認証情報でログインできる

- 前提: アプリを起動している
- 操作: メールアドレスを入力する
- 操作: パスワードを入力する
- 操作: ログインボタンをタップする
- 期待: ホーム画面が表示されること

## 誤ったパスワードはエラー

### 手順
1. 誤ったパスワードでログインする

### 確認内容
- エラーメッセージが表示されること
- ログインボタンが押せること
```

## 下書きを作る

```bash
fleetest draft-scenario --project SampleApp --testbase docs/testbases/login.md
```

| オプション | 説明 |
|---|---|
| `--project <project>` | テストプロジェクト名(省略時は唯一のプロジェクト、または既定のプロジェクト) |
| `--testbase <パス>` | テストベースのファイル(省略時は `docs/testbases/` にある唯一のファイル) |
| `--name <名前>` | 生成するテストクラスの名前(省略時はテストベースの見出しから決める) |
| `--app-id <ID>` | テスト対象のアプリの bundle ID。指定すると生成コードの `@TestClass(app:)` に書く。省略時はアプリプロファイルの値で解決し、コードには書かない |
| `--platform <ios\|android>` | 対象の OS(省略時は両方)。指定すると `@TestClass(platform:)` に書く |
| `--no-fm` | FM を使わず、Markdown の見出しと箇条書きだけで構造化する |
| `--dry-run` | ファイルを書かず、生成コードを標準出力に出す |

構造化は既定では Foundation Models(FM。オンデバイスだけで動く)で行います。FM が使えない・うまく構造化できないときは、
自動で上の書式の機械的な読み取りに切り替わります。FM に渡すのはテストベースの**先頭 2400 文字**までで、
超えると警告が出ます(超えた分は下書きに反映されません。ファイルを分けるか `--no-fm` を使います)。
書式どおりに書いてあれば `--no-fm` で十分で、結果も毎回同じになります。

生成物は `TestProjects/<プロジェクト>/scenarios/Drafts/<クラス名>.swift` に書かれ、書いた後にビルドで検証されます。
ビルドに通らないコードは `scenarios/_disabled/` へ退避され、スイート全体は巻き込まれません。
`--name` を明示して同じ名前の下書きがあるときは、上書きせずにエラーになります。

## 生成物と `@Draft`

生成されるクラスには `@Draft` が付きます。

- `@Draft` は「実装中(未完成)」のマークです。**一覧には「作業中」として残り**、全実行・フォルダ実行・クラス名指定の一括実行からは**除外**されます。
  **完全一致の ID を指定したときだけ実行できます**(`--scenario <クラス>.<メソッド>`)。実装しながら個別に回す経路です。
- セレクタは `#TODO` で出ます。`#TODO` は決して解決できない id なので、置き換え忘れのまま `@Draft` を外すと、
  **「ロケータを解決できません」で必ず失敗します**(空の実装で緑になるよりよい、という意図です)。
- 手順の文章は、各コマンド行の末尾のコメントに必ず残ります。コマンドへの当てはめが外れても元の意図が読めます。

手順の文章は、語彙の単純な包含でコマンドの雛形に写されます(目安であり、最終的には直します)。

| 区分 | 文に含まれる語 | 出る雛形 |
|---|---|---|
| 条件 | 起動・立ち上げ・launch、または「アプリ」と「開く / 表示」の両方 | `launchApp()`(これ以外の条件は `// TODO` のコメントだけ) |
| 操作 | 入力・記入・打ち込 | `type("#TODO", "TODO")` |
| 操作 | 長押し・ロングタップ | `tap("#TODO", holdSeconds: 1)` |
| 操作 | スクロール・スワイプ | `scrollTo("#TODO")` |
| 操作 | 再起動・起動し直 / 起動 / 待 | `restartApp()` / `launchApp()` / `wait(1)` |
| 操作 | 上のどれでもない | `tap("#TODO")` |
| 期待 | 表示されない・消え・閉じ・非表示 など | `notExist("#TODO")` |
| 期待 | 押せない・無効 / 押せる・有効 | `select("#TODO").enabledIsFalse()` / `enabledIsTrue()` |
| 期待 | 「3件」「5 個」のような個数 | `countIs("#TODO", 3)` |
| 期待 | と表示・文言・メッセージ | `select("#TODO").textIs("TODO")` |
| 期待 | 上のどれでもない | `exist("#TODO")` |

最初の `scene` には、条件に起動が無ければ `launchApp()` が足されます。

### 下書きを仕上げる

1. 下書きを開き、`scene` ごとに実画面でセレクタを採ります。AIアシスタントに頼むなら、`ft_snapshot` で今の画面を読ませて
   `#TODO` を置き換えさせます([エージェント向けの手引き](../tools/agent_guide_ja.md))。
2. `--dry-run` でセレクタの構文などを確かめ([dry-run](./dry_run_ja.md))、デバイスで実行します。
   `@Draft` が付いている間は、完全一致の ID で個別に回します。
3. 通ったら、クラスの `@Draft(...)` の行を消します。以後は一括実行の対象になります。

## AIアシスタントに頼むときの指示文

テストベースを置いたあとは、次のように頼みます([AIアシスタントへの指示の仕方](../../tutorial/asking_ai_ja.md))。

```text
docs/testbases/login.md をテストベースにして、fleetest draft-scenario でシナリオの下書きを作って。
そのあと実際のアプリを操作して #TODO を実セレクタに置き換え、実行して通るようにして。通ったら @Draft を外して。
```

```text
docs/testbases の仕様書を根拠に、iOS 向けのシナリオを書いて。仕様どおりに動かない箇所があったら、
テストを実挙動に合わせて緑にせず、仕様どおりの期待のまま失敗させて、不具合として記録して。
```

下書きを経由せず、AIアシスタントが仕様書を直接読んでシナリオを書くこともできます。`draft-scenario` は、
まず骨組みを機械的に作ってから仕上げたいときの入口です。なお、MCP の `ft_draft_scenario` は別物で、
探索中に実行した操作列を Swift シナリオにして返します([MCP サーバ](../tools/mcp_server_ja.md))。

## 仕様違反が見つかったとき

テストベースを根拠にシナリオを書くと、実行結果が仕様に従わない箇所が見つかることがあります。
AIアシスタント用のスキル(`/fleetest-scenario`)の標準の扱いは次のとおりです。

- **仕様違反は緑にしません。** テストを実挙動に寄せて通すと仕様違反を緑で隠してしまい、退行を検知できなくなります。
  **仕様どおりの期待のまま失敗(赤)にして追跡します。** 後始末は `afterEach` に書きます
  (失敗でシナリオは中断しますが、`afterEach` だけは失敗後でも実行されるので、残留を防げます)。
- **不具合は 1 件 1 ファイルで `TestProjects/<プロジェクト>/issues/defects/` に起票します。** 命名・テンプレート・凡例は
  同じフォルダの `README.md`(ファイル名は `D-<連番2桁>-<slug>.md`)にあり、状態の一覧は同じフォルダの `INDEX.md`
  (対応状況のダッシュボード)にまとめます。起票や状態を変えるときは、個別のファイルと `INDEX.md`(集計を含む)の両方を更新します。
  各ファイルには、対象・対応する SC / TC・重大度・状態・検出元のシナリオ・再現手順・期待・実際・証拠・仕様の裁定案を書きます。
- **テストが仕様の正誤を独断で決めません。** TC 自身が「実挙動を合格として記録し、仕様の裁定は別に起票する」と
  明示しているケース(仕様と実装が食い違っているなど)は、その指示に従って緑のままにし、裁定が要る事項として不具合の起票側に回します。
- 不具合が修正されたら、状態を更新し、対応するテストが緑に変わることを確認します。
