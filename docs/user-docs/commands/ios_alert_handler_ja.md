# iosAlertHandler

これから出る iOS のシステムアラート(権限の許可・ATT・「"◯◯"で開きますか?」)を1枚予告し、
押すボタンを指定します。

## 関数

| 関数 | 説明 |
|---|---|
| `iosAlertHandler(alert:, button:)` | これから出るシステムアラートを1枚登録します。`alert:`(どのアラートか。題名との照合)は必須です。`alert:` も `button:` もセレクタと同じ記法(`\|\|` で候補・`*` で一致方法)を使います。押せた登録は外れます —— 2枚目を待つならもう一度呼びます。`engine=hybrid` のときだけ効きます。 |

## 例

```swift
iosAlertHandler(alert: "*写真ライブラリ*", button: "許可しない")
iosAlertHandler(alert: "*トラッキング*||*wants to track*",
                 button: "許可||Allow")                              // 日英両対応
```

## 注意点

### なぜ要るか

位置情報・通知の許可や「"◯◯"で開きますか?」は、別プロセスの SpringBoard が描画するため、
アプリ自身のアクセシビリティツリーには最初から現れません。よって
[`irregularHandler`](./irregular_handler_ja.md) はこれらを見ることも閉じることもできません。

| エンジン | 書き方 |
|---|---|
| **hybrid**(実行プロファイルの既定) | 普通に書けます —— `tap("許可")` / `exist(...)` / `ifCanSelect(...)` は、アプリ側で解決できないセレクタを SpringBoard 側へ照会して掴みます。`iosAlertHandler` で登録しない限り、自動では何も閉じません。 |
| **xcuitest 単独** | SpringBoard 側のセレクタを解決できません。アラートを操作するシナリオは hybrid で回してください。 |
| **inapp 単独** | 同じ制約があります(注入先アプリのプロセスしか見えません)。 |

宣言なしで既定で自動的に閉じるのは、`openURL` の初回確認アラートだけです。

### 登録する

- **`alert:` は必須です。** ボタンのラベルだけでは「どのウィンドウのボタンか」が読めず、
  題名を照合しないと無関係のアラート(別アプリの許可要求が前面にキューされている形)を
  押してしまうことがあります。
- 両方の欄はセレクタと同じ記法です: bare = 完全一致 / `x*` = 前方一致 / `*x` = 後方一致 /
  `*x*` = 部分一致。アラートの題名にはアプリの表示名が埋め込まれる(「"MyApp"が写真への
  アクセスを求めています」)ため、実用上 `alert:` は `*x*` で書くことになります。`#id` /
  `.型` は受け付けません(SpringBoard の題名に対して意味を持たないためです)。
- **1回の呼び出しは1枚のアラートの予告です。** 一致するアラートを押すと登録は外れるので、
  2枚目を待つならもう一度呼びます。アラートを出す操作の前に登録してください —— `setUp()` に
  置けば各 `@Test` の前に1回登録されます(`irregularHandler` と同じ寿命です)。
- **登録は順に試され、シナリオが要求した要素がアプリ側・SpringBoard 側のどちらでも解決
  できなかったときだけ押されます** —— シナリオ自身が操作しているアラート(`tap("許可")` や
  `ifCanSelect`)からは奪いません。
- **`ifCanSelect` が不成立のときも登録を参照します** —— そうしないと、下のような列が
  アラートの上を全部素通りして「不成立」になり、後から押しても手遅れになります。

  ```swift
  ifCanSelect("#btn_start||はじめる") { tap("#btn_start||はじめる") }
  ifCanSelect("#btn_agree||同意する") { tap("#btn_agree||同意する") }
  ```

- **ラベルは完全一致で、ツールは既定ボタンを推測しません。** どのボタンが「是認」かは文脈
  依存で(位置情報の許可には「1回だけ許可 / Appの使用中は許可 / 許可しない」等の変種があり)、
  文言も並びもロケールと OS 版で変わります。書いたラベルだけを押し、部分一致もしないので
  `button: "許可"` が誤って「許可しない」を押すことはありません。拒否側で自動拒否したいときは
  同じ形で拒否ラベルを登録します。
- **押したことは run ログに残ります**(何を押したかまで)。権限は後に響く状態なので、痕跡が
  無いまま自動で変わるのは沈黙になります。対象アプリと無関係のアラート(別アプリの許可要求が
  前面に出た場合)を押していても、これで後から気付けます。

### システムアラートがアプリを覆っている間

これは `iosAlertHandler` の登録が残っている間だけ働きます。アラートがアプリを覆っている間、
アプリへの操作と検証は進みません —— アラートが消える(または登録したボタンで閉じられる)のを
待ち、待ち切れなければ `failureKind=system-ui-covered` で落ちます。

```
❌ 6. [action] tap "#btn_something"
   system UI is covering the app ("MyApp"が写真ライブラリへのアクセスを求めています).
   The in-app engine could still reach the app, but a person could not, so the step was not
   performed. None of the registered iosAlertHandler entries matched a button on it.
   Buttons on this alert: 「写真を選択」 / 「フルアクセスを許可」 / 「許可しない」.
   Register the one you want pressed with iosAlertHandler(...), or dismiss it in the scenario.
```

- 失敗メッセージにはそのアラートに実際にあるボタンが出ます —— ラベルは完全一致なので、
  正しい文字列を知る手段として、数秒で消えるアラートを動画で捕まえずに済みます。
- これが要る理由は、in-app エンジンのタップが OS のタッチイベントではなく直接の呼び出し
  だからです —— 何もしなければ、覆っているアラートの下にあるアプリへ、人には不可能な操作が
  届いてしまいます。Android は影響を受けません(木の根が active window なので、覆われた
  アプリの要素は木から消えます)。
- アプリ自身が出しているモーダル(アプリが描いたもの)は対象外です —— OS が描く UI がアプリを
  覆っているときだけ働きます。
- 成功した検証も同じ扱いです。覆われた状態で緑になっていたら、まず覆いを晴らそうと試み、
  晴れた画面で判定し直してから受理します。

### アラートを画面に残したときの影響

- **アラートを出すシナリオは、そのシナリオ内で閉じてください。** SpringBoard が描くため、
  `terminateApp()` や `removeApp()` をしても画面に残り、その端末で次に走る何にでも残り、
  以降のシナリオが全部上記の失敗になります。
- **残ったアラートは run を跨ぎます。** run 開始時に端末に既にアラートが残っていると警告が
  出ます。
- **`clearAppData()` で権限をリセットできます** —— 同じダイアログが次の run でも再び出るので、
  常に未決定の状態から始めたいシナリオに使えます。
- **MCP で詰まったときは** `ft_launch bundleId: com.apple.springboard` —— 非破壊で
  SpringBoard に attach するだけなので、`ft_snapshot` でダイアログを ref から読めます。
  終わったら対象アプリへ `ft_launch` で戻ってください。
