# MCP 監査ラウンドの回し方(深さでなく幅)

実アプリを触って MCP(`ft_*`)の欠陥を拾い、直す作業の手順書。
**1ラウンド = 初見の「形」1つ**(アプリ1本ではない。次節)。

## 何を1ラウンドと数えるか —— 軸は2本

**軸① 画面の形**(木がどう出るか): 本文 / 格子 / 深いリスト / フォーム / モーダル /
全画面キャンバス / 無限スクロール / タブ …

**軸② セッションの形**(サーバが何を覚えるか): 1台1アプリ / **2台以上** / **OS 跨ぎ** /
アプリ切替 / 長時間 / ブリッジの建て直しを挟む …

**アプリ名は軸ではない。** 2026-08-13 にこの数え方へ直した。それまで「1ラウンド = 初見のアプリ
1本」と数えていたため、**ブラウザ6ラウンドが全部「天気」で、うち5回は同じ格子**という状態を
台帳が検出できなかった(アプリ名は tenki.jp / Yahoo!天気 / 気象庁 と変わっていたので
「初見」に見えていた)。6ラウンド目に至っては **2・3ラウンド目と同じ tenki.jp を再訪**し、
木まわりで拾ったものは全部が既記録の再発見だった。

## なぜ深さでなく幅か

同じ対象(地図)を繰り返した 19 ラウンドの収穫:

| ラウンド | 実バグ |
|---|---|
| 1(2026-08-07・初回) | 12 |
| 2〜3 | 9 → 6 |
| 4〜7 | 4 → 0 |
| 8〜19(08-10〜08-12) | **0〜2/回**(0 の回が4回) |

**収穫は対象の新しさに比例し、深さには比例しない。** 初見の対象は毎回まとまって出た
(sut-ec-mobile の in-app 初監査で4件 / React Native 対応で固有の罠 / 2026-08-12 に
設定・チャット・ブラウザをコーパスへ足しただけで、注記の汎用性判定が3本ひっくり返り、
実 web ページで既知型の誤検知が 10 件出た)。一方、19 ラウンド目の地図から出るのは
ほぼ言い回しだけになった。

**同じ対象でも「画面の形」が変われば初見と同じだけ出る**(2026-08-12・ブラウザ3ラウンド目)。
1・2ラウンド目は**縦に流れる本文**を読ませていて、実バグは要素上限と a11y の取りこぼしだった。
3ラウンド目に**格子(週間表)**を読ませたら実バグ4件 —— 見出し行の欠落・空振りの偽成功・
`scrollFrameRect` の見落とし・codegen の書き戻し漏れ。

## 自作の機構を監査しているとき、それは収穫ではない

**入れたばかりの検知は、次のページで誤検知を出す。** 3ラウンド目に入れた
`gridWithoutHeaderNote` は固定コーパス30枚で誤検知0だったが、**次のラウンドで触った1ページで
2件出した**。30枚の「誤検知0」は**その30枚に無い形については何も言っていない**。

これは観察としては正しいが、**美点として運用すると原理的に終わらない**。直近2ラウンドの
「実バグ」を出自で分けると:

| ラウンド | 自作機構の欠陥 | 元からあった欠陥 |
|---|---|---|
| browser 4 | ⒜ `gridWithoutHeaderNote`(3で新設)/ ⒝ `webViewGapNote`(2で新設)/ ⒞ `gridMinRows`(3) | ⒟ `ft_scroll_to` の注記落ち |
| browser 5 | ⒜ `webViewGapNote`+`emptyTreeNote` が測れない / ⒝ `looksUnchanged`(15 の waitForChange 由来)/ ⒟ ⒜と同じ指標 | ⒞ 横スクロールの複製 |

**3/4 が自作機構の欠陥。** 1本足すと次のラウンドが1本確定し、そのラウンドでまた足すので、
実バグの本数は減らないまま注記だけが増える(ブラウザは 3→3→4→4→4 で**減衰していない**。
同じ期間に `NoteCatalog` は 17 本になった)。

**だから増設と検分は同じラウンドでやらない**(手順の 5.5)。

## 台帳が数えていなかった軸(2026-08-13 追加)

木の形とは独立に、**「2台以上を触ったセッション」でだけ出る欠陥**がある:

- ラウンド19: `serial` だけの呼び出しが黙って iOS へ
- ラウンド20: キャッシュ命中でセッション記憶が更新されない
- 2026-08-13: 失敗キャッシュの再生がライブの失敗と見分けられない / 宛先記憶が曖昧なまま適用

3件とも、天気タスクが「**両OSで**」だったから**副産物として**露出した。狙って触った回は一度も無い。
軸②はこれを狙うためにある。

**地図(Google マップ / Apple マップ)の反復監査は 2026-08-12 に閉じた。**
再開するのは、地図に固有の新しい経路(新しい画面・新しい操作)を触るときだけ。
「赤羽→立川をもう一周する」はしない。

## ラウンドの手順

1. **形を選ぶ**(下の台帳の「未着手」から1つ)。条件は**軸①か軸②のどちらかが初見**であること。
   **アプリが初見でも、形が既出なら初見ではない**(ブラウザで別の天気サイトを開くのは同じ形)
2. **タスクを1つ決めてから触る**(「探索する」ではなく「◯◯を達成する」)。
   目的の無い探索は画面を並べるだけで、詰まりが観測できない
3. **触る。詰まったところをその場で記録する** —— 何を撃って、何が返って、なぜ止まったか
4. **拾ったものを3つに分ける**(下の節)
5. **バグを直す**。同じ型が他に無いかを機械的に掃討する(CLAUDE.md の規律)
5.5. **このラウンドが「検分の回」なら、新しい注記を足さない**(下の交互規則)
6. **フィクスチャを1枚採る**(`Tests/Fixtures/RealAppSnapshots/`)。
   `NoteCoverageTests.archetypes` に分類を足し、`SweepHarnessTests` の基準値は
   **検知を1件ずつ検分してから**書く
7. **台帳へ1行足す**(形・セッションの形・出自の内訳を書く)

### 増設と検分は交互にやる

前のラウンドで**新しい注記・新しい検知を入れたら、次のラウンドは検分の回**にする。
検分の回にやってよいのは **誤検知の修正・条件の絞り込み・削除**だけで、**新しい注記は足さない**。
拾った増設案は台帳に積んで次の増設の回へ回す。

これが無いと、1本足すたびに次のラウンドが1本確定し、そのラウンドでまた足すので終わらない
(上の「自作の機構を監査しているとき」)。**注記の本数は `NoteBudgetTests` が固定している**ので、
増やす回には根拠(手数の差 or 実機 witness + コーパス誤検知0)を台帳へ書くことになる。

## 拾ったものを3つに分ける

| 種類 | 例 | 判定の仕方 |
|---|---|---|
| **バグ** | 別の要素を撃った / 成功と言って届いていない / 画面の値を誤って報告した | その場で直す。再現テストを足す |
| **自作機構の欠陥** | 前のラウンドで入れた注記が誤検知する / 測れない形がある | その場で直すが、**収穫として数えない**(台帳の内訳へ「自作」と書く) |
| **言い回し・注記** | 「もっと分かりやすく言えたはず」「この注記は誤解を招く」 | **その場で直さない**。`Scripts/mcp-bench.sh` の手数が動くかで決める |

**この分離がこの手順書の要点。** バグは有限なので減衰するが、言い回しの改善案は無限に出る
(評価者が読んで違和感を探す限り、必ず何か出る)。分離せずに回すと、収束するのは
バグだけで、注記と分岐は単調に増え続ける —— 実際そうなった(docs/verification.md
§「注記は『読んだ印象』でなく『まっさらなエージェントの手数』で足し引きする」)。

**2列目を分けたのは 2026-08-13。** 「実バグ4件」と書き続けていたが、出自で割ると
3件が自作機構だった。混ぜて数えると**収穫が減っていないように見えて、実際は自分の尾を
追っている**ことに台帳が気付けない。

## 停止規則

- **1ラウンドの終わり**: 決めたタスクを完遂したら終わり。「ついでにもう1画面」はしない
- **その形の終わり**: **同じ形で、元からあった欠陥が0のラウンドが2回続いたら閉じる**。
  数えるのは1列目だけ —— **自作機構の欠陥は0の判定に入れない**(入れると、自分で入れた
  注記の手直しが「まだ収穫がある」の証拠になり、永久に閉じられない)。
  **ただし「その形を実際に触れなかった回」は 0 に数えない**(2026-08-13 追加)——
  ブラウザ・格子の6回目は、両 OS とも表が a11y に出ず**セルを1つも読めないまま終わった**。
  欠陥は0だが、**格子の判定を1度も走らせていない**ので閉じる根拠にならない。
  数えてよいのは**タスクを完遂した回**と、**その形の機構に当たったうえで0だった回**だけ
- **全体の終わり**: 無い。台帳の未着手が尽きたら、そのとき残っている形の空きを埋める

### 実機のブリッジが短時間で死に、ポートが 8143 ⇄ 8144 を往復する(2026-08-14。**原因まで測って修正済み**)

混在ラウンドの副産物。**症状**: `ft_launch` のたびにランナー再構築で約190秒かかる回が続いた。

**結論**: **1台の実機に XCUITest ランナーを2本立てると、2本目の起動が1本目を即殺し、
その約5分半後に1本目の後始末が2本目を道連れにする。** 対照と時系列(すべて実測):

| 条件 | 生存 |
|---|---|
| ランナー1本だけ | **27分健全**(01:53:47 起動 → 02:21:04 に下記の道連れで終了するまで。無操作 5 分を挟んでも死なない) |
| 2本目を立てた瞬間 | **1本目が即死**(2本目が応答を始める **2秒前**に黙る) |
| その後 | **約5分半で両方終了**(02:21:04.879 と 02:21:05.716 = **0.8 秒差**) |

**機構(3段)**:

1. **2本目の起動が1本目の端末側アプリを殺す。** 実測: 8143 が 02:15:35 に黙り、
   8145 が答え始めたのが 02:15:37 —— **黙るほうが先**なので、後始末の巻き添えではなく
   起動そのものが原因
2. **殺された1本目は終了しない。** XCTest が端末側ランナーを建て直そうとするが、
   端末は2本目が握っているので**その建て直しがハングする**
   (`xcresult` の `failureText` = **`The test runner hung before establishing connection.`**)。
   ここで**約5分半**待つ —— 台帳が2度観測した「5分32秒 / 5分27秒」は**このハング締切**であって、
   端末側のタイマー(自動ロック等)ではない
3. **締切が切れた1本目の後始末が2本目を道連れにする。** 1本目は `devicectl diagnose` を走らせて
   セッションを畳み、**その 0.8 秒後に2本目も `Test crashed with signal kill.` で落ちる**

ログには異常が1行も無い(`bridge listening on 0.0.0.0:8143 ttl=7200s` の後は普通の
`Getting device orientation` が並ぶだけ)。**クラッシュログは端末にも残らない。**

「先に死んだ1本目の teardown が原因」という当初の対抗仮説は、上の①で否定された。

**修正: 実機専用の手当ては要らなかった —— 規則は既にあり、実機だけがそこから見えていなかった。**

同じ「同一デバイスに2本目を建てる」操作を両方で撃つと結果が割れていた:
シミュレータは **`reusing the running xcuitest bridge`** で2本目を建てないのに、実機は建てた。
`planBridge` の同一デバイス判定(`sameDevice`)自体は正しく、材料を作る
**`BridgeProvisioner.scanRunningBridges` が udid を `/status.device` の名前引きだけで解決していた** ——
実機は `device` が汎用名 `"iPhone"`、プロファイル名は `"iPhone wave(実機)"` なので
**udid は nil・名前も不一致**になり、**生きている実機ブリッジが同一デバイス判定に一度も当たらない**。
昨日 `BridgeDiscovery.scan` 側だけ直した引き当ての**2つ目の実装**で、そこに修正が届いていなかった。

修正は引き当てを **`BridgeDiscovery.resolveUDID` の1箇所**へ寄せ、
`status.udid`(仮想)→ `BridgeDeviceRecord`(実機)→ 名前引き(旧ブリッジ)の優先順にした。
**ついでにシミュレータ側の劣化も直る** —— 従来は `status.udid` を使わず名前引きだったので、
コード自身が認めるとおり「同名 sim が複数 booted だと udid を nil に落とす」= そのとき二重起動を許していた。

**ゾンビ(/status 無応答)の側は元から塞がっていた**: `provision()` の `startingByUDID` が
`BridgeLauncher.portsByUDID`(プロセス引数の `-destination id=<UDID>` 照合。HTTP を使わないので
両プラットフォームで同じに効く)で拾い、`.adopt` → 応答しなければ `stopAndWait` → **同じポートで**
建て直す。だから塞ぐべき穴は「映っているのに端末を特定できない」1つだけだった。

**検証**: `swift test --parallel` 緑 / 変異 6/6 検出 / **陽性対照は実機とシミュレータの両方**で、
別ポートを要求しても `reusing the running xcuitest bridge`(実機は port 8145、端末上のランナーは1本のまま)。
**修正前の同じ操作は実機で2本目を建てていた。**

**残っている周辺の穴**(この修正では触っていない。実害はまだ観測していない):

- 黙ったポートを **`MCPServer` の `trustBound(bound:ownerAlive:)` は `.busy`(retry せよ)と読む** ——

### 探索が「見つけた要素」をタップしていた(2026-08-14・append-on-scroll のラウンド。**修正済み**)

**症状**: `ft_scroll_to '*ぼる塾田辺*'` が 7 スワイプの末に**その記事を開いて**返り、しかも
`scrolled to …` と成功を報告する。読み取り専用のはずのコマンドがアプリの状態を変える。
実機 SmartNews で **2/2 再現**(別の記事でも予測どおり開いた)。

**真因**: 探索終端の**空打ちドラッグ**の終点計算 `emptyDragEndX`。この関数の doc 自身が
「離した点が要素の中ならクリックとして成立するので、**必ず矩形の外へ横に抜ける**」と書いているのに、
左右どちらへも 4pt 出られないときの最終行が **`return x`(= 開始点)** だった。
始点と終点が同じ 0.30 秒のプレスは**タップそのもの**。

**なぜ自前 SUT で出ないか**: 発火条件は「要素が画面幅いっぱい」で、5 SUT の行はすべて
インセット(例 `16,270 330x56` → 右へ抜けられる)。**全幅の行は実アプリに固有**。
加えて `AppBundleInspector.detect` は**実機では必ず nil を返す**設計なので
`shouldEmptyDrag` が常に true になり、**実機では全アプリが対象**になる。

**修正**: `emptyDragEndX` の戻り値を `Double?` にし、抜けられないときは nil = **その回は撃たない**。
Optional にしたのは**呼び出し2箇所(探索終端・救済の後)をコンパイラに拾わせる**ため
(片方だけ直す掃討漏れが台帳に何度も出ている)。撃たない代償は「容器が次の1タッチを
消費したまま」= やり直しで回復するが、撃った代償は**戻せない状態変化**。

**検証**: `swift test --parallel` 緑 / **変異 4/4 検出**(元のバグへ戻す・常に拒否する・
呼び出し2箇所それぞれを素通しにする)/ **E2E `--cmp --ios` 34/34 成功**(インセット行では
従来どおり空打ちが出ることの実機側確認)/ **実機の陽性対照**: 修正後は 6 スワイプで
目的の行 `(0,328 393x116)` に到達し、返るのは**フィードの木**(記事の chrome は無い)。

### 不採用: カメラの遮蔽誤検知は直さない(2026-08-14・費用が測れたので閉じる)

**症状**: Google カメラでモード切替(`Video`/`Camera`)を撃つたびに
「`#bottom_bar` が中心を覆っている」と警告が出る。**タップは毎回正しく通る**。

**重要度は低い**と判定した:

- 撃つ対象は**エージェントがまさに押したい可視の操作子**で、**誤った操作は起きない**(助言止まり)
- 損なのは注意とトークン、せいぜい助言に従って `ft_screenshot` を1手増やすこと
- **直す費用が赤字**: 唯一見つかった規則(ラベルも値も持たない `other` の器は遮蔽にしない)を
  全数で測ると**真陽性が30件失われる** —— Safari の浮遊 URL バー・フッタ・アプリバーが本文を
  覆う、いずれも受理済みの形。雑音1件のために本物の警告を30件捨てることになる

真因は原理的なもの(Android の z は「上」と言うが**透明性は a11y から見えない**)なので、
新しい材料が増えない限り再検討しない。

**この判定は `isHittable` 案の評価軸も変えた**: 偽陽性側が低優先なら、
**Android で偽陽性を解けないことはブロッカーではない**。オラクルは**偽陰性側だけ**で
評価すればよく、そちらは iOS 限定で構わない。

木は「何が手前か」を答えられない(iOS は z を出さない)。上の2件(潜ったセル / 透明な器)は
どちらもその限界で、木だけで当てる規則は**4案とも全数で測って棄却**した。
そこで判定をプラットフォームへ委ねる —— `XCUIElement.isHittable` はヒットテストそのもの。

**実装済み**: `GET /hittable?ref=N`(版 67)。引き当ては identifier → label で、候補が1つに絞れて
frame も一致するときだけ答える(曖昧なら `hittable:null` で呼び手は黙る)。

**費用の実測**(iPhone 17 Pro / iOS 27・126ノード):

| 測定 | 実測 |
|---|---|
| 木の取得 `app.snapshot()` 1回 | 102 ms |
| `isHittable` 1件 | 中央 39 ms |
| 対象1件を引いて評価 | 72〜146 ms(id 引き / label 述語) |
| **全 121 要素に付けると** | **約 5.1 秒 = snapshot の 50 倍**(= 常時は不可) |

**オラクルの妥当性は確認済み**(iOS カレンダー月表示): ナビバーの下へ潜った `7月26日` は
`hittable:false`、普通に見える `8月17日`/`8月11日` は `true`。**木が答えられなかった問いに正しく答える**。

**Android では使えない**(論理的に確定): `SnapshotBuilder.java` は木を組む時点で
`isVisibleToUser()==false` のノードを除外しているので、**木に載っている要素は定義上すべて true** =
情報量ゼロ。そもそも Android の `isVisibleToUser()` は「View が可視でクリップされていないか」で、
上に重なった別ビューがタッチを取るかは答えない(iOS の `isHittable` とは問いが違う)。
**カメラの偽陽性はこの手では解けない** —— ただし上の判定でその件は不採用にしたので、**この非対称は設計上のブロッカーではない**(オラクルは偽陰性側だけで評価する)。

**ゲートの絞り込み(2026-08-14 に全数で測った)**:

| ゲート | 発火 |
|---|---|
| A: 素直(中心を覆う非系譜がいて、木の順序では奥なので現状黙っている) | 197/820 = **24%** |
| B: A + 覆う相手が victim のスクロール容器の**外** | 52/820 = **6.3%** |
| **B のうち iOS だけ**(下記の理由で Android は対象外) | **14件**(`ios-browser_startpage` 7 / `ios-maps_suggest_keyboard` 7) |

**Android には掛けない**のが要点。あちらは **z が実測で採れていて `drawnAbove` が権威**なので、
黙っているのは正しい判断であり、そもそも聞く先(`isHittable`)も無い。B で鳴っていた32件
(`and-place_expanded` 17・`and-results` 15)は全部 Android で、**聞く必要が無いものだった**。

つまり採るべきゲートは **「z が無い(= iOS)」+「victim が容器の中」+「覆う相手が容器の外」+
「現状黙っている」** で、タップ対象の数%に収まる。狙いの形(ナビバーの下へ潜ったカレンダーのセル)は
まさにこの形なので入る。

**配線済み**(2026-08-14): `AppDriver.hittable`(プロトコル要件として宣言。既定は nil)→
`BridgeClient` が `/hittable` を叩く → MCP のタップ経路が
`TapTargetGeometry.suspectedHiddenUnderChrome` で疑ったときだけ聞く。

**実画面の対照**(iOS カレンダー月表示): 潜ったセルへの `ft_tap` が
`the platform reports button "7月26日 日曜日" is NOT hittable at its reported position —
it is scrolled under the navigation bar or another overlay` と警告し、
**普通に見えるセルは黙る**。今日「木だけでは解けない」と結論した沈黙の誤操作が塞がった。

**配線で1回外した**(台帳の既知の型): ラッパードライバ5つ
(`SessionRecoveryDriver`/`HybridFallbackDriver`/`FastLaunchDriver`/`LaunchPreflightDriver`/
`AppAttachDriver`)が転送していないと既定の nil に落ちる。**純粋関数もブリッジも正しいのに
実画面で1バイトも変わらなかった** —— `snapshot(bypassingCache:)` と同じ罠で、5つとも転送を足して解消。

**変異で合成盤面の誤りが2つ出た**(どちらも「条件を外しても落ちない」形): ⑴ 覆う相手の z を
**上**にしていたので既存の遮蔽判定が先に拾い、z の条件を検証していなかった ⑵ **塗り順は配列順ではなく
ref の大小**なのに配列の並べ替えで前後を作ったつもりでいた。両方直して 3/3 検出。

### 未修正の持ち越し: 別の画面の同じ id を黙って撃つ(2026-08-13・長時間のラウンド)

**実測**: スクロール画面で `#btn_back`(ref 2)を採る → **別プロセスが同じ機をセレクタ画面まで
進める** → 90秒の無操作 → その ref を撃つと **`tap [2] done` で警告ゼロ**。実際にはセレクタ画面の
同名ボタンに当たり、画面はホームまで戻った。

**原因**: `RefGuard.match` は **identifier だけ**で同一性を決める。`#btn_back` は両画面に
**同じ座標**であるため `moved=0`・ラベル不変となり、既存の警告(gone / ghost / moved /
ラベル変化 / 遮蔽)がどれも当たらない。**既に2回直した型の3つ目**である ——
別デバイスの同じ id(udid 照合で修正済み)/ 別アプリの同じ id(`sessionBundleID` で修正済み)/
**別画面の同じ id(無防備)**。

**2026-08-13 追記(タブ切替のラウンドで範囲が狭まった)**: **別画面へ再照合したこと自体は
検知されている** —— タブを跨いで `#txt_screen_title` の古い ref を撃つと
`caution: its label has changed from "コントロール" to "情報" since the snapshot` が出た
(`RefGuard.labelChangeNote`)。長時間のラウンドで黙ったのは `#btn_back` が**両画面で
id もラベルも同じ**だったからで、**盲点は「同じ id かつ同じラベル」に限られる** ——
実質はナビゲーションの chrome(戻る・閉じる・タブ自身)。**当たっても遷移先が同じになりやすい**
要素群なので、当初書いた「別デバイス・別アプリに続く3つ目」という重さではない。

**直さない理由(設計ではなく実測で決めた)**: 画面には udid や bundleID のような固有 ID が
無いので、判定材料は木しかない。「ref を採った木の id が、撃つ直前の木にどれだけ生き残るか」を
E2EAppCMP で実測した:

| 種別 | 操作 | 生存率 |
|---|---|---|
| 同一画面 | 何もしない / 非同期で要素が増える / スイッチ切替 | 1.00 |
| 同一画面 | 入力 + ソフトキーボード | 0.94 |
| 同一画面 | リストをスクロール(1回 / 4回) | 0.92 / **0.54** |
| 画面遷移 | スクロール→セレクタ / ホーム→スクロール / →WebView / セレクタ→ホーム | 0.19〜0.27 |
| 画面遷移 | ホーム→タブ(情報) | **0.67**(タブバーが生き残り、木が小さいので比が上がる) |

**2つの母集団が重なる**(同一画面の最小 0.54 < 画面遷移の最大 0.67)。閾値 0.35 なら
この盤面では誤検知0・検出 4/5 になるが、**行が id を持つ長いリストを数画面ぶんスクロールすれば
生存率は 0 に近づく** —— つまり**無限スクロール(台帳の未着手)でちょうど誤検知する**。
「入れたばかりの検知は次の画面で誤検知を出す」を、入れる前に測って確認できた形。

**severity は device / app の2件より低い**: 撃った先は同じアプリ・同じ機の**いま前面にある画面**で、
呼び手は撮り直せば気付ける(あちらは呼び手に知りようが無かった)。

**次にやるなら**: 木だけで当てようとしない。案は ⑴ 事実だけ言う(「この ref は N 秒前の木のもの」)
—— 誤検知はゼロだが、効くかどうかは `Scripts/mcp-bench.sh` の手数で測ってから
⑵ 呼び手が期待する画面を渡せるようにする(`expectScreen`)—— 検知ではなく契約にする。
**どちらも「1画面で測って入れる」をやらないこと**(上の表がその危険を示している)。

**2026-08-13 追記: この案は実アプリで測って完全に閉じた。** Android 設定の「すべてのアプリ」
(`and-apps_list`)で同じ指標を測ったところ:

- **id 生存率は 0/0** —— この画面は 40 要素すべてが identifier を持たない。**指標が定義できない**
- **ラベル生存率は、同じ画面をスクロールしただけで 2回目以降 0.28 に張り付く**
  (生き残るのはアプリバーの chrome 5 本だけ)。CMP で測った**画面遷移の 0.19〜0.27 と完全に重なる**

つまり閾値をどこに置いても、**長いリストを2回送っただけで画面遷移と同じ値になる**。
「木の id/ラベルの生存率で画面遷移を当てる」案は**設計しない**。

### 取り下げ: 「フォームの行き止まり」は行き止まりではなかった(2026-08-13・同日に測って撤回)

**最初に書いたこと**: Android 設定の「ネットワークを追加」で WPA を選ぶとフォームが伸び、
`#buttonPanel` が (0,1529 1080x12) に潰れて `保存`/`キャンセル` が1つもツリーに出なくなる
(`and-form_keyboard` として固定)。この状態で `ft_scroll_to '保存'` も `'#button1'` も届かず、
**呼び手は詰む**と書いた。

**測ったら詰まなかった**(`Bench/tasks/and-form-wifi` を新設・`--repeat 5`)。**5/5 完了**、
手数の中央値 13、回復はどの run も**1手**:

- 2/5 は `ft_scroll_to '#button1'` に **`scrollFrame: "#content_parent"` を添えて成功**
- 3/5 は `ft_navigate back`(Android の戻るキーはキーボードを閉じる)で成功

**私の実験系が間違っていた。** 手動プローブは `scrollFrame` を渡していなかった ——
そして `#content_parent` は**ツールが自分で出していた**:
「note: 2 scroll areas on screen: #content_parent / #security. **Pass scrollFrame: to
ft_scroll_to to search inside one of them.**」。**当たらない助言だと書いたものが、正解だった。**

**教訓**: 「呼び手は詰む」と書く前に、**自分がツールの助言に従ったかを確かめる**。
今日これで3回目の実験系の誤り(前2回は「前の run の残り」と「grep せずに無いと言った」)。

**続けて A/B も回した**(`full` vs `scrollFrameCandidates` を落とした版・`--repeat 5`):
**tools ±0**。陽性対照は取れている(full は 1 run に 4〜5 回発火・variant は 0 回)。
落とすと 5/5 とも `ft_navigate back` に流れるだけで、**同じだけ安い代替がある**。
**ただしこれは消す根拠にならない** —— この注記は 10 フィクスチャで発火しており、
**容器の中でしかスクロールできない画面**(地図のシート等)には back という代替が無い。

**ここで型が1つ分かった**: 注記が効いているように見えるのは**代替手段が無い盤面**でだけ。
**代替がある盤面で A/B を組むと、効いている注記でも必ず ±0 が出る。**
測る前に「その注記が無いと本当に手詰まりか」を考えること(詳細は Bench/measurements.md)。

### 決着した持ち越し(測って「足さない」と決めた)

**`unlabeledClickablesNote` の「矩形の包含」形には規則を足さない**(2026-08-13 に計測して決着)。

観測はこうだった —— Android メッセージの「新しい会話」画面で `[16] clickable (12,85 126x126)` が
「安定したセレクタで指せない」と報告されるが、**その内側に一意ラベル `戻る`(43,116 63x63)**
があり、**実機で `tap '戻る'` が成功する**(= 注記の主張は偽)。同日の修正は**矩形の完全一致**しか
見ないのでここには効かない。一般規則の設計も難しく(「内側に `.stable` が1つだけなら黙る」は
iOS 設定の行を壊す・面積比で切ると Android の戻るボタン 25% が漏れる)、保留していた。

**測った**(Bench/measurements.md §2026-08-13。`and-chat-newconv` = この注記が発火する盤面 /
`and-settings-keyboard` = 対照。`--repeat 5`)。結果は **tools ±0** —— **注記を丸ごと落としても
手数が1手も動かない**。陽性対照も取れている(base では 1 run に4回出ており、variant では0回)。
偽の主張をしている盤面ですら効いていないのだから、**正しくして得られる手数は 0 以下**。

**この決着の型を覚えておく**: 保留の理由は「規則の設計が難しい」だったが、測ってみると
**そもそも設計する価値が無かった**。難しさで保留すると、いつか腕が上がったら着手する話に
見えてしまう。**設計の難易度ではなく効果で閉じる**。

**消す判断は別**(未着手): 測ったのは2盤面だけで、`ios-home` / `ios-maps_route_options` では
真陽性として出ている(`SweepHarnessTests`)。消すならその2形にも手数タスクが要る。
