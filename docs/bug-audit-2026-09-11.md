## 1. Android: 容器タップ → `type` が前に焦点のあった別の欄へ入って緑になる【大】(F13)

**再現**(物理 Pixel 3a・Android 12・`com.ftester.e2e.android`。`ft_batch` は StepExecutor = シナリオと同じ経路):

```
ft_batch  tap "#nav_input"
ft_batch  tap "#field_single"; type "kb"      → single=kb
ft_batch  tap "#field_wrapped"; type "W3"     → 1. tap — ok / 2. type — ok / All 2 step(s) passed
木:       single=kbW3 / wrapped=(空)          ← 入り先が違う
```

焦点がどこにも無い状態(起動直後)から同じことをすると救済が働き `wrapped=W4` になる(対照)。
**セレクタ付きの形 `type("#field_wrapped", "W5")` は正しく入る**(注記付き。エミュレータで確認)= 誤るのは `tap(容器)` と別行の `type(文字)` の組だけ。
**エミュレータ(Pixel_9_Android_15_-02)でも同じく再現**(物理端末固有ではない)。

**素性**(確認): 救済 `retypeTargetIfUnfocused` の門は `InputFocusRescue.nothingHasFocus(snapshot.elements)`
(`StepExecutor+Actions.swift:2136`)= **木の全体で**焦点が無いときだけ救う。Android は焦点を持たない容器を
叩いても前の EditText の焦点を外さないので、門で帰り、`type` はフォーカス中の別の欄へ送られる。
読み返し(Android 注入器は `verifiesTypedText = true`)も**焦点のある別の欄**を読んで一致するので、
誤りがどこにも出ない。

**害**: CLAUDE.md が「支えるべき書き方」と定める `tap(入力欄) → type()` の Shirates 伝統形が、
**直前に別の欄へ入力していた**という普通の画面遷移で黙って誤る。witness(`E2EAppAndroid` の
`#field_wrapped`)は焦点の無い状態からしか叩かないので、E2E は緑のまま通る。

**同型**: MCP の `ft_tap(容器)` → ref なし `ft_type` も同じ(MCP 担当が 2/2 再現。
`MCPServer+Dispatch.swift` は Android の ref なし type を読み返しの対象から外しているので、どこへ入ったかも言わない)。

**直す向き**: 門を「全体に焦点が無い」ではなく「**焦点のある要素が、叩いた要素そのものでもその内側でもない**」に。
witness に「別の欄へ入力してから `#field_wrapped`」の1本を足す。

## 2. システムアラートに覆われた iOS 台を「画面凍結」と誤判定する【大】(F9)

①と同じ経過で離脱×2、最後に **-08 のブリッジ2本を止めて**終わった(一時シナリオは実行後に削除済み)。

**素性**(確認): アラートでアプリが非アクティブになると、Flutter の **in-app スクショが一様な白**になる

②ブリッジの作り直し・復活・再実行で数十秒を払い、**結果は変わらない**(台を変えていない)
③「別の台で再実行」と言うが実際は同じ台(文言は `RunOrchestrator.swift:1225`。再実行先が同じ物理台かを見ていない)
④終わり際にその台のブリッジを止めるので、次の run とモニターが張り直しを払う。

白フレームを凍結の根拠にしない。再実行の文言は再実行先が同じ UDID なら「同じ台で」。

## 3. 拡張の「テストを中断」で `api run` が即死し、録画が孤児になる【大】(F28)

**再現**(手元だけ・2台): `fleetest api run --project E2E-CMP --profile ios-inapp --runner local --set record=true --scenario …`
を、最初の `scenarioFinished` の3秒後に **pid へ SIGTERM**(拡張の中断と同じ届き方)。

- `api run` は **0 秒で rc=143**(既定の動作で終了。巻き戻しが1つも走らない)
- **`simctl io <udid> recordVideo` が5本、PPID=1 の孤児として録画を続けた**(40 秒以上。私が SIGINT で止めて確定させた)
- `recordings/index.json` が書かれない = 拡張の録画タブからこの run のクリップが見えない。切り出し前の生 `.mov` 約 50 MB だけが残る
- run.json は `finishedAt` 無し(= insights の「クラッシュか強制終了」)、NDJSON に `runFinished` も出ない
- シナリオ子(`fleetest-scenarios`)は ParentDeathWatch で消えた。`warm-ocr` は設計どおり残る(有限)

**素性**(確認): SIGTERM を受けて巻き戻すのは多機械の fanout(`ApiRunMachineFanout.swift:291`)・常駐系(`api monitor` 等)・
リモート経路で InterruptRelay が登録されている間だけ。手元だけの `api run` には受け口が無い。
一方、拡張は `proc.kill("SIGTERM")` だけを送り(`vscode-fleetest/src/cli.ts:152`)、コメントと CLAUDE.md の
「終了猶予の方針」は「`api run` は自前の後始末を持つので SIGTERM を送って待つ」を前提にしている。
多機械 profile でも fanout が手元の子 `api run` へ SIGTERM を中継するので、手元の分は同じ形になる。
拡張から起こした場合、孤児は `FT_PARENT_PID` を継ぐので**次に拡張が activate したときの掃除**で消えるが、それまでは録り続ける
(負荷とディスクを食い続ける。私の手元では `FT_PARENT_PID` 無しで起こしたので、放っておけば掃除の対象にもならなかった)。

**Android の録画も同じ**(E2E-Android で同じ中断 → ホスト側の `adb -s … shell screenrecord … /sdcard/ftrec-src-*.mp4` 5本と端末側の `screenrecord` 5本が孤児。
こちらは `--time-limit 180` が付いているので3分で自ら終わる = **上限が無いのは iOS の `simctl recordVideo` だけ**)。
**CLI の `fleetest run` も同じ**(pid への SIGTERM で rc=143・0 秒、`simctl recordVideo` の孤児 7 本。CI の中断や `kill <pid>` の形)。
終了スクリプトは控え(`.fleetest/hooks/<pid>.json`)が残り、`fleetest hooks reap` が代理実行した = この安全網は正常。

**直す向き**: 手元の `api run` にも SIGTERM/SIGINT の受け口を置き、録画の停止・index.json・lease の解放・run.json の完了・
`runFinished` を通ってから終わる(fanout と同じ `DispatchSourceSignal` の形)。

## 4. XCUITest エンジン: 焦点が無い `type` が緑を返してランナーを殺す【大】(F30)

**再現**(予備シミュレータ・XCUITest ブリッジ 8199・`com.ftester.e2e.ios`):

```
ft_batch  tap "#tab_home"; tap "#nav_input"; tap "#btn_input_clear"; type "zz"
→ 4. type "zz" — ok (3097ms) / All 4 step(s) passed     ← 何も入っていない
→ 直後に 8199 の LISTEN が消える(ランナー終了)
```

MCP の `ft_launch` → 焦点なしの `ft_type "x"` も `Typed: "x" (warning: nothing has input focus…)` を返した約5秒後に同じく死ぬ
(iOS 担当は 3/3。入力欄でない要素の ref を渡した `ft_type` も同じ)。
**対照**: 同じ DSL を in-app エンジン(手元 -08・CMP の SUT)で撃つと
`409: no focused input field — tap the target field first` で**正しく失敗**する。

**素性**(確認): `Runner/FleetestRunnerUITests/BridgeRouter.swift:597-602` の guard の else が、ref 無し・入力欄でない対象のとき
`app.typeText(req.text)` をそのまま撃つ。焦点が無いと XCTest が
`Failed to synthesize event: Neither element nor any descendant has keyboard focus` で失敗し、テストが Tear Down してランナーが終わる
(`.fleetest/bridge-8199.log`。`continueAfterFailure = true` はこの失敗には効かない)。

**害**: run の途中なら、そのステップは緑・以後は「ブリッジに届かない」でワーカー離脱に化け、原因(焦点の無い type)が記録に残らない。
**物理 iPhone は in-app が使えず XCUITest だけ**なので、実機ではこの経路しか無い。in-app と XCUITest で同じ DSL の合否が割れる。

## 5. XCUITest エンジン: パスワード欄の打ち直しで伏せ字が文字として入る【大】(I2)

**再現**(8199・SwiftUI の SUT。iOS 担当は UIKit・RN でも 3/3、`ft_type` の ref 経路でも):

```
ft_batch  tap "#btn_input_clear"; type "#field_password" "abc"; tap "#field_single"; type "#field_password" "XY"
→ 4 step とも ok / All 4 step(s) passed(注記は「追記になる」)
木:       password=XY•XY
```

**対照**: 同じ手順を in-app × CMP の SUT で撃つと `password=abcXY`(正常)。Flutter も正常(担当)。

**素性**(担当の読み・一部確認): iOS は再フォーカスした secure 欄の中身を最初の打鍵で消す。ランナーは入力前の値として
**伏せ字 `•••` をそのまま**期待値に使い(`BridgeRouter.swift:604` の `expected = normalizedValue(target) + main`)、
消えた後の値が期待の前方一致になるので `TypeReadback` が `.resend("•XY")` を返して「•」を追送する。

**害**: ログインのパスワード等を**黙って壊したまま緑**にする。物理 iPhone は XCUITest だけなので実機で必ず通る経路。

## 6. リモート回収後の走査が約50秒 — 手元レーンが遊ぶ【大・性能】(F10)

**再現**(時刻付きの単発ディスパッチ。E2E-CMP 1本・M1Max):

```
05:12:16.461 ⏱ Total: 8.2s                        ← リモートの run 本体
05:12:16.904 ==> collecting recordings and run logs
05:13:08.255 ==> relinked 1 report path(s)          ← 51.4 秒
05:13:09.096 ==> remote run finished (exit 0)
```

rsync 自体は 1 秒(`--dry-run --stats` で 1,896 ファイル)。残りは回収**後**の
`collectedScenarioTexts`(当月+前月の scenario JSON を**全件** `String` で読み `contains(stamp)`)で、
`saveHostFacts` と `relinkCollectedReports` が**同じ走査を2回**呼ぶ(`RemoteRunDispatcher.swift:93-94` / `:142-143` / `:573`)。
同じ走査を最適化ビルドで単独に測ると、手元の E2E-CMP は **46,945 ファイル / 342 MB / 23.6 秒**。

**害**: 複数機械の profile は「最後の機械の完了」で終わるので、この 50 秒がそのまま壁時計に乗る。
r1 の各 profile で手元の 8 レーンが `idle=60〜120s`(E2E-CMP/ios-inapp: 手元 72s・リモート 143s、
リモートの run 本体は 55s)。**履歴が増えるほど悪化**する(走査対象は2か月分の全 run)。
受け手の `run --runner` / 複数機械プロファイルも同じ経路(cliRun / apiRun の両方)。

**直す向き**: 走査を今回回収した run に限る(stamp を含む run はこのディスパッチの runID だけ。
rsync の `--itemize-changes` か、リモート側で runID を出力して受ける)。少なくとも2回を1回に。

## 7. 中断した複数機械 run がリモートの dispatch.lock を残す【大】(F12)

**再現**: `fleetest run --project E2E-CMP --profile ios-inapp`(3機械)を、M1Max の worker が join して
8 秒後にプロセスグループへ SIGINT(端末の Ctrl-C と同じ届き方)。1 秒で終了し、手元・リモートとも
プロセスは残らなかった。ところが**リモート2機の `<base>/.fleetest/dispatch.lock`(mkdir 型)が残り**、
保持者の pid(74216 / 74217 = 手元の死んだディスパッチ)のまま。以後のディスパッチは全て
`another dispatch is already running on this remote host (started by wave1008 (from pc2.local, pid 74216) …)`
で拒否され、**2周目の E2E のリモート分が全滅**(各 3〜10 秒で exit 1)。モニターの占有表示もこのロックを読む。

**交絡**: この実験は出力を時刻付けの perl へパイプしていた(同じグループなので perl も SIGINT で死に、
fleetest が SIGPIPE で巻き戻しの前に死んだ可能性がある)。docs/remote-runner.md §16.1 は
「端末の Ctrl-C はグループ全体に届くので子も自力で止まる」と書いている。**パイプ無し(素の端末の Ctrl-C)でのリモートの対照は未実施**
(ロックの解除 `remote unlock` が自動承認で止められ、以後リモートに出せなかった)。
ただし `fleetest run … | tee log` の Ctrl-C は同じ形なので、交絡を除いても利用者が踏む形ではある。

**コードで確認した経路**: ロックを外すのはリモートではなく**手元のディスパッチ側の `defer { releaseDispatchLock }`**
(`RemoteRunDispatcher.swift:57-58` / `:114-115`。ssh でロックのディレクトリを消す)。fleetest 本体は stdout/stderr の
SIGPIPE を無視していない(`signal(SIGPIPE, SIG_IGN)` / `F_SETNOSIGPIPE` は配信ヘルパーと `Shell` の子への書き込みにだけある)ので、
**出力の読み手が先に死ぬと、中断後の巻き戻しでログを1行書いた瞬間に SIGPIPE で落ち、`defer` に届かない**。
複数機械の親子(機械ごとの子の出力を親が読む)でも、親が先に終わると子が同じ形で落ちる。

**SIGPIPE の経路は手元で直接再現した**: `fleetest run … --set record=true 2>&1 | head -45`(読み手が途中で抜ける)で
fleetest は **rc=141(SIGPIPE)で即死**し、`simctl recordVideo` が7本、PPID=1 の孤児として残った(§3 と同じ残骸)。
= 交絡とみた要因は、それ自体が「fleetest は出力の読み手が死ぬと巻き戻し無しで死ぬ」という同じ欠陥の別の入口。
`fleetest run … | tee run.log` を Ctrl-C する使い方(CI のログ取りでも普通)で、手元なら録画の孤児、リモートなら dispatch.lock の残存になる。

**条件によらず残る点**: 次のディスパッチは「保持者 = この機械・その pid は死んでいる」を知り得るのに
自動では回収しない(`remote unlock` の手作業が要る)。

## 8. 手元の同じ台へ2つの run を同時に当てても無警告【中〜大】(F29)

**再現**: `fleetest run --project E2E-Android --profile android --runner local` と

**素性**: リモートには dispatch.lock(fail fast)があるのに、手元には同じ台の二重使用を見る門が無い。
`run-<key>.lease`(pid + mtime)は既にあり、他の生きた pid が握っている台は検出できる。
保守者向けには docs/verification.md「E2E を同時に2つ走らせない」の運用注意があるだけで、受け手(2つのウィンドウ・CI と手元の併走)には届かない。

- **判定できる場面(ユーザー確認: デバッグビルドのファイルがある前提でよい)**: 材料は .app と .ipa(`AppPackageReader`。

  リソースを使わないアプリには無いので補助に降格)、それ以外 = uikit。同じ読み口で appName の警告と
  `appPathPhysical` の警告も .ipa を読む
- **判定できない場面を最大限埋める**: 判定できたら **bundle ID ごとの台帳**(`AppFrameworkLedger` =

### 19.10 「木からフレームワークを推定できないか」の計測(翌 2:50〜3:40・未コミット)

ユーザーの問い: 他人のアプリ(材料も台帳も無い)でも、取得した木からヒューリスティックに判定できないか。
答え: **採れない**。根拠は3つの計測。

- **同じ画面の XCUITest の木を4フレームワークで比較**(E2E のスクロール画面・-01・8123): CMP だけ「根に画面全体の
  `scrollView`、リストの容器 `#list_rows` / `#carousel_tags` は scroll 印の無い `other`」。Flutter・RN・SwiftUI は
  容器そのものが `scrollView` / `table`(Flutter は a11y 用の本物の UIScrollView を出す)
- **その署名を実アプリの固定コーパスに当てる**(`Tests/Fixtures/RealAppSnapshots/` の iOS 22 画面): 「画面全体の
  scrollView + 内側にスクロール型の容器が無い」に **UIKit の 10 画面が一致**(Safari の 7 画面・設定・写真・地図の経路)。
  誤検知は「UIKit の行を空打ちで押す」側 = 取り消せない側に倒れる。Flutter は木で UIKit と区別できない
- **空打ちが今も要るか**(前提の確認。`FT_EMPTY_DRAG=off` の殺しスイッチを本線に足して計測): 単発の MCP witness
  (`scrollTo '#row_40'` → tap ×3、空打ち無し)は CMP・Flutter とも通ったが、**E2E-CMP / ios-xcuitest を3回回すと
  `S0080`(`selected=-`・注記 swallowed)と横向きの `S0020` が 3/3 で赤、E2E-Flutter は 2 回中 1 回 `S0080` が赤**。
  空打ちは今も要る(2026-08-03 の ghost の修正で不要になった訳ではない)。**空打ちの要否は E2E の規模で判定する**
- **要素の型の名前でも不可**(ユーザーの問い): UIKit のクラス由来の型(`cell` / `table` / `collectionView` / `navigationBar` /
  `tabBar` / `toolbar` / `webView` / `searchField` / `switch` …)は CMP・Flutter・RN の木に1つも出ない(CMP のコーパス
  5 画面も 0)ので「あれば UIKit = 撃たない」は正しいが、既定と同じで何も増えない。逆(無ければ Compose / Flutter)は
  **RN の木が Compose / Flutter と同じ顔ぶれ**(`button` / `staticText` / `scrollView` だけ)で、しかも UIKit の実アプリ
  22 画面中 4 画面(Safari の Yahoo・地図の乗換案内 ×2・プロフィール)もクラス由来の型を持たない = 撃つ側の誤検知。
  XCUITest はビューのクラス名を出さない(型は UIKit のクラスか a11y の trait から決まる)ので、これ以上の材料は木に無い
- **起動時やその後の木の観測でも不可**(ユーザーの問い。XCUITest で撮り直した 23 枚 = 4 SUT × 4 状態(起動直後・スクロール画面・
  1回送った後・キーボード表示中)+ 実アプリ 6 本(設定・地図・Safari・写真・メッセージ・カレンダー)+ 設定を送った後):
  ①根の形 —— CMP は根が全画面の `scrollView` だが、実アプリ 6 本も全部が全画面のスクロール型を持つ /
  ②Flutter と RN は根の形・型の顔ぶれ・属性の付き方(id / label / value / checked)まで**同じ** —— 片方は撃ち、片方は撃ってはいけない /
  ③属性のパターン —— CMP はボタンの下に同じラベルの `staticText` を別要素で出し、入力欄は `textView` だが、地図(UIKit)も同じ形 /
  ④画面外の要素・同じ frame の積み重なり・1px の要素 —— 起動時はどれも 0。送った後は SwiftUI が 31 件積むが CMP は 0(逆) /
  ⑤`scrollable` の印 —— CMP は根の1つだけ・内側のリストには付かないが、設定・Safari・写真・カレンダーも「全画面の1つだけ」/
  ⑥depth —— アプリごとに違い、フレームワークでは分かれない。木にビューのクラス名は載らないので観測で決められる状態は無い
- **XCTest の非公開属性にはクラス名がある(翌 3:40〜4:30 に実測)**: `XCElementSnapshot.additionalAttributes`(非公開の辞書)の
  **属性番号 5004** が要素のクラス名。反射で洗った(wt0 のランナーに `/probe-attrs` = プロパティ・メソッド・KVC・AX クライアントの総当たり、
  `/probe-tree` = 根の `app.snapshot()` から `children` を辿る形)。公開 API(`XCUIElementSnapshot`)には無く、`XCAXClient_iOS` の
  属性照会でも取れなかった(`sharedClient` は無い)。**根から辿るだけで全要素に付き、追加の往復はゼロ**(walk 0 ms。missing 0)
- **その値はフレームワークをそのまま名乗らないが、必要な分け方にはなる**(予備シミュレータ `iPhone 17 Pro(iOS 27.0)`・XCUITest):

  | アプリ | button / staticText のクラス名 | 全要素のうち `UIAccessibilityElement` |
  |---|---|---|
  | CMP(E2E-CMP) | `UIAccessibilityElement` 14/14・16/16 | 34/44 |
  | Flutter(E2E-Flutter) | `UIAccessibilityElement` 14/14 | 25/31 |
  | React Native(E2E-RN) | `UIView` 14/14 | 2/40 |
  | SwiftUI(E2E-iOS) | `NSObject` 16/16 | 0/30 |
  | 設定(UIKit + SwiftUI) | `NSObject` / `UIDictationSearchButton` / `UICollectionViewListCell` 系 | 0/166 |
  | 地図 | `UIButton` / `NSObject` / `_UIGrabber` | 6/111 |
  | Safari / メッセージ / 写真 / カレンダー(各 60 件) | UIKit のクラス名 | 0 / 2 / 0 / 0 |

  Compose と Flutter は a11y をビューでなく `UIAccessibilityElement`(自前描画の上に置く要素)で出す。RN は `UIView`、SwiftUI は
  `NSObject`、UIKit は本物のクラス名。**空打ちが要る2つ(Compose / Flutter)だけが `UIAccessibilityElement`** で、他は違う。
  UIKit の実アプリにも `UIAccessibilityElement` は出る(地図 6・メッセージ 2)ので、判定は**アプリ全体ではなく「スクロール容器の中の
  対象(と兄弟)のクラス名」**で行う必要がある
- **採るなら**: ブリッジが要素ごとに `axClass`(または容器ごとの要約)を snapshot に載せ(ワイヤ変更 = 版を上げる。P6 / A1 と同じ回に)、
  ホストは「探索で掴んだ要素とその容器の対話要素が `UIAccessibilityElement` なら空打ち」を、材料 → 台帳 → **木のクラス名** →
  不明の順の第3段に置く。非公開属性(番号 5004)は Xcode の版で変わりうるので、**取れなければ不明 = 撃たない**へ落とし、
  固定コーパス(4 SUT + 実アプリ)の等号テストで版の変化を検出する
- 結論(材料と台帳の形は据え置き): 判定は材料(.app / .ipa)と台帳。木のクラス名(5004)を第3段として実装した(§19.11)。
