# 保守者向けの事故台帳

CLAUDE.md は**規則だけ**を持つ。ここは、その規則が**なぜその形なのか**を思い出すための台帳
——「一度実際に壊した」記録と、判断の経緯を置く。

**読む場面は2つだけ**:

1. CLAUDE.md の規則を**緩めたく / 消したく**なったとき(たいていここに、緩めた結果が書いてある)
2. 同じ型の設計判断を新しい場所でするとき(「同型」で辿れるようにしてある)

日常の作業でここを読む必要は無い。CLAUDE.md の該当行から `→ maintainer-notes.md §N` で来る。

**subsystem に属する設計・計測は各 docs が正典**(ここには置かない):
docs/design.md(設計)/ docs/verification.md(検証の規律)/ docs/performance-tuning.md(性能)/
docs/remote-runner.md(リモート)/ docs/mcp-audit-rounds.md(MCP 監査の台帳)。

## 1. 受け手フロー(install.sh / update.sh)

### 1.1 実行中のシェルスクリプトを pull で差し替えても、古い内容が最後まで走る

`bash` は開いた fd で読み進めるので、git が rename で置換しても**開いた fd は旧 inode を指し続ける**
(実験で確認)。このため pull 直後に自分自身を再 exec しないと、**pull で入った新しいステップは
その回に1つも実行されない**。次回は update.sh が up-to-date で即終了するので、
**永久に実行されない**。

実害: ステップ7.6(受け手の CLAUDE.md へ入口ブロックを置く)が、版だけ上がって一度も走らなかった。

`update.sh` にも同じ再 exec がある。一度は「委譲が中心だから影響は小さい」と判断して入れずに
残したが、**直後に利用者向けの修正(project sync を外部構成でも走らせる)が update.sh 側へ入り、
受け手が2回更新しないと直らない状態を作った**。2周目に `FT_UPDATE_REEXEC` で up-to-date の
早期終了を通さないのは、直前に pull しているので必ず up-to-date になり、素通しすると
project sync とプラグイン更新が飛ぶため。

→ 規則: CLAUDE.md「受け手の一括導入」「受け手の更新」

### 1.2 マーカー置換を素朴に書くと、2回目に利用者の記述を巻き込んで消す

`end` マーカーだけ壊れた CLAUDE.md に対して「最初の begin 〜 最初の end」を置換する実装だと、
**1回目に2つ目のブロックを追記 → 2回目に間に挟まれた利用者の記述ごと削除**する。
2026-08-06 に実際にデータを消して確認した。

いまは begin/end がちょうど1組でなければ1バイトも書かない(片方だけ・2組以上・逆順は
`damaged` で warn 止まり)。`installClaudeMdBlock.test.mjs` が install.sh から python を
抜き出して実行し、この3形を守る。

→ 規則: CLAUDE.md「受け手の一括導入」

### 1.3 クローンが git 管理しているファイルへ書くと、次の更新が永久に止まる

clone 構成では受け手の CLAUDE.md は**クローン自身の追跡ファイル**で、書くとツリーが dirty に
なり、2回目以降の更新が pull ガードで必ず止まる。`git reset --hard` で戻しても次の更新が
同じブロックを書くので堂々巡りになる。2026-08-07 に自己破壊を実再現した。

判定は**レイアウトではなく `git ls-files --error-unmatch` で追跡の有無**を見る
(レイアウトで判定すると、新しい構成が増えるたびに条件が増える)。

**同型**: `packageLockSync`(npm install が lock を書き換えてクローンが dirty になる)。
**一般化**: 受け手のフローに「クローンの中を書く」工程を足すときは必ず追跡を見る。

→ 規則: CLAUDE.md「受け手の一括導入」

### 1.4 出力量と無音は、どちらも承認とフローを壊す

- 生ログを画面へ出すと(54KB)エージェント側で切られ、結果を探す `grep` が承認を増やす。
- 逆に数分の無音は人に「止まった」と誤解され、中断される。

だから**画面は各ステップ1行(逐次)+ 集計だけ・生ログはファイルへ**。逐次表示は人のためのもの。

→ 規則: CLAUDE.md「受け手の一括導入」

## 2. エージェント連携・配布

### 2.1 Codex 対応をインストーラから撤去した理由(2026-08-27)

面倒を見ようとすると、規約位置・プラグインのサブコマンド名・版照合・設定書式が全部その
エージェント固有の分岐になり、**Swift・install.sh・install-skill.sh・update.sh の4箇所へ
手で写す**ことになる。中核はどれもエージェント固有ではない(機械作業 = インストーラ /
`ft_*` = 標準の stdio MCP サーバ / runbook = ツール中立の markdown)ので、案内を
docs/user-docs/tools/other_agents に集約する形に寄せた。経緯と表は docs/design.md §15。

受け手のグローバル設定へ1バイトも書かないのは、そこがセキュリティ境界であることに加え、
**TOML は同じテーブルの重複でファイル全体が無効になる**ため。

### 2.2 Codex のサンドボックスはシェルだけを縛る(2026-08-27 実測)

**MCP サーバはサンドボックスの外**で動くので `ft_*` は既定設定のまま全部動く。通らないのは
シェル経由の導入・更新だけで、原因は権限ではなく **①SwiftPM が `sandbox-exec` を入れ子に使う
(`swift build` が起動できない)②`simctl` が CoreSimulatorService へ届かない**。

`network_access` / `writable_roots` では直らない。以前 install.sh のステップ7.7 が
これらを根拠に false green を出していた。

### 2.3 リポジトリのルートに置いたものはプラグインに載って配られる

プラグイン root = repo ルートなので、ルートの規約ファイルは**そのままプラグインで配布される**。

- 同梱していた `.mcp.json` は `$PWD/Scripts/mcp-server.sh` 依存で、クローンの外でエージェントを
  起動した受け手の MCP が**必ず落ちていた**(`claude plugin details` に `MCP servers (1)`)。
- 同型: ルートの `skills → .claude/skills` リンク。Claude Code は `plugin.json` の明示パスと
  **既定の `skills/` の両方を読む(置換ではなく加算)**ため、**6本が12本として登録**され、
  常時コストが倍(~1,270 → ~2,537 tok)になっていた。

**一般化**: ルートに何か置くときは「プラグインに載ってよいか」を必ず問う。

→ 規則: CLAUDE.md「MCP サーバの起動口」

### 2.4 正典をシンボリックリンクの側へ移さない

raw.githubusercontent はリンクを**本文でなくリンク先の文字列**として返すので、
`install-skill.sh` の curl が SKILL.md ではなく1行のパスを掴む。

## 3. リモート実行・監視

### 3.1 型検査の効かない境界は、片側だけ改名すると黙って壊れる

2026-08-26 の用語統一(host / machine)で `api monitor` の `machineHost`・`api devices-up` の
`host`・`api remote-compat` の `hosts[].name` を改名し ProtocolVersion 9 にした。
同時配布なので旧キーは読まない設計にしたところ、**webview だけ旧キーのまま残り**、
実行プロファイルのリモート参照が `machine: "local"` へ書き換わった。

→ 規則: 型検査の効かない webview 境界は往復テストで縛る(CLAUDE.md「用語」)

### 3.2 親を殺しても子は死なない

ssh 越しの子を spawn する経路では、親を殺しても ssh が生き残ってリモートが走り続け、
`dispatch.lock` も残る(2026-08-18 実測)。SIGKILL へのエスカレートを自分の子に掛けると、
ロック解放と終了スクリプトを飛ばすので **ssh にだけ**掛ける。

**シグナルソースは1プロセスに1組**(2026-08-24・受け手報告): relay ごとに立てて `stop()` で
SIG_DFL を戻すと、並行する子のうち**先に終わったものの stop() が残りの横取りまで解き**、
`kill -INT` で親だけ死ぬ。

### 3.3 実績の回収と後処理の順序

facts の machine 採取は relink より前。relink が reportPath を書き換えると stamp がファイルから
消え、stamp 走査が空振りする(実ディスパッチで machine 欠落を確認)。

**一般化**: 回収後の後処理を足すときは、後段の走査が stamp に依存していないかを見る。

### 3.4 macOS の openrsync では dir-merge が `--delete` から受け側を守らない

`rsync -F`(dir-merge)を使うとランナー機の台帳が消える(実験で確認)。除外は
`.fleetest-transfer-ignore` を `--exclude` 相当で明示的に読む形にしてある。

### 3.5 ssh 越しのコマンドにグロブを書かない(相手は zsh。マッチ無しは「文字列のまま」にならない)

`ssh <host> '<コマンド>'` を解釈するのは**相手のログインシェル**で、macOS の既定は zsh。
sh/bash と違い、**マッチしないグロブはエラーになる**(`no matches found`)。しかも壊れ方が
2通りあり、どちらも 2026-08-31 に実機で確認した:

| 形 | zsh の挙動 |
|---|---|
| `rm -rf <nomatch>` (単純コマンド) | そのコマンドだけ失敗(exit 1)。**後続の文は動く** |
| `for w in <nomatch>; do …; done` | **シェルごと終了**(exit 1)。**後続の文が1つも動かない** |

前者は「録画が無い run のたびに `warning: failed to delete …`」、後者は「まだ誰も setup して
いないランナーで、旧 `work` の片付けまで丸ごと落ちる」という形で出る。**2文に分けても直らない**
(後者はシェル自体が終わる)。

→ 規則: **リモートで回す一覧は `find … 2>/dev/null` で作る**(1件も無ければ空の出力になるだけ)。
`RemoteHooksReap.commandAcrossIssuers` と `RemoteArtifactCollection.deleteRecordingsCommand` が
その形。パスに空白が入らないこと(`validateBase` / `validateIssuerKey`)が語分割の前提。

### 3.6 「消す」コマンドは階層を数え間違えても静かに成功する

回収済み録画の削除を `results/runs/*/recordings` と書いたが、実際の置き場は
`results/runs/<YYYY-MM>/<runID>/recordings`(`RunResultsStore.runDir` が月の階層を挟む)。
**1件も消えないのに成功**するので、テストが文字列を固定しているだけだと気付けない
(2026-08-31 のレビューで発見。単体テストは誤った期待値ごと緑だった)。

→ 規則: パスの深さに依存する削除・走査は、**実データのあるランナーで `-print` して1件以上
当たることを確かめる**(実際に当ててから `rm` へ変える)。

### 3.7 ツールチェーンの照合は「何が境界を越えるか」を数えてから緩める

適合チェックは Xcode の指紋が1バイトでも違えば全ディスパッチを止めていた。由来は
「『片方だけ変えない』規律をマシン間に広げる」という一般原則からの流用(§7 の表にも
「既存適合チェック流用」と書いてある)で、**toolchain の差で壊れた実害の記録は1件も無かった**。

実際に境界を越えるものを数えると: 転送されるのは `TestProjects/<project>/` のソースだけで、
`fleetest` 本体・XCUITest ランナー・in-app dylib は**ランナー機が自分の Xcode でビルドする**。
機械的な結合は `appPath` のアプリが手元ビルドのままワークスペース経由で入る1点だけで、
止める理由は「結果の比較可能性」に縮む —— これは **macOS の混在で既に受け入れている**性質
(OCR・FM は OS 付属)と同じ強さしかない。そこでベータ seed の違い(製品版が同じで build だけ違う)
だけを advisory に落とした(2026-09-21 ユーザー決定)。

→ 規則: 「揃っていないと止める」gate を緩めるか迷ったら、**何が実際に境界を越えるかを列挙する**。
列挙できない止め方は、規律の見かけをした思考停止になっている。

### 3.8 Xcode 自動選択で出たもの

**(a) 既定値つきの `let` は memberwise init から欄ごと落ちる。** `HostRow` に
`let xcodeSelectionRefusalReason: String? = nil` を足したところ、呼び出し側が
`extra argument` で落ちた(Swift は既定値を持つ `let` を memberwise init の引数にしない)。
**サブエージェントはビルドを打たない規律**なので、この型は必ずメインの初回ビルドで初めて出る。
→ 規則: 既定値を持たせたい格納プロパティは `var` にする。

**(b) 拒否の文言を1つにまとめると対処が逆になる。** 「一致する Xcode が0個」と「同じ製品版が
複数あって選べない」を同じ文にしていたため、複数のときにも `none of the … matches` と出ていた。
前者の対処は**その Xcode を入れる**、後者は **pin する**で**逆**なので、まとめた文言は必ず
どちらかを誤誘導する。文言を分け、テストで remedy の語(`install the matching Xcode` /
`pin one for this machine`)を両方向に固定した。
→ 規則: 拒否・失敗の文言は**原因ごとに分ける**。分けた根拠はテストに残す(文言は
pass/fail では守れない。§4.14 と同じ)。

**(d) 一致を見るだけの欄は、全機が等しく「無い」ときに緑になる。** Xcode 27.2 beta を 4 機に入れて
自動選択を実機で確かめた際、TOOLCHAIN は ✅ なのに RUNTIME が `✅ iOS 27.2: none` になった ——
**ランタイムは Xcode に付いてこない**(CoreSimulator のランタイムは機械共有)ので、新しい Xcode を
選んだ直後は「その SDK のランタイムがどこにも無い」が普通に起きる。手元と突き合わせる判定では、
全機が等しく持っていないときに一致 = 緑になり、その iOS の台を要求した run が供給で落ちるまで
誰も気づかない。→ 規則: **一致を見る欄でも「そもそも使えない値」は一致より先に判定する**
(ユーザー決定 2026-09-21 で `none` は常に ⚠️。exit code は変えない)。
**この形は単体テストでは出ない** —— 実機械で1回動かして初めて見えた(CLAUDE.md
「単体テストが緑でも実データで1回動かすまで信用しない」)。

**(c)** 選択の解決は**ディスパッチと `remote status` / `api remote-compat` で同じものを1回だけ**
通す。片方が ambient に戻ると**表は ✅ のままディスパッチだけ止まる**(逆も同じ)。
型では守れない文字列合成なので `RemoteDeveloperDirWiringTests` がソース走査で両方を固定する。

**(e) 鮮度の門は「建てるとき」にしか無く、生きたブリッジは素通りしていた。** 27.2 beta で建てた
ブリッジが生きたまま 27.0 の run に**再利用**され、`build-for-testing` が1度も走らなかった
(実機で観測。run は緑だったので**気づく手掛かりが無い**)。この指紋はそもそも「旧 Xcode の
ランナーを新ランタイムに載せると実行中に `Application is not running` で落ちる」を防ぐために
入っており、**ブリッジは run を跨いで生かす設計**なので、Xcode を替えた後の数 run は必ずここを通る。
→ 規則: **鮮度の門を足すときは「作る経路」と「再利用する経路」の両方に置く**。再利用側は
起動時点の値を控えて比べる(`.fleetest/bridge-<port>.toolchain`)—— **成果物の指紋と比べてはいけない**
(成果物は後から独立に建て直されるので、ディスクとプロセスの食い違いを検出できない)。

**(f) 「呼んでいること」を固定しても、枝が空なら緑のまま。** (e) の門に付けた走査テストは
`decide` を呼ぶことと引数は見ていたが、**`.restart` の枝が実際に止めて建て直すか**は誰も見て
いなかった —— 再起動の呼び出しを丸ごと消す変異が**生き残った**。
→ 規則: 配線の走査テストは**呼び出しの有無ではなく、その枝が仕事をしているか**まで見る
(この件では枝の中に `stopStalePort` と `executeBridge` があること)。

## 4. ビルド・検証

### 4.1 E2E の最中に本線をビルドすると、run が「テストの失敗」に化ける

同じ `.build` を共有するので、**実行中の `fleetest` バイナリが差し替わってプロセスが SIGKILL
される**(`Killed: 9`)。2026-08-15 にフル E2E の最中に単体テストを回したところ、3プロファイルが
同時刻の連番 PID で落ち、**テストの失敗に見える形で赤くなった**(実際は1本も走っていない)。

見分け方: `Scripts/e2e.sh: line NNN: <pid> Killed: 9` と、シナリオ0本での即死。
**待つ間に手を動かしたくなる場面ほど踏む**。

### 4.2 長時間ジョブを `pgrep` で待つと、待機どうしが相互に「実行中」と見る

`pgrep -f <文字列>` は自分自身こそ除外するが、**同じ文字列を含む他のシェルは拾う** ——
待機コマンド自身のコマンドラインにその文字列が載るので、待機を2つ以上同時に走らせると
全員が止まらない。2026-08-09 に E2E の待機が3つ残り、次のスイートが1本も起動しないまま
「実行中」と表示され続けた(実験で機構を確認済み)。

→ 規則: ジョブ自身が出す成果物で待つ(CLAUDE.md「ビルド・検証」)

### 4.3 jsdom の閉じ忘れ1本でスイート全体が止まる

`pretendToBeVisual` の rAF と `main.js` の `setInterval` が残るとプロセスが終了せず、
`node --test` はファイル単位の子プロセスの終了を待つ。2026-08-17 に**10本中1本の漏れで
`npm test` が終わらなくなった**(個々のテストは1〜2秒で、遅いテストは1つも無かった)。

二重に塞いである: `jsdomTeardown.test.mjs` がソース走査で落とし(**コメント中の
`window.close()` を実装と数えない** —— 規律はコメントで説明されているので素の一致だと
素通しする)、`npm test` は `--test-force-exit` を付けてある。

**同型**: `argumentHelpLiteral.test.mjs` —— `ArgumentHelp` は文字列リテラルからしか作れないので
`help: "…" + "…"` はコンパイルが通らない(4回踏んだ)。
**一般化**: 「コンパイルで落ちる誤り」や「テストが終わらない」型は、`swift build` / `npm test` を
1回払うまで気付けないので、ソース走査で秒未満に落とす。

### 4.4 版を上げ忘れると、稼働中の旧ブリッジが再利用されて変更が反映されないまま緑になる

実害2回。**Android の版上げは revert しても端末側が戻らない**(2026-08-14):
Android は versionCode の引き下げインストールを拒否するので、上げた版を配った後に版を戻すと
ホストは古い版を入れ直せず、**全台が「no response to status」で応答不能**になる。
フリート8台が全滅し、`adb uninstall com.example.ftbridge` を全台に打つまで復旧しない
(その後も数台が凍結し、落ち着くまで2周かかった)。

→ **試行的な変更ほどブリッジに入れない**。ホスト側で完結できないかを先に問う
(この件の本修正は結局ホストだけで足りた)。

### 4.4.1 フレームワーク差の退行は SUT を跨がないと出ない

探索終端の空打ちドラッグは **CMP では無害・SwiftUI ではタブバーが反応**し、E2E-iOS を回すまで
5/5 の回帰に気付けなかった。

→ 規則: スナップショット/型写像と操作合成を触ったら SUT を絞らず全部回す

### 4.5 回さなかったエンジンは、緑の E2E からは見えない

in-app / xcuitest 両方のスナップショット生成を変えた回の E2E **254 本が全部 engine=xcuitest**
で、in-app 側は1度も動かないまま緑になった。いまは `BridgeSourceSet` の digest を

### 4.7 「読む回数を減らす」最適化は、その読みが担っている砦を先に列挙する

### 4.8 「差が出ない」ときは仮説より先に実験系を疑う

差が出ないことは、**変更が無効だったこと**と**実験が無効だったこと**を区別しない。
実行の実体は `fleetest` ではなく **`fleetest-scenarios-<project>` サブプロセス**なので、
A/B で `fleetest` を差し替えても base と fix が同一コードを走る(2026-08-03 に性能の A/B と
修正案2件を取り違えた)。詳細は docs/verification.md。

### 4.9 並列テストはプロセスを分けるので、ホスト共有資源に触るテストは自分で隔離する

既定のパスを直接見に行くと、無関係なテストの後始末と競合して落ちる(2026-08-10 に `FMBreaker`
で実際に発生)。状態ファイルがホスト単位なのは仕様なので、**テスト側が差し替え口で
プロセスごとの一時パスへ逃がす**。

### 4.10 検知は「出ない」ことを設計の根拠にしない

- 自前 SUT の全数掃討で誤検知0でも、**実アプリでは出る**(2026-08-06 に5形、2026-08-07 に3形。
  どちらも自前 SUT は0件)。木が要る検知は dry-run では当てられない。
- 逆向きも成り立つ: **固定コーパスで0件も自前 SUT の実画面を代表しない**。木の欠落検知
  (`TreeCoverage`)は 37 枚のコーパスで誤検知0だったのに、**フル E2E では 5 SUT すべての
  緑の run で毎回発火**した(真陽性 —— `webview.html` は `aria-hidden` の見出しを持つ、
  この検知の offline witness そのもの)。

**実 web ページの幾何判定**も同じ6枚で誤検知が出た(折り返す inline テキストの矩形が重なる形。
件数と内訳は docs/verification.md が正典 —— CLAUDE.md 側の数字は食い違っていたので落とした)。

→ 規則: 「出ない」を根拠にするなら、コーパスとデバイス実行の**両方**で確かめる。とくに注記を
毎ステップの経路へ配線するときは、発火率がそのまま出力とレポートの雑音になる。

### 4.11 陰性(誤検知0)の確認は「常に false を返す検出器」と区別できない

2026-08-11 の凍結カウンタは「10台すべてに frozen が乗り誤検知0」を根拠にマージされ、
**恒久 false のまま入った**(抑制ガードが観測より手前にあり、実運用の全デバイスが判定対象から
外れていた)。だから意図的に起こせない事象には注入口(`FrozenInjection` /
`FT_FAKE_FROZEN_KEYS`)を用意し、注入は**観測と公表の経路だけ**を通す。

**同型の一般形**: 「観測」と「配信(表示の最適化)」を同じループに書かない。配信中のタイルの
フレーム生成を止める `suppressFrames` が**観測より手前**にあったため、実運用の全デバイスが
判定対象から外れていた。

### 4.12 変異が生き残ったときに疑う順序

1. フィルタが狙ったクラスに当たっているか(`--filter` は**ファイル名ではなくクラス名**。
   `--filter TapTargetAdvisoryTests` を打ったのに、同じファイルの別クラス
   `TapAdvisoryKindPriorityTests` が1本も走っていなかった。同型を2回踏んでいる)
2. **先に落ちたテストがプロセスごと死んで後続を隠していないか**(ログに `Fatal error` /
   `signal code`。2026-08-18: テスト内の強制アンラップが変異でクラッシュし、同プロセスの
   残り全テストが走らないまま「生き残り」に見えた)。
   → **テストでは失敗アサーション後に `!` で触らない** —— guard + XCTFail で止める
3. **変異式が本当に挙動を変えているか**(既定引数を足すだけ・使われない関数を足すだけは
   何も壊していない)

**逆向き(「殺せた」の誤認)も同じだけ起きる**: 変異がコンパイルエラーでも `swift test` は exit 1 を返す。
2026-09-19 の existImage で、存在しない enum の case へ差し替えた変異が `Build failed` で落ち、exit code だけ見て
「検出した」と数えかけた。**変異の判定は exit code でなく、狙ったテスト名の失敗行で取る**
(`error: -[<Class> <test>]` が出ているか。`Build failed` なら変異を書き直す)。
4. そのうえで初めてテストの内容

### 4.13 テストが production の関数を実際に通っているか

掃討ハーネスが `!e.enabled` を自前で書いていたため、`RefGuard.disabledWarning` を壊しても
落ちなかった。検出できない変異が出たらテストを境界へ寄せる(要素数を増やす・既定値でなく
限界値で呼ぶ)。

### 4.13.1 テストが production の代わりに前処理をしていないか

`XCTAssertEqual(plan(target, normalize(actual)), .done)` のようにアサーション側で production と
同じ前処理を掛けると、production の前処理を外しても落ちない。渡すのは**生の入力**だけにする。

**併せて**: 壊れ方が入力で割れるものは、割れた先ごとに入力を用意する。不可視文字の混入は
**途中なら `.unverifiable` で黙って受理・末尾なら `.deleteExcess` で打ち直しループ→失敗**と
別々に壊れ、途中形の入力だけでは正規化を外した変異を1つも殺せない。

### 4.14 陽性対照は pass/fail でなく出力の文言まで読む

主張を含む文言(「天井でも足りない」等)は、**主張が偽になる周回**が設計に残っていても
単体テストでは緑のままになる。2026-08-15 に実際に嘘を出し、latch へ設計変更した。

## 5. 同じ判定を2箇所に持つと、同じ画面で違うことを言う

**共有するのは「判定」であって「文言」ではない**(2026-08-15)。文言まで一本化しようとすると
既存の応答文字列を壊して MCP のテストと `NoteBudgetTests` に当たる。正しい形は
**①判定・順序・当たり判定を FTCore に1つ ②文言は呼び手ごとに持つ**。

食い違っていた実例:

| 事実 | 中核(FTCore) | 呼び手 | 起きていたこと |
|---|---|---|---|
| タップ前警告の連鎖 | `TapTargetGeometry.advisoryKind` | `occlusionAdvisory`(DSL)/ `RefGuard.overlapWarning`(MCP) | 同じ優先順を2箇所に手で書いており、**2形(ゼロ幅高さ frame・縁の細切れ)が DSL にだけあって MCP のタップ時に出ていなかった**。「同じ優先順」はテストのコメントに書いてあっただけで、照合するテストは1本も無かった |
| 近い候補の選定 | `FTCore.SimilarLabels` | MCP / `StepExecutor.candidateHint` | DSL 側が MCP の捨てた旧版(部分文字列一致・文書順の先着3件)のままで、装飾要素が枠を埋めて実在する操作可能要素を出せない画面があった |
| back の空振り | `FTCore.BackEffect` | 中核文 + 呼び手ごとの advice(MCP は `ft_screenshot` / `ft_scroll_to`、DSL は `back()` を呼び直す) | ― |
| 打ち切りの逃げ道 | `FTCore.SnapshotTruncation.remedy` | MCP / DSL | **DSL だけが「対象に近づくようスクロールする」と勧めていた**。同じ事実に MCP は「スクロールしても戻ってこない」と書いており、同じ画面で逆のことを言っていた |
| 画面外の一致 | `TapTargetGeometry.offscreenScrollGateCentre` | 探索のゲート / 逆走査 `reverseSweep` / `ft_scroll_to` の再照合 / `requireVisible` の幾何 Tier-0(`StepExecutor.occlusionFlip`) | 逆走査と `requireVisible` に述語が無く、iOS の木に残る通り過ぎた要素への `exist(scroll:)` が成功していた(受け手報告) |
| ghost の掴み直し | ― | `RefGuard.ghostWarning`(MCP) | DSL の「掴み直して送り直す」合図を MCP でタップ拒否へ格上げしたら、実アプリで誤検知が5形出て警告へ後退した(docs/design.md §10) |

pressEnter の焦点待ち)。**ただし同じ判定をそのまま強い挙動へ流用しない** —— DSL の
「掴み直して送り直す」合図を MCP でタップ拒否に格上げしたら、実アプリで誤検知が5形出て
警告へ後退した。

→ 規則: CLAUDE.md「判定は MCP と DSL で共有する」/ 新しい検知はまず警告から

## 6. 部分失敗の扱いは両方向に間違える

- **1台の失敗で全体を落とさない**: ブリッジ供給が 10台中8台 ready でも残り2台の期限切れで
  throw し、**Flutter/RN の 51 本が1本も走らなかった**(健全な8台は待機のまま。2026-08-11)。
- **逆向きも守る**: 全レーンが同時に落ちているときにレーンを離脱させない。外部障害で全部離脱 →
  revive 上限 → 未実行が連鎖した(受け手報告。2026-08-24)。連続失敗での離脱は
  「その streak の間に別のレーンが通った」証拠があるときだけ。

→ 一般化: 「N個中1個の失敗を致命にしていないか」と「全部落ちているのに1個ずつ切っていないか」を
供給・インストール・回復の各段で両方見る。

## 12. 実機探索(2026-09-01・iPhone 13)で出た構造的な誤り

### 12.1 比で置いた余白は、窓が低い文脈で縁の内側へ落ちる

横向き(844x390)の SUT で `scrollTo` / `swipe` / `scrollFrame` 指定のすべてが
「nothing moved」で終わった。原因はスワイプの始点で、`BridgeAPI.defaultSwipeMarginRatio`
(0.25)は**窓の高さに対する比**なので 0.75×390 = 292.5pt となり、下部タブバーの上端 290pt の
**2.5pt 内側**に落ちていた。座標ドラッグを 250→60 に変えると同じ画面が 137pt 動く。

比そのものは縦向き(0.75×844 = 633pt、下端から 211pt)で詰めた値で、その文脈では正しい。
**同じ比が、窓が低い文脈では「縁からの絶対距離」を失う**。定数の doc には
「横向きの下部バーは ~y=341 から始まる」という当時の実測が残っていたが、
アイコン+ラベルのタブバー(実測 80pt + セーフエリア 20pt)では 290pt から始まる。

直しは**比に絶対距離の床を足す**(`BridgeAPI.bottomChromeClearance` = 120pt)。
ランナー(木を持たない)と host(木を持つ)の両方が同じ定数を使い、host 側は
`ScrollGeometry.startMarginClearingBottomChrome` で viewport の下端から測る。
キーボードで削られた viewport には掛けない(あちらは既存の分岐が担当)。

**一般化**: 比で置いた余白を別の向き・別の窓サイズへ持ち込むときは、
**その比が縁から何 pt になるか**を両方の文脈で書き出すこと。片方でしか成り立たない値は、
比のままでは移せない。→ CLAUDE.md「片方の文脈で詰めた値を別の文脈へ流用しない」

### 12.2 平坦な木では、depth からの祖先復元は「収めている」を意味しない

同じ探索で、上に貼り付いた検索欄(`textView #field_search` (56,55 326x57))が
**両方向の誤り**を同時に起こしていた。

- **見逃し**: スクロールでその欄の下へ潜った `#btn_wishlist_electronics_4` (332,85 32x32) を
  ref タップすると、警告ゼロで「クリア」ボタンに当たり検索語が消えた。
  `suspectedHiddenUnderChrome` は「中心を覆う相手が**スクロール容器の外**に居ること」を
  条件にしていたが、sticky ヘッダは victim と**同じ root scrollView の中**に居る
  (ヘッダ depth 10 / victim depth 12 / scrollView depth 7)。
  さらに、平坦な木の depth 由来の祖先復元はこの欄を victim の**祖先**にしてしまうので、
  「系譜を除く」書き方でも落ちる。**収めているかは幾何で見る**(`contains`)。
- **誤検知**: 同じ画面で、商品写真の上に正しく描かれているハート4件に
  ⚠️scroll-leftover が付いた。`clippingContainer` の「同じ depth の行を2件以上含む直近の
  浅い候補」規則を、その検索欄が満たしてしまうため(平坦な木では後続の全要素がその欄の
  「子孫」になる)。**行を2件供給していたのは、その欄の下に潜り込んだクランプ残骸そのもの**で、
  誤りが強いほど条件が満たされる形だった。直しは**入力欄を容器候補にしない**。

**一般化**: preorder + depth からの復元は「木の形」であって「描画の包含関係」ではない。
包含・遮蔽・クリップを論じる述語では、復元した親子関係をそのまま根拠にしない。

### 12.3 検知のゲートを「そこに在るもの」で絞ると、消える形ほど外れる

`TreeCoverage.missingPageContent` は「アドレス欄が在ること」をブラウザ判定に使っていた。
モーダル(Safari の「さらに表示」)は**アドレス欄ごと**木を置き換えるので、
ページが画面に見えているのに未代表率 0.523 で黙る = **悪い形ほど検知が外れる**。
根拠を「セッションのアプリが既知のブラウザか」(`holdsWebContent`)へ移すと、
固定コーパス40枚の発火集合は1枚も変わらないままこの形だけを拾える。

**一般化**: 「X が無い」ことを言う検知のゲートに「X の隣にある Y が在ること」を使わない。
Y も一緒に消える壊れ方があると、そこだけ穴になる。

**続き(2026-09-04): 「区別できないから見逃す」を、測ってから覆した。**
上の修正では「ネイティブアプリのモーダルは正当に疎な画面と区別できない」として対象外にし、
根拠に `and-overflow`(未代表率 0.564)を挙げていた。**その根拠が誤りだった** ——
中身を開くと、あの木は地図のメニュー項目18件だけで背後の地図は消えており、**真陽性**。
同じ形が `and-dialog_confirm`(設定の確認ダイアログ。木は6要素だけ)にもあった。

分離できたのは、**閾値をキーボードを除いた viewport で測り直した**から:
素の分布では真陽性の最小 0.411 のすぐ下に `and-form_keyboard` 0.364 が居て重なるが、
あの空き帯の正体はソフトキーボードで、除くと圏外へ落ちる。結果、**健全な最大 0.151 /
真陽性の最小 0.411** と 2.7 倍の差が開いた(閾値 0.35)。生きた画面6枚の実測も 0.000〜0.208。

**一般化**: 「2つの形が区別できない」と判断する前に、**片方だけを説明する既知の要因**
(ここではキーボード)を取り除いて測り直す。取り除くと分布が割れることがある。
また、**見逃す根拠に挙げた画面は中身まで開く** —— 「これは健全」と書いた1枚が、
実は拾うべき真陽性だった。

## 14. PCC(クラウド側のモデル)は1語で届く場所にあった(2026-09-07)

受け手の「FM がネットワークへ送るのでは」という問いから調べ、**3つ誤っていた**。

**①「PCC は設計書の構想止まり」ではなかった。** `Sources` に PCC の文字列が無いことを根拠に
「実装されていない = 到達できない」と答えたが、実際は macOS 27 SDK に
`PrivateCloudComputeLanguageModel` が **public な final class として実在**する
(`availability` / `quotaUsage` / `Error.networkFailure` を自前で持つ)。design.md が
「PCC(32K ctx) を同一 Session API で差替」と書いていたのは**正しい記述**だった。

**②「型が防いでいる」は誤り。** `LanguageModelSession(instructions:)` の `model:` が
`SystemLanguageModel` 型だから PCC は渡せない、と読んだ。実際に書いて確かめると
**typecheck が通った** —— 汎用の `init(model: some LanguageModel, …)` が別に居る。
守っているのは型ではなく**既定値**で、両者はこう違う:

| init | `model:` の既定 |
|---|---|
| `init(model: SystemLanguageModel = .default, …)` | **あり** |
| `init(model: some LanguageModel, …)` | **なし** —— 明示しないと選べない |

`model:` を省く限りオンデバイスに束縛されるが、**1語書けばクラウドへ出る**。

**③「PCC が無効だから安全」も使えなかった。** 切り分けに使おうとしたが、実測でこの Mac の
`PrivateCloudComputeLanguageModel.availability` は **`available`** だった(オンデバイス呼び出しは
907ms で成功)。「今は使えないから安全」という論法は最初から成り立っていない。

**一般化**: **「実装されていない」は「到達できない」ではない。** 自分のソースに無いことは、
1行足せば届く場所に無いことを意味しない。**フレームワーク側に何が生えているかを SDK の
`.swiftinterface` で直接読む** —— 記憶と設計書の要約は、世代が変わると静かに古くなる。
そして**「型が弾く」と言う前に、弾かれるはずのコードを実際に書いてコンパイルする**
(陽性対照。ここでは `ng.swift` が通ったことで見立てが崩れた)。

門は `PrivateCloudComputeProhibitionTests`(ユーザー決定: 完全禁止・利用者向けトグルも置かない)。
**PCC のインスタンスは型名を書かずに得られない**ので、型名の走査1本で経路は閉じる。
`model:` の明示禁止は二重の備え。規則は CLAUDE.md §個別の規律、設計は design.md §1.1 末尾。

## 15. 「録画が空」の警告は予備の台が出していた(2026-09-08)

`record: true` の小さな run で毎回
`⚠️ [recording] 1 device(s) produced no usable recording` が出ていた。

**仮説は外れた。** モニターの Android 配信(`fleetest-androidstream`)が端末上で `screenrecord` を
掴んでおり、Android は同一端末で 1 本しか動かせないので run 側の録画が空になる —— と読んだ。
プロセスを見ると実際に配信が `screenrecord` を持っており、`monitor pause` で 0 本に解放される
ことまで確認できたが、**止めた状態で回しても警告は消えなかった**。

真因は `recordings/index.json` にあった: `clipsAttempted: 1, clipsFailed: 0, sourcesFailed: 1`。
**回したシナリオの録画は成功していて、失敗していたのは「シナリオが1本も来なかった予備の台」**。
`ResolvedProfile.deviceKeepCount` は本数 + 予備1台を残すので、**本数 < 台数の run では予備が
必ず空になる**。`finalize` は `stop()` が nil を返した時点で数えており、アイドル判定
(区間が0件)はその後ろにあったため、予備が毎回1件として計上されていた。

直しは「区間を `stop()` より先に引き、アイドルなら数えない」の1行。この警告の目的は
**録画が全滅した run を録画タブから消さないこと**(2026-08-26 の実害)なので、
実仕事をした台の空ソースは従来どおり数える。両方向のテストを置いた
(`testIdleWorkerWithEmptySourceIsNotCountedAsFailure` / `testWorkerThatRanScenariosWithEmptySourceIsCounted`)。

**一般化**: **小さい run のたびに出る警告は、まず「その run の構成が警告の前提を満たしているか」を
疑う**。ここでは「台数 > 本数」という正常な構成そのものが発火条件だった。
毎回出る警告は読まれなくなり、**本物の全滅と見分けが付かなくなる**ので、
発火条件を機構の側で絞る。もう1つ: **仮説が観測と一致しても対照は取る** ——
配信が `screenrecord` を掴んでいるのは事実だったが、それは真因ではなかった。

## 16. CLI とプロファイルの対応が 20 対 4 まで崩れていた(2026-09-08)

受け手の指摘は「CLI のオプションとチェックボックスの指定方法が対応していない」だった。
数えると**実行プロファイルの Bool チェックボックス 20 個に対し CLI は 4 個**しかなく、
しかも形が3通りに割れていた:

| キー | CLI | 形 |
|---|---|---|
| `heal` | `--heal` / `--no-heal` | 両方向 |
| `falsePositiveCheck` | `--no-false-positive-check` | 否定のみ |
| `iosFastInput` | `--fast-input` | 肯定のみ・**キー名もずれている** |
| `enableAnimations` | `--enable-animations` | 肯定のみ |

**否定形だけを足したのは私で、「既定が true だから」という理屈だった。** 個別には筋が通るが、
全体で見ると規則性が無く、次に足す人の指針にもならない。**この非対称は一度に生まれたのではなく、
必要になるたび1つずつ足して育った。**

`--set <キー>=<値>` へ一本化した。**育たない仕組みを2つ入れたことが本体**で、対応表を
作るだけでは同じことがまた起きる: ①上書きは `ProfileResolver.resolve` が**読み込み直後の
文書へ当てる1箇所**(消費側へ配線しない)②**キー集合を `Mirror` で等号固定**
(新しい欄が `--set` から漏れたら落ちる)。

**掘って分かった同型3つ**(どれも「黙って効かない/黙って落ちる」型):

- **`profileOnlyBoolKeys` の8キーは2種類の混在だった。** 原理的に devices 一覧が要るもの
  (`iosInappEngine` 等4つ)と、**材料は揃っているのに配線が無かっただけ**のもの
  (`record` 系・`homeOnStart`)。後者は配線したら動いた。**「デバイス依存だから」という
  説明が実態と食い違ったまま定数名になっていた**ので、名前もコメントも直した
- **`run-file` は3つ目の実装だった。** `arguments.append("--heal")` で**文字列の引数列を
  組み立てて `run` へ渡す**ので、`--heal` を消すと**コンパイルではなく実行時に落ちる**。
  `run` と `api run` の2つしか数えていなかった
- **`api run` が `performanceMode` を `finish` へ渡していなかった。** 拡張から起こした
  フリート計測 run が run.json 上で通常 run と見分けられず、「有効な計測 run」として
  拾えていなかった。値を渡すだけでなく**既定値を外してコンパイル門にした**(呼び忘れ8箇所が実際に落ちた)

**一般化**: **「同じ設定に口をいくつ持たせるか」は、足すたびに1つずつ決めると必ず崩れる。**
口の形と、**集合が漏れていないことを機械で見る仕組み**を先に決める。
そして**「デバイス依存だから」のような理由づけは、コードで確かめてから書く** ——
確かめずに書いた分類は、次に読む人が同じ誤解を引き継ぐ土台になる。

## 17. 実行設定を7層で書き直していた(2026-09-08)

`runParallel` の引数を読んだ指摘から出た ——「`FMConfig` や `VideoRecordingConfig` は
場当たり的ではないか」。

数えると**集約はすでにあった**(`DeviceIndependentRunSettings` / `ResolvedProfile`)。
壊れていたのは集約ではなく**継ぎ目**で、実行経路の入口で解かれ、同じ集合が7層で書き直されていた:

`runSequential`/`runParallel` → `RunOrchestrator.init` → `ScenarioRunner.runOne` →
`ScenarioHost.run` → 子の CLI フラグ → `ScenarioRunnerMain` → `FTRuntime.init`

**同じ既定値が3箇所にリテラルで書かれていた**(`containerInference: Bool = true, ocr: Bool = true`)。
だから**渡し忘れが「引数の省略」として合法**になり、コンパイルでも実行でも見えない。実際
`ft_run_scenario --profile` は `fm` と `defaultTimeout` だけを拾い、**`ocrFalsePositiveCheck` /
`containerInference` / `scenarioTimeout` を落としていた** —— プロファイルがそれらを既定と違う値に
していても、`fleetest run --profile` では効き MCP 経由では黙って無視される。

**`FMConfig` が「場当たり」に見えた理由は FMConfig 自体ではなく非対称だった。**
プロファイル上は兄弟のトグルなのに、FM 系だけ構造体で `ocr` と `containerInference` は素の Bool。
`VideoRecordingConfig` は種類が違う(プロファイルの写しではなく `runDir` や `androidADBPath` を
含む注入物で、`nil` 自体が「録画無効」を運ぶ)ので統合しなかった。

**名前が実体とずれていた。** 呼び出し側は全経路で**親スイッチ `ocr` ではなく
`ocrFalsePositiveCheck`**(親を掛けた後の実効値)を `ocr:` へ渡していた。`ScenarioHost` の
コメントだけが正しく、`FTRuntime` のコメントは「実行プロファイルの `ocr`」と書いてあった。
**この形のまま OCR の用途が増えると、`RunOrchestrator(ocr:)` を読んだ人は親スイッチだと読んで
occlusion-guard の値を得る** —— 落ちずに誤る型。

直したのは3つ: ①`FTCore.ScenarioExecutionSettings` に束ねて**解かずに運ぶ**(既定値はこの型の
init 1箇所)②変換 init(`ResolvedProfile` / `DeviceIndependentRunSettings` から)**だけ**を
写像元にし、`Mirror` で「既定のままの欄が1つも無い」ことを固定 ③`occlusionOCR` へ改名
(子のフラグも `--no-occlusion-ocr`。旧 `--no-ocr` は `Unknown option` で明示的に落ちるので、
ホストと子がずれても沈黙しない)。

**副産物**: `OCRToggleWiringTests` が6本から3本になった。「値が7層を通っているか」をソース走査で
確かめていた3本は、構造体が運ぶようになった時点で**コンパイルが同じことをする**。
**走査テストは型の効かない継ぎ目にだけ置く** —— 型で守れる区間に走査を残すと、リファクタのたびに
走査だけが落ち、守っていない性質のために手を入れることになる。

**一般化**: **設定の集約は「型を作ったか」ではなく「継ぎ目で解いていないか」で見る。**
同じ集合を2層以上で書き直していたら、各層の既定値が**渡し忘れを合法にする装置**になっている。

## 18. ステップの締め切り(120 秒)を食っていたのは認識器のコンパイルだった(2026-09-10)

フル E2E の赤 7 件がすべて `the command timed out (120s)` で、20 秒超のステップの 99.7% が
snapshot/action/wait のどれにも計上されていなかった。「負荷が高いと壁時計の締め切りは不当なので、
スレッドの CPU 時間のような仕事量の尺度に代えられないか」が出発点。**代用尺度は要らなかった** ——
締め切りが不当だったのではなく、**ステップの予算でプロセスの初期化を払っていた**。決着までに踏んだ型:

### 18.1 計器は「消す」ために置く

置いた欄: `scheduleDelayMs`(順番待ち)/ `cpuMs`(貰えた CPU)/ `ioBlockedMs`(出力ブロック)/
`stallMs` `poolStallMs`(2 本の心拍)/ `guardMs` `ocrMs`(ガードの段)。前 5 つは全件 0 か 100 秒に対し
3〜6 秒で、**候補を 1 つずつ消した**。正体は最後に足した `guardMs` が 99.9% を占めて確定した。
「CPU 時間で伸縮」案はこの過程で否定された(プロセスは CPU を欲しがってすらいなかった)。
**仮説を 1 つ直すたびに走らせるのではなく、まず計器で候補を消す**。

### 18.2 テストが戻り値だけを見て、所要を測っていなかった

予算(1.3 秒)を入れた最初の版は `withTaskGroup` の本体を抜けるとき残った子を待っていて、
**戻り値は `.exhausted` なのに所要は仕事の全長のまま**だった。テストは `.exhausted` が返ることしか
確かめておらず緑。実走行で「予算切れの注記は出るのにステップは 42〜63 秒」で気付いた。
**締め切り・予算・タイムアウトのテストは、戻り値ではなく所要を直接測る**(`TaskBudgetTests`)。
合流点は非構造化タスクの `value` を await する子にせず、先着だけを 1 回 resume する門にした。

### 18.3 `FileManager.createFile` は inode を置き換える

`flock` の鍵ファイルを `createFile(atPath:contents:)` で用意したら、2 本目が既存パスに書いた瞬間に
**別の inode に置き換わり**、先客の flock(旧 inode)と衝突しなくなった(同じプロセスの 2 回目が
取れてしまうテストで発覚)。既存ファイルをそのまま開くのは `open(2)` の `O_CREAT`。

### 18.4 テストプロセスと素の CLI は、原因を隠していた

Espresso のコンパイルキャッシュは**プロセス名とバイナリの素性ごと**で、xctest ホスト
(`com.apple.dt.xctest.tool`)も素の CLI も 2 回目は 160ms。8 プロセス同時・シミュレータ稼働中・
main を塞いだ状態・言語集合の切り替え、**どれも外からは再現しなかった**。決め手は
**プロセス自身に 3 秒時点のスタックを採らせる**口(`FT_OCR_HANG_SAMPLE=1`)と、
**同じバイナリを別名にコピーしただけでコールドに戻る**実験。「シナリオ実行プロセスの中で測る」
を最初にやっていれば 1 走行で済んだ。同型の教訓は §4.8(実験系を疑う)。

### 18.5 「同じビルドの 2 回目も遅い」の観測が 1 度は誤りだった

`swift build` は決定的なので、ソース無変更の再ビルドは同じバイナリになり「作り直しても暖まっている」
ように見えた。一方で私はコミットのたびにソースを変えていたので、単発の診断は毎回コールドだった。
**キャッシュの鍵を主張する前に、素性(cdhash)を実際に比べる**。

### 18.6 例外を 1 つ置いた: 親の死を生き延びる子

`warm-ocr` は `FT_PARENT_PID` を渡さない(ParentDeathWatch を武装しない)。1 シナリオだけの短い run
では親が先に終わり、一緒に死ぬとコンパイルがコミットされず当の問題が残る。有限(≤ 約 1.5 分)で
自分で終わり、拡張の孤児掃除は印を持つものだけを殺す。dry-run では起こさない(終了テスト
`CrossLayerTerminationTests` が dry-run を使い、生き延びる子を正しく「残った」と落とす)。

## 19. FM は期待文字列を写す(2026-09-15)

### 19.1 「見えるか」と訊いた瞬間に手本を渡していた

occlusion-guard の FM 段は 2 か月間、期待文字列を prompt に入れて「見えるか」を訊いていた。日本語 UI の
精度確認で合成した空白・別の文字の crop に当てると、observedText に**期待文字列をそのまま写して**
visible=true と答えた(空白 20〜23% / 別の文字 33〜56% の見逃し)。同じ crop を OCR は正しく読めていた。
7 月の合成計測(§4: 空白 100% 検知)が通っていたのは、当時のモデル・当時の形がたまたま写さなかっただけ。
欄順を「転写 → 可否」に替えても直らない —— **読む前に結論を書く**のではなく、**手本が見えている**のが原因。
直し方は転写だけを求め、可否をホストで決めること(docs/poc-fm-occlusion-guard.md §5.18)。
**FM に「答え」を含む入力を渡して判定を訊かない**。

### 19.2 隠れていた真陽性が 2 つ出た

見逃しが 0 になった途端、E2E-iOS の `#txt_offscreen`(タブバーの裏に 2pt しか描かれていない)が赤になった。
7 週間「存在する」で通っていたのは FM のおうむ返しのおかげで、探索側の穴(容器推定が「可視域に兄弟 1 つ」で
nil に落ち、viewport が画面全体に広がる)は誰にも見えていなかった。**検知を直すと、それが隠していた
別の穴が出る**。E2E-RN の「単一行」も同型で、こちらは en ロケールのシミュレータの字形(§19.3)。

### 19.3 予防のために切った言語補正が、字形の取り違えを固定していた

OCR 段を入れたとき(9/7)に「欠けを推測で埋めさせない」と言語補正を切った。実害の計測は無く、予防だった。
en ロケールの端末が「単」を中国語フォントで描くと、補正なしの Vision は日本語モデルでも「单」と読み、
期待と一致しない。補正ありなら「単一行」と読める。合成コーパスで「補正は覆われた語を補完しない」ことを
確かめてから、日本語の集合でだけ有効にした。**予防で切った機能は、切った理由が計測されているかを疑う**。

### 19.4 E2E の最中にソースを編集して、その E2E を壊した

`Scripts/e2e.sh` はプロファイルごとにシナリオをビルドするので、走っている最中にソースを編集すると
後段のプロファイルがコンパイルエラーで落ちる(Flutter / RN の xcuitest 段が走らなかった)。
「E2E 中に `swift build` を打たない」は**編集も含む**。

## 20. 同じ Mac で実機とシミュレータの run を並走させたら、実機の緑が別の台で成立していた(2026-09-15)

3 時間の負荷テスト(3 機フリートの仮想 26 台 + 実機 SE3 / Pixel 4a / Pixel 3a を並走)で拾った同居の事故。
台帳は memory `load-test-20260915-ledger`(F1〜F27)。

- **ポートの奪取**(F8): シミュレータ供給の `scanRunningBridges` は /status に 2 秒で答えないブリッジを
  「無い」と見る。ステップ実行中の XCUITest ランナー(実機 SE3)は答えないので、その port が採番に
  出て、`PortHolder.stopIfOwnedBridge` が実機の iproxy を「自分の残骸」として kill した。
  → 採番は生きた `iproxy-<port>.pid` を除外し、iproxy を止めるのは台帳 `.device` の UDID が
  供給中の台と一致するときだけ(`PortHolder.classifyIproxy`)。
- **別デバイスで緑**(F8b): 奪った port にシミュレータの in-app ブリッジ(同じ bundle ID)が立ち、
  実機レーンのクライアントはそのまま撃ち続け、1 シナリオがシミュレータ上で PASS した。露呈したのは
  システム UI 探りへの 409 だけ。→ シナリオ実行プロセスの事前確認とホスト側の再プローブの両方が
  `BridgeIdentityCheck`(udid / engine)を通し、別の台なら `BridgeProbeOutcome.hijacked` = 接続不能扱い。
  **bundle ID が同じなら見分けられない**ので、同一性は /status の申告で確かめる。
- **ステージ先の衝突**(F6): 同じプロジェクトの別アプリプロファイルが同名 .app を
  `workspace/apps/<basename>` へ上書きし合い、実機の run がシミュレータ build を install した(0xe8008014)。
  → ステージ先は宣言文字列(declared)の SHA-256 で名前空間を分ける。絶対パスから導かない
  (repoRoot がローカルとリモートで違う)。
- **install 失敗の握りつぶし**(F5): `(try? await installIfNeeded(...)) ?? workers` は全員失敗の throw を
  飲んで失敗前の一覧に戻し、「dropped out」と言った直後に同じ台が古いアプリで走った。
  → `try?` で戻さない(走査テスト `InstallIfNeededTryOptionalSourceScanTests`)。
- **ガードの 1 フレーム誤反転**(F22): FM の直列化待ち + 推論(6.2 秒)がアサーションの timeout(5 秒)を
  超え、1 枚目の古い描画で反転が確定した(木は更新済み・失敗時の絵は正しい)。→ 1 回目のガード評価が
  締切を跨いだときだけ 1 度延長して撮り直す(`guard-retaken`)。**FM が死んでいる機械では出ない**
  (素通りになる)ので、FM が生きている機械ほど出る型。
- **無応答ランナーを「起動途中」と見て 180 秒待つ**(F24): 直前の run で健全だった長寿ランナーが
  /status 無応答になると起動予算を満額待った。→ pid ファイルが startupTimeout より古ければ
  起動予算ではなくウェッジ確定の刻み(`BridgeLivenessBudget.logSilenceSeconds`)で待つ。
  即座に建て直さないのは、ログが伸び続けている正当な冷えた起動を殺さないため。

### 20.1 暖機の「早く始める」は、DSL の経路では一度も効いていなかった(同日)

`StepExecutor.init` は「ガードに入った時ではなく、ここで暖機を始める」と書いてあったが、条件が
`occlusionGuardEnabled && occlusionGuard`(executor の**既定**のガード)だった。DSL の FTRuntime は executor の
既定を off のまま作り、ガードは `exist` の `requireVisible`(既定 true)でステップごとに効かせる ——
**だから暖機は最初のガードの中で初めて始まり、全シナリオの最初のガードが OCR の近道を逃していた**
(E2E-CMP で 48/48。温まっていれば探りは 0.2〜0.3 秒なのに、開始から中央値 8.7 秒後のガードで間に合わない)。
見つけたのは F29 で足した注記 `ocr-shortcut-not-warm`(見送った理由を残しただけ)の件数で、
**「近道の使用率 7 割」は以前から同じだったので、率だけを見ていたら気付かなかった**。
直しは FTRuntime が開始時に暖機を始めること + 近道の直前で完了を待つこと(ユーザー決定)。
待ちは締め切りから差し引く(`DeadlineExclusion`)—— 9/10(§18)の「初期化をステップの予算で払って
締め切りに当たる」は、**待たないことで防いでいたが、差し引くことで防ぐ形に変えた**。
**同型の見分け方**: 「X の時点で始める」と書いた処理が、既定値の組み合わせで実際には一度も走らない形。
配線は「呼んでいるか」だけでなく「その条件が実際の経路で真になるか」を見る。
**実測(2026-09-15・この Mac・E2E-CMP/ios-inapp・8 台・37 本)**: 建て直した直後の初回は近道の使用率が
19%(直す前・3 機)→ **100%**(待ち 5 回 = 各台の最初のガード・中央値 25 秒・最大 34 秒。シナリオ所要の合計は
温まった run より約 2 分増え、ほぼ待ちの合計)。建て直さない 2 回目は 100%・待ち 0 回・所要は温まった run と同じ。
**延長の陽性対照**: 認識器のキャッシュを退避して `--set scenarioTimeout=50` → 34 秒待ったシナリオが 68 秒で緑、
同じシナリオを温めたまま `scenarioTimeout=20` → 20.6 秒で打ち切り(= 緑は差し引きの効果)。

## 24. 親の死を知らせる1行が、親の死のたびに子を abort させていた(2026-09-16)

3 時間の負荷テスト(仮想 26 台 + 実機 4 台 + MCP 常駐)で、フリートの親を `kill -9` したら
機械ごとの子が **8 秒後に SIGABRT** で死んだ(`~/Library/Logs/DiagnosticReports/fleetest-*.ips`)。
落ちた場所は `ParentDeathWatch.swift:37` の `FileHandle.standardError.write(_:)`。

**機構**: 子の stderr は親が読むパイプ。親が死ぬと読み手が居なくなり、`Fleetest.main` が掛けた
`F_SETNOSIGPIPE` のおかげで write は SIGPIPE ではなく **EPIPE** を返す。ところが旧 API の
`FileHandle.write(_:)` は失敗を **ObjC 例外**で投げるので Swift では捕まらず abort する。
**次の行の `kill(getpid(), SIGTERM)` に到達しない** = InterruptRelay も defer も走らず、
dispatch.lock の解放・結果の回収・run.json の完了・終了スクリプトが全部飛ぶ。
`fleetest-scenarios` 側は `F_SETNOSIGPIPE` すら無いので同じ write で SIGPIPE 即死だった。
**2026-09-05 に発話を足して以来、親の死で子が後始末する経路は一度も働いていなかった**。

**砦が踏まなかった理由**: `CrossLayerTerminationTests` は子の stdout/stderr を**ファイルへ
リダイレクト**していた。ファイルは読み手が要らないので write が原理的に失敗せず、本番
(拡張・機械ファンアウトの**パイプ**)だけが踏む形だった。**この種のテストは出力をパイプ/FIFO にする**。

**直し**: `ParentDeathWatch.writeNotice`(fd に `F_SETNOSIGPIPE` を掛けた生の `write(2)`・失敗は
黙って諦める)+ `ScenarioRunnerMain` にも `F_SETNOSIGPIPE`。テストは FIFO を `exec cat` で読む
spawner(= 親だけが読み手)を足した。**陽性対照**: 同じ形で親を SIGKILL → クラッシュレポート 0・
リモート 3 機の dispatch.lock は子自身が解放(修正前は次の run の自動回収待ちだった)。

## 25. 同じ負荷テストで出た、後始末と検知の穴4つ(2026-09-16)

## 27. 文言と記録が事実と違っていた7件(2026-09-16)

9/16 の負荷テストで拾った「読み手を誤らせる出力」をまとめて直した。**どれも判定ではなく言い方の問題**だが、
受け手は文言で次の手を決めるので、誤った断定は誤った調査を生む(実測: Android 実機の失敗に
「xcuitest のプロファイルを使え」と出ていた)。

- **`DriverError` が構成を知らなかった**: `bridgeUnreachable` / `bridgeConnectionRefused` の説明文は固定で、
  Android の実機にも「inapp/hybrid はシミュレータ専用 —— xcuitest を使え」、xcuitest の接続拒否にも
  「アプリが落ちた可能性が最も高い」と書いていた。`DriverErrorContext`(engine + 実機か)を**必須の同伴データ**に
  して、構成ごとに起こりうる原因だけを並べる。**既定値を置かない**ので、新しい経路が文脈を渡し忘れると
  コンパイルで止まる。
- **同じ文が入れ子で二重**: `AndroidDriver` が完成した説明文(`errorDescription`)を次の `detail` へ渡していた。
  **detail に渡すのは一次情報だけ**(`adb forward failed: …`)に統一。
- **adb の断を「アプリが居ない」と読んでいた**: `adb shell pidof` の exit≠0 を一律で「プロセス不在」と
  解釈し、`device offline` のときに「クラッシュの疑い」を**失敗記録とレポートに事実として**書いていた。
  `processAbsence` が adb 自体の失敗を `nil`(判定できない)として返し、**言えないときは欄ごと省く**。
- **開始行の 2 実装差**: `api run` は iOS の台が無くても「iOS joins…」、`run` は Android 0 台でも
  「0 Android worker(s)」と言っていた。`RunStartLine.text` に一本化(走査テストで両実装が呼ぶことを固定)。
- **MCP の案内が効かなかった**: 「`fleetest bridge up` を打て」は `--udid` を受けず、既定の別の台に建つ。
  udid 入りの完成したコマンドを返す。**生きているが応答しないブリッジを「居ない」と言わない**ために
  台帳から候補ポートを絞って LISTEN を確かめる。
  **この診断の初版は全ポートへ `lsof` を同時に撃って協調スレッドプールを塞ぎ、ft_status が 200 秒返らなくなった**
  (`sample` のスタックで特定)。**プールにブロッキングを載せない**の規律は、こういう「診断のために外部コマンドを
  撃つ」経路でも同じように効く。台帳から絞る形(`ps` 1 回 + `isBound` 最大 4 本)で 1.2 秒に戻した。
- **中断を「失敗」と書いていた**: 4 機ファンアウトの中断で「the run failed before writing any」。
  中断と失敗を言い分ける。
- **`remote clean --dry-run` が本番と食い違っていた**: 本番はロックを読んで中止するのに、予告は
  「ブリッジを止める」と言っていた。dry-run でもロックを読む(読めないときは従来どおり通す)。

**確かめ方**: 文言はテストだけでは足りないので、**実機で実際に踏んで出た文面を読んだ**
(Android 実機のブリッジ停止 / iOS 実機のランナー停止 / iOS だけ・Android だけのプロファイルの開始行 /
ロック保持中の `remote clean --dry-run` / MCP の案内どおりに打って回復すること / 終端から始めた探索)。
busy なブリッジの分岐だけは実機で再現できず(XCUITest が処理中でも /status に答えた)、単体テスト止まり。

## 29. 2 つの検知が同じ台について正反対の帰属を言い、建て直しは空振りしていた(2026-09-16)

レビュー後のフル E2E(in-app)と `--ios-xcuitest` で、同じ台(local -01)について:

- **遅いレーンの警告(§26 の L25)が「the simulator itself is slow (not the runner)」と断定していた**。
  入力はワーカーごとの snapshotMs だけで、台かランナーかは導けない。同じ run の供給時プローブは
  「ランナーの stale remote element」と名指しして建て直しており、**2 つの検知が正反対を言った**。
  → 帰属の節を落とし、数字と「この観測では何もしていない」だけにした(`SlowWorkerFinding.consoleWarning`)。
- **stale remote element の検査は供給時の再利用の入口だけ**だった。4 プロファイルで毎回「検出 → 建て直し →
  run 中にまた 2 秒超のステップ」を繰り返した。→ 素の xcuitest レーンでは、緑のシナリオの直後に
  (ステップの snapshot 所要が 2 秒以上だったときだけ)同じ 1 問で測り直す(`RunnerMidRunRecheck`)。
- **その建て直しは空振りだった**。実装した直後の対照で、建て直した直後の新しいランナーが次の 1 問でまた
  2.9〜3.0 秒かかり、緑のたびに約 10 秒を払っていた。アイドルで直接測ると -01 だけ 3.0 秒・他の台 0.03 秒、
  **シミュレータの再起動で 0.03 秒に戻った**(3 シナリオの合計 42.3s → 22.1s)。§19.27 の「ランナーを
  建て直せば直る」は、この形では成り立たない。→ **建て直した直後にもう 1 問測り**、新しいプロセスでも
  遅ければ事実を 1 行言って、そのプロセスではもう建て直さない(`RunnerRestartFutility`。測って健全なら忘れる)。

**教訓**: **直す操作は、効いたかを直後に測る**。「効くはず」の操作を効果を見ずに繰り返すと、回復の機構が

## 34. LAN の実機ランナーが SIGPIPE で落ち、ホストが生きたランナーも止めていた(2026-09-18 負荷テスト N4 / N7 / N1)

**実害**: Wi-Fi 接続の iPhone 13 が 1 run に 3 回離脱し、6 run でほぼ全滅(35 本中 32〜34 本が赤)。同時刻の USB の SE3 は 0 回。

**2 つの事象が混ざっていた**(外から 1 秒ごとに `/status` と ping を打つ判別 witness で分けた):
- **(a) ランナーは生きているのに一瞬だけ接続不能(-1004)** —— 外からの `/status` は失敗の 1 秒前も 6 秒後も 401 で応答していた。
  `bridgeUnreachable` は `.refused` を観察窓なしで即「死亡」と確定し、`cleanupRetiredWorker` の `stopMatching` が
  **生きた xcodebuild を SIGTERM** していた(ログの「Stopped stale bridges」がその印)。
  → `BridgeProbeOutcome.refusalIsConclusive(host:)`: 即断してよいのはループバック(シミュレータ・USB トンネル)だけ。
  LAN は `.silent` と同じ観察窓 + ランナーログの静止で判定し、ブリッジが生きていれば Android と同じ「残して再キュー」
  (`requeuesWithoutRetiring(…, host:)`。ブレーカは数える)。陽性対照: 本当に死んだ回は約 23 秒観察してから正しく離脱した。
- **(b) ランナーが本当に落ちる** —— 「Stopped stale bridges」が出ない離脱。xcresult の失敗は **`Test crashed with signal pipe`**。
  直前はスクリーンショット取得の完了で、端末にクラッシュログは無い。HTTP のソケットは `SO_NOSIGPIPE` 済みなので、
  出どころはそれ以外(LAN ではネットワーク越しに転送される標準出力 = XCTest の活動ログ、と見ている。特定はしていない)。
  → ランナーの入口で `signal(SIGPIPE, SIG_IGN)`(専用プロセスなので全体で無視してよい。ホスト CLI の Shell.swift が
  fd 単位にしている理由とは別)。ブリッジ v111。**同じ構成で 3 離脱/run → 0 離脱・35/35 緑**。
  手元 8 台の `ios-xcuitest` 4 SUT(125 本)も全緑。

**付随**

**学び**: 「ブリッジ不達で離脱」は、ホストの誤判定とランナーの本当の死が同じ文言になる。**「Stopped stale bridges」の有無**が

## 38. 待ちを速くした迂回が、次の操作に古い座標を読ませた(2026-09-19 負荷テスト P5)

ステップを1本ずつしか見ておらず(exist → tap の並びを通していなかった)、エミュレータでも 1/19 と薄く、**遅い実機の負荷テストで

## 39. 発行者ごとの設定で、共有ランナーの他人の台を落としていた(2026-09-20)

設定タブの「マシン有効」(docs/remote-runner.md §21)を off にした機械について、「デバイスモニター」
タブを開いたときにその機械の起動中の仮想デバイスを終了する掃除を入れた(a2434410 / 70a2fa4e /
71b3f96f)。**共有ランナーでは他人の台を落とす**ので撤去した(ユーザー決定)。

壊れ方は3つ:

- **設定の持ち主と、効果の及ぶ範囲が一致していない**。「マシン有効」は発行者ごとの登録簿
  (`~/.config/fleetest/config.json`)にあり、意味は「**自分は**ここへ配らない」。その個人の都合で
  機械全体の共有状態(起動中の台)を壊していた
- **意味が逆に取られうる**。「今は他の人が使っているから自分は配らない」でチェックを外す運用が
  自然で、そのときに起きるのが「その人の台を落とす」
- **守れていたのは run-lease と MCP の印だけ**(`--force` は付けていないので `deviceInUseRefusal` は
  効く)。run の合間に温めてある台・供給の途中の台・他人が配信して眺めている台(`streamedByOther` は
  届いているのに読んでいなかった)・手で起こした台は落ちる。A が無効・B が有効だと、A がタブを
  開くたびに落ちて B の run が起こし直す綱引きになり、双方から相手が見えない

§18.7 は破壊的操作について「他人の run を殺す操作はロックを読む」「確認に保持者を添える」
「奪う口を GUI に出さない」と決めている。この経路は**自動・無確認・タブを開くだけ**で発火して
いたので、どれも通っていなかった。

**一般化**: **発行者ごとの設定を、共有資源を壊す動作の引き金にしない**。「配らない」は発行者の
都合でよいが、「止める」は共有状態の変更なので、**持ち主を知っている操作**(明示の停止・保持者を
添えた確認)からしか撃たない。

**再提案するなら**: 「自分が起こした台だけ止める」= 起動時に `FT_ISSUER` を控える所有者台帳を
先に置き、**所有者不明は止めない側へ倒す**(§18.7 の「不明と空きを混ぜない」と同じ向き)。
台帳なしで「止める」を自動化しない。

## 39.1 反映済みの欄を 4 秒待って落とした clearInput(2026-09-20・負荷テスト O2)

- ループは 20ms ごとに root を取り直し、id + 座標でノードを引き直し、`refresh()` してから読む。

原因は2つに絞れるが、**記録からは割れなかった**: ①読みが古い(`refresh()` が false のまま古い
値を読み続けた)②アプリ/IME が本当に値を戻した。

**やったこと**(ブリッジ v69):

- **`refresh()` の戻り値を見る**(4 経路。docs/design.md §8.7)。false の読みは古いと分かって
  いるので、それを「値がまだ入っている」の根拠にしない
- **失敗文言に判別できる事実を載せる**(`failureFacts`): 読み返した値(マスク欄は長さだけ)/
  refresh の成否 / 受理回数 / IME ウィンドウの有無。次に出たら①②が1回で割れる
- **推測の対処は入れない**(キーボードを畳んでから撃つ・composing を切る等)。根拠が無いものを
  ブリッジへ入れない

**一般化**: **読みを新しくする対策(refresh)を入れても、その対策の失敗を見ていなければ
元の誤りは同じ顔で残る**。「取り直した」ことと「取り直せた」ことは別。

## 40. 前面と答えたものを activate して画面を真っ黒にした(2026-09-22・ライブ操作)

ホーム画面の「検索」(Spotlight)を叩くと、キーボードが出たあと**画面が真っ黒**になった。
拡張・webview の不具合に見えたが、**シミュレータの画面が本当に黒かった**:

| 観測 | 正常 | 黒いとき |
|---|---|---|
| スクリーンショット | 2.2〜3.8 MB | **47〜68 KB** |
| SpringBoard の木 | 24 要素(アイコン・Dock) | **6 要素**(window + 空の scrollView + ステータスバー) |

XCUITest・simctl の両方が同じものを返したので、絵の供給経路の問題ではない。SpringBoard の
クラッシュレポートも無く、**プロセスは生きたままホーム画面の中身だけを失っていた**。

原因は**ライブ操作の前面追従**(`LiveSessionFollower`)。Spotlight を開いている間、
`launchctl list` の候補に `/appstate` を聞くと **`com.apple.Spotlight` だけが前面と答える**。
除外一覧に無いのでこれを採り、`activate()` でセッションを向け直していた。
**Spotlight は SpringBoard の拡張**で、activate するとホーム画面が描画を失う。
陽性対照で確定(同じ台・同じ状態で `attachOnly` と `activate` を撃ち分け):

- `attachOnly` → スクリーンショット 2,233,613 B・**Spotlight の木が 28 要素**(検索欄・候補)
- `activate` → **67,768 B・木が 6 要素** = 利用者が見ていた黒画面そのもの

**やったこと**: 向け直しを `AppDriver.attach`(前面確認だけ・前面化を撃たない)に変えた。
**除外一覧を増やす形にしない** —— 裏方プロセスは OS の版で増えるので追い切れないし、
Spotlight は attach なら**むしろ中身が読める**(28 要素)ので落とすのは損。

同じ経路にもう1つあった: **自アプリへの向け直しも活きていない** ——
`InAppDriver` は `activate` を実装しないので既定実装から `launch` = **dylib 注入付きの再起動**へ
落ちる。`HybridFallbackDriver.attach` は**自アプリでも XCUITest 側へ回す**(セッションを
持つのは XCUITest だけ)。

**規律**: **「前面と答えた」は「利用者が見ているアプリ」ではない**。観測しただけの相手に
**画面を動かす操作を撃たない** —— 向け直せないことより画面を壊すほうが害が大きいので、
`attach` の既定実装は activate へ倒さず 501 を投げる(`AppDriverDefaultDispatchTests`)。

**一般化**: **観測のための操作が画面を変えてはいけない。**「確かめてから撃つ」の
「確かめる」側に副作用があると、症状は撃った側ではなく**観測した側**に出るので、
webview・配信・デコーダといった無関係な場所を延々と疑うことになる。
判別は「その絵はデバイスにもあるか」を先に測ること(スクリーンショットのバイト数で足りた)。

## 41. ピンチの縮小だけがパンに化けていた —— 非公開 API で座標ピンチを持つ(2026-09-22)

ライブ操作の「縮小」が、Apple マップで**地図を右下へ動かすだけ**だった。原因は
**XCTest のピンチが拡大と縮小で指の置き方が逆**であること(実測・iPhone 17 Pro / iOS 27.0):

| | 指の動き | マップでの結果 |
|---|---|---|
| 拡大 (scale > 1) | 枠の**中央から**開く | 正しく拡大(要求 2.0 に対し POI 間の距離比 1.803) |
| 縮小 (scale < 1) | 枠の**長辺の両端から**閉じる | **パン**(距離比 1.000・重心だけ移動) |

マップは地図の容器(`ChromeViewController.Viewport`)の下端が検索カードに接しているので、
縮小では必ず下の指がカードに乗る → 地図から見ると指1本 → パン。アプリ要素を渡していた頃は
指が画面の端に着き、カードが開閉していた(同じ原因の別の顔)。

**公開 API に代替は無かった**(すべて実測):
`XCUIElement.pinch` は指の位置を選べない(iOS 27 の SDK にも座標版は無い)/ 2本指タップは
**4通り試して1度も反応しない** / ダブルタップは拡大しかできない。要素を選び直す案も、
**マップには「両端が中身に収まる要素」が存在しない**ため成立しなかった。

**やったこと**: ユーザー決定で**非公開 API を採用**し、座標指定の2本指ピンチを自分で組む
(`Runner/.../CoordinatePinch.swift`)。Appium/WebDriverAgent と同じ
`XCPointerEventPath` / `XCSynthesizedEventRecord`(**`XCUI` 接頭辞は付かない**・公開ヘッダに宣言なし)。
守る規律4つ: **①実行時に存在を確かめてから使う**(無ければ従来の要素ピンチへ縮退し、注記で言う)/
**②起動時にも一行出す**(`coordinate pinch: available` —— 消えたことが run を待たずに分かる)/
**③completion ブロックは引数を宣言しない**(実際は先頭に BOOL が来るので `(Error?) -> Void` で
受けると Swift の thunk が 1 を objc_retain して**落ちる**。実測 EXC_BAD_ACCESS at 0x1)/
**④指の位置はホストが決め、ブリッジは写すだけ**(`FTCore.PinchRegion` が「両方の指が同じものに
載る」位置を探す。端の規則は `closingTouchPoints` が唯一の定義元)。

**指は原則 横に並べる** —— 縦に並べると、同時に効いている縦スクロール/ドラッグの recognizer が
指を取る(実測: 縦長の `#pad_map` を縦にピンチすると SUT が `pan=none-down` を記録し拡大率は 1 のまま)。
**Android には領域を渡さない** —— あちらは領域の短辺から指の幅を決めて中心に置くので、
狭い領域だと最小スケール幅(27mm)に届かない(実測: 対象未指定の pinchOut が `zoom=-` になった)。

**一般化(この調査で2度払った)**: **ブリッジの挙動を変えたら必ず版を上げる**。
版を据え置いたまま E2E を回して「直っていない」と3回読み違えた ——
**稼働中の旧ブリッジが再利用される**ので、直した側のコードは1行も走っていなかった。
もう1つ、**「何か動いた」を「効いた」と読まない**: 最初の修正で POI が動いたのを縮小と誤読したが、
実際はパンだった。**ズームとパンを分ける測り方(POI 間の距離比)を先に用意すべきだった**。

## 42. 負荷テストで出たロックとライブ操作の穴(2026-09-22)

3 機フリート(手元 8 + M1Max 4 + M1Ultra 6)を回しながら、**実機 4 台は MCP で並行に叩く**構成で
50 分(MCP/ライブ 10,023 呼び出し・fleet run 7 本)。**実機を `fleetest run` で回さない**のは、
`dispatch.lock` が 1 マシン 1 run を保証する以上、実機の run(1 本 30〜40 分)がロックを占有して
フリートが 1 周も走らないため —— MCP はロックを取らないので、フリートと同時に叩ける
(ユーザー提案)。

### 42.1 待っている間に保持者が死んだロックが、永久に残る

run の親を SIGKILL したあと、`--wait-lock 3600` で待っていた run が `still queued … 420s` を
出し続けた。`~/.fleetest/dispatch.lock/info.json` の pid は死んでいる。手動の
`fleetest remote unlock --runner local` は「your dispatch (pid …) is no longer running on this
machine」と正しく外せたので、**判定は正しく、呼ばれるタイミングだけが穴**だった。

```swift
// (1回だけ試す —— 他人のロックは何周しても答えが変わらない)
if case .held = outcome, !autoReleaseTried { … }
```

コメントの前提は**他人のロックには正しい**。だが**自分のロックは、待っている間に保持者が死ぬ**
= 答えが変わる。しかも待ち始めた時点では保持者が生きているのが普通なので、**その1回はほぼ必ず
空振りする**。`autoReleaseOurDeadLock()` はロックを読む + `pidAlive`(sysctl 1回)だけなので、
毎周撃っても安い。**「答えが変わらない」と書くときは、誰のどの性質が変わらないのかを確かめる**。

### 42.2 ロックが「空き」のままの時間が長い —— 取るのがビルドの後だった

ユーザー指摘「ロックしても 空き のままになっている時間が多い」。時刻付きで測ると:

```
07:32:09  run 開始 → "building E2E-RN locally to split the scenarios"
07:32:34  local: 1 scenario(s) on 8 device(s)     ← ビルド + 配分に 25 秒
07:32:35  （ここで初めてロックを取りに行く）
```

規律③は「取るのは run の入口(ビルドにもデバイスにも触る前。`swift build` も重い負荷なので
直列化する)」。**規律が防ごうとした当のものが、規律の外で起きていた**。加えて FIFO の待機列の
順序が実質「ビルドが終わった順」になり、先に打った run が追い越される。

**構造上の依存は本物**(機械ごとのロック対象は配分の結果で決まり、配分にはシナリオ一覧が要る)
なので、2 段に分けた: **①チケットだけ先に確定させる**(`setenv` まで書く —— 発行だけでは
取得時に `Date()` で採り直される)**②ローカルのロックをビルドの前に先取りし、配分が確定したら
無条件で解放する**。本取得は従来どおり `DispatchPrelock` が全順序で行う。

### 42.3 その修正が、循環待ちの禁止を壊しかけた(レビューで差し戻し)

42.2 の最初の実装は、`DispatchPrelock` に `preacquiredLocal` を足して**手元だけ全順序の外へ
出していた**。`DispatchPrelock.live` のコメントは、**以前からこの形を名指しで警告していた**:

> 手元だけ順序の外へ出すと、**A が手元を握って M1Max を待ち、B が M1Max を握って手元を待つ**
> 形が作れる(手元も全順序の1要素でなければ循環は消えない)

Mac X(X + M1Max)と M1Max(M1Max + X)が同時に複数機械 run を起こすと、互いに待つ。
§18.10 は「循環待ちを**作れない**(検出も自己解消も要らない)」という**構造的保証**で、
「現実には起きにくい」で崩してよい種類のものではない。差し戻して、**ロック本体は全順序どおり・
列に並ぶ順番だけを前倒し**という形にした。`DispatchLockBeforeBuildOrderingTests` が
「local の実取得を飛ばす口が無いこと」を走査で固定する。

**教訓**: 既存のコメントが警告している形を、その警告のすぐ上に足そうとしていた。
**規律の理由が書いてある場所を通るときは、その規律を自分が今から破らないかを読む**。

### 42.4 `--wait-lock` を渡しても、台の先読みで即死していた

`run --profile … --scenario <1本> --wait-lock 300` が 1 秒も待たずに
`refusing to start: already in use by another fleetest run … (held by pid …)` で終了した。
判定は `rejectIfLocalDevicesLeasedBeforeDispatch`(fan-out の先読み。どのロックも取る前に断る)で、
**断ること自体は正しい**。だが **1 マシン 1 run を保証している以上、走っている run が終われば
台の lease は必ず空く** —— 待てば必ず解消するものを待たずに断ると、連続実行(CI・ループ・
拡張の再実行)の後発が FIFO の待機列にすら並べない。`--wait-lock` があるときは
`WaitLockPolling` の同じ刻みで待ってから再判定する。

### 42.5 いちばん使用中のときだけ開く門(`bridge down`)

**決定的な対照が 1 分で取れた**:

| 対象 | 同時刻の `bridge status` の走査 | `bridge down --port` |
|---|---|---|
| 8153 | 載る | ❌「is being driven by an MCP session (fleetest-mcp pid …)」= **門が効く** |
| 8154 | **載らない** | ✅ **一言も言わずに停止**(MCP が駆動中・lease も生きていた) |

門は鍵(udid)を `BridgeDiscovery.scan` = **/status の応答**からしか取らない。XCUITest ブリッジは
**操作の実行中は応答しない**ので、**いちばん使用中のときだけ「宛先が引けない」に落ちて素通りする**。
「引けないときは通す」の意図は「無応答のブリッジを止められないと回復手段が無くなる」だが、
無応答には**死んでいる**(待受もない)と**忙しい**(待受はある)の 2 種類がある。
`BridgeDiscovery` 自身は `isBound` / `.preferredBusy` でこの区別を持っていたのに、門は使っていなかった。

**一般化**: **「観測できなかった」を「存在しない」と読む分岐は、観測が失敗する条件を列挙してから書く**。
ここでは「忙しい」が失敗条件で、しかもそれは**門が最も効くべき状態**だった。

### 42.6 ライブ操作が、指定していない台を操作し、その台のブリッジを止めた

`api live serve --udid <台A>` を `--port` なしで起こしたら、stderr に
`Detected a bridge from an older build (port 8123) — restarting it` が出て、
`actionResult.app` は**別の台で動いていたアプリ**を返した。直後に 8123 と**台A 自身の健全な
ブリッジ**の両方が消えた(「台A の udid で 8123 に建て直す」ため、台A が既に持っていた
ブリッジも止められる)。

原因は、`XCUIBridgeResolver.resolve` の宛先を `--udid` と**一度も突き合わせていなかった**こと。
「接続先の同一性は `FTCore.BridgeIdentityCheck` で確かめる」は run の 4 経路と MCP が通していて、
**ライブ操作だけが漏れていた**。非破壊の対照も取れた: `--udid <A> --port <B の台>` で
`{"cmd":"refresh"}` → **B の画面を ok:true で返す**(警告なし)。

**直し方で一度間違えた**: 最初の実装は「不一致なら serve を起動しない」だった。これは
**この不具合が実際に起きる場面を塞ぐ** —— 拡張は port が分かるときだけ `--port` を渡すので、
**ブリッジのまだ無い台を開く**と必ず既定 8123 にフォールバックする(= 自動起動が想定している
まさにその場面)。そこで断ると「別の台を操作する」が「開けない」に変わるだけ。
`--port` の明示/既定で分け、既定なら**その udid のポートを探す / 無ければ空きポートへ向けて
自動起動に委ねる**形にした。

**教訓**: **安全側に倒すときは、倒した先で「本来の使い方」が通るかを実際の呼び出し元
(ここでは拡張の `buildDeviceArgs`)まで辿って確かめる**。

### 42.7 ライブ操作の launch に門が無く、serve ごと落ちていた

`{"cmd":"activate","bundle":""}` と `{"cmd":"launch","bundle":"no.such.app.live"}` のどちらでも、
そのコマンドが 30 秒刺さり `A single command stalled for over 30s — force-quitting (command
watchdog)` で serve が終了した。再起動後は接続拒否 → 自動起動が走り、
`Cleaned up leftover runner(s) on port 8153` で**健全だったランナーまで掃除**して建て直す。

`guard let bundle = command.bundle` しか無く、**nil は断るが空文字列も実在しない bundleID も通す**。
`XCUIApplication` はそれで返ってこない —— **2026-09-21 の T1(MCP の `ft_launch`)とまったく同じ型**で、
あのとき門を入れたのは MCP だけだった。判定を `InstalledAppCheck.launchGuard` に切り出して
**両方が共有**する形にした(「判定は 1 箇所・文言は呼び手ごと」)。

**同型の掃討は、同じ判定を持つべき経路を列挙してから行う** —— T1 のとき「ft_launch を直した」で
止めず、「`XCUIApplication.launch/activate` を撃つ口はどこか」で数えていれば、ここも同時に塞げた。

### 42.8 小さいもの

- **型違いの黙殺(ライブ操作)**: `{"cmd":"pinch","scale":"2"}` が stderr に
  `Ignored a line in an unknown format` を出すだけで無応答。プロトコルの「壊れた行は無視」は
  **JSON でない / `cmd` が無い**行の話で、型違いはその外。MCP の同じ操作は型を名指しして断る
  (2026-09-20 の Q1)。拡張は応答を待つので `SERVE_REQUEST_TIMEOUT` まで固まり serve を再起動する
- **`--udid` が口ごとに逆の意味**: `api start-device --udid` は**実機専用**・
  `api stop-device --udid` は**シミュレータ専用**で、どちらも「渡されたものが相手側の種類だった」
  ことを言わずに「無い」とだけ言っていた。MCP の `ft_*` は同じ文字列で両方を受けるので、
  エージェントは取り違える。両方とも相手側のカタログを引いて名指しする
- **`held by started by …`**: `DispatchWaitStatus.queuedLine` だけが `holderSummary`
  (= "started by …" を返す)に `held by` を前置していた。**既存のテストが誤った文言を期待値として
  固定していた**(基準値が現状の追認装置になる型)
- **`is a existence DSL command`**: 冠詞。`is a DSL command in the <category> category` に変えて
  カテゴリ名の頭文字に依存しない形にした

### 42.9 レビューで見つけて直したもの(修正そのものの欠陥)

修正を入れたあとの差分レビューで、**修正が別の規律を破っていた**ものが3件出た。どれも
「テストは緑・実装も動く」状態で見つかったので、**差分は通しで読む**価値がそのまま出た形。

1. **判定に文言が埋まっていた**: `BridgeIdentityCheck.verdict` の detail は
   「The lane's port was taken over; the worker must be re-provisioned」で終わっていた。
   run の4経路だけが呼んでいた頃は正しかったが、ライブ操作へ共有した瞬間に
   **「lane」も「worker」も無い文脈でその対処文が出た**(実地で確認)。
   対処文は `remedy` として呼び手が渡す形にし(既定値なし)、run が共有する文は
   `runLaneRemedy` に置いた。detail が要らない呼び手には `matches(expected:status:)` を用意した。
   → CLAUDE.md「共有するのは判定であって文言ではない」に追記

2. **採番を `ProvisionLock` の外で撃っていた**: ライブ操作が「要求された台のブリッジがどこにも
   無い」ときに `XCUIBridgeResolver.freePort` を呼ぶ経路を足したが、ロックの外だった。
   `ProvisionLockStartupPathsSyncTests` のコメントが warn している当のもの
   (「同時に走ると同じ空きポートを選んで bindFailed(48) で衝突していた」)。ロックの内側へ移し、
   期待集合にこのファイルを足した。**この経路は「選ぶだけで起動しない」= 予約ではない**ので、
   起動までに埋まったら自動起動側が占有者を名指しして諦める、という限界もコメントに書いた

3. **テストが落ちるときにプロセスを殺していた**: 新しく足したテストが
   `XCTAssertNotNil(x)` の直後に `x!` を使っていたため、**変異チェックが「検出」ではなく
   「ERROR(ビルド失敗)」と判定した**(実際は狙ったテストが落ちていた)。
   CLAUDE.md の「**『殺せた』も exit code で数えない** —— 狙ったテスト名の失敗行で取る」が
   まさにこれ。`guard let … else { return XCTFail(…) }` に直した

**変異チェックで穴が1つ見つかった**: ライブ操作の型違いのテストは double(`scale`)と
string(`text`)しか見ておらず、**int(`ref`)の欄のエラー設定を消しても落ちなかった**。

## 45. 失敗の出口が MCP にしか配線されていなかった(2026-09-23 の掃討)

**発端**: 負荷テスト3回で同じ型が3回続けて出た —— T1(`ft_launch` が未インストールの bundleID で

**同じ型が3回続けて出るのは個別の不具合ではない**ので、型として掃討した。

**棚卸し**: ブリッジ3実装が返すエラー応答を全数(XCUITest 34 / in-app 35 / Android 33 = 102 件)、
ホストの3経路(MCP・ライブ操作・DSL)と突き合わせた。

**構造**: 判定は FTCore / FTBridgeClient に置いて共有されているのに、**それを呼んで利用者への
出口にするのは MCP だけ**だった。

| 判定 | MCP | ライブ操作 |
|---|---|---|
| `BridgeDiscovery.probeStatus`(固まり / busy / 不在の4値) | 6 | **0** |
| `DriverError.isNoReadableWindow`(Android の木が読めない) | 2 | **0** |
| `FTCore.StaleFrameDetector`(絵が古い) | 9 | **0** |

3回とも MCP にだけ足して直したので、**ライブ操作には一度も届いていなかった**。あちらは人間が
拡張の UI で画面を見ながら触る経路なので、一次情報だけだと「壊れた」と判断してパネルを閉じる・
ブリッジを落とす、という袋小路の行動を誘う。

### 45.1 直した4件

- **HYB-1(呼び手で成否が変わる)**: テキスト入力系の 409 を、DSL は XCUITest へ回すのに
  `HybridFallbackDriver` は回さなかった —— 同じ hybrid 構成の同じ操作が、シナリオなら通り

### 45.2 規律

**利用者が次の一手を打つ経路は MCP とライブ操作の2つ**。判定を足したら**両方へ配線する**。
run(DSL)は別扱い —— あちらは失敗をレポートへ残して自動回復する経路で、人がその場で次の一手を
打つ場ではない。`LiveControlExitParityTests` が集合を等号で固定する。
**走査はコメントを落としてから行う** —— 判定の名前は doc コメントにも出るので、素のまま検索すると
**配線を消してもコメントだけで通る**(変異で実際に素通りした)。

### 45.3 直さなかったもの

- **素通し約 60 件の文言**: ブリッジの応答の多くは一次情報しか返さないが、「もっと分かりやすく

構成: フリート run の周回(手元 + M1Max / M1Ultra / M1mini の4機)+ **実機 4 台(iPhone 13 /

+ CLI/api 面のファズ。MCP 約 2.4 万呼び出し・fleet run 27 本・ライブ 2.4 千コマンドで6件見つけた。

**途中で iPhone 2 台が画面ロックし、ランナーが死んだ**(`Unlock iPhone SE3 to Continue`)。
ツールの文言は正しく、以降は仮想機へ振り替えて継続した —— が、**その死んだ実機のトンネルが

### 46.1 残骸ランナーの照合がポートだけで、別デバイスの生きたブリッジを殺していた(最重要)

`BridgeLauncher.killOrphanRunners` と `PortHolder.stopIfOwnedBridge` は
`FleetestRunner-<port>.xctestrun` のパス一致だけで「自分の残骸」と決めていた。**ファイル名は
ポートしか持たない**ので、同じ種別(実機どうし・シミュレータどうしで DerivedData が同じ)の
別デバイスが同じポートに居ると、**駆動中のブリッジを残骸として SIGTERM→SIGKILL する**。

実地の形: ブリッジを失った実機 2 台がどちらも既定ポート 8123 へ倒れ、
`→ Cleaned up leftover runner(s) on port 8123` で互いを殺し合った。同じ形で、MCP が駆動中だった
シミュレータのブリッジも巻き添えになった(その MCP セッションは以後「no running bridge」しか
返せなくなる = 袋小路)。

直し: `FTBridgeClient.RunnerDestination` がコマンド行の `-destination …,id=<udid>` を読み、
**肯定的に別デバイスと読めた回だけ**殺さない(宛先が読めない・こちらが名前指定のときは従来どおり
止める —— 「分からないから残す」に倒すと本物の残骸が永久にポートを塞ぐ)。

### 46.2 `.inapp` 台帳の生死を「誰かが待受しているか」だけで決めていた

`StaleLedgerSweep` の `inappListening` は `PortHolder.describe(port:) != nil`、つまり
**占有者が誰かを見ていなかった**。別のデバイスのブリッジがそのポートを取ると古い `.inapp` が
生き残り、供給が「別アプリに注入された in-app ブリッジ」と読んで
`InAppBridgeState.terminateAndRemove` → **無関係なデバイスのアプリを simctl terminate** する。
直し: `PortHolder.listenerIsAnotherSimulator`(CoreSimulator のパスに別の UDID が出たときだけ true。
実機の in-app は iproxy が握るので形が違う = 従来どおり「生きている」側)。

### 46.3 ライブ操作が「応答しないポート」を自分の台のものと決めつけていた

`ApiLiveCommand.identityMismatch` は `/status` が答えないと nil(= 一致)を返していた。
既定ポートへのフォールバックでこれに当たると、**別のデバイスのブリッジが居るポートを宛先に採り**、
その後の自動起動がそこへ自分のブリッジを立てて占有者を殺す(46.1 の発火経路)。
直し: 戻り値を3値(`.mine` / `.mismatch` / `.silent`)にし、`.silent` は
**プロセスの実体で占有者を見る**(`PortHolder.isHeldByAnotherDevice`)。
**busy は正常**(XCUITest は駆動中 `/status` に答えない)なので、**肯定的に別デバイスと読めた
ときだけ**掴むのをやめる —— 単に「待受している」で断ると、自分の busy なブリッジを見捨てて
同じ台に 2 本目のランナーを立ててしまう(先代が蹴り出される)。

### 46.4 `bridge down` が「固まった転送」を busy と誤って帰属していた(§44.1 の残り)

`BridgeDownRefusal.unresponsiveButBoundRefusal` は `isBound` だけを見て「待受しているのに
答えない = 忙しい」と決めていた。画面ロックで死んだ実機のトンネルが握ったポートに対して
**「待て、`--force` で押し切れ」と言い続ける** —— 止めることが唯一の回復手段なのに断る袋小路。
直し: §44.1 と同じ `BridgeDiscovery.probeStatus` の4値を通し、断るのは `.timedOut`(本当に busy)
だけ。`.transportFailed`(固まり)は止めさせる。並列プローブは
`BridgeDiscovery.probeStatuses`(1ポートずつ直列に撃つと上限 2 秒 × ポート数を払う)。

### 46.5 宛先を取らない MCP ツールが udid で道連れになっていた

`call` は**ツールを問わず** `foldingUDIDIntoPort` を通していたので、`ft_list_devices` /
`ft_list_projects` / `ft_dsl_commands` / `ft_list_scenarios` / `ft_dry_run` /
`ft_draft_scenario` / `ft_doctor` の7つが、`udid` を添えるだけで
「no running bridge is on udid …」で落ちた。**文面が案内する `ft_list_devices` 自身が同じ
エラーを返す**ので、1台を駆動していた呼び手(udid を毎回添える)はブリッジが死んだ瞬間に
一覧も診断も失う。直し: `toolAcceptsDeviceTarget(tool)` のときだけ畳む。

### 46.6 画像で掴めなかった要素の「飾りの名前」を構文検証に掛けていた

`findImage` / `existImage` は見つからないと `<image "[Switch]": not found>` というラベルの
`FTElement` を返す。これは**利用者が書いたセレクタではない**のに `FTSelector.label` 経由で
実行前の構文検証に掛かり、連鎖したアサーション(`findImage("[Switch]").idIs("sw_notify")`)が
`invalid selector syntax: a clause starting with '<' …` で落ちていた。
**dry-run は画像を探せないので必ずこの形になる** —— つまり画像で探す手を含むシナリオを1本でも
持つプロジェクトは**dry-run が丸ごと赤**で、シナリオ作成の中間ゲート(コンパイル → dry-run →
デバイス実行)が死んでいた。直し: プレースホルダは `structured: true`(構文検証を通さない印)で組む。

### 46.7 a11y サーバの一時停止(kAXErrorAPIDisabled)の出口が run にしか無かった

run は同じ事象を「a transient accessibility fault」として結果を捨てて振り直す
(`RunOrchestrator`)。MCP とライブ操作は `SessionRecoveryDriver` が数秒ぶん読みを撃ち直すが、
**尽きたら生の `Error Domain=com.apple.dt.xctest.automation-support.error Code=8 …` だけ**が返り、
呼び手にはアプリの不具合と区別が付かない。判定(`isAccessibilityTemporarilyDown`)は共有のまま、
文言を両方へ配った(`LiveControlExitParityTests` の表に載せた = §45 の規律どおり)。

### 46.9 死んだ実機ブリッジのトンネルを誰も片付けられなかった

画面ロックで実機のランナーが死んだ後、**iproxy だけが採番範囲のポートを握ったまま**残った。
この状態は3つの口すべてで詰んでいた: `doctor` は `/status` に答えたポートしか見ないので
**「✅ No unmanaged or stale bridges」**と言い、`bridge down --port N` は台帳
(`iproxy-<port>.pid`)が消えていると **「the bridge is not running」**で何もせず、
`bridge up` は「port N is in use by another bridge」と言って別のポートへ逃げるだけだった
(= ポートが1つずつ食い潰される)。

直し: **判定はプロセスの実体で**(`PortHolder.isHeldByTunnelOnly`)—— doctor はそのポートを
名指しして `bridge down --port N` を案内し、`BridgeLauncher.stop()` は台帳が無くても
トンネルだけの占有者を止める(`PortHolder.stopTunnelHolder`)。
**応答の速さ(`probeStatus`)で決めない** —— 最初そうしたら、駆動中で `/status` に答えないだけの
in-app ブリッジまで 8 ポート分「固まり」として並んだ(実測)。「答えないこと」は状態を1つに
決めない、という §44.1 の裏返しがここにも要る。

### 46.10 ブリッジを失ったトンネルが採番の窓を食い潰す

実機のブリッジ起動が途中で落ちる(画面ロック)・起動した側のプロセスが kill される
(拡張は応答の無い `api live serve` を kill→respawn する)と、**iproxy のトンネルだけが
ポートを握ったまま残る**。台帳すら残らない形がある(`stopIproxy` は pid ファイルを消してからでも
殺し損ねる)ので、誰も片付けられない。**窓は 8123-8154 の 32 ポート**で、1台が最大2本
(in-app + xcuitest)使うため、残骸が数本乗るだけで埋まる —— 実地では埋まり切って
`--broadcast` が **`no free port`** で 8 台とも全滅した。

直し2つ: **①供給の入口で掃除する**(`StaleLedgerSweep.sweepTunnelOnlyPorts`。
台帳が1つも無いポートで占有者がトンネルだけのときに止める。起動中のブリッジは `.pid` を
トンネルより**先に**書くので進行中の起動を巻き込まない)/ **②`no free port` に次の一手を添える**
(何が塞いでいるか = `bridge status`・残骸の名指し = `doctor`・空け方 = `bridge down --port`)。

### 46.11 起動しきれないランナーが永久に待ち続けて積み上がる(最重要のリソース漏れ)

ロックされた実機のように**二度と用意できない宛先**に対して `xcodebuild test-without-building` を
撃つと、"Run Destination Preflight: Waiting for the destination to become ready" のまま
**永久に待つ**。起動した側(`api live serve` の自動起動)は拡張に kill→respawn されるので、
その detached タスクごと消え、**誰も止めない**。実地では同じ実機向けのランナーが **10 本**
(+ トンネルの残骸)積み上がり、ポート・DerivedData・CPU を握ったまま採番の窓を埋め尽くした。

直し: 供給の入口で `StaleLedgerSweep.sweepStuckStartingRunners` —— **判定は既存の
`StartingRunnerVerdict.decide` をそのまま使う**(待受していない + 生存が起動予算超え +
起動ログが予算ぶん伸びていない)。起動中のブリッジはログが伸び続け、busy なブリッジは
待受しているので、どちらも巻き込まない。実地確認: 1 run の供給で**トンネル 1 本 +
ランナー 9 本**を回収し、その run は緑のまま完走した。

## 47. 他の機械に繋がった実機のライブ操作が「開けない・別の台が映る・要素が出ない」を順に踏んだ(2026-09-24)

iPhone wave(実機。この Mac とは Wi-Fi、M1Ultra とは USB)をタイル右クリックの「ライブ操作」で
開こうとして、1晩で5つの穴を順に踏んだ。**どれも単体では黙って前の状態を出し続ける**型で、
利用者からは「iPhone wave の画面が出ない」の1文にしか見えない。

### 47.1 前の台の絵・デコーダを捨てていなかった(拡張 0.1.211)

Android → iOS 実機へ切り替えると Android の画面が残った。iOS 実機に simstream(シミュレータ専用)を
起こしていたため新しい絵が来ず、その間にデコード待ちだった Android のフレームが描けて canvas を前面に
戻していた。直し: ①iOS 実機の映像はポーリングへ直行 ②台を切り替えたらデコーダも捨てる
(`clearSnapshot` で `disposeLiveH264`)③右クリックで別の台を開いた時点で前の静止画を消す。

### 47.2 実機のブリッジは udid を名乗らない → 既定ポートの別の実機を「自分」と読んだ

`/status` の udid が nil のとき `BridgeIdentityCheck` は「エンジン一致 = 一致」に倒れ、8123 に居た
iPhone SE3 のブリッジを iPhone wave のものとして掴んだ(返った画面は 750×1334 = SE3)。
`bridge status` が udid を出せるのは台帳 `.device` から読むためで、本人確認だけがこの補完を
通していなかった。直し: `BridgeDiscovery.statusForIdentityCheck`(申告が無いときだけ記録で補う)を
ライブ操作の2か所(宛先確認・`checkAndRestartIfStale`)に通す。**run 側の4か所は未対応**
(その台のために採番したポートを見る経路。実機のレーンが別の実機に奪われても気付かない = 沈黙型)。

### 47.3 自動のフレーム取得は自動起動を撃たない

ブリッジ未起動(booted)の台を開くと「接続できません」のまま何も始まらなかった。serve の自動起動の
引き金は観測・操作の接続拒否だけで、`frame` は受動的な観測として起動を撃たない(設計どおり)。
直し: booted の台へ切り替えたら観測を1回撃つ(`requestOpenObservation`。切り替えが必ず通る
`ensureServeProcess` から)。**busy 中に届いた選択・観測は busy が解けた時点で消化する** ——
`pendingSelectId` を拾うのが `refreshDevices` 後の `applyDevices` だけだったので、画面取得の最中に
届いた右クリックは黙って捨てられていた。

### 47.4 押せる「ライブ操作」が他の機械のタイルだけだった

同じ実機が Wi-Fi 越しに別の Mac からも見えるとき、モニターは USB 側(M1Ultra)のタイルだけを残す。
その台はこの Mac の list-devices に居ないので、`openDevice` は黙って前の台(先頭の停止中シミュレータ)を
出し続けた。**計測(OUTPUT に `[live DIAG]`)で初めて id が `ios:M1Ultra/iPhone wave` だと分かった**
—— 推測で3回外したあと。ユーザー決定: **その機械で動かす**(Wi-Fi でこの Mac から2本目のランナーを
立てると1台に2本になり両方落ちる)。直し: serve を `fleetest remote exec <machine> -- api live serve` で
向こうに起こす。右クリックの `openLiveForDevice` が machine・udid を運び、一覧の取り直しで足し戻す。
配信は張らず serve の frame で取る。一覧に無い台はバナーで言う。

**副産物**: `remote exec` の到達確認の ssh(`echo $HOME`)が **stdin を読んで本番の子の最初の
コマンドを捨てていた**(`-n` で直した。`RemoteExecStdinTests`)。さらに、この `-n` を変異テストで
外したあと**手元のバイナリを作り直さず**に「試して」と言い、利用者が「応答がタイムアウト」を踏んだ
(→ memory `rebuild-after-mutation-testing` 3回目)。

### 47.5 実機では前面のアプリを探せなかった

画面は YouTube なのに要素が SpringBoard のもの。前面追従(`LiveSessionFollower`)は起動中アプリを
`simctl spawn <udid> launchctl list` で採る = 実機では候補が空 → springboard のまま。直し: 実機は
`devicectl device info processes`(実行ファイルのパス)× `apps --include-all-apps`(bundle ID と `url`)で採る
(`IOSPhysicalRunningApps`。0.6 秒前後)。前面の判定は従来どおり `/appstate` で「除外してちょうど1つ」。
実測(SE3・設定アプリ表示中): 候補 14 件のうち前面と答えたのは Preferences と SpringBoard だけ。
iPhone wave(M1Ultra・YouTube)で `frontmost app is com.google.ios.youtube`・要素 43 件を確認。
**この Mac に USB で繋いだ実機でも同じ**(リモート固有ではない)。

### 47.6 ホームボタン機ではアプリスイッチャーの窓が常に「触れる」(ブリッジ v124)

SE3(ホームボタン機・iOS 26)は設定アプリが前面でも `SBSwitcherWindow:Main` を `isHittable` と答え、
`/systemui/covering` が常に true → 前面追従が走らず、47.5 を入れても設定の木が読めなかった

前面アプリ(設定)のカード `card:com.apple.Preferences:…` が**窓いっぱい(375×667)・hittable** のまま
1 枚残る(スイッチャーの窓がアプリの面を抱えている形)。開いているスイッチャーのカードは縮んで並ぶ
(シミュレータ実測 281×612 × 5 枚)ので、**窓より小さいカードがあるときだけ**覆い
(`BridgeAPI.appSwitcherCardIsShrunken`。1pt の許容は端数)。
確認: SE3 設定前面 → false / シミュレータ `POST /appswitcher` → true → `/home` → false。
**診断は応答の marker に載せて読んだ**(スナップショットは窓いっぱいのカードを出さないので、
