# 保守者向けの事故台帳

CLAUDE.md は**規則だけ**を持つ。ここは、その規則が**なぜその形なのか**を思い出すための台帳
——「一度実際に壊した」記録と、判断の経緯を置く。

**読む場面は2つだけ**:

1. CLAUDE.md の規則を**緩めたく / 消したく**なったとき(たいていここに、緩めた結果が書いてある)
2. 同じ型の設計判断を新しい場所でするとき(「同型」で辿れるようにしてある)

日常の作業でここを読む必要は無い。CLAUDE.md の該当行から `→ maintainer-notes.md §N` で来る。

**subsystem に属する設計・計測は各 docs が正典**(ここには置かない):
docs/design.md(設計)/ docs/verification.md(検証の規律)/ docs/performance-tuning.md(性能)/
docs/remote-runner.md(リモート)/ docs/mcp-audit-rounds.md(MCP 監査の台帳)。

## 1. 受け手フロー(install.sh / update.sh)

### 1.1 実行中のシェルスクリプトを pull で差し替えても、古い内容が最後まで走る

`bash` は開いた fd で読み進めるので、git が rename で置換しても**開いた fd は旧 inode を指し続ける**
(実験で確認)。このため pull 直後に自分自身を再 exec しないと、**pull で入った新しいステップは
その回に1つも実行されない**。次回は update.sh が up-to-date で即終了するので、
**永久に実行されない**。

実害: ステップ7.6(受け手の CLAUDE.md へ入口ブロックを置く)が、版だけ上がって一度も走らなかった。

`update.sh` にも同じ再 exec がある。一度は「委譲が中心だから影響は小さい」と判断して入れずに
残したが、**直後に利用者向けの修正(project sync を外部構成でも走らせる)が update.sh 側へ入り、
受け手が2回更新しないと直らない状態を作った**。2周目に `FT_UPDATE_REEXEC` で up-to-date の
早期終了を通さないのは、直前に pull しているので必ず up-to-date になり、素通しすると
project sync とプラグイン更新が飛ぶため。

→ 規則: CLAUDE.md「受け手の一括導入」「受け手の更新」

### 1.2 マーカー置換を素朴に書くと、2回目に利用者の記述を巻き込んで消す

`end` マーカーだけ壊れた CLAUDE.md に対して「最初の begin 〜 最初の end」を置換する実装だと、
**1回目に2つ目のブロックを追記 → 2回目に間に挟まれた利用者の記述ごと削除**する。
2026-08-06 に実際にデータを消して確認した。

いまは begin/end がちょうど1組でなければ1バイトも書かない(片方だけ・2組以上・逆順は
`damaged` で warn 止まり)。`installClaudeMdBlock.test.mjs` が install.sh から python を
抜き出して実行し、この3形を守る。

→ 規則: CLAUDE.md「受け手の一括導入」

### 1.3 クローンが git 管理しているファイルへ書くと、次の更新が永久に止まる

clone 構成では受け手の CLAUDE.md は**クローン自身の追跡ファイル**で、書くとツリーが dirty に
なり、2回目以降の更新が pull ガードで必ず止まる。`git reset --hard` で戻しても次の更新が
同じブロックを書くので堂々巡りになる。2026-08-07 に自己破壊を実再現した。

判定は**レイアウトではなく `git ls-files --error-unmatch` で追跡の有無**を見る
(レイアウトで判定すると、新しい構成が増えるたびに条件が増える)。

**同型**: `packageLockSync`(npm install が lock を書き換えてクローンが dirty になる)。
**一般化**: 受け手のフローに「クローンの中を書く」工程を足すときは必ず追跡を見る。

→ 規則: CLAUDE.md「受け手の一括導入」

### 1.4 出力量と無音は、どちらも承認とフローを壊す

- 生ログを画面へ出すと(54KB)エージェント側で切られ、結果を探す `grep` が承認を増やす。
- 逆に数分の無音は人に「止まった」と誤解され、中断される。

だから**画面は各ステップ1行(逐次)+ 集計だけ・生ログはファイルへ**。逐次表示は人のためのもの。

→ 規則: CLAUDE.md「受け手の一括導入」

## 2. エージェント連携・配布

### 2.1 Codex 対応をインストーラから撤去した理由(2026-08-27)

面倒を見ようとすると、規約位置・プラグインのサブコマンド名・版照合・設定書式が全部その
エージェント固有の分岐になり、**Swift・install.sh・install-skill.sh・update.sh の4箇所へ
手で写す**ことになる。中核はどれもエージェント固有ではない(機械作業 = インストーラ /
`ft_*` = 標準の stdio MCP サーバ / runbook = ツール中立の markdown)ので、案内を
docs/user-docs/tools/other_agents に集約する形に寄せた。経緯と表は docs/design.md §15。

受け手のグローバル設定へ1バイトも書かないのは、そこがセキュリティ境界であることに加え、
**TOML は同じテーブルの重複でファイル全体が無効になる**ため。

### 2.2 Codex のサンドボックスはシェルだけを縛る(2026-08-27 実測)

**MCP サーバはサンドボックスの外**で動くので `ft_*` は既定設定のまま全部動く。通らないのは
シェル経由の導入・更新だけで、原因は権限ではなく **①SwiftPM が `sandbox-exec` を入れ子に使う
(`swift build` が起動できない)②`simctl` が CoreSimulatorService へ届かない**。

`network_access` / `writable_roots` では直らない。以前 install.sh のステップ7.7 が
これらを根拠に false green を出していた。

### 2.3 リポジトリのルートに置いたものはプラグインに載って配られる

プラグイン root = repo ルートなので、ルートの規約ファイルは**そのままプラグインで配布される**。

- 同梱していた `.mcp.json` は `$PWD/Scripts/mcp-server.sh` 依存で、クローンの外でエージェントを
  起動した受け手の MCP が**必ず落ちていた**(`claude plugin details` に `MCP servers (1)`)。
- 同型: ルートの `skills → .claude/skills` リンク。Claude Code は `plugin.json` の明示パスと
  **既定の `skills/` の両方を読む(置換ではなく加算)**ため、**6本が12本として登録**され、
  常時コストが倍(~1,270 → ~2,537 tok)になっていた。

**一般化**: ルートに何か置くときは「プラグインに載ってよいか」を必ず問う。

→ 規則: CLAUDE.md「MCP サーバの起動口」

### 2.4 正典をシンボリックリンクの側へ移さない

raw.githubusercontent はリンクを**本文でなくリンク先の文字列**として返すので、
`install-skill.sh` の curl が SKILL.md ではなく1行のパスを掴む。

## 3. リモート実行・監視

### 3.1 型検査の効かない境界は、片側だけ改名すると黙って壊れる

2026-08-26 の用語統一(host / machine)で `api monitor` の `machineHost`・`api devices-up` の
`host`・`api remote-compat` の `hosts[].name` を改名し ProtocolVersion 9 にした。
同時配布なので旧キーは読まない設計にしたところ、**webview だけ旧キーのまま残り**、
実行プロファイルのリモート参照が `machine: "local"` へ書き換わった。

→ 規則: 型検査の効かない webview 境界は往復テストで縛る(CLAUDE.md「用語」)

### 3.2 親を殺しても子は死なない

ssh 越しの子を spawn する経路では、親を殺しても ssh が生き残ってリモートが走り続け、
`dispatch.lock` も残る(2026-08-18 実測)。SIGKILL へのエスカレートを自分の子に掛けると、
ロック解放と終了スクリプトを飛ばすので **ssh にだけ**掛ける。

**シグナルソースは1プロセスに1組**(2026-08-24・受け手報告): relay ごとに立てて `stop()` で
SIG_DFL を戻すと、並行する子のうち**先に終わったものの stop() が残りの横取りまで解き**、
`kill -INT` で親だけ死ぬ。

### 3.3 実績の回収と後処理の順序

facts の machine 採取は relink より前。relink が reportPath を書き換えると stamp がファイルから
消え、stamp 走査が空振りする(実ディスパッチで machine 欠落を確認)。

**一般化**: 回収後の後処理を足すときは、後段の走査が stamp に依存していないかを見る。

### 3.4 macOS の openrsync では dir-merge が `--delete` から受け側を守らない

`rsync -F`(dir-merge)を使うとランナー機の台帳が消える(実験で確認)。除外は
`.fleetest-transfer-ignore` を `--exclude` 相当で明示的に読む形にしてある。

### 3.5 ssh 越しのコマンドにグロブを書かない(相手は zsh。マッチ無しは「文字列のまま」にならない)

`ssh <host> '<コマンド>'` を解釈するのは**相手のログインシェル**で、macOS の既定は zsh。
sh/bash と違い、**マッチしないグロブはエラーになる**(`no matches found`)。しかも壊れ方が
2通りあり、どちらも 2026-08-31 に実機で確認した:

| 形 | zsh の挙動 |
|---|---|
| `rm -rf <nomatch>` (単純コマンド) | そのコマンドだけ失敗(exit 1)。**後続の文は動く** |
| `for w in <nomatch>; do …; done` | **シェルごと終了**(exit 1)。**後続の文が1つも動かない** |

前者は「録画が無い run のたびに `warning: failed to delete …`」、後者は「まだ誰も setup して
いないランナーで、旧 `work` の片付けまで丸ごと落ちる」という形で出る。**2文に分けても直らない**
(後者はシェル自体が終わる)。

→ 規則: **リモートで回す一覧は `find … 2>/dev/null` で作る**(1件も無ければ空の出力になるだけ)。
`RemoteHooksReap.commandAcrossIssuers` と `RemoteArtifactCollection.deleteRecordingsCommand` が
その形。パスに空白が入らないこと(`validateBase` / `validateIssuerKey`)が語分割の前提。

### 3.6 「消す」コマンドは階層を数え間違えても静かに成功する

回収済み録画の削除を `results/runs/*/recordings` と書いたが、実際の置き場は
`results/runs/<YYYY-MM>/<runID>/recordings`(`RunResultsStore.runDir` が月の階層を挟む)。
**1件も消えないのに成功**するので、テストが文字列を固定しているだけだと気付けない
(2026-08-31 のレビューで発見。単体テストは誤った期待値ごと緑だった)。

→ 規則: パスの深さに依存する削除・走査は、**実データのあるランナーで `-print` して1件以上
当たることを確かめる**(実際に当ててから `rm` へ変える)。

## 4. ビルド・検証

### 4.1 E2E の最中に本線をビルドすると、run が「テストの失敗」に化ける

同じ `.build` を共有するので、**実行中の `fleetest` バイナリが差し替わってプロセスが SIGKILL
される**(`Killed: 9`)。2026-08-15 にフル E2E の最中に単体テストを回したところ、3プロファイルが
同時刻の連番 PID で落ち、**テストの失敗に見える形で赤くなった**(実際は1本も走っていない)。

見分け方: `Scripts/e2e.sh: line NNN: <pid> Killed: 9` と、シナリオ0本での即死。
**待つ間に手を動かしたくなる場面ほど踏む**。

### 4.2 長時間ジョブを `pgrep` で待つと、待機どうしが相互に「実行中」と見る

`pgrep -f <文字列>` は自分自身こそ除外するが、**同じ文字列を含む他のシェルは拾う** ——
待機コマンド自身のコマンドラインにその文字列が載るので、待機を2つ以上同時に走らせると
全員が止まらない。2026-08-09 に E2E の待機が3つ残り、次のスイートが1本も起動しないまま
「実行中」と表示され続けた(実験で機構を確認済み)。

→ 規則: ジョブ自身が出す成果物で待つ(CLAUDE.md「ビルド・検証」)

### 4.3 jsdom の閉じ忘れ1本でスイート全体が止まる

`pretendToBeVisual` の rAF と `main.js` の `setInterval` が残るとプロセスが終了せず、
`node --test` はファイル単位の子プロセスの終了を待つ。2026-08-17 に**10本中1本の漏れで
`npm test` が終わらなくなった**(個々のテストは1〜2秒で、遅いテストは1つも無かった)。

二重に塞いである: `jsdomTeardown.test.mjs` がソース走査で落とし(**コメント中の
`window.close()` を実装と数えない** —— 規律はコメントで説明されているので素の一致だと
素通しする)、`npm test` は `--test-force-exit` を付けてある。

**同型**: `argumentHelpLiteral.test.mjs` —— `ArgumentHelp` は文字列リテラルからしか作れないので
`help: "…" + "…"` はコンパイルが通らない(4回踏んだ)。
**一般化**: 「コンパイルで落ちる誤り」や「テストが終わらない」型は、`swift build` / `npm test` を
1回払うまで気付けないので、ソース走査で秒未満に落とす。

### 4.4 版を上げ忘れると、稼働中の旧ブリッジが再利用されて変更が反映されないまま緑になる

実害2回。**Android の版上げは revert しても端末側が戻らない**(2026-08-14):
Android は versionCode の引き下げインストールを拒否するので、上げた版を配った後に版を戻すと
ホストは古い版を入れ直せず、**全台が「no response to status」で応答不能**になる。
フリート8台が全滅し、`adb uninstall com.example.ftbridge` を全台に打つまで復旧しない
(その後も数台が凍結し、落ち着くまで2周かかった)。

→ **試行的な変更ほどブリッジに入れない**。ホスト側で完結できないかを先に問う
(この件の本修正は結局ホストだけで足りた)。

### 4.4.1 フレームワーク差の退行は SUT を跨がないと出ない

探索終端の空打ちドラッグは **CMP では無害・SwiftUI ではタブバーが反応**し、E2E-iOS を回すまで
5/5 の回帰に気付けなかった。

→ 規則: スナップショット/型写像と操作合成を触ったら SUT を絞らず全部回す

### 4.5 回さなかったエンジンは、緑の E2E からは見えない

in-app / xcuitest 両方のスナップショット生成を変えた回の E2E **254 本が全部 engine=xcuitest**
で、in-app 側は1度も動かないまま緑になった。いまは `BridgeSourceSet` の digest を
「そのエンジンの実行が全部成功したときだけ」記録し、食い違いを警告する(落とさない)。

### 4.5.1 「フル E2E」は iOS を in-app で回すので、慣性のある経路の退行を見逃す(2026-08-28)

`8a416bc0`(容器推定を scrollable 申告の祖先優先へ)が **CMP の xcuitest 限定の退行**を入れた。
コミットは「フル E2E 5 SUT 緑」で検証を宣言し、**同時に CLAUDE.md へ「この関数は…触ったら
5 SUT のフル E2E」という規律を自分で書き足している**。規律は守られていて、それでも見逃した ——
**既定のフルスイートは iOS を in-app で回す**からで、in-app は慣性を持たないので
この退行は原理的に現れない。

**壊れ方**: 縦リストの `[8] id=list_rows` は `scroll` を申告せず、その外側の全画面
`[1] scrollView` だけが申告する。新規則は最も近い scrollable 祖先を採るので、**容器が
画面全体になる**。旧規則(同じ深さの子を2つ持つ直近の祖先)は `#list_rows` を採っていた。
容器が画面全体だと「先頭へ」直後にまだ慣性で動いているリストの見切れ・整定判定が効かず、
行を**移動前の座標で撃つ**(`the target has moved (0,-13) since the preceding tap`)。

**特定の仕方(35 分・2 run で足りた)**: 単一シナリオを `fleetest run --scenario` で回すと
36 秒で決定的に再現する。worktree に古いコミットを出し、**SUT の成果物は本線から
シンボリックリンクで固定**して道具だけを変数にする。窓の手前(`265b51fe`)で PASS することを
先に確かめてから二分した(FM が死んでいる状態も両側で揃えた —— 揃えないと「FM のせい」と
読み違える)。

| | S0110 | S0020 |
|---|---|---|
| `8a416bc0^` | PASS(2/2) | PASS |
| `8a416bc0` | FAIL | FAIL |

**同日 `931897d6` で修正済み**(起票 16:37 → 修正 18:56)。単純な revert は受け手の横カルーセルの
不具合を戻すので不可。採ったのは**倒す条件を元の不具合そのものの形に絞る**こと ——
申告の祖先へ倒すのは `canHold` が偽、つまり**深さ由来の候補が要素を収められない**ときだけで、
それ以外は 2026-08-23 以前とまったく同じ経路(候補が無ければ nil を返すところまで含めて。
nil と「画面全体」は下流で別物として効く)。**位置を見る述語は実機で2案とも否定された**
(収まり/重なり。動いている最中は行が容器の縁・外に報告されるので、まさに効いてほしい瞬間だけ
申告容器へ倒れる)。**意図した代償**: 実アプリコーパス `and-browser_weather_weekly` の ghost 誤検知が
1件戻る(スクロール探索が別の行を撃つ実害と、警告レベルの検知1件を秤にかけた判断)。
回帰の witness は `ClippingContainerScrollableTests` の
`testKeepsTheRowContainerWhileOtherRowsAreReportedOutsideIt`(退行の形)と
`testFallsBackToTheDeclaredScrollerWhenTheTightCandidateCannotHoldTheElement`(元の不具合の形)。
検証は退行した2シナリオの実機 PASS と `e2e.sh --ios-xcuitest` で CMP 34/34(退行前と同値)。

**この節は 2026-09-03 まで「未修正」のまま残っていた** —— 起票と修正が同じ日でも、
**台帳を閉じるのは別の作業**。閉じ忘れると次のセッションが着手して初めて気づく(実際に着手しかけた)。

**規律への反映**: 幾何・容器推定・整定のように**実ジェスチャの慣性で挙動が変わる**変更は、
フルスイートに加えて **`--ios-xcuitest`** を明記する(CLAUDE.md の範囲表)。

### 4.6 コードの正しさと、それが受け手へ届くことは別

9コミット積んだ後で `Scripts/update.sh` を実際に走らせたら、**2回目以降の更新が必ず失敗する**
欠陥が出た(2026-08-07)。3ラウンドの実アプリ監査でも単体テストでも1度も出ていない。

### 4.6.1 同じ型はほぼ必ず複数ある

2026-07-31 の1セッションで4回掃討して**4回とも見つかった**: Android の読み前 `refresh()` 漏れが
3経路目にも / `forScroll` を落とすラッパー群 / ランナーの 409 多重定義 / 整定の打ち切りを黙る3層。

→ 規則: CLAUDE.md「不具合を直したら『同じ型が他に無いか』を機械的に掃討する」

### 4.7 「読む回数を減らす」最適化は、その読みが担っている砦を先に列挙する

MCP の `ft_scroll_to` が 0 スワイプでも木を2回読むのを1回にしたら、既存の回帰テスト2本が
落ちて**2枚目を読むこと自体がガードだった**と分かった(2026-08-12。返す木 = 照合した木に
すると、対象の消失も画面外への移動も定義上検出できなくなる)。実装は撤回。詳細は docs/design.md。

**一般化**: 節約できるのは**誰も見ていない読み**だけ。省く前に「この読みの結果を何が見ているか」を
grep で数え、ガードなら速さと引き換えにしない。

### 4.8 「差が出ない」ときは仮説より先に実験系を疑う

差が出ないことは、**変更が無効だったこと**と**実験が無効だったこと**を区別しない。
実行の実体は `fleetest` ではなく **`fleetest-scenarios-<project>` サブプロセス**なので、
A/B で `fleetest` を差し替えても base と fix が同一コードを走る(2026-08-03 に性能の A/B と
修正案2件を取り違えた)。詳細は docs/verification.md。

### 4.9 並列テストはプロセスを分けるので、ホスト共有資源に触るテストは自分で隔離する

既定のパスを直接見に行くと、無関係なテストの後始末と競合して落ちる(2026-08-10 に `FMBreaker`
で実際に発生)。状態ファイルがホスト単位なのは仕様なので、**テスト側が差し替え口で
プロセスごとの一時パスへ逃がす**。

### 4.10 検知は「出ない」ことを設計の根拠にしない

- 自前 SUT の全数掃討で誤検知0でも、**実アプリでは出る**(2026-08-06 に5形、2026-08-07 に3形。
  どちらも自前 SUT は0件)。木が要る検知は dry-run では当てられない。
- 逆向きも成り立つ: **固定コーパスで0件も自前 SUT の実画面を代表しない**。木の欠落検知
  (`TreeCoverage`)は 37 枚のコーパスで誤検知0だったのに、**フル E2E では 5 SUT すべての
  緑の run で毎回発火**した(真陽性 —— `webview.html` は `aria-hidden` の見出しを持つ、
  この検知の offline witness そのもの)。

**実 web ページの幾何判定**も同じ6枚で誤検知が出た(折り返す inline テキストの矩形が重なる形。
件数と内訳は docs/verification.md が正典 —— CLAUDE.md 側の数字は食い違っていたので落とした)。

→ 規則: 「出ない」を根拠にするなら、コーパスとデバイス実行の**両方**で確かめる。とくに注記を
毎ステップの経路へ配線するときは、発火率がそのまま出力とレポートの雑音になる。

### 4.11 陰性(誤検知0)の確認は「常に false を返す検出器」と区別できない

2026-08-11 の凍結カウンタは「10台すべてに frozen が乗り誤検知0」を根拠にマージされ、
**恒久 false のまま入った**(抑制ガードが観測より手前にあり、実運用の全デバイスが判定対象から
外れていた)。だから意図的に起こせない事象には注入口(`FrozenInjection` /
`FT_FAKE_FROZEN_KEYS`)を用意し、注入は**観測と公表の経路だけ**を通す。

**同型の一般形**: 「観測」と「配信(表示の最適化)」を同じループに書かない。配信中のタイルの
フレーム生成を止める `suppressFrames` が**観測より手前**にあったため、実運用の全デバイスが
判定対象から外れていた。

### 4.12 変異が生き残ったときに疑う順序

1. フィルタが狙ったクラスに当たっているか(`--filter` は**ファイル名ではなくクラス名**。
   `--filter TapTargetAdvisoryTests` を打ったのに、同じファイルの別クラス
   `TapAdvisoryKindPriorityTests` が1本も走っていなかった。同型を2回踏んでいる)
2. **先に落ちたテストがプロセスごと死んで後続を隠していないか**(ログに `Fatal error` /
   `signal code`。2026-08-18: テスト内の強制アンラップが変異でクラッシュし、同プロセスの
   残り全テストが走らないまま「生き残り」に見えた)。
   → **テストでは失敗アサーション後に `!` で触らない** —— guard + XCTFail で止める
3. **変異式が本当に挙動を変えているか**(既定引数を足すだけ・使われない関数を足すだけは
   何も壊していない)
4. そのうえで初めてテストの内容

### 4.13 テストが production の関数を実際に通っているか

掃討ハーネスが `!e.enabled` を自前で書いていたため、`RefGuard.disabledWarning` を壊しても
落ちなかった。検出できない変異が出たらテストを境界へ寄せる(要素数を増やす・既定値でなく
限界値で呼ぶ)。

### 4.13.1 テストが production の代わりに前処理をしていないか

`XCTAssertEqual(plan(target, normalize(actual)), .done)` のようにアサーション側で production と
同じ前処理を掛けると、production の前処理を外しても落ちない。渡すのは**生の入力**だけにする。

**併せて**: 壊れ方が入力で割れるものは、割れた先ごとに入力を用意する。不可視文字の混入は
**途中なら `.unverifiable` で黙って受理・末尾なら `.deleteExcess` で打ち直しループ→失敗**と
別々に壊れ、途中形の入力だけでは正規化を外した変異を1つも殺せない。

### 4.14 陽性対照は pass/fail でなく出力の文言まで読む

主張を含む文言(「天井でも足りない」等)は、**主張が偽になる周回**が設計に残っていても
単体テストでは緑のままになる。2026-08-15 に実際に嘘を出し、latch へ設計変更した。

## 5. 同じ判定を2箇所に持つと、同じ画面で違うことを言う

**共有するのは「判定」であって「文言」ではない**(2026-08-15)。文言まで一本化しようとすると
既存の応答文字列を壊して MCP のテストと `NoteBudgetTests` に当たる。正しい形は
**①判定・順序・当たり判定を FTCore に1つ ②文言は呼び手ごとに持つ**。

食い違っていた実例:

| 事実 | 中核(FTCore) | 呼び手 | 起きていたこと |
|---|---|---|---|
| タップ前警告の連鎖 | `TapTargetGeometry.advisoryKind` | `occlusionAdvisory`(DSL)/ `RefGuard.overlapWarning`(MCP) | 同じ優先順を2箇所に手で書いており、**2形(ゼロ幅高さ frame・縁の細切れ)が DSL にだけあって MCP のタップ時に出ていなかった**。「同じ優先順」はテストのコメントに書いてあっただけで、照合するテストは1本も無かった |
| 近い候補の選定 | `FTCore.SimilarLabels` | MCP / `StepExecutor.candidateHint` | DSL 側が MCP の捨てた旧版(部分文字列一致・文書順の先着3件)のままで、装飾要素が枠を埋めて実在する操作可能要素を出せない画面があった |
| back の空振り | `FTCore.BackEffect` | 中核文 + 呼び手ごとの advice(MCP は `ft_screenshot` / `ft_scroll_to`、DSL は `back()` を呼び直す) | ― |
| 打ち切りの逃げ道 | `FTCore.SnapshotTruncation.remedy` | MCP / DSL | **DSL だけが「対象に近づくようスクロールする」と勧めていた**。同じ事実に MCP は「スクロールしても戻ってこない」と書いており、同じ画面で逆のことを言っていた |
| 画面外の一致 | `TapTargetGeometry.offscreenScrollGateCentre` | 探索のゲート / 逆走査 `reverseSweep` / `ft_scroll_to` の再照合 / `requireVisible` の幾何 Tier-0(`StepExecutor.occlusionFlip`) | 逆走査と `requireVisible` に述語が無く、iOS の木に残る通り過ぎた要素への `exist(scroll:)` が成功していた(受け手報告) |
| ghost の掴み直し | ― | `RefGuard.ghostWarning`(MCP) | DSL の「掴み直して送り直す」合図を MCP でタップ拒否へ格上げしたら、実アプリで誤検知が5形出て警告へ後退した(docs/design.md §10) |

**MCP は DSL と別経路**なので、鮮度・防御を DSL 側に入れただけでは届かない
(2026-08-06 に3件まとめて踏んだ: スクロール後の古い木・容器外 ghost への座標タップ・
pressEnter の焦点待ち)。**ただし同じ判定をそのまま強い挙動へ流用しない** —— DSL の
「掴み直して送り直す」合図を MCP でタップ拒否に格上げしたら、実アプリで誤検知が5形出て
警告へ後退した。

→ 規則: CLAUDE.md「判定は MCP と DSL で共有する」/ 新しい検知はまず警告から

## 6. 部分失敗の扱いは両方向に間違える

- **1台の失敗で全体を落とさない**: ブリッジ供給が 10台中8台 ready でも残り2台の期限切れで
  throw し、**Flutter/RN の 51 本が1本も走らなかった**(健全な8台は待機のまま。2026-08-11)。
- **逆向きも守る**: 全レーンが同時に落ちているときにレーンを離脱させない。外部障害で全部離脱 →
  revive 上限 → 未実行が連鎖した(受け手報告。2026-08-24)。連続失敗での離脱は
  「その streak の間に別のレーンが通った」証拠があるときだけ。

→ 一般化: 「N個中1個の失敗を致命にしていないか」と「全部落ちているのに1個ずつ切っていないか」を
供給・インストール・回復の各段で両方見る。

## 11. 「陽性/陰性」の極性が2つあった(2026-09-03 に一本化)

occlusion-guard **だけ**が「発火すると赤になる検知」で、他のあらゆる場所では陽性 = 緑。
そのため**同じ事象——覆われているのに警告が出ない——が、検知として語ると偽陰性、判定として
語ると偽陽性**になっていた。2026-08-14 のカレンダー(ナビバーの下へ潜ったセルを黙って撃つ)は
mcp-audit-rounds では「偽陰性」、StepExecutor+Assert 側の同じ現象は「偽陽性」と書かれている。

**新語は作っていない。実勢の追認**(一本化前の件数):

| 語 | Sources | docs | Tests |
|---|---|---|---|
| 誤検知 | 51 | 91 | 109 |
| 真陽性 | 8 | 25 | 73 |
| **偽陽性** | **26** | **44** | **17** |
| 誤反転 | 5 | 32 | 3 |
| 誤った緑 / 誤った成功 | 21 | 10 | 15 |

カレンダーの表は**同じ段落の中で**「+189 件の**誤検知**」「**真陽性**が 30 件失われる」と書いており、
実務では既に `真陽性 ⇄ 誤検知` で対になっていた。跨いでいたのは `偽陽性` の一語だけなので、
**その語を捨てるのが最小の手当て**(語を増やす案・接頭辞で修飾する案は、書くたびにどちらか
判断が要る点が変わらないので採らない)。

**`falsePositiveCheck` は改名しない**。受け手の実行プロファイル JSON に既に書かれている鍵で、
拡張のフォーム・user-docs・README もこの名前で説明している。**例外を1つに閉じるほうが、
契約を割って例外をゼロにするより安い** —— 代わりに [RunProfile.swift](../Sources/FTCore/RunProfile.swift)
の宣言に「= 誤った緑の検査」と定義を1行添えてある。

**受け手向けの面も走査する**。docs/user-docs/ に散文の用例は1件しかなく(Android の WebView が
スクショに写らない節)、**受け手向けには用語ごと落として平文にした**(「シナリオ自体とは無関係な
理由で失敗することがあります」/ en: `can fail for reasons that have nothing to do with your
scenario`)—— 受け手に検知と判定の語彙を教える必要は無く、平文のほうが短い。残りは `falsePositiveCheck`
のラベルなので例外に載る。**対象外は TestProjects/(ユーザー資産。CLAUDE.md「並列一括作業」)と
reports/(.gitignore 済みの生成物と Apple へ提出済みの資料)だけ**。

→ 新しい混入は `Tests/FTCoreTests/VocabularyPolarityTests.swift` が落とす。
**規則を定義している2ファイル(CLAUDE.md・この文書)だけは走査の対象外** —— 禁止語を書けないと
規則そのものが書けないため。この2ファイルは人間の規律で守る。

## 12. 実機探索(2026-09-01・iPhone 13)で出た構造的な誤り

### 12.1 比で置いた余白は、窓が低い文脈で縁の内側へ落ちる

横向き(844x390)の SUT で `scrollTo` / `swipe` / `scrollFrame` 指定のすべてが
「nothing moved」で終わった。原因はスワイプの始点で、`BridgeAPI.defaultSwipeMarginRatio`
(0.25)は**窓の高さに対する比**なので 0.75×390 = 292.5pt となり、下部タブバーの上端 290pt の
**2.5pt 内側**に落ちていた。座標ドラッグを 250→60 に変えると同じ画面が 137pt 動く。

比そのものは縦向き(0.75×844 = 633pt、下端から 211pt)で詰めた値で、その文脈では正しい。
**同じ比が、窓が低い文脈では「縁からの絶対距離」を失う**。定数の doc には
「横向きの下部バーは ~y=341 から始まる」という当時の実測が残っていたが、
アイコン+ラベルのタブバー(実測 80pt + セーフエリア 20pt)では 290pt から始まる。

直しは**比に絶対距離の床を足す**(`BridgeAPI.bottomChromeClearance` = 120pt)。
ランナー(木を持たない)と host(木を持つ)の両方が同じ定数を使い、host 側は
`ScrollGeometry.startMarginClearingBottomChrome` で viewport の下端から測る。
キーボードで削られた viewport には掛けない(あちらは既存の分岐が担当)。

**一般化**: 比で置いた余白を別の向き・別の窓サイズへ持ち込むときは、
**その比が縁から何 pt になるか**を両方の文脈で書き出すこと。片方でしか成り立たない値は、
比のままでは移せない。→ CLAUDE.md「片方の文脈で詰めた値を別の文脈へ流用しない」

### 12.2 平坦な木では、depth からの祖先復元は「収めている」を意味しない

同じ探索で、上に貼り付いた検索欄(`textView #field_search` (56,55 326x57))が
**両方向の誤り**を同時に起こしていた。

- **見逃し**: スクロールでその欄の下へ潜った `#btn_wishlist_electronics_4` (332,85 32x32) を
  ref タップすると、警告ゼロで「クリア」ボタンに当たり検索語が消えた。
  `suspectedHiddenUnderChrome` は「中心を覆う相手が**スクロール容器の外**に居ること」を
  条件にしていたが、sticky ヘッダは victim と**同じ root scrollView の中**に居る
  (ヘッダ depth 10 / victim depth 12 / scrollView depth 7)。
  さらに、平坦な木の depth 由来の祖先復元はこの欄を victim の**祖先**にしてしまうので、
  「系譜を除く」書き方でも落ちる。**収めているかは幾何で見る**(`contains`)。
- **誤検知**: 同じ画面で、商品写真の上に正しく描かれているハート4件に
  ⚠️scroll-leftover が付いた。`clippingContainer` の「同じ depth の行を2件以上含む直近の
  浅い候補」規則を、その検索欄が満たしてしまうため(平坦な木では後続の全要素がその欄の
  「子孫」になる)。**行を2件供給していたのは、その欄の下に潜り込んだクランプ残骸そのもの**で、
  誤りが強いほど条件が満たされる形だった。直しは**入力欄を容器候補にしない**。

**一般化**: preorder + depth からの復元は「木の形」であって「描画の包含関係」ではない。
包含・遮蔽・クリップを論じる述語では、復元した親子関係をそのまま根拠にしない。

### 12.3 検知のゲートを「そこに在るもの」で絞ると、消える形ほど外れる

`TreeCoverage.missingPageContent` は「アドレス欄が在ること」をブラウザ判定に使っていた。
モーダル(Safari の「さらに表示」)は**アドレス欄ごと**木を置き換えるので、
ページが画面に見えているのに未代表率 0.523 で黙る = **悪い形ほど検知が外れる**。
根拠を「セッションのアプリが既知のブラウザか」(`holdsWebContent`)へ移すと、
固定コーパス40枚の発火集合は1枚も変わらないままこの形だけを拾える。

**一般化**: 「X が無い」ことを言う検知のゲートに「X の隣にある Y が在ること」を使わない。
Y も一緒に消える壊れ方があると、そこだけ穴になる。
