- **ライブ操作の入口の型検査**: JSON の true/false が `intField`/`doubleField`/gesture の点で 1/0 として通った(`{"cmd":"type","ref":true}` がドライバへ)。
  MCP は `isJSONBoolean` で弾いていた → `ArgumentBounds.isJSONBoolean` に移して共有。逆向き(数値 1 を「the boolean true」と書く)も。
  **`case let v as Bool where isJSONBoolean(v)` は束縛後の値を見るので数値の 1 も真になる** —— 判定は束縛前の値で
- **ライブ操作の ref 付き type/clear に「入力欄でない要素」の門が無い**: ボタンを先にタップしてから 4 秒待って 500/409。判定を

- **ライブ操作の文字列の欄に NUL の門が無い**(MCP は宣言欄の NUL を断る = `Process` が abort するため)→ `ArgumentBounds.nulViolation` を共有。
  配列の欄の型違いに「pass a JSON string」と言っていた → 「pass a JSON array」
- **リモートの ssh の 255 を「run が終わった/失敗した」と言い切っていた**: 飽和した M1Max(load 658)で banner exchange のタイムアウト = run が始まったかも

## MN-90 iOS Simulator の描画崩壊の検査(2026-10-19)
MN-89 の「CMP の iOS アプリが全 Simulator で白紙」が出発点。木は正常なまま画面だけが壊れるので、木だけを読む検証(`keyboardIsShown`・`checkIsON`・`exist("#id")` …)が壊れた画面で緑になる。
文字の検証は既存のテキストの可視性検証が赤にする。設計は docs/design/dsl-execution.md「描画崩壊の検査」。

### MN-90.1 観測
- **形は2つ**: アプリの領域が**一色**(白・黒。観測の約 70%)/ 図形は描かれるが**文字が一つも無い**(約 30%・Compose のみ)。一色は Compose・Flutter で見た
- **直らない**: 壊れた Compose のプロセスは、触らずに置いても 26 分以上文字なしのままだった。アプリを起動し直すまで戻らない
- **アプリのログの Metal エラーは信号に採らない**: 健全なプロセスも同じエラーをログに出す(壊れていない画面と区別できず、誤検知の元)

### MN-90.2 閾値と全数走査
- iOS の失敗スクリーンショット 2,453 枚(レポートの要素一覧 + PNG)を全数走査。目視で崩壊と確かめた最小は文字要素 2 個。全てインク無しだが崩壊でなかった最大は 2 個
  (木と絵を取った時刻が違った)。そこで閾値は **3 個以上**
- もう一つの崩壊でない当たりは**横向きに回転したスクリーンショット**(木の向きと違う)。**向きが違えば判定しない**門を置いた理由
- インクの閾値(輝度の標準偏差 12)はテキストの可視性検証と同じ値を共有する

### MN-90.3 検査点を区間の終わりにした理由
- 通る検証ごとに撮ると、画素で文字を確認した検証(静的テキスト要素のインク・OCR の読み・FM の可視)が既にある区間でもスクリーンショットを払う。
  文字の確認が通れば描画は確認済みなので負債を消し、**確認の無かった区間の終わり**(`launchApp` / `restartApp` / `clearAppData` / `terminateApp` の直前・`afterEach` の前・シナリオの末尾)に1回だけ撮る
- 費用はスクリーンショット1枚(Simulator で約 100〜115ms)。撮るのは E2E の iOS 実行の 15%(直近3日)
- 見つけても即赤にせず、1 秒あけて撮り直し、**まだ見つかるときだけ**失敗にする(描画の追いつきを赤にしない)
- 計測と陽性対照の入口: `FT_RENDER_COLLAPSE_EVERY_ASSERTION=1`(通る検証ごとに判定して赤にする。デバイス実行で誤検知を数える用)/ `FT_FAKE_RENDER_COLLAPSE=1`(判定の答えだけを差し替える)
- 実機と Android は対象外(ユーザー決定)

### MN-90.4 画面全体が一色の写真は書き分ける

失敗レポートの全数走査で SwiftUI に当たった 3 件は、**ステータスバーとホームインジケータまで画素値 0** の真っ黒だった
(ステータスバーは OS が描く = アプリの描画ではなく画面そのものが写っていない・表示が止まった)。同じ日の Flutter の当たり
12 件も、一覧画像では時計の帯が写っていない同じ形だった(元画像は消えていて測り直していない)。そこで判定は、アプリの領域が
一色のうち**画面全体まで一色**(`BlankFrameDetector.isUniformBlank`)を `wholeScreenBlank` として別の事実で書く。
自前描画でないアプリ(SwiftUI・UIKit・RN)は判定しないので、この形で木だけの検証が緑になる余地は残る(docs/open-issues.md)。

## MN-91 別のワークスペースのランナーの隣に2本目を起動していた(2026-10-19)

worktree から回した E2E の最中に、本線のワークスペースの版のブリッジが -02・-04・-05・-07・-08 に1台ずつ起動し直され、
worktree の run がそれらの端末を「別のワークスペースのブリッジ」として使えなくなった(Flutter の run がほぼ全滅)。
- 起こしたのはおそらく本線のモニターの xcresult の保持(`monitorBridgeLogRotation.ts` → `fleetest api restart-bridge`)。
  時刻は xcresult の束の作成時刻と一致し、親の外れた xcodebuild として起動されていた(拡張のログはその時間帯が残っておらず直接の記録は無い)
- restart-bridge の「使用中なら断る」は**自分のワークスペースの lease** だけを見る。別のワークスペースの run の lease は見えない
- 供給の計画段は、`/status` に答えた別のワークスペースのランナーは止めずに避ける(`.reuseForeign` / `.blockedByForeign`)が、
  **答えないランナーは自分の台帳(pid ファイル)でしか探さなかった**。run の操作を処理中のランナーは 2 秒の `/status` に
  答えないことがあり、「居ない」と読んで同じ端末に新しいポートで2本目を起動した(1台1ランナーなので相手が壊れる)
- 直し: 起動引数から持ち主を読み(`BridgeOwnership.runnerProcess`)、答えない別のワークスペースのランナーが居る端末は
  `.blockedByForeign` にする。restart-bridge も run の入口も同じ計画段を通るので両方に効く

### MN-92.4 type(replace:) が撮り直す前の ref で打ち、別の欄へ入ったのに成功を返した
- E2E-CMP S0040(xcuitest)の `password=xyz` の形。消去の事後確認(`residualClearValue`)が `/snapshot` を撮るとランナーは ref の表を作り直すのに、
  打鍵はステップ開始時の ref で撃っていた。番号がずれてパスワード欄を指し、ランナーはそこへ打って読み返し(CMP のパスワード欄は `textView` で
  伏せ字扱いされず、`•••` は比べられない = `.unverifiable` で受理)、成功を返した
- 直し(ホストだけ・版上げなし): 消去は最後に actingDriver が撮った木を返し(`ClearOutcome.cleared(actingDriverSnapshot:)`)、type はその木で
  引き直してから撃つ。引けなければ撃たずに失敗。同型の掃討: Android の消去(`valueBeforeClear` で撮り直した後に古い ref で消していた)と、
  in-app の読み返しの追送・打ち直し(`awaitTypeCommit` で撮った後に古い ref で撃っていた)も、撮った木の ref で撃つ
- S0040 の残り 14 件(欄は `xyz`・echo が `single=` に見えた形)は、木は `single=xyz` で写真は形だけで文字が無い = CMP の iOS の描画崩壊を
  可視性検証が止めた赤だった(このシナリオに偏りは無い。docs/open-issues.md の白紙の項目)。木の値を見ずに「echo が更新されない」と読んだのが誤り
- **規律**: ブリッジの ref はそのドライバが最後に撮った木の中でだけ有効。撮ったら、その後に撃つ ref はその木から引く(`liftCoveredTarget` と同じ)
- 残り: ブリッジ側の二重の備え(ref と一緒に期待する identifier と型を送り、食い違えば断る)は版上げを伴うので未着手。
  **Android も備えは無い** —— 注入層が使う `refIds.get(ref)` はブリッジ自身の表から引いた identifier で、ホストの期待との照合ではない
  (古い番号なら新しい表の別の要素の identifier を引いてそのまま撃つ)。中身は docs/open-issues.md
