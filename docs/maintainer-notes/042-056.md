## MN-42 負荷テストで出たロックとライブ操作の穴(2026-09-22)

3 機フリート(手元 8 + M1Max 4 + M1Ultra 6)を回しながら、**実機 4 台は MCP で並行に叩く**構成で
50 分(MCP/ライブ 10,023 呼び出し・fleet run 7 本)。**実機を `fleetest run` で回さない**のは、
`dispatch.lock` が 1 マシン 1 run を保証する以上、実機の run(1 本 30〜40 分)がロックを占有して
フリートが 1 周も走らないため —— MCP はロックを取らないので、フリートと同時に叩ける
(ユーザー提案)。

### MN-42.1 待っている間に保持者が死んだロックが、永久に残る

run の親を SIGKILL したあと、`--wait-lock 3600` で待っていた run が `still queued … 420s` を
出し続けた。`~/.fleetest/dispatch.lock/info.json` の pid は死んでいる。手動の
`fleetest remote unlock --runner local` は「your dispatch (pid …) is no longer running on this
machine」と正しく外せたので、**判定は正しく、呼ばれるタイミングだけが穴**だった。

```swift
// (1回だけ試す —— 他人のロックは何周しても答えが変わらない)
if case .held = outcome, !autoReleaseTried { … }
```

コメントの前提は**他人のロックには正しい**。だが**自分のロックは、待っている間に保持者が死ぬ**
= 答えが変わる。しかも待ち始めた時点では保持者が生きているのが普通なので、**その1回はほぼ必ず
空振りする**。`autoReleaseOurDeadLock()` はロックを読む + `pidAlive`(sysctl 1回)だけなので、
毎周撃っても安い。**「答えが変わらない」と書くときは、誰のどの性質が変わらないのかを確かめる**。

### MN-42.2 ロックが「空き」のままの時間が長い —— 取るのがビルドの後だった

ユーザー指摘「ロックしても 空き のままになっている時間が多い」。時刻付きで測ると:

```
07:32:09  run 開始 → "building E2E-RN locally to split the scenarios"
07:32:34  local: 1 scenario(s) on 8 device(s)     ← ビルド + 配分に 25 秒
07:32:35  （ここで初めてロックを取りに行く）
```

規律③は「取るのは run の入口(ビルドにもデバイスにも触る前。`swift build` も重い負荷なので
直列化する)」。**規律が防ごうとした当のものが、規律の外で起きていた**。加えて FIFO の待機列の
順序が実質「ビルドが終わった順」になり、先に打った run が追い越される。

**構造上の依存は本物**(機械ごとのロック対象は配分の結果で決まり、配分にはシナリオ一覧が要る)
なので、2 段に分けた: **①チケットだけ先に確定させる**(`setenv` まで書く —— 発行だけでは
取得時に `Date()` で採り直される)**②ローカルのロックをビルドの前に先取りし、配分が確定したら
無条件で解放する**。本取得は従来どおり `DispatchPrelock` が全順序で行う。

### MN-42.3 その修正が、循環待ちの禁止を壊しかけた(レビューで差し戻し)

42.2 の最初の実装は、`DispatchPrelock` に `preacquiredLocal` を足して**手元だけ全順序の外へ
出していた**。`DispatchPrelock.live` のコメントは、**以前からこの形を名指しで警告していた**:

> 手元だけ順序の外へ出すと、**A が手元を握って M1Max を待ち、B が M1Max を握って手元を待つ**
> 形が作れる(手元も全順序の1要素でなければ循環は消えない)

Mac X(X + M1Max)と M1Max(M1Max + X)が同時に複数機械 run を起こすと、互いに待つ。
RR-18.10 は「循環待ちを**作れない**(検出も自己解消も要らない)」という**構造的保証**で、
「現実には起きにくい」で崩してよい種類のものではない。差し戻して、**ロック本体は全順序どおり・
列に並ぶ順番だけを前倒し**という形にした。`DispatchLockBeforeBuildOrderingTests` が
「local の実取得を飛ばす口が無いこと」を走査で固定する。

**教訓**: 既存のコメントが警告している形を、その警告のすぐ上に足そうとしていた。
**規律の理由が書いてある場所を通るときは、その規律を自分が今から破らないかを読む**。

### MN-42.4 `--wait-lock` を渡しても、デバイスの先読みで即死していた

`run --profile … --scenario <1本> --wait-lock 300` が 1 秒も待たずに
`refusing to start: already in use by another fleetest run … (held by pid …)` で終了した。
判定は `rejectIfLocalDevicesLeasedBeforeDispatch`(fan-out の先読み。どのロックも取る前に断る)で、
**断ること自体は正しい**。だが **1 マシン 1 run を保証している以上、走っている run が終われば
デバイスの lease は必ず空く** —— 待てば必ず解消するものを待たずに断ると、連続実行(CI・ループ・
拡張の再実行)の後発が FIFO の待機列にすら並べない。`--wait-lock` があるときは
`WaitLockPolling` の同じ刻みで待ってから再判定する。

### MN-42.5 いちばん使用中のときだけ開く門(`bridge down`)

**決定的な対照が 1 分で取れた**:

| 対象 | 同時刻の `bridge status` の走査 | `bridge down --port` |
|---|---|---|
| 8153 | 載る | ❌「is being driven by an MCP session (fleetest-mcp pid …)」= **門が効く** |
| 8154 | **載らない** | ✅ **一言も言わずに停止**(MCP が駆動中・lease も生きていた) |

門は鍵(udid)を `BridgeDiscovery.scan` = **/status の応答**からしか取らない。XCUITest ブリッジは
**操作の実行中は応答しない**ので、**いちばん使用中のときだけ「宛先が引けない」に落ちて素通りする**。
「引けないときは通す」の意図は「無応答のブリッジを止められないと回復手段が無くなる」だが、
無応答には**死んでいる**(待受もない)と**忙しい**(待受はある)の 2 種類がある。
`BridgeDiscovery` 自身は `isBound` / `.preferredBusy` でこの区別を持っていたのに、門は使っていなかった。

**一般化**: **「観測できなかった」を「存在しない」と読む分岐は、観測が失敗する条件を列挙してから書く**。
ここでは「忙しい」が失敗条件で、しかもそれは**門が最も効くべき状態**だった。

### MN-42.6 ライブ操作が、指定していないデバイスを操作し、そのデバイスのブリッジを止めた

`api live serve --udid <デバイスA>` を `--port` なしで起こしたら、stderr に
`Detected a bridge from an older build (port 8123) — restarting it` が出て、
`actionResult.app` は**別のデバイスで動いていたアプリ**を返した。直後に 8123 と**デバイスA 自身の健全な
ブリッジ**の両方が消えた(「デバイスA の udid で 8123 に起動し直す」ため、デバイスA が既に持っていた
ブリッジも止められる)。

原因は、`XCUIBridgeResolver.resolve` の宛先を `--udid` と**一度も突き合わせていなかった**こと。
「接続先の同一性は `FTCore.BridgeIdentityCheck` で確かめる」は run の 4 経路と MCP が通していて、
**ライブ操作だけが漏れていた**。非破壊の対照も取れた: `--udid <A> --port <B のデバイス>` で
`{"cmd":"refresh"}` → **B の画面を ok:true で返す**(警告なし)。

**直し方で一度間違えた**: 最初の実装は「不一致なら serve を起動しない」だった。これは
**この不具合が実際に起きる場面を塞ぐ** —— 拡張は port が分かるときだけ `--port` を渡すので、
**ブリッジのまだ無いデバイスを開く**と必ず既定 8123 にフォールバックする(= 自動起動が想定している
まさにその場面)。そこで断ると「別のデバイスを操作する」が「開けない」に変わるだけ。
`--port` の明示/既定で分け、既定なら**その udid のポートを探す / 無ければ空きポートへ向けて
自動起動に委ねる**形にした。

**教訓**: **安全側に倒すときは、倒した先で「本来の使い方」が通るかを実際の呼び出し元
(ここでは拡張の `buildDeviceArgs`)まで辿って確かめる**。

### MN-42.7 ライブ操作の launch に門が無く、serve ごと落ちていた

`{"cmd":"activate","bundle":""}` と `{"cmd":"launch","bundle":"no.such.app.live"}` のどちらでも、
そのコマンドが 30 秒刺さり `A single command stalled for over 30s — force-quitting (command
watchdog)` で serve が終了した。再起動後は接続拒否 → 自動起動が走り、
`Cleaned up leftover runner(s) on port 8153` で**健全だったランナーまで掃除**して起動し直す。

`guard let bundle = command.bundle` しか無く、**nil は断るが空文字列も実在しない bundleID も通す**。
`XCUIApplication` はそれで返ってこない —— **2026-09-21 の T1(MCP の `ft_launch`)とまったく同じ型**で、
あのとき門を入れたのは MCP だけだった。判定を `InstalledAppCheck.launchGuard` に切り出して
**両方が共有**する形にした(「判定は 1 箇所・文言は呼び手ごと」)。

**同型の掃討は、同じ判定を持つべき経路を列挙してから行う** —— T1 のとき「ft_launch を直した」で
止めず、「`XCUIApplication.launch/activate` を撃つ口はどこか」で数えていれば、ここも同時に塞げた。

## MN-44 実機のブリッジが固まると「busy」と言い続けて出口を塞いでいた(2026-09-22 3回目の負荷テスト)

### MN-44.1 固まったブリッジを busy と誤って帰属し、回復手段を勧めない

実機 iPhone SE3 の XCUITest ランナーが落ち、**USB の転送役(iproxy)だけがポートを握ったまま**に
なった。この状態で MCP の全ツールが 10 分以上こう返し続けた:

> a bridge … is listening on port 8152 but did not answer /status within the scan window —
> **it may be busy** … **Retry in a moment**; `fleetest bridge up` … would start a second one on this device.

事実は busy ではなくブリッジの消失で、**唯一の出口である `bridge up` を名指しで禁じていた**。
実際に `bridge up` を撃つと残骸の iproxy を掃除し、原因(`Unlock iPhone SE3 to Continue` =
端末の画面ロック)まで正しく言う —— **同じツールの別の口は答えを知っていた**。
2026-09-21 の T1・2026-09-22 の B1 と同じ「袋小路」の3例目。

**分けるものは所要時間**(実測): 健全 = HTTP 応答が返る(トークン不一致の 401 も「生きている」の
証拠なので**ステータスコードで判定しない**)/ 固まった転送 = connect は 0.5ms で通り、
応答が1バイトも来ないまま **2.5ms で切れる** / 本当に busy な XCUITest = **上限まで保持する** /
不在 = connect が即 拒否。`BridgeDiscovery.probeStatus` が `answered / timedOut / transportFailed /
notBound` の4値を返し、`MCPServer.bridgeWedgedOnUDIDMessage` と `bridgeWedgedHint` が
「転送だけ残っている」事実 + 典型原因(画面ロック・USB/ネットワーク圏外)+ 完成した `bridge up`
コマンドを出す。**in-app ブリッジには wedged の文言を出さない**(`bridge != "inapp"` で分ける)(あちらは `bridge up` で起動する物では
なく、前面から外れただけのことが多い)。

**`bridgeOwnerAlive`(欠陥④)では捕まらない** —— このとき `.pid` が指す `xcodebuild` は生きたまま
「Run Destination Preflight: Waiting for the destination to become ready」を回していた。

陽性対照は `iproxy <port> 9999 -u <udid>` を素で立てるだけで作れる(受け側の居ないポートへ転送する =

## MN-45 失敗の出口が MCP にしか配線されていなかった(2026-09-23 の掃討)

### MN-45.2 規律

**利用者が次の一手を打つ経路は MCP とライブ操作の2つ**。判定を足したら**両方へ配線する**。
run(DSL)は別扱い —— あちらは失敗をレポートへ残して自動回復する経路で、人がその場で次の一手を
打つ場ではない。`LiveControlExitParityTests` が集合を等号で固定する。
**走査はコメントを落としてから行う** —— 判定の名前は doc コメントにも出るので、素のまま検索すると
**配線を消してもコメントだけで通る**(変異で実際に素通りした)。

### MN-45.3 直さなかったもの

  `BridgeRouter.handle` の総括 catch は今も `String.valueOf(e)` を返す。ブリッジの版上げを伴う
- **TYPE-1: ツールが答えを持っているのに失敗時だけ捨てる**: `type` は撃つ前に「この欄は既に値を

  でしか出力に合流しない**。Android がマスク欄への追記を 422 で断るケースは、まさにその注記が

  `StepNote` にするか。`throw` 経由だと `execution error: ` の形が変わる)の設計が要る

## MN-46 ポートの同一性を見ずに他人のブリッジを殺していた(2026-09-23 の3時間負荷テスト)

### MN-46.1 残骸ランナーの照合がポートだけで、別デバイスの生きたブリッジを殺していた(最重要)

`BridgeLauncher.killOrphanRunners` と `PortHolder.stopIfOwnedBridge` は
`FleetestRunner-<port>.xctestrun` のパス一致だけで「自分の残骸」と決めていた。**ファイル名は
ポートしか持たない**ので、同じ種別(実機どうし・シミュレータどうしで DerivedData が同じ)の
別デバイスが同じポートに居ると、**駆動中のブリッジを残骸として SIGTERM→SIGKILL する**。

実地の形: ブリッジを失った実機 2 台がどちらも既定ポート 8123 へ倒れ、
`→ Cleaned up leftover runner(s) on port 8123` で互いを殺し合った。同じ形で、MCP が駆動中だった
シミュレータのブリッジも巻き添えになった(その MCP セッションは以後「no running bridge」しか
返せなくなる = 袋小路)。

直し: `FTBridgeClient.RunnerDestination` がコマンド行の `-destination …,id=<udid>` を読み、
**肯定的に別デバイスと読めた回だけ**殺さない(宛先が読めない・こちらが名前指定のときは従来どおり
止める —— 「分からないから残す」に倒すと本物の残骸が永久にポートを塞ぐ)。

### MN-46.2 `.inapp` 台帳の生死を「誰かが待受しているか」だけで決めていた

`StaleLedgerSweep` の `inappListening` は `PortHolder.describe(port:) != nil`、つまり
**占有者が誰かを見ていなかった**。別のデバイスのブリッジがそのポートを取ると古い `.inapp` が
生き残り、供給が「別アプリに注入された in-app ブリッジ」と読んで
`InAppBridgeState.terminateAndRemove` → **無関係なデバイスのアプリを simctl terminate** する。
直し: `PortHolder.listenerIsAnotherSimulator`(CoreSimulator のパスに別の UDID が出たときだけ true。
実機の in-app は iproxy が握るので形が違う = 従来どおり「生きている」側)。

### MN-46.3 ライブ操作が「応答しないポート」を自分のデバイスのものと決めつけていた

`ApiLiveCommand.identityMismatch` は `/status` が答えないと nil(= 一致)を返していた。
既定ポートへのフォールバックでこれに当たると、**別のデバイスのブリッジが居るポートを宛先に採り**、
その後の自動起動がそこへ自分のブリッジを立てて占有者を殺す(46.1 の発火経路)。
直し: 戻り値を3値(`.mine` / `.mismatch` / `.silent`)にし、`.silent` は
**プロセスの実体で占有者を見る**(`PortHolder.isHeldByAnotherDevice`)。
**busy は正常**(XCUITest は駆動中 `/status` に答えない)なので、**肯定的に別デバイスと読めた
ときだけ**掴むのをやめる —— 単に「待受している」で断ると、自分の busy なブリッジを見捨てて
同じデバイスに 2 本目のランナーを立ててしまう(先代が蹴り出される)。

### MN-46.4 `bridge down` が「固まった転送」を busy と誤って帰属していた(MN-44.1 の残り)

`BridgeDownRefusal.unresponsiveButBoundRefusal` は `isBound` だけを見て「待受しているのに
答えない = 忙しい」と決めていた。画面ロックで死んだ実機のトンネルが握ったポートに対して
**「待て、`--force` で押し切れ」と言い続ける** —— 止めることが唯一の回復手段なのに断る袋小路。
直し: MN-44.1 と同じ `BridgeDiscovery.probeStatus` の4値を通し、断るのは `.timedOut`(本当に busy)
だけ。`.transportFailed`(固まり)は止めさせる。並列プローブは
`BridgeDiscovery.probeStatuses`(1ポートずつ直列に撃つと上限 2 秒 × ポート数を払う)。

### MN-46.5 宛先を取らない MCP ツールが udid で道連れになっていた

### MN-46.6 画像で掴めなかった要素の「飾りの名前」を構文検証に掛けていた

### MN-46.7 a11y サーバの一時停止(kAXErrorAPIDisabled)の出口が run にしか無かった

### MN-46.9 死んだ実機ブリッジのトンネルを誰も片付けられなかった

画面ロックで実機のランナーが死んだ後、**iproxy だけが採番範囲のポートを握ったまま**残った。
この状態は3つの口すべてで詰んでいた: `doctor` は `/status` に答えたポートしか見ないので

直し: **判定はプロセスの実体で**(`PortHolder.isHeldByTunnelOnly`)—— doctor はそのポートを

### MN-46.10 ブリッジを失ったトンネルが採番の窓を食い潰す

実機のブリッジ起動が途中で落ちる(画面ロック)・起動した側のプロセスが kill される
(拡張は応答の無い `api live serve` を kill→respawn する)と、**iproxy のトンネルだけが

直し2つ: **①供給の入口で掃除する**(`StaleLedgerSweep.sweepTunnelOnlyPorts`。

### MN-46.11 起動しきれないランナーが永久に待ち続けて積み上がる(最重要のリソース漏れ)

直し: 供給の入口で `StaleLedgerSweep.sweepStuckStartingRunners` —— **判定は既存の

## MN-47 他の機械に繋がった実機のライブ操作が「開けない・別のデバイスが映る・要素が出ない」を順に踏んだ(2026-09-24)

### MN-47.2 実機のブリッジは udid を名乗らない → 既定ポートの別の実機を「自分」と読んだ

### MN-47.7 ホームボタン機のアプリスイッチャーは XCTest では開けない(2026-09-24 に4案を実測・不採用)

## MN-48 ライブ操作タブを開いたまま「全て終了」を押すと何も止まらなかった(2026-09-24)

**追記(2026-09-24 午後)**: 入口(MCP/ライブ操作)だけの上限では DSL 等の経路が塞がらないままだった。

testmanagerd は残る** —— 止めるには testmanagerd 自体を kill するしかない。

直し: ランナーが合成タッチを XCTest へ渡す前に見積もり所要を計算して断る(press はそのまま・
drag は press+distance/velocity(クランプ後)・swipe は velocity 指定時だけ distance/velocity・

**追記(2026-09-24 夕)**: 10 秒固定は安全側だが、正当に長い長押し・スワイプ・ピンチを書けなく
していた。ユーザー決定: **既定は 10 秒のまま・コマンドの `maxGestureSeconds:` 引数でその1回だけ

上限60)は**ホスト側**に置く(`FlowStep.gestureDurationViolation` = DSL の `StepExecutor` 入口/

ホストに寄せた(ランナーに2つ目の閾値ロジックを持たせない)。

(例: 30 秒)が Android だけ注入層で黙って 10 秒に切られ「done」を返す**誤った成功**になる(丸め先は

## MN-50 ジェスチャの指の置き方をホストへ寄せた回に分かったこと(2026-09-24)

`gesture` / `ft_gesture` の追加(v126)と、ピンチの指の置き方を `FTCore.PinchGesture` へ集約・
XCUITest の `/doubletap` を独立した2タッチに変えた回(v127)。探りのシナリオ(一時ファイル)で対照を取った。

### MN-50.1 Compose は XCTest の合成タッチをダブルタップとして数えない

以前の docs は「XCTest の `doubleTap()` は2打の間隔が 0ms なので Compose が2打目を捨てる」と書いていたが、
**推測で、誤りだった**。独立した2タッチ(接触 0.05〜0.08 秒・2回目は 0.1 / 0.25 秒後)にしても CMP は
`double=0`(シミュレータの ios-xcuitest・inapp-boost モードの XCUITest 回し・実機 SE3 の全部)。in-app の合成タッチだけが届く。
**XCUITest 側の打ち方を調整して Compose を通そうとしない**(間隔は効かない)。実機の Compose アプリには
ダブルタップの手段が無い → 利用者向け docs は拡大の確認を `pinchOut` へ誘導している。

### MN-50.2 E2E-RN のダブルタップは JS の時計判定で間欠になる

独立した2タッチは RN に届くが、この SUT は PanResponder が JS スレッドの `Date.now()` で「300ms 以内に離す・
350ms 以内に2回」を判定するので、XCUITest 経由では 8 回中 3 回 `double=0`(直前の単タップ・ピンチ・端末に依らない)。
**間隔を詰めると逆に全滅する**(接触 0.05 秒・2回目 0.1 秒後)= 調整で安定させられる性質ではない。
**探り1回の緑(V2)で「RN 対応済み」と docs に書きかけ、E2E で2本とも落ちた** —— 間欠する経路は1回の緑を
根拠にしない。E2E-RN 04 の doubleTap は `android {}` のまま(iOS のダブルタップは E2E-iOS / E2E-Flutter が担う)。

### MN-50.3 ピンチの置き方が4箇所に割れ、Flutter の対象なしピンチが開かなかった

置き方を持っていたのは ホストの `PinchRegion.closingTouchPoints`・XCUITest ランナー・Android・in-app の4箇所。
iOS では `PinchRegion.area` が横長の細い領域を渡す(長辺に指を置く前提)のに、in-app は**短辺の 90%** まで
開く規則だったので、inapp-boost モードの Flutter で `pinchOut()`(対象なし)がほとんど開かず `zoom=-` のままだった。
E2E-Flutter はピンチを `android {}` に閉じていたので隠れていた(探りで初めて出た)。
直し: 置き方は `PinchGesture`(iOS / Android の規則を OS ごとに1つ)、**ブリッジは `PinchRequest.fingers` を
再生するだけ**。規則を OS で分けたのは意図(Android は領域の短辺から幅を決める = 狭い領域を渡さない)で、
1つに畳まない。ブリッジに規則を戻さないことは `PinchRegionTests` / `BridgeRouterGuardsJavaSyncTests` の走査が守る。

### MN-50.4 実機の「起動だけが止まる」状態は、手で再起動すると直る

`Failed to read socket ID from device`(下位は EAGAIN)で XCUITest ランナーが起動しない。SE3(手元)と
iPhone 13(M1Ultra)の2台で同時に出た。ロック解除では直らない。切り分け(SE3):
`devicectl device info details` = 1 秒で成功 / `devicectl device install app` = 1 秒で成功 /
`devicectl device process launch <bundle>` = **120 秒無応答**。接続・インストールは生きていて、
**端末側のプロセス起動だけが止まっている**。`xcrun devicectl device reboot` は「Full reboot requested」と
返すが**実際には再起動しない**(撃ち直さない)。**手で再起動すると直った**(直後の process launch = 1 秒)。
原因は特定していない(2台とも同じ日の負荷テストで使った端末)。ブリッジの起動し直し・リトライでは直らないので、
この症状を見たら process launch で1回確かめてから手での再起動を依頼する。

### MN-50.5 witness は「壊れても通る形」を対照で潰す

連続ジェスチャの witness(マップ画面の `drag=<n>`)は、最初「1本指の折れ線 = `drag=1`」と「タップ = `drag=0`」
だけを見ていた。これは**カウンタが常に 1 で止まる壊れ方でも通る**ので、連続と分割を見分けている証拠にならない。
同じ折れ線を2回に分けて撃つ = `drag=2` の場面を足して判別になった(全 SUT・両 OS で緑)。


### MN-50.6 座標ジェスチャを細かく割ると XCTest が時間を守らない(ブリッジ iOS v128)

ライブ操作の軌跡(pointermove ごと = 16〜20ms 間隔の点)を Apple マップで再生すると地図が動かなかった。
原因はランナーの `CoordinatePinch` がキーフレーム間を **1/60 秒刻みに割って**送っていたこと ——
**1つの move が短いと XCTest(`XCSynthesizedEventRecord`)は時間を守らない**。実測(シミュレータ・
3 秒の直線): 間隔 8ms → 0.45 秒 / 16.7ms → 4.4 秒 / 20ms → 5.4 秒 / 33ms 以上 → 3.4〜3.7 秒。
形(直線/ジグザグ)には依らず、間隔だけで決まる。細かい軌跡は実時間の約 1.7 倍に伸び、指が遅く動く
= マップはパンではなく**長押し(ピンを立てる)**として受け取った。粗い軌跡は逆に縮んだ(11 秒 → 約 6 秒)。

- **XCTest は1つの move の中を自分で補間する**(4 秒の1区間でもドラッグとして届く)ので、細かく割る必要は無い。
  直し: `resample` = ①50ms(`minimumSegment`)未満の間隔の点を間引く(先頭・末尾・静止区間の端は残す)
  ②0.1 秒(`maximumSegment`)を超える移動だけ割る(ピンチの「数点に割る」の趣旨)。
  直した後は間隔 8〜100ms・点 17〜551 の全部で要求 +0.4〜1 秒(シミュレータ)/ +0.9〜2 秒(実機 SE3・USB)に揃った
- **前回(MN-50 本体)の「時間どおり」の確認は穴だった** —— 使った witness の軌跡は区切り点4つで大半が静止区間。

### MN-51.1 桁外れの座標で Android のドライバが trap してプロセスごと落ちた
ライブ操作の `{"cmd":"drag","fromX":1e308,…}` で serve が `Double value cannot be converted to Int32` で死んだ。
座標は `ArgumentBounds` で `.unbounded` のまま、`AndroidDriver.drag/press` が `Int32(x.rounded())` していた。
MCP は画面外の座標を先に断るので落ちない(= MN-45 の「MCP にだけ出口がある」型)。直し: 画面内の判定を
`TapTargetGeometry.isPointOnScreen` に移して MCP とライブ操作で共有・Android は `checkedInt32` で投げる側へ。
**呼び手の入口で断っても、整数へ畳む最後の砦は別に要る**(DSL の `tap(x:y:holdSeconds:)` も届く)
ライブ操作の画面内の門は画面の大きさを**直近の観測の控え(`LiveScreenMemo`)で先に見る** —— パネルのクリックは
座標の tap なので、毎クリック木を読むと負荷下で命令ごとに数秒足す。控えで外れたときだけ撮り直して確かめる
(回転で広がった画面を古い控えで断らない)

確かめていなかった。フリートの起動し直しで予備ポートが in-app ブリッジに化け、`/gesture`・`/drag` が 404
(= in-app に来た証拠)。別のデバイスなら home/drag を黙って別のデバイスへ撃つ。直し: `HybridFallbackIdentity.drifted`
を MCP(キャッシュ命中)とライブ操作(`frame` 以外の命令ごと)が共有。**`BridgeIdentityCheck.verdict` は udid が
両側にあるとブリッジを見ない**ので、同じデバイスの in-app に化けた形は `hybridFallbackDrift` でブリッジを先に見る

### MN-51.4 供給中の中断で run の記録が「クラッシュ」になった(新規)
`InterruptRelay.observing`(= SIGINT/SIGTERM/SIGHUP を無視に倒す)の登録が供給段の**後**だった。供給中の

**1回目の中断で1行言う** —— 供給は止まるまで数十秒かかり、無言だと利用者は強制終了して記録を失う
