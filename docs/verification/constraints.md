## iOS(XCUITest・Simulator・in-app)

### 画面外要素の frame は信用できない —— XCUITest は容器の原点へクランプする(2026-08-05 実測)

確認環境: 2026-10-25 に再現(macOS 27.2(26B118)・Xcode 27.2(27B48)・Simulator iPhone 17 Pro / iOS 27.0(24A434)・XCUITest ブリッジ v214。E2E-iOS のスクロール画面で、可視域外の行のラベルが (16,270) にクランプ・行 12〜40 のラベルも木に載る)。初回の観測(2026-08-05 時点を git から復元): iOS ブリッジ v51・Compose Multiplatform 1.11.0・Kotlin 2.4.10。macOS・Xcode・ランタイム・デバイスは未記録

**一時的な不整合ではなく、静止画面で常に成立する規則**。1回スナップショットを撮れば確認できる
(長時間の再現待ちは要らない)。E2E-iOS のスクロール画面(`UITableView`)を開いた直後の実採取:

```
[5]  table id=list_rows (16,270 370x395)     ← 容器は 270..665
[20] clickable "行 08" id=row_08 (16,662 …)   [21] staticText "行 08" (36,662 …)   ← 可視域内は親子一致
[22] clickable "行 09" id=row_09 (16,718 …)   [23] staticText "行 09" (16,270 …)   ← 子だけ容器の原点へ
[28] staticText "行 12" (16,270 330x56) … [56] staticText "行 40" (16,270 330x56)  ← 32 個が同一座標
```

- **可視域を外れた子孫は frame の原点が容器の原点にクランプされる**(サイズはそのまま)。
  親のセルは真の座標のまま返るので、**親子で矛盾したツリー**になる
- **セルが実体化していない行のラベルまでツリーに載る**(`row_12`〜`row_40`)。
  `cell.textLabel?.isAccessibilityElement = false` にしても消えない ——
  XCUITest の要素木は a11y ツリーそのものではない
- **実害はタップの空振りではなく「沈黙の誤タップ」**: クランプ先は先頭行の位置なので、
  `tap("行 15")` のようなラベル指定が **`row_01` をタップする**(2026-08-05 に実採取で再現。
  `ft_tap` した結果 `selected=row_01`)。`exist("行 15")` も画面外のまま真を返す =
  「exist は非スクロール(現在画面のみ判定)」の契約と食い違う
- 現状 E2E が踏んでいないのは、シナリオが**セル側(id 付き)**を指しているから。
  **利用者がラベルでタップを書くと普通に踏む**

**Compose iOS も同じクラスだが規則が違う**: あちらは縁をまたぐ行で
「原点はクリップ前・高さはクリップ後」の混成を返し、**中心が可視領域の外**に落ちる
(`#row_30` が `y=206 h=26〜45`・容器の上端は 230)。S0110 の失敗 21 件を分類すると
**またぎ 12 / 完全に外 7(うち ghost 注記あり2)/ 容器の中 2**。

**決着(2026-08-05・8並列で 160 サンプル)**: 失敗の**全部**でタップ座標が容器の外だった
(またぎ 26 / 完全に外 14)。しかも木は**1ピクセルも動いていない**(無変化の注記 17/20)
= **frame は安定していて、ただ間違っている**。だから:
- **整定を足しても無駄**(既に安定している) —— 触る直前に対象の静止を確かめる案は
  **fix 20/40 対 base 20/40 = 差ゼロ**で撤去した
- **送ると悪化**(動かすと座標がずれる) —— 掴み直しの対象をまたぎへ広げたら 2/10 → **5/10**
- **座標そのものを直すのが正解**: 中心が容器の外に落ちるときだけ
  **見えている部分(frame ∩ 容器)の中心を座標で撃つ**(`StepExecutor.visibleTapRect`)。
  交互 A/B(各40サンプル)で **base 18/40(45%)→ fix 5/40(12.5%)**、
  またぎクラスは **12 → 3**。残るのは「完全に外」= そもそも見えていない行を掴む形

**残りも決着(2026-08-05・8並列で さらに 176 サンプル)**。2段で消えた:
1. **救済は全画面スワイプで送っていた** —— ずれは 100pt 程度なのに1回が約1ページ動くので
   **行き過ぎて反対側へ出て往復する**(失敗 13 件は全部が救済を撃ち切り、tap 4.0s → 約8.0s、
   `#row_30` は容器の**上** y=116〜174 に戻っていた)。WebView のヒント跳躍と同じく
   **距離を測ってその分だけ**動かす(`recoveryJump` → `hintDrag`)。
   率では有意差が出なかった(4/40 対 7/40)が、**失敗の内訳が入れ替わった** ——
   「完全に外」5→0・「またぎ」2→0 で、残ったのは**容器のど真ん中**にある要素だけ
2. **救済で送った直後の1タッチを容器が吸っていた**。探索終端では空打ちドラッグで
   肩代わりしているのに**救済経路には無かった**。相関が決定的だった ——
   救済が走った 18 件のうち **4 件が失敗**、走らなかった 22 件は **0 件**(p≈0.03)。
   探索終端と同じ順序(肩代わり → 静止 → 掴み直し)を足すと **fix 0/48 対 base 8/48**(p≈0.006)

**通しの改善**: 45% → 12.5% → **0/48**。**回帰テストは S0110**(領域を指定しない探索)。

**⚠️ 事後の分類には注意**: 下の「またぎ 12/21」は失敗**時**の要素一覧から採ったもので、
「タップした瞬間の姿」ではない
(2026-08-05 に訂正)。**またぎは原因ではなく結果**のことがある —— 探索が掴んだ時点では
容器の中にあり、その後リストが動いて縁へずれた、でも同じ絵になる。
実際、下の修正を入れて S0110 を**スイート10周**回すと **8/10 通過・2/10 失敗(いずれもまたぎ)**で、
**修正は一度も発火していなかった**(`tap "#row_30"` の所要が10周とも 4.01〜4.11s = 追加スワイプ無し)。
= この screen では探索は**常に容器の中で**行を掴んでおり、ずれるのはその後。
**残りの本命は「掴んだ後に座標が古くなること」**(docs の計装記録でも FOUND y=347 → TAP y=249 と
98pt 動いていた)。iOS には Android の `bypassingCache` に当たる手が無いのが効いている可能性が高い。

**対処(2026-08-05・入れたが現状は潜在)**: `clippingAncestor` を**用途で2つに割った**。
旧実装は「祖先と交差しないこと」を条件にしていたため、**またいでいる行では nil に落ちて
viewport が画面全体になり**、「見えている」と誤判定して探索が止まっていた。
判定として正しいので残すが、**上のとおり現状の SUT では発火しない**(コスト0の保険。
同条件 A/B でスクロール系 39.3/39.7s 対 39.6/39.6s = 差なし)。

| 関数 | 条件 | 用途 |
|---|---|---|
| `clippingContainer` | 交差の有無を**問わない** | 見切れ判定の viewport。またぐ行を「見切れ」と判定して**もう1回送る** |
| `isOutsideContainer` | 容器と**交差しない**(完全に外) | ghost の掴み直し。またぐ行は ghost ではないので掴み直さない |

どちらも「同じ depth の兄弟が2つ以上その中に居る」ことを確かめてから容器を採る(叔父を掴んだ
ときに nil へ落とすため)。[[compose-ios-ax-frame-clamp]]

**対処(2026-08-05 実装)**: **ホスト側で解決候補から外す**(`ContainerGeometry.hasClampedCoordinates`)。
ブリッジ側で落とす案は採らなかった —— 要素集合が変わって `.型[n]` の序数・ref・`truncatedCount`
まで動くため。ホスト側なら候補の選び方だけが変わる。

**判定は症状ではなく機構で書く**。最初は「同じ場所に同 depth の要素が3つ以上」だけで書いたが、
**既存の単体テスト 13 件が落ちた** —— 同じ矩形を共有する兄弟自体は珍しくない。機構は
「**容器の原点にちょうど固定され、かつ容器より小さい**」なので、それを条件にする:

| 条件 | 何を守るか |
|---|---|
| 同一 frame(±0.5pt)が **3つ以上** | 親子2重で誤爆させない(`OcclusionSuspicion.isClampGhost` と同じ閾値) |
| **depth が同じ**(= 兄弟) | `homepage_container > app_bar > app_bar_container` のような**入れ子の連鎖**を残す(親子が同じ矩形を持つのは普通)。過去レポート 466 件へ当てて実際に引っかかった形 |
| 上位に**原点が一致し、より大きい**要素が居る | クランプ先が居ることの確認。居なければ「ただの重なり」と読む |
| 群が容器より**小さい** | 全面に重ねたオーバーレイ(容器と同じ大きさ)を残す |

**消したら必ず理由を書く**(`clampedStackHint`)。利用者には「ツリーには在るのに見つからない」と
しか見えないので、失敗文言に「N 個が同じ場所に積み上がっている / 先にスクロールして可視域へ入れる」
を添える。**黙って消すのが最悪**。

**当面の指針**: 位置に依存する判断(タップ座標・見切れ判定・覆い判定)は
**可視域内の要素の frame だけを信用する**。

### 常駐ブリッジのセッション(iOS xcuitest を CLI で直接叩くとき)

確認環境: 2026-10-25 に再現(macOS 27.2(26B118)・Xcode 27.2(27B48)・Simulator iPhone 17 Pro / iOS 27.0(24A434)・XCUITest ブリッジ v214。`/session` の前の `/snapshot`・`/tap` は 409、張った後は 200)

`bridge up` で立てた常駐ランナーへ curl 等で直接 `/snapshot`・`/tap` すると、最初の1回が
`409`(セッション無し)で返ることがある。ランナーはアプリ参照(`sessionBundleID`)を `/session`
で初めて確立するため。**先に `POST /session` を投げる**こと(Runner/FleetestRunnerUITests/BridgeRouter.swift)。

- `simctl launch` で既に起動済みのアプリへ後付けで繋ぐ場合は `{"bundleID":"...","attachOnly":true}`。
  attachOnly は activate/launch せず前面到達だけ確認する(前面に無ければ即エラー)。通常 run は
  driver が自動で `/session` を張るのでこの手順は不要=CLI 直叩き時だけの話。
- **`/status` の `sessionBundleID` は次の `/session` まで残る in-memory 値**。対象アプリを
  アンインストールしても消えないため、削除済みアプリの死んだ参照が見えることがある(無害。
  次の `/session` で上書きされる)。`/status` の session 欄=「今アタッチ可能」の保証ではない。

### 未インストールのアプリを launch するとランナーが死ぬ(2026-08-06)

確認環境: 2026-10-25 に再現(macOS 27.2(26B118)・Xcode 27.2(27B48)・Simulator iPhone 17 Pro / iOS 27.0(24A434)・XCUITest ブリッジ v214)。初回の観測(2026-08-06 時点を git から復元): iOS ブリッジ v52。macOS・Xcode・ランタイム・デバイスは未記録

**2026-10-25 の環境では落ちるまでが長い**: 要求は無応答のまま、待受が消えるまで約65秒・ランナーのプロセスが消えるまで約95秒(下の「約5秒 → 10秒以内」は初回の観測の値)。

外部フィードバック #7「Safari 操作後にブリッジが切断」は **Safari と無関係**だった。
報告元のログで確定した経過:

1. ポート 8123 のランナーで未インストールの `com.example.myapp` を launch → `TEST EXECUTE FAILED`
   でランナー終了(04:47:34)。この時点で 8123 は死亡
2. 以後 `port` を指定しなかった呼び出しは、**既定 8123 決め打ち**(当時)で死んだポートを叩き続け、
   `Connection refused` になった。Safari を操作していた 8124 は別デバイスで、切断時も生きていた
   (ログは t=187s まで継続)

「ツールごとにポート解決経路が違うのでは」という推測は否定された ——
`ft_snapshot` も `ft_screenshot` も同じ `driver(_:)`・同じキャッシュ鍵(`driverCacheKey` は
port を含む)を通る。**port を書いた呼び出しと書かなかった呼び出しが混在していた**のが実態。

**ランナー死は直接再現できる**(遊休ブリッジ1本を潰すので、使っていないポートで):

```
curl -s -X POST http://127.0.0.1:<port>/session -d '{"bundleID":"com.example.nonexistent"}'
```

無応答(**待受は継続**)が約5秒 → 10秒以内にランナーのプロセスが消え、待受も消える。
原因は `XCUIApplication.launch()` の失敗 issue が main queue 上で記録されること(`requireLiveApp`
のコメントにある無限再帰と同じ経路)。対処も同じで、**XCUI に触れる前にホスト側で弾く**
(`MCPServer.installedVerdict`(判定そのものは `InstalledAppCheck.launchGuard`))。

**この実験は「応答しないが生きている」状態の witness でもある** —— 上の約5秒間、`/status` は
返らないのにポートは待受している。ブリッジ探索が「応答なし=死」と読むと、この隙に
**別デバイスのブリッジへ黙って乗り換える**。`BridgeDiscovery.isBound`(TCP 接続可否)で
死と忙しいを分けること。外部ログでは整定待ちで **33.7 秒**ブロックした区間が観測されている。

## Android

### ポーリングはキャッシュを突破しない —— 「撮り直せば新しくなる」は Android では偽(2026-08-14)

確認環境: 2026-10-25 に再現(macOS 27.2(26B118)・Emulator Android 15(API 35)・Android ブリッジ VERSION_CODE 109・Compose Multiplatform 1.12.1・Kotlin 2.4.21。E2E-CMP の `#field_single` へ打って消した直後、通常の `/snapshot` は10回中6回が消す前の値を返し、`refresh=1` は毎回空。並列負荷なしでも起きる)。初回の観測(2026-08-14 時点を git から復元): Android ブリッジ VERSION_CODE 61・Compose Multiplatform 1.11.0・Kotlin 2.4.10・React Native 0.86.2。macOS・Xcode・ランタイム・デバイスは未記録

`clearInput` の事後検証は「クリア前の値」と「クリア後の値」を比べ、`after == before` なら
「消えていない」と報告する。ここが E2E-CMP/android の S0040 で**並列負荷 10 周中 8 周落ちた**。
実際には消えており、**誤った失敗**である。

**根因は a11y キャッシュで、比較の両側に穴があった**:

- **`before` 側**: 解決済みの `element.value` をそのまま使っていた。古い読みだと、空欄の `value` に
  ヒント文字列が載る欄(CMP の `#field_single` は placeholder を送らず `value="単一行"`)で
  「撃つ前=ヒント」「クリア後=ヒント」が一致してしまう
- **`after` 側**: 3周ポーリングしていた。コメントは「単発では反映遅れを誤検出するのでポーリングする」と
  書いていたが、**a11y ノードはキャッシュ供給なので撮り直しても同じ古い値を返す**。
  周回数を増やしてもこの穴からは抜けられない

**判定の指針**: 「リトライ/ポーリングで吸収している」と書いてある箇所は、**その再読が本当に
再取得なのか**を確かめる。キャッシュ越しなら回数は気休めにしかならない。修正は
`snapshot(bypassingCache:)`(全ノード `refresh()`)で、**失敗と決まる直前の1周だけ**払う
(既存の `AssertFreshRetry` と同じ規律。正常系は1周目で判定が付くので追加費用ゼロ)。

#### 不採用: ブリッジ側で editable ノードだけ `refresh()` する(2026-08-14)

同じ穴を「木を作るときに入力欄だけ取り直す」で塞ぐ案は**実測で棄却した**。

- 狙いは当たった: step5 の誤検出 **12/28 → 0/4**
- **しかし別の入力欄を消す退行**が出た: 同じ run の後段 step12(パスワード欄の replace)が
  **0/17 → 2/4**。レポートの要素一覧が、step7 で `single=xyz` を検証済みの `#field_single` を
  `value="単一行"` / `single=` / `len=0`(= 空)と示していた。**偽の失敗ではなく誤った破壊**
- 疑いは**木が混世代になること**(一部のノードだけ新しい版のレイアウトを持ち、ref の座標が
  他のノードと食い違う)。機構は未確定 —— `findEditable` は id 一致が効けば座標に落ちないはずで、
  「id 一致が効いている(だから refresh も発火する)」と「座標へ落ちた(だから別欄を消した)」が
  両立しない。**再挑戦するならここを先に計測する**
- 全ノード refresh は不可(snapshot +65ms・View/XML の scenario sum +43%。2026-08-01 実測)。
  `bypassingCache` は**全ノードを取り直すので世代が揃い**、この危険が無い

**教訓**: 木の一部だけ鮮度を上げると、**座標と内容が別の時点を指す**。鮮度は木の単位で揃える。

#### 否定アサーションは通る側にも鮮度を払う(2026-08-14)

同じキャッシュの穴が**誤った成功**として出る場所があった。`AssertFreshRetry` は
**失敗と決まる直前にしか**キャッシュを捨てない設計だったので(「通ったアサーションは
1円も払わない」)、`notExist` / `textNotEquals` / `valueIsEmpty` / `keyboardIsNotShown` は
**古い木のまま pass を返していた**。要素が現れた直後はキャッシュが追いつかず、
「まだ現れていない」姿で不在が成立する。

**肯定形が同じ穴を持たないのは運**である —— 古い木は期待値に一致しないのでポーリングが続き、
迂回する周まで到達する。つまり「肯定形は安全」ではなく「肯定形は待つ用途だから助かっている」。
**否定形だけが通る側にも払う**(`AssertFreshRetry.confirmPass`)。
予算は失敗側と別に持つ(共有にすると、pass の確認で使い切ったアサーションが期限切れ時に
取り直せず、塞いだ穴の隣に**誤った失敗**を作る)。

費用は Android の**通る否定アサーション1回につき snapshot 1枚**。E2E-CMP には否定形が 42 あるが、
実測では scenario sum の差はセッション間のばらつきに埋もれた(412.9s / 409.1s 対 直前の 428.1s)。
**「速くなった」ではなく「退行は検出できない水準」**と読むこと。

#### 待つ間の読み直しは、Android の Compose ではキャッシュを迂回する(2026-09-18)

「肯定形は待つ用途だから助かっている」には続きがあった —— **助かってはいるが 1 周期遅れる**。
E2E の Android で、1 秒後に表示される `#txt_delayed` の検出が CMP だけ一律に約 1 秒遅かった
(遅延ボタンを押してから: View/XML・Flutter 1.8 秒 / CMP 2.9 秒。差はすべて `waitMs` = ポーリングの待ち)。

- **ブリッジを HTTP で直接叩いて切り分けた**: `exist` と同じ間隔(`PollBackoff` の 100/200/400/800/1000ms)で
  読むと、素取得は押してから 1.79 秒の読みでまだ無く 2.80 秒で見つかる。`refresh=1` は 1.08 秒(4 回とも同じ)。
- **罠: 50ms 刻みで読み続けると遅れは出ない**(素取得でも 1.10〜1.15 秒で見つかる)。最初の計測はこれで
  「ブリッジは遅れていない」と誤って結論しかけた。**鮮度の計測は、実際の読み手と同じ間隔で読む**
- 迂回の費用は snapshot 1 回あたり約 +45ms(要素 19 個の Compose 画面で 8 → 50〜60ms)

**規則**(`StepExecutor.repollBypassesCache`): Android かつ自前描画(`isSelfRendered`)のアプリでは、
**待つ間の 2 回目以降の読み**をキャッシュ迂回にする。1 回目の読み(見つかれば終わるふだんの経路)では払わない。
効かせる場所は2つで、どちらも既定値を置かない —— アサーションの待ちは `AssertFreshRetry(bypassOnRepoll:)`、
操作の待ち(要素の出現を待つ再試行)は `SnapshotFreshness.repoll`。不明なフレームワークは迂回しない。

**配線の罠**: 最初の実装は単体テストが全部緑なのに E2E で**まったく効かなかった** —— シナリオ実行バイナリが
Android では `uiFramework` を決めていなかった(空打ちに無関係だから判定を省いていた)。単体テストは
`uiFramework: .compose` を直接渡すので通る。配線は `RepollCacheBypassTests` の走査で固定した。
**効果**(手元のエミュレータ 6 台・1 秒遅延の出現待ちの中央値): CMP 2876 → 1074ms、Flutter 1828 → 1063ms、
View/XML(一部 Compose)1823 → 1175ms。対象外の RN は 936 → 942ms で不変、他のステップの中央値も不変。

#### 「無い」の観測は、対象が生成されていることを先に確かめる(2026-08-15)

不在の観測は「本当に無い」と「まだ作られていない」を区別しない。値が違う・遅いといった
肯定の観測と違い、**不在だけは実験系の不備と見分けがつかない**。

3連続で誤診した。Android のアプリ内 WebView が CDP に届くかを
`adb shell cat /proc/net/unix | grep devtools` の有無で測ったが、**WebView 画面に到達しておらず
WebView インスタンスが生成されていなかった**(ソケットは WebView 生成時に開く)。
どの回も空になるのは当然で、それを根拠に「debuggable では不十分・アプリが
`setWebContentsDebuggingEnabled(true)` を呼ぶ必要がある」と結論し、**SUT に不要な1行を足した**。
対照を取ると、呼んでいないビルドでもソケットは開いた —— 前提は最初から満たされていた。

- **不在を測る観測に、対象が在るはずの条件を並べて出す**
  (この件なら `uiautomator dump | grep -c android.webkit.WebView` を同時に出す)。
  片方だけ見ると、実験系の不備が「発見」に化ける
- **対照は同一デバイス・同一手順で、コードだけを変える**。別デバイスを対照にして2回失敗した
  (端末ごとに画面の状態が違い、「対照でも不在」が対照の不備によるものだった)
- **画面遷移を座標決め打ちでやらない**。ディープリンクは契約に定義された経路しか遷移しない
  (`fte2ecmp://screen/webview` は存在せず、未定義パスは「遷移しない」が仕様)。
  遷移したつもりで別画面を測るのが最も起きやすい形

#### 仕様を撤回したら、その仕様を根拠に書かれたコードを grep で洗う(2026-08-15)

「WebView 内は `#id` を使わない」という確定仕様を撤回したコミットは、共有側だけを直し、
**iOS in-app の経路に `identifier: nil` を残した**。撤回から翌日まで、iOS の WebView シナリオが
ずっと赤のままだった(`cannot resolve the locator: id=wv_input`)。

拾えたのは、コメントに**契約名がそのまま書いてあった**から
(`// 契約: WebView 内は #id を使わない`)。**契約名をコメントに書く価値はここにある** ——
撤回時に grep の取っ掛かりになる。docs も同時に洗うこと(設計書に残っていた「確定仕様」の記述は
撤回の翌日まで残り、実装と正面から矛盾していた)。

#### 症状が「失敗」でなく「ハング」になる構造を作らない(2026-08-14)

上の修正で `continue` を使って確認の周を回したが、**`continue` は deadline 検査を飛ばす**。
確認が2回以上発火すると**無限ループ**になり、変異テストが 40 分ハングして発覚した
(本番は一発制限で防げていたが、「通るたびに確認しよう」という将来の編集で成立する)。

**予算のような単一の不変条件だけに無限ループの防止を任せない**。各ループに局所フラグを置き、
不変条件が壊れても症状が**通常の失敗**に落ちるようにする。失敗はログに出るが、
ハングはテストのタイムアウトまで何も分からず、原因の場所も指さない。

**変異テストは「テストの検出力」だけでなく設計の壊れ方も暴く** —— ハングした変異は
「テストが弱い」ではなく「production の構造が脆い」を意味していた。

#### フレークは後段のフレークを隠す —— 直したら「その先」を数え直す(2026-08-14)

step5 が 8割で落ちていた間、step12 は**8割の周で skip**されており有効サンプルは 17 しかなかった。
step5 を直した瞬間に step12 が毎周走るようになり、そこで初めて退行が見えた。
**手前を直したら、それまで到達していなかった後段の失敗率をベースラインから取り直す**
(前後比較の母数が変わっていることに気付かないと、直した側の効果と後段の退行を取り違える)。

### Android ブリッジの版を上げた直後の1回目は落ちることがある(2026-08-01)

確認環境(2026-08-01 時点を git から復元): Android ブリッジ VERSION_CODE 37。macOS・Xcode・ランタイム・デバイスは未記録。2026-10-25 時点では再現の条件を作れず未確認(ブリッジの版上げの直後でないと起きない)

`expectedBridgeVersionCode` を上げると各機のブリッジ APK が再インストールされる。これが
**実行中のレーンを踏む**と、そのシナリオは `Cannot reach the driver ... The network connection
was lost` で落ちる(実測: 版上げ直後の E2E-Android で 4/40 失敗 → 全機が新版になった直後の
再実行は 40/40 成功)。logcat の
`Package [com.example.ftbridge] reported as REPLACED, but missing application info` が目印。

- **版上げ直後の1回目を性能・成否の判定に使わないこと**(sum も再インストールぶん膨らむ)
- 判定は**2回目以降**で行う。ブリッジのクラッシュと見分けがつかないので、
  この行を知らないと存在しないバグを追うことになる
- **同じ版のまま APK の中身だけ変えたら端末側は入れ替わらない**(`expectedBridgeVersionCode` が
  一致するので再インストールが走らない)。反復開発中は `adb uninstall com.example.ftbridge` を
  全機に撃ってから測ること。§「ブリッジ版数の上げ忘れ検出」の「同じ版・別バイナリ」と同じ罠
- **版を下げる操作はすべて Android が拒否する**。`git stash` での A/B も、**採用しなかった
  変更の revert** も同じで、`expectedBridgeVersionCode` が下がるとホストは入れ直せず
  **全機で「cannot connect (no response to status)」= 全滅**になる(2026-08-01 に 40/40、
  2026-08-14 に 34/34 で実測)。復旧は全機の `adb uninstall com.example.ftbridge`。
  **戻した後も1周では復調しない** —— 8台一斉の入れ直しで数台が表示凍結し、
  2026-08-14 は 13/34 失敗 → 次の周で 34/34 成功と、**捨て周が1回要る**
  (§「Android ブリッジの版を上げた直後の1回目は落ちることがある」と同じ現象が
  アンインストール後にも起きる)。この捨て周を測定に混ぜないこと
- **上げる前に「ホスト側だけで足りないか」を問う**。版上げは**片道**(上の理由で戻せない)なので、
  仮説検証のための変更をブリッジへ入れると外れたときの後始末が全機に及ぶ。
  2026-08-14 の clearInput 鮮度問題は、ブリッジ案を棄却した後**ホストだけで完結**した
