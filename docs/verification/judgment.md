## flake・性能の判定規律(1回の結果で断じない)

- **発生率は台帳で出す**: `python3 Scripts/flake-ledger.py`(結果 JSON の全数・デバイス不要・約1秒。
  既定は直近14日・標準3プロファイル・10本以上の run・中断/`--set`/abort/skip 除外・「毎回落ちる」キーは別勘定)。
  **率は `--by host` で機械別に割ってから読む** —— 2026-10-01 の台帳で静かなリモート機 0.2%・負荷テストを回す
  この Mac 2〜4% だった(混ぜるとこの Mac の条件がツールの率に見える)。条件を変える実験は `--runs-file`
  (`runID<TAB>ラベル`)で run を束ねて `--by label`。**先に run.json の `fmDead` を見る**(FM 死の run の緑は
  OCR だけの弱い緑)→ MN-63

- **測り方を先に疑う —— 検出力が足りないと、正しい修正も誤った修正も同じ「差なし」に見える**
  (2026-08-05)。S0110 のフレークを**スイート実行**で追っていたが、1ラウンド約110秒で
  **サンプルは1個**しか採れず、「2/10 → 1/10」級の比較を重ねても何も言えなかった
  (実際その間に、効かない修正を2つ入れて1つは 5/10 の退行まで出した)。
  **同じシナリオを8本同時に流す**(`--scenario` を8回渡す = 同じ8レーン負荷)へ変えたら、
  **1サンプル約3秒・失敗率 50%** になり、原因の特定も棄却も数分で回るようになった。
  「負荷の質が違うから軽い形にはできない」は**仮説にすぎなかった**(実際は同じ事象がより強く出た)。
  **同一シナリオの多重投入は結果ファイルが `~2`〜`~8` に分かれる**ので集計もそのまま採れる。
  判定に迷ったら、まず**1サンプルあたりの秒数**と**失敗率**を上げられないかを見ること
- **flake の修正は「1回グリーン」で判定しない**。flake は確率的で、低負荷なら偶然通る。
  確認は**反復+負荷**で叩く(該当シナリオ単独 ×10、または該当プロファイルをフル並列で **×10**)。
  **単独実行では出ないことがある**(2026-07-31: 8台並列のフルスイートで約40%出る flake が、
  同じシナリオの単独反復では8回中0回だった。負荷そのものが条件)。
  実害: 「v10 で直した・10連続グリーン」と報告した直後にフル並列で再発し、修正コードが**実際には
  実行されていなかった**と判明した(2026-07-23。type(ref) をホスト側で tap+ref:nil に分解していて
  ブリッジの ref 経路に到達していなかった)
- **「一様に増えた」は変更の効果ではなく負荷の交絡**(2026-08-05)。見分け方は
  **変更が届かない経路まで増えているか** —— スクロール探索の見切れ判定を直した前後で
  E2E-Flutter/ios-xcuitest のスクロール系が +15s(+15%)に見えたが、`flick` や `scrollDown`
  (どちらも見切れ判定を通らない)まで全項目が増えており、`host-metrics.ndjson` の CPU 中央値が
  **34.7% → 76.1%** だった。同条件で測り直すと **39.3/39.7s 対 39.6/39.6s(差なし・CPU 42%)**。
  **run をまたぐ比較の前に必ず host-metrics の CPU を並べる**(run.json と同じディレクトリにある)
- **「N 周回して再現せず」は、N を発生率から逆算してから言う**(2026-08-05)。稀な事象では
  「再現しなかった」が**何の情報も持たない**ことがある。目安は「95% の確率で1回は引くのに要る
  周回数 ≒ 3 ÷ 発生率」:

  | 発生率 | 40 周で引ける確率 | 95% に要る周回数 |
  |---|---|---|
  | 1/52 | 54% | 約 155 |
  | 1/298 | 13% | 約 890 |
  | 1/529 | 7% | 約 1,580 |

  実害: E2E-iOS `S0010` の「タップの空振り」を **40 周**回して「再現せず」と記録していたが、
  過去レポート全数での発生率は **1/529** で、40 周の検出力は 7% しかなかった
  (= 出なくて当然)。**発生率は過去の実行データから出せる**(`TestProjects/*/reports` と
  `results/runs` の全数集計)ので、キャンペーンを組む前に必ず出すこと。
  8 レーンなら 1,600 周でも実時間 1.5 時間程度 —— **回数が足りないまま「追えない」と結論しない**
- **レビューで入れる「正しさの修正」も挙動変更として扱う**。挙動に触れる修正は、見た目の
  正しさではなく**計測・検証済みの状態とリクエスト空間の列挙で等価か**を確認してから入れる。
  実害(2026-08-02): Android /swipe の「明示値を常に尊重する」修正が、軸別だった距離既定
  (縦 0.4・横 0.6)を一律 0.4 に潰し、**gesture / search を含む横スワイプ全部を黙って狭めた**。
  レビュー3周目の等価性列挙で検出(それを守る自動テストは無く、E2E のジェスチャシナリオは
  狭いスワイプでも通り得る)。リクエスト空間が小さいときは表にして全ケース突き合わせる
- **修正を入れたら、その修正コードが実行される経路か確認する**。層をまたぐ実装(ホスト↔ブリッジ、
  driver↔StepExecutor)では上の層が下の層の入力を作り替えていて下の修正が空振りすることがある。
  症状が消えないときは「直したはずの箇所に本当に到達しているか」をログ/ブレークで確かめてから次を疑う
- **flake は「基準値」を測ってから対策を測る**。対策の前後で同じ負荷・同じ周回数を回さないと
  改善したのか揺れたのかが言えない。実害: 「対策で 2/5 に改善」と読んだ数値が、対策を撤去して
  測り直すと素で 5/5 だった(2026-07-31。つまり最初の 2/5 が偶然の当たりで、対策は無関係)。
  **判定は 10 周**まで伸ばす(5 周では 0/5 と 1/10 を区別できない)
- **ブリッジを変えたら版数を上げてから測る**。上げないと稼働中の旧ブリッジが再利用され、
  **修正前のコードを測ってしまう**(2026-07-31 に**同日2度**踏んだ。§ブリッジの版)。
  **見分け方**: 直したはずの症状がそのまま出る / 消したはずの一時診断メッセージがまだ出る。
  後者は決定的で、実際「診断文が応答に残っている」ことで旧 APK 再利用に気付いた。
  iOS の dylib と Android の APK は**版が一致していると再利用される**ので、A/B で
  旧実装を測りたいときも版を進める(下げると Android はインストールを拒否する)
- **スクロール系の性能は 1 周では判定できない(最低3周・設定を交互に)**。2026-08-02 に
  iOS の scrollToEdge 速度を各設定1周で測り、「1500 は基準より悪い(最大 30.9s)」
  「2500 は scrollToBottom を 3 倍悪化させる(3,459→16,390ms)」と結論して**一度は不採用にした**。
  3周ずつ回すと**どちらも再現せず**(scrollToBottom はむしろ両設定とも −31〜41%)、採用へ覆った。
  1周ぶんの sum は設定間の差(−23%)と同程度に揺れる。**設定ごとに連続で回さず交互に回す**
  (セッション内劣化が特定の設定に偏る。Android は同一コードでもセッション内で +24〜33% 遅くなる)。
  数値は PT-3.17
- **「症状が変わった」は前進**。嘘の成功(成功を返すのに値が入っていない)を潰すと、失敗は
  「後続の検証が謎の値で落ちる」から「操作自体が理由付きで落ちる」に変わる。失敗率が同じでも
  原因の特定が可能になるので、まずここを塞ぐ
- **失敗ログは「期待値と実際値」を必ず読む**。今回の根本原因(マスク文字列の書き込み・二重追記)は
  実際値(`password=•••…secret42` / `hello123hello123`)を見て初めて分かった。
  「失敗した/しない」の集計だけを見ていると、**自分の対策が値を壊している**ことに気付けない
- **性能・不具合を1回の観測で断じない**。壁時計はコールドスタートの供給や一過性のブリッジ切断で
  大きく揺れ、どちらも定常性能ではない。各プロファイル 2〜3 回計測して定常値を取る。
  揺れの要因・数値・誤評価の実害事例は PT-7 に集約(数値の更新はそちらで)
- **「この指標が異常個体を表す」は1個体でなく全数で確かめる**。壊れた個体だけを見ると、たまたま
  高い指標が原因に見える。実害: 凍結した1台の Metal エラー増加速度(+148/5分)を見て「速度で
  異常機を特定できる」と結論しかけたが、**フリート8台を集計すると健全機の方が高かった**
  (最大 288/分)。指標が個体を分離できるかは「異常機 vs 健全機」を並べて初めて言える
  (このケースの結論と全数データは PT-7)

### ブリッジ差のある機能を触るときの規律(2026-08-02〜03 の実測から)

スクロール領域指定(`scrollFrame`)の実装で、**設計を3回・実測で覆した**。同じ型の失敗を
繰り返さないための規律。

- **1ブリッジの実測で一般化しない**。E2E-iOS だけで「終端ドウェルで慣性を消せる」「慣性を消すと
  所要が半減する」と結論しかけたが、3 SUT へ広げると**両方とも覆った**(ドウェルは効かない・
  CMP/Flutter では +130% の退行)。ブリッジの経路は4つ(Android / XCUITest / in-app UIKit /
  in-app Compose・Flutter)あり、**どれか1つの物理は他の3つを説明しない**
- **実装してから実測で否定するのは正常なコスト**。「未指定も座標化する」「in-app でも領域を
  切り分ける」「終端ドウェル」はいずれも作ってから測って撤回した。**撤回した理由と再検討条件を
  docs へ書く**(PT-3.18〜PT-3.20)ことで、次に同じ案が出たときの再発明を防ぐ。
  撤回時は**独立に正しいと確認できた部分だけ残す**(このときは実バグ2件が副産物として残った)
- **「見えている」の基準を取り違えない**。要素の見切れ判定を**画面**基準にしていたため、
  リスト下端で見切れた行を可視とみなし、タップが**容器の外(タブバー)に当たって別画面へ遷移**した。
  スクロールは容器の中で起きるので、判定も**容器 ∩ 画面**で行う
- **境界は `<` か `<=` かを疑う**。「ビューポートより大きい要素は判定対象外」のガードが `<` だった
  ため、**容器と同じ幅を持つリストの行が丸ごと漏れて**いた(行は容器と同幅が普通)
- **5 SUT は同じシナリオでも前提が違う**。画面に要素を1つ足しただけでリストの可視行数が変わり、
  「初期表示で見えている行」に依存したシナリオが SUT ごとに別々に壊れた
  (SwiftUI 版は `#row_06` まで・CMP は `#row_08` まで)。**契約(ui-contract)に数値の前提を書く**
- **負荷の有無で結論が変わる**。単独では 3/3 通るのにフルスイートでは落ちる形が2回あった。
  **判定はフルスイートで行い、単独実行の緑を根拠にしない**

### 制約を外したら、その制約を根拠にしている決定を棚卸しする(2026-08-05)

**MCP(`ft_*`)は profile 無しだと in-app ブリッジを掴んでも XCUITest へ振り替えていた**。
根拠は「in-app は home/appSwitcher/drag/座標 press を実装できず、`ft_*` は StepExecutor を
通らないのでフォールバックが効かない」(2026-07-28 の決定)。**その穴は 2026-08-04 に
`HybridFallbackDriver` で埋めた**が、振り替えの決定はそのまま残り、探索が**利用者の実行既定
(inapp モード)と別のブリッジ**で走り続けていた —— Compose のダブルタップと Flutter のピンチが
「MCP では無反応・シナリオでは通る」になる状態で、指摘されるまで気付かなかった。

(**2026-10-11 の追記**: MCP の iOS は常に XCUITest へ戻した。この節の「振り替えをやめた」判断自体は取り消したが、「制約を外したら、それを根拠にした決定を棚卸しする」という教訓は変わらない)

- **「なぜこの制約があるか」をコメントに書いてあることが、外したときに効く**。今回は
  XCUIBridgeResolver 冒頭の理由書きから、根拠が既に消えていることを1分で確認できた
- **穴を塞ぐ変更を入れたら、`grep` で「その穴を理由にしている記述」を洗う**(コード・docs・
  SKILL)。理由を書いた場所と、それを根拠に制限した場所は**別のファイル**になりがち
- **決定の棚卸しはユーザーの一言から始まることがある**。「Simulator なら in-app が既定では?」は
  仕様の質問ではなく**前提が古いという指摘**だった。前提を確かめずに答えを書かない
- **「どのブリッジが撃つか」と「撃った結果どのブリッジが使えなくなるか」は別**。home/appSwitcher は
  もともと XCUITest が受けていた(in-app は 501)が、**背面化した瞬間に in-app 側が丸ごと死ぬ**
  (アプリのプロセス内に住むため suspend される。実測: 直後の snapshot がタイムアウト)。
  対処は「誰が撃つか」ではなく**背面化中は全操作を XCUITest へ寄せる**こと(読みと書きを
  同じ側に寄せると ref の名前空間も揃う)。launch/activate で解除する
- **引数へ統合する前に「単独で使う経路」を探す**。Enter を `ft_type(pressEnter:)` に畳んだとき
  「type の直後にしか撃たない」を前提に text を必須にしたが、**iOS はソフトキーボードを閉じる
  手段が pressEnter しかない**(`hideKeyboard` は Android 専用)と docs/commands.md に書いてあった。
  統合は選択肢を減らす代わりに**組み合わせも減らす** —— 畳む前に対象コマンドの既存の用途を引く

### 道具の外の性質を、その道具の出力だけで断定しない(2026-08-13)

**「4つの環境で揃って再現した」は「対象の性質だ」の根拠にならない。**
4つが共有しているのは自分のコードでもあるからで、**揃った再現はむしろ共通の原因が
自分側にある可能性を上げる**。

実害: 「`android.webkit.WebView` は `<table>` のセルを a11y へ1つも公開しない」と
**4 SUT で実測して**断定し、その上に CDP/DOM 経路を丸ごと積んだ。実際はセルは a11y に在り、
`SnapshotBuilder.mappedType` の葉テキスト救済が `contentDesc` しか見ていなかったための
取りこぼしだった(版 61 で修正)。**測っていたのは自分のブリッジの出力**で、4 SUT が
共有していたのは WebView ではなく共通のフィルタ。実機を繋いで `uiautomator dump` と
突き合わせた瞬間に崩れた。

- **裏取りは別系統の観測で**。Android なら `uiautomator dump`(別の a11y クライアント)、
  iOS なら CDP / inspector を直に叩く。**エミュレータでは `uiautomator` が動かないことがある**
  (全台で無言失敗した)ので実機が要る場面がある
- **「黙って消える」形をとくに疑う**。今回は `<table>` 自身が GridView + id で残ったため
  `webViewGapNote` の空白帯にもならず、検知が1つも鳴らなかった

### 揃えた瞬間に、見分ける手掛かりも消える(2026-08-13)

DOM の粒度・命名を a11y へ揃えた直後、**ラベルだけでは a11y の木と DOM の木を区別できなく**
なった。それに気付かず a11y の木を見て「DOM 経路が効いている」と報告しかけた。
**検証は木の構造で行う**(ブラウザなら chrome の後に id 無しノードが続くか)。
一般化すると、**2つを見分けるために使っていた差を消す変更をしたら、検証手段を先に作り直す**。

### 型検査の効かない境界(拡張 ⇄ webview)は往復テストで縛る(2026-08-26)

用語の改名(`host` → `machine`)で **webview 側だけ旧キーが残り、3件が黙って壊れた**。
拡張は TypeScript なので改名漏れはコンパイルで止まるが、**webview の JS は
postMessage 越しで型が消える**ため、送る側と読む側がズレても誰も落とさない。
壊れ方は3つとも「エラーにならない」形だった:

- 一覧が常に空(`hosts[].name` を読んでいた → リモートのマシンを1つも選べない)
- メッセージが最終ゲート(`isMonitorFromWebviewMessage`)で丸ごと捨てられ、
  **画面上は成功したように見えて登録簿に届かない**
- 参照のマシンが読めず、確定すると `machine: "local"` として保存 ——
  **利用者の実行プロファイルからリモートのデバイスが消えた**

**テストは旧キーを固定していたので3件とも緑のまま通った**。フィクスチャは production と
同じキーで書かれている限り、片側だけの改名を検出できない。要るのは
**「webview が組み立てた payload をそのまま拡張側のゲート/パーサへ通す」往復テスト**
(`webviewRemoteHostsSettings.test.mjs` / `webviewRunProfileDeviceMachine.test.mjs`)。
実バンドルを jsdom で動かし、`postMessage` で出た値を `isMonitorFromWebviewMessage` に
食わせる。旧キーへ戻す変異でどちらも落ちることを確認してある。

**同型を疑う場所**: postMessage の両側・NDJSON のキー・`dataset.*` 属性・CSS クラス名 ——
どれも「片方だけ変えてもビルドが通る」。改名したら **grep でキー名の全出現を数え、
production とテストの両方が新しいキーになっているか**を見る。

### SUT アプリのビルドを守るゲートは E2E だけ(2026-08-13)

`swift test` は `TestProjects/` のシナリオを型チェックするが、**`E2EAppIOS` 等の SUT アプリは
別プロジェクトなのでビルドしない**。同じ HTML を 6 SUT へ配るような変更では、
**埋め込み先の言語ごとにリテラルの制約が違う**ため片方だけ落ちる(実害: RN の
テンプレートリテラルがバッククォートで終端 / Swift の複数行リテラルで字下げ不足)。

- **Swift は最初のエラーで止まる**ので、報告された行だけ直すと次の周回で別の行が出る。
  1周4〜7分の E2E で1件ずつ潰すことになった。**リテラル全体を機械的に見る**
- 配り終えたら E2E を待たず `xcodebuild -project E2EAppIOS/FTE2EIOS.xcodeproj -scheme FTE2EIOS
  -destination 'generic/platform=iOS Simulator' build` を直接1回打つ

### 実機でしか出ない前提(iOS Safari の DOM。2026-08-13)

`docs/design/` §実機だけの罠 が正。検証で詰まったら先にこの3つを疑う:
**⑴ 1通が大きいと黙って捨てられる**(上限は固定でなく約600バイト揺れる)/
**⑵ Web インスペクタが無効だと TLS 直後に切断**(設定 → Safari → 詳細)/
**⑶ 有効化より前から動いていた Safari は登録されない**(起動し直す)。
⑵⑶ は stderr で名指しするようにしてある(`SafariWebInspector.inspectorHint`)。

### デバイスで確かめるときに嘘をつく2つの実験系(2026-08-05)

どちらも「実装は正しいのにデバイスで誤った結果を見る」形なので、原因をコード側に探すと迷う。

- **変異テストの後は製品バイナリを作り直す**。`swift test` は `.build/debug/` の実行ファイルも
  **変異版で上書き**する。ソースを戻しただけでデバイスでの検証に進むと、**変異版が走って**
  「直したのに直っていない」を見る(実際に踏んだ: 出るはずのない助言文が出続けた)。
  ソース復元と `swift build --product <名>` は必ずセットにする
- **単体テストは `--parallel` で回す**(2026-08-10。実測 127s → 34s。ウォームで 33〜35s)。
  ただし**プロセスが分かれる**ので、ホスト単位の共有資源に素で触るテストは落ちる。
  実例: `FMBreaker` は落ちた事実を `~/Library/Caches/fleetest/fm-breaker.state` に置く
  (14 ワーカーがプロセスを跨いで共有するための仕様)。テストが既定パスを直接読み書きしていたため、
  並列だと**他プロセスの `tearDown` にある `reset()` がファイルを消し**、トリップ判定が競合して必ず落ちた
  (直列では通るので、既定が直列である間は誰も気づけない)。
  型どおりの直し方は2つに割ること —— **①実在の確認はプロセスごとの一時パスで**(`stateURLForTesting`
  のような差し替え口を production に持たせ、テストが UUID 付きの temp を入れる)/
  **②「どこに置くか」は I/O 抜きで表明する**(`defaultStateURL` の形だけを見る)。
  片方だけだと、隔離した瞬間に「ホスト単位である」という要件の表明が消える。
  同型の危険は `.fleetest/` の台帳書き込み・`DiagnosticReports` の走査・simctl/adb を呼ぶテスト。
  **並列を初めて通したときは数回まわす**(今回は 6 連続で緑を確認してから既定にした)
- **共有資源に触るテストの方針は2段**: **①隔離できるなら隔離**(差し替え口を production に
  持たせ、テストは一時パスを使う。`FMBreaker` と `FMCallSlots` がこの型)/ **②隔離できないホストの実体**
  (simctl・adb・起動中の Simulator/Emulator・固定パス)は `Sources/FTTestSupport/SharedResource.swift`
  の `SharedResource.<key>.locked { }` で資源キーごとにファイルロック(flock)して直列化する
  (①が使えないときの下位の手段。クラス単位の直列化は採らない)。
  **同一スレッドでの同じキーの再入は即座に失敗する**(fd が別なので flock は自分自身とデッドロック
  する。検出しないと 120 秒待つ謎のタイムアウトになる)。**異なるキーの入れ子は禁止**(順序次第で
  相互デッドロックする。検出はせず呼び出し側の規律)。**プロセス死で自動解放される**のが flock を
  選んだ理由(存在チェック方式のロックファイルだとテストが落ちた回に残留し、以降が全部止まる)。
  `XCTSkipUnless` によるスキップ判定は必ずロックの外に置く(既定の実行でロックを取らない)
- **`SharedResource` は「同じ資源に触る他のテスト」しか止められない**(実害 2026-09-10):
  `FMCallSlots` の枠は `~/Library/Caches/fleetest/fm.lock.<slot>` で**機械の全 fleetest プロセスと
  共有**するので、`swift test` の最中に**走っている run から枠を奪う/奪われる**。フル
  `swift test --parallel` で `acquire(timeoutSeconds: 1)` が2回落ちた(単独では緑)。
  `SharedResource.hostCaches` は他のテストとの競合しか防げない —— 隔離は①の型(置き場の
  差し替え口 `FMCallSlots.lockDirectoryForTesting`)で行う。**確かめ方**: 本番の枠5本を flock で
  掴んだまま該当テストを回す —— 隔離前は 18 件落ち、隔離後は緑(この witness が無いと
  「たまたま通った」と見分けられない)
- **in-app ブリッジは `simctl launch` で消える**(dylib が注入されない素の起動になる)。
  検証の下準備でアプリを前面に戻すつもりの `simctl launch` が**検証対象のブリッジを壊す**ので、
  in-app を使う実験では前面化も `ft_launch`(= 注入つき再起動)で行う

### 「起動中のブリッジを待つ」は pid の生死では打ち切れない(2026-08-05)

ランナーが落ちた後の provision が 3 分級になった。原因は adopt(他プロセスが起動中の
ブリッジを引き取る)経路が `waitUntilReady` の既定 180 秒を丸ごと待っていたこと。

- **最初に pid の生死で短絡しようとして外した**: テストが失敗しても xcodebuild は後始末の間
  生きており `ps` にも残る。しかも「起動中」の一覧は pid × `ps` 照合で作られるので、
  **死んだ pid はそもそも adopt 対象にならない** = その短絡は永久に発火しない
- 正しい材料は**ログの終端マーカー**(`** TEST EXECUTE FAILED **` /
  `** BUILD INTERRUPTED **` / `Testing failed:`)。ログは起動のたびに空で作り直されるので
  前回の残骸で誤爆しない
- **「関数が正しい」と「ループが見ている」は別**なので、待ちの本体が1秒以内に降りることまで
  テストする(応答しないポート + マーカー入りログで実測)
- **マーカーが出ない孤児もある**(2026-09-04: シミュレータ停止後に xcodebuild が固まって残り、
  6〜16 分生きたまま announce しない。ログにはマーカーが無いので上の短絡は効かず、引き取りの
  たびに 180 秒待って起動し直していた。同日3回)。2つ目の材料は**プロセスの経過時間**
  (`ps -o etime=`。`BridgeLauncher.runnerElapsed`)—— **startupTimeoutSeconds 以上生きて
  announce していないランナーは、起動した側が既に待ち切って諦めたもの**なので待たずに止めて
  起動し直す(`StartingRunnerVerdict.decide`。経過が測れないときは従来どおり待つ)

### macOS のファイル名は NFD —— 文字列一致が黙って外れる(2026-08-05)

シナリオのクラス名を改名し、`results/` と `reports/` の履歴(6,656 ファイル)を追随させたとき、
**ファイル名の置換が 0 件で「完了」した**。原因は macOS がファイル名を **NFD** で保存すること
(`で` = `て` + U+3099)。NFC のリテラルで `in` を取ると、目で見えているのに一致しない。
しかも `grep -rl` も同じ理由で 0 件を返すので、**「残存 0」の確認まで一緒に騙される**。

- **ファイル名は `unicodedata.normalize("NFC", name)` してから照合する**(置換後の名前は
  NFC で書けばよい。APFS は正規化非依存で引けるので参照は壊れない)
- **ファイルの中身は NFC のことも NFD のこともある**。ツールが書いた文字列は NFC、
  **ファイル名から作った文字列(reportPath 等)は NFD** で混在していた。両方の形を置換対象にする
- 検証は「残っていないこと」ではなく**「新しい名前で引けること」**で行う
  (`fleetest results summary` に 694/333/333 件の履歴がそのまま出ることを確認した)
- **語の一括置換は正しい用法まで巻き込む**。この移行で `ScenarioRunnerMain` の
  「mode=xcuitest なら**実機で動く**、と誤認しやすい罠」(物理端末の意味で正しい)を
  巻き込んで書き換えた。**追跡対象ファイルの差分は1行ずつ読む**
  (`git show --stat` で想定外のファイルが出ていないかも見る。今回それで気付いた)

### snapshot が「今の画面」とは限らない —— セッションのアプリに閉じている(2026-08-05)

MCP で「タップしたのに画面が変わらない」が続いたとき(**症状の初出は iPhone 実機・機構の確定は
シミュレータ**)、実体は**前面のアプリが入れ替わっていた**。
XCUITest の snapshot は**セッションのアプリの木**なので、別のアプリが前面に来ても同じ木を返し、
ホスト側は変化を検出できない。スクリーンショットを撮って初めて判明した。

- 経路: 入力欄を `clearInput` → キーボードが出て画面が上へスクロール → 「戻る」ボタンが
  **ステータスバーの帯に重なる** → そこへのタップが**システム UI(「◀ 元のアプリへ」)に当たり**、
  別アプリへ切り替わった。以後の snapshot は元アプリの最後の画面を返し続けた
- **要素一覧はアプリの中しか映さない**。システムのダイアログ・キーボードのチュートリアル・
  ステータスバーの帯は**木に出ないのに操作を奪う**。「何も起きない」ときは
  **ft_screenshot を撮る**のが最短の切り分け
- 対処は「前面に居るか」を snapshot のたびに問い合わせ(`/appstate` 1往復・実測で誤差程度)、
  居なければ**先頭に警告を出す**。黙って古い木を返すより安い

### ブリッジの版を上げた直後のフル E2E は「第1フェーズだけ」条件が違う(2026-08-07)

`bridgeProtocolVersion` を上げると**全ブリッジが起動し直される**ので、`Scripts/e2e.sh` の
**最初に回るプロジェクトだけがコールドなシミュレータ**に当たる。実測ではその回の
`launch` が **24.5 秒**(通常は数秒)かかっていた。

このとき E2E-CMP / ios-xcuitest の `type "#field_single"` が 4 本落ちた
(422「入力が期待した値になりませんでした」・**打った文字が周回数ぶん累積**する形で
8→32 / 3→9 / 9→36)。読み返しが実際の値より遅れて空を返し、`plan` が `.resend` を
返し続けたときの形。**同じプロジェクト・同じプロファイルを同じ並列度(レーン 98%)で
回し直すと 48/48 緑**、低負荷の絞り込み実行でも緑、MCP 単発の `ft_type` も成功した。

**同時に入れたブリッジ変更のせいではないことは A/B で確定させた**(推測で片付けない):
テキスト入力画面(キーボード表示中)のノード数を dedupe の ON/OFF で数えると
26 → 25 で、**減るのは重複していた `#dictation` だけ**。`#field_single` は
どちらでも 1 件なので、読み返しの一致件数(`TypeReadback.value` は候補が
複数だと nil = 検証不能で受理)は変わらない。value の placeholder 正規化も、
この欄は `placeholderValue` を持たないので発火しない。

- **教訓1**: ブリッジの版を上げた回のフル E2E は、第1フェーズの失敗を
  「コールドスタート由来かもしれない」と疑う。順番を変えるか、その1プロジェクトだけ回し直す
- **教訓2**: **変更前のベースラインを取らずにフルを回すと、回帰か既存かを区別できない**。
  今回は A/B の計測で決着したが、先に HEAD で1回回しておけば往復が減った

### snapshot の木が**別のアプリのもの**に入れ替わる(Android。2026-08-06)

上の「セッションのアプリに閉じている」の**逆**が Android で起きる。あちらは
「session のアプリが背面に回っても同じ木を返す」だったが、Android のブリッジは
`SnapshotBuilder` が `root.getPackageName()` を返すので **session が前面のアプリへ追従する**。

- 決定的再現: `ft_launch com.ftester.e2e.android` → `ft_navigate back` **1回**。
  最初の画面からの back でアプリが終了し、以後の `ft_snapshot` は**背後に居た
  `com.ftester.e2e.flutter` の木**を、注記なしで返す
- **4 SUT は `#id`・ラベルが共通契約**なので、木を見ても入れ替わりに気付けない。
  これが「E2E アプリだから起きる特殊事情」ではないことに注意 —— 実利用でも
  「テスト対象アプリと似た画面を持つ別アプリ」は普通にある
- `backgroundedSessionNote`(session が前面か)は**構造上まったく発火しない**:
  session 自体が動くので、常に「前面に居る」と読める
- 対処は**ホスト側で「最後に ft_launch した bundleID」を覚えて突き合わせる**
  (`MCPServer.switchedAppNote`)。ブリッジ側の session の意味は変えていない

### 「消えた」は消したファイルではなく**次の起動が読む値**で確かめる(2026-08-05)

`clearAppData`(iOS)は**データコンテナの中身を消すところまでしか効いていなかった**。
NSUserDefaults は cfprefsd がドメインを抱えており、次の起動で消したはずの値を配って plist を
書き直す。**消去は成功を返す**ので、気付けるのは「clearAppData から始めたのに前回の状態で
立ち上がる」を踏んだときだけ —— 実際、MCP に `ft_clear_app_data` を足して初めて発覚した。

- **検証は消した直後ではなく、消して**起動してから**見る**。ファイルが消えたことは
  「消えた」の証拠にならない(デーモンのキャッシュ・書き戻しがある)
- **判定にはカウンタを使う**(この SUT は `launch_count`)。消えたはずの値が
  2→3→4 と増え続けることで、3回とも効いていないと即断できた。真偽値だと1回の観測で迷う
- **候補は「実行できたか」ではなく「効いたか」で採る**。`defaults delete` は
  exit 0 でも domain not found、`killall` はシミュレータに存在せず**エラーが握り潰されていた**
  (どちらも1回だけの観測では効いたように見えた)。対照3回を並べて初めて分かれた

### 「遅くなった」は同一プロセスの2回目で測る(2026-08-05)

MCP プロセスを毎回起動して外形時間を測ると、inapp モードの経路が xcuitest モードの経路より **+0.5s** に見えた。
内訳は home の費用ではなく**フォールバック先ブリッジを探すポートスキャン**で、セッションに1回だけ。
同一プロセスで2回撃つと 1.02s → 0.475s(= xcuitest 直と同値)で、**空振りの 501/404 は 1.3ms**。
**初回費用と1回あたりの費用を分けて測る**(分けないと、消せない固定費を毎回の費用と誤認する)。

### 「整定した」は機構ごとに見ているものが違う(2026-08-02)

整定(settle)の実装はブリッジごとに別で、**それぞれ「動き」の一部しか見ていない**。
どれにも掛からない動きがあるので、整定を信じる前に**何を見ている実装か**を確認する。

| ブリッジ | 見ているもの | 見落とすもの |
|---|---|---|
| in-app(iOS) | CALayer のアニメーション | **`setContentOffset(animated:)`**(UIScrollView の
プログラム的スクロール)は CALayer アニメーションを伴わないので素通しする |
| xcuitest | 直前操作後のツリー差分(`captureSettled`) | アニメーションが**始まる前**に採ると
「変化なし」で確定する |
| Android | a11y イベントの静穏(`QuietWaiter`) | a11y ノードはキャッシュ供給で、
**読む前に `refresh()` しないと古い座標を返す**(../design/bridge.md「Android のテキスト注入の規律」) |

**実害(2026-08-02)**: 「先頭へ」ボタンのアニメーション付きスクロールの直後に要素を解決すると、
**動く前のツリーの座標をタップして別の要素が選ばれる**。ステップは成功と記録されるので
黙って誤った結果になる。塞ぎ方は2層 —— in-app の整定に**スクロールの動きそのもの**
(可視 `UIScrollView` の `contentOffset` の差分)を足し、ホスト側は**スクロール探索の1周目だけ
静止を待つ**(`StepExecutor.runScrollSearch`)。後者はブリッジ非依存なので、
すり抜けが in-app 以外にもあることの保険になっている。

**コスト**: 「スワイプせずに見つかったら静止待ちを挟まない」最適化を捨てたが、実測は
共通シナリオで +0.1〜1.0%(run 間ノイズ以下)。黙って誤る危険には見合わない。

### Compose の探索直後タップ(2026-08-03: 原因1・原因2 とも修正済み)

**症状**: CMP(Compose Multiplatform)で、**スクロール探索の直後のタップが効かない**。
**E2E-iOS / E2E-Android / E2E-Flutter では同じ形が安定して通る = Compose 固有**。
**原因は2つあり、別物**なので分けて読むこと。

**「狙った行ではなく数行先が選ばれる」と長く記録していたが、これは誤り**だった ——
E2E アプリは選択状態を launch を跨いで永続するので、`clearAppData` していない検出器が
**前の run の残留を読んでいた**。汚染を除くと値は `selected=-` = **タップが丸ごと飲まれている**。
判定に使う検出器は必ず `clearAppData()` から始めること。

#### 原因1(修正済み): 容器の外に並ぶ ghost 要素で探索が止まる

Compose iOS は**容器の外に子を報告する**: `#list_rows`(y 230..692)に対し `#row_10`(y 734)
`#row_11`(790)`#row_12`(846)が並ぶ。**いずれも `label` を持たない**(容器と交差する行だけが
ラベル付き。4スナップショットで一致)。`scrollable` の申告が出ない Compose では見切れ判定の
viewport が**画面全体**になるため、ghost は「画面内 = 見えている」と判定されて探索がそこで止まり、
**容器の外の座標をタップする** → タップが飲まれる(計装で確認: `#row_30` を `label=nil`・
y=783 で掴んでいた)。

**残存の正体(2026-08-04 特定・対処済み)**: 修正が**探索ループの中だけ**に入っていた。
ループを抜けた後の再解決(`StepExecutor` の解決リトライ)は同じ判定を持たず、
**木が一瞬 ghost を返すとそれを掴んでタップし、容器の外を撃って飲まれていた**。

決め手は「実行中に I/O を足さない診断」だった(上記の heisenbug のため):
掴んだ要素が容器の外なら**ステップの注記に出す**ようにしてスイートを回したところ、
失敗した run で `tap "#row_30"(the element is still reported outside its scroll container
(3 re-resolve(s)))` が出た —— **タップ時点で容器の外に報告されている**ことが確定した。

対処は2段(どちらも探索ループと同じ判定 —— 2026-08-05 以降は `isOutsideContainer`):
1. **解決し直す**(木の遅れなら撮り直しで直る)
2. それでも容器の外なら**もう1回送る**(探索ループの「見えるまで送る」と同じ)。
   1周目は撮り直しだけにして、正常系のコストを増やさない
救えたか救えなかったかは**必ず注記に残す**(黙ってタップして飲まれるのが最悪)。

**効果は部分的**(スイート8周で測定。CMP/ios-xcuitest):

| 版 | 失敗率 | 失敗時の ghost 注記 |
|---|---|---|
| 再解決のみ | 3/6 | **2件に付いた**(掴み直しても容器の外のまま) |
| 再解決 + 追加スワイプ | 2/8 | **0件**(ghost 経路では落ちなくなった) |

**残りは別の機序**: 解決した要素は容器の中(注記が付かない)なのに、タップが効かず
`selected=-` になる。**ghost の取りこぼしと混同しないこと** —— 注記の有無で見分けられる。
次に追うならここから(容器が最初の1タッチを吸う既知の形〈空打ちドラッグで肩代わり〉が
効いていない可能性。ただし**計装は I/O を足さない方法で**)。

**再現条件は「iOS 8 レーン同時稼働」**(= スイート実行)。単独実行では出ない:

| 条件 | 失敗率 |
|---|---|
| スイート実行(計装なし) | **3/10(30%)** |
| 単独実行(1レーン) | 2/96(2%) |
| スイート実行(**計装あり**) | **0/13(0%)** |

**計装を入れると消える(heisenbug)**。probe のファイル書き込みがタイミングを変えてしまい、
FOUND / DRAG / TAP を出す版では 13 周回して一度も再現しなかった。**同じ手で追ってはいけない** ——
次に追うなら、実行中に I/O を足さない方法(メモリに貯めてシナリオ終了時に一括で吐く、
既存の `FT_EVENT_LOG_PATH` の step 内訳を使う等)にすること。

**負荷モデルを間違えて 42 回無駄にした(2026-08-03)**: 「iOS 単独 + Android スイート並走」を
負荷と考えて追ったが、**効くのは iOS 側のレーン数**だった。**負荷の当て方は、失敗が実際に
起きている実行形態に合わせる**(このときは E2E-CMP/ios-xcuitest のスイートを反復するのが正解)。

**成功時の記録から分かったこと**(次に追うときの材料):
- 修正は意図どおり働いている —— `attempt=3` で ghost(`label=nil`・y 768..824・容器 230..692 の外)を
  `clipped=true` で弾き、`attempt=4` で実体(`label=行 30`)を掴んでいる
- ただし **FOUND(y=347)と TAP(y=249)の間でリストが 98pt 動いている**。空打ちは横向きなので
  スクロールしないはずで、**整定後もまだ動いている**。再解決が拾うので成功しているが、
  ここが残り 2% の機構の候補
- もう一つの未検証の仮説: 空打ちの点が手前の要素に取られると**いまは丸ごと飛ばす**ので、
  容器の 1 タッチが肩代わりされない。容器の矩形は分かっているので**別の安全な点を選ぶ**
  余地がある(未実装・未検証)

**修正**: スナップショットは pre-order + depth なので、**直前にある depth の小さい要素**が祖先。
これを復元して見切れ判定の viewport に使う(`ContainerGeometry.clippingContainer`)。
ブリッジは要素を間引くので候補が叔父のことがあり、**同じ depth の兄弟が2つ以上その中に居る**
ことを確かめてから採用する。**スクロールの座標化には使わない** —— 暗黙の座標化とは別物で、
あちらは2度撤回済み(3度目は無い)。回帰テストは **CMP の S0110**(領域指定なしの形)。

#### 原因2(Android・修正済み): a11y ツリーの公開遅れ

慣性ではなく**古いツリーを掴んでいた**。Android の a11y ノードはキャッシュ供給で、
ブリッジの整定(静穏待ち)を通っても**数十 ms 遅れて公開される** —— スワイプ直後の素の snapshot が
**スワイプ前の位置**を返す瞬間がある(実測: 4回中2回。素 = `#row_01` / `refresh=1` = `#row_06`)。
古い木で探索を続けると「動かなかった」と誤認し、見つけた要素が直後の解決で消えて
`cannot resolve the locator` になる。

**修正**: スワイプ後に読む snapshot をすべて `snapshot(bypassingCache: driver.supportsCacheBypass)` へ
(`StepExecutor` の 探索ループ本体 / 探索後の解決とその再試行 / `settleAfterScroll` / `settledSignature`)。
**効く場所は探索ループ本体の1枚**だった —— 以前ここに「`settleAfterScroll` に入れても効かなかった」と
書いていたのは、整定ヘルパだけを直して**探索ループが古い木を掴んだままだった**ため。

**規律**: 静止判定に使う snapshot も必ずキャッシュを捨てること。古い木は連続して同じ署名を返すので、
素取得だと**「2回続けて同じ = 止まった」が遅れて公開された古い位置で成立する**(しかも
`settledSignature` は静止時の木を呼び出し側へ返すので、そのまま古い座標で解決される)。

**コスト(2026-08-03 に A/B 実測): Android の scroll 系ステップに +3.2s。その約6割は回収済み**。

1 枚あたりはブリッジ直叩きで **5.1ms → 39.9ms(+35ms)**(emulator-5554・要素 5.8KB の画面・
各 15 回の中央値。**refresh の費用はノード数に比例する**ので重い画面ではもっと掛かる)。
整定ポーリングは1呼び出しにつき 2 枚以上撮るので、これが回数ぶん積み上がる。

| | base | fix | 差 |
|---|---|---|---|
| E2E-CMP android・**scroll 系ステップの中央値合計**(シナリオ・index 単位で突き合わせ) | 70,538ms | 73,765ms | **+3,227ms** |
| 同・共通53シナリオの中央値合計 | 347.15s | 350.95s | +3.80s(+1.1%) |
| E2E-CMP ios-xcuitest(対照) | 477.54s | 477.24s | −0.30s(−0.1%) |

**集計はシナリオ・index 単位で揃える**。コマンド名だけで中央値を取ると別シナリオの
`scrollToTop` が混ざり、実際より大きい差(`+1,007ms`)に見える —— 最初はそう書いていた。
劣化は1コマンドに集中しているのではなく、`scrollTo` / `scrollDown` / `scrollToTop` に
**+130〜1,100ms で広く散る**(= 整定の呼び出し回数に比例している)。

**それでも払う**: 素取得だと `scrollToEdge` の「2回続けて変化なし = 端」が**遅れて公開された
古い位置で成立して途中で止まる**(沈黙の誤り)。実際、base では `settledSignature` が
ポーリング上限に達して「did not settle」を出していたが、迂回後は一度も達していない
= 遅くしただけでなく**整定の判定を成立させている**。

**回収(`settleSleepMs`)**: 追加コストの正体は「1ポーリングあたり +35ms」なので、
**待ちから snapshot の実測時間を差し引いて周期を一定に保つ**。判定したいのは
「約 100ms の周期で画面が変わらないこと」であって sleep の長さではない。
実測で **scroll 系ステップ合計 −1,989ms**(14 ステップ中 12 が改善または横ばい)。
**迂回しないブリッジ(iOS)では引かない** —— あちらは snapshot 自体が重く、引くと周期が
大きく縮んで「早すぎる静止判定」に倒れる。純粋ロジックなので `SettleSleepTests` で固定。
**スイート総計では改善を主張しない** —— Android の run 間ばらつき(同条件で 363〜398s)の方が
大きく、n=3 では解像できない([[android-perf-degrades-within-session]])。

**この A/B のノイズ床**: iOS 対照(コード経路が同一 = 真の差ゼロ)でも個別シナリオは
**±1.0s 振れた**。シナリオ1本の差は 1s 程度まで意味を持たないと読むこと。
判定は必ず**共通シナリオの中央値合計**で行う([[perf-regression-verdict-by-results-db]] の方式)。

**iOS ブリッジへ `?refresh=1` を送ってはいけない** —— クエリ付きは別ルート扱いで
`404 not found: GET /snapshot?refresh=1` になる(2026-08-03 実測)。`BridgeClient` の
`supportsCacheBypass` は既定 false で、呼び出し側は必ずこれで閉じること。

#### 原因3(修正済み): 空打ちドラッグがクリックとして成立していた

探索終端の**空打ちドラッグ**(容器が飲む1タッチを肩代わりする補助操作)が、Compose iOS では
**クリックとして成立して指の下の行を選んでいた**。`scrollTo("#row_40")` だけで
`selected=row_40` が入る = **読み取り専用のはずのコマンドがアプリの状態を書き換える**
(`clearAppData` 済みでも再現。2026-08-03 に計装で確認)。

**距離では消せない** —— 2pt / 24pt / 120pt、0.05s / 0.30s のどれでもクリックした。
Compose は**離した点が要素の矩形の中なら**クリックを成立させるので、中に留まる限り無駄。

**修正: 終点を要素の矩形の外へ横に抜く**(`StepExecutor.emptyDragEndX`)。矩形の外で離せば
クリックは取り消される。**縦に抜いてはいけない**(容器がスクロールとして消費して内容が動き、
直後に「今ここにある」を確かめる assertion が壊れる。実測: `E2E-CMP/ios-inapp` の S0020 が
3/3 → 0/3)。**止めるという選択肢も無い**(完全に外すと肩代わりが効かず S0080 が
CMP/ios で落ちる)。切り分けは変種A(祖先 clip のみ)3/3 / 変種B(縦ドラッグのみ)0/3。

**既存資産は1本も検出できなかった** —— 後続のタップが誤選択を上書きするため。
回帰テストは **4 SUT の S0100**(`clearAppData` してから探索だけ行い、`selected=-` を読む)。

#### 試して撤回した案(再提案しない)

**「自己発見」(2026-08-03)**: 前後 snapshot で 4pt 以上動いた要素が2つ以上あれば、その
**外接矩形**を容器とみなす案。iOS は 0/3 → 3/3 に直ったが、**リスクが2つ現実化**して収束しなかった:
- **外接矩形は容器ではない**(動いた行の集合 = 実容器より狭い)。見切れ判定に使うと縁の行が
  常に「見切れ」扱いになり永久に送り続ける(CMP/Android が「15回送っても見つからない」
  決定的失敗へ**悪化**した)
- **プラットフォームで裏目が逆**。iOS は刻みを抑えると直る(frame クランプ対策)が、
  Android は注入ドラッグの実移動量が元々小さく、抑えると届かない。片方を直すともう片方が
  壊れる往復になり、ヒューリスティクスの重ね掛けでは両立しない

また、整定署名に**可視要素の id を混ぜても直らない**(仮想リストの行入れ替えを署名が
見落としている説は否定された)。「先頭へ」のスクロール自体は**550ms 以内に完了**しており
(ブリッジ直叩きで実測)、整定の取りこぼしとは別の経路だった。

## 高負荷では XCUITest の `typeText` が打鍵を取りこぼす(2026-07-31)

`/clear` は「残り文字数ぶんの delete を送る」を繰り返すが、**送った打鍵が全部入る保証はない**。
実測(6シミュレータ並列 + Android スイート並走)では毎周 6 割前後しか入らず、
`"hello123"(8打鍵)→"hel"`、`"hel"(3打鍵)→"h"` と減っていった。周回数を 2 で固定していた頃は
ここで打ち切られ「値が残っています」で落ちていた(**約 2%**。フルスイートでのみ再現し、
該当シナリオ単独では出ない)。**打鍵数ぶん送ったことを完了の根拠にしないこと** —— 読み返して
空になるまで回す(`BridgeRouter.handleClear`。上限は周回数ではなく deadline と進捗なし回数)。

**この手のフレークはシナリオ経由では効率が悪い**。1周(約2分)で clear が数回しか走らず
1/5〜1/11 でしか出ないため、ブリッジを直接叩くハーネス(ホストと同じ
snapshot→ref→/type→/clear の順で6台並列)で 1 回 150〜180 clear を回した。
再現率の比較には**同じ負荷・同じ回数**を使う(修正前 5/270 → 修正後 0/510)。
負荷源は合成 CPU 負荷(`yes`×20)では不十分で、**実際に別スイートを並走させる**必要があった。

**`/type` も同方式で対策済み**(2026-08-01・v29。`BridgeRouter.handleType` + 判定は
`TypeReadback`)。こちらの実害は取りこぼしだけでなく**コミットの遅れ**: `typeText` は
打鍵がアプリの状態に入る前に返り(打鍵はキーボード=別プロセス経由で非同期、タッチは直接届く)、
直後の送信タップが**空の値のまま処理される**(フル E2E 1 回で `type "#field_single"
"persist99"` 成功扱い → 失敗画面は `single=persist99` / `len=9` なのに `submitted=` 空。
= タップ処理の後に打鍵が届いた動かぬ証拠)。実測のコミット遅延は同負荷で通常 40〜80ms、
**まれに 0.6〜1.2s** —— ホストの次リクエストまでの間隙(100〜250ms)を超えるので順序が入れ替わる。
読み返して期待値(入力前の値 + 本文)に一致するまで返さないことで、この窓を構成的に閉じた。

`/type` の対策で踏んだ罠(いずれも実測):
- **要素スコープの `typeText`(`focused.typeText`)を使わない**。イベント合成の失敗が XCTest の
  失敗になり**ランナーごと落ちる**(高負荷で `Synthesize event` を最後にランナーが死んだ実測1件。
  同run では6台中5台が死んだが、残りは下記の SpringBoard 起因と切り分けきれていない)。
  打鍵は従来どおり `app.typeText`
- **読み返しにライブクエリ(`descendants` + `hasKeyboardFocus`)を使わない**。1回 0.5s 級で
  /type の p50 が 842ms → 2,166ms に悪化した。スナップショット(`captureOnce` 数十 ms)で
  読み、対象は直前スナップショットの ref→要素対応から採る(`refElements`)
- **追送の前に「値が動かなくなる」まで待つ**(1.5s)。まだ届いていないだけの欄へ追送すると
  二重入力になる(Android `InputInjector` と同じ罠)。読めない・曖昧(同 identifier が複数)・
  前方一致でない(自動修正・マスク欄)は**検証を諦めて受理**する(嘘の成功は潰すが、
  加工された入力を失敗にしない)。判定の境界は `TypeReadbackTests` が固定する
- **ハーネスで毎周 `launchApp` し直さない**。高負荷での連続再起動は SpringBoard を落とし、
  ランナーの launch 失敗(= XCTest 失敗で死ぬ)を誘発する。warm な画面で入力クリア→type→
  即 submit を回す方が安全で、実際の失敗窓(type 直後のタップ)も正しく突ける
- **ハーネスで酷使した直後の e2e 失敗は、まず沈静化後の再実行で切り分ける**。SpringBoard を
  連続で落とした後のシミュレータは、`launchApp` がアプリの画面状態をリセットしない類の失敗を
  出す(実測: 直後のフル e2e で「起動直後なのに前のシナリオの画面のまま → `#nav_*` を解決
  できない」が 7/40。同一シミュレータで沈静化後に再実行したら 40/40 緑)。修正のせいに
  見えるが環境ダメージ。失敗画面が「ホーム以外」ならまずこれを疑う
- この失敗クラスは**直叩きハーネスでは再現しにくい**(修正前 v28 で計 1,495 type・再現 0。
  シナリオ実測はフル E2E 298 本で 1 回)。窓が「コミット遅延 > ホストの間隙」という
  タイミング条件のため。再現率で判定できないときは、**失敗記録の画面状態から機構を確定し**、
  コミット遅延の実測(上記)で窓の実在を示したうえで、窓を構成的に閉じる修正を選ぶ

**確定判定はまだ**(2026-08-01 時点): 元の発生率が 1/298 本のため、修正直後のフル E2E
全緑(既定 233 + --ios-inapp 115)1回では「直った」と断定できない。以後のフル E2E で
S0030 型(type が成功扱いなのに後段の検証で値が空)の再発ゼロを重ねて確定とする。
再発したら、まず失敗レポートの要素一覧で「入力欄の値」と「echo/submitted」を突き合わせる
(値が入っているのに submitted が空なら別クラス = タップの空振り。下記)。

同型で**未対策のまま残している**もの(再発時はここから疑う)。
**2026-08-05 以降、どれも「直前のタップで画面が変わっていない」という注記が付く**
(上記「操作は ✅ なのに画面が変わらないとき」)。読み返しによる**予防**はできないままだが、
失敗の場で**タップまで遡れる**ようになったので、まずレポートの注記の有無を見ること:
- **/pressEnter**: 完了(IME アクション発火)を汎用に読み返す先が原理的に無い
  (`#txt_ime_action` は E2E SUT の都合で、実アプリに同等物は無い)。未再現のため記録のみ
- **タップの空振り**: /tap が 200 を返したのにタップが処理されない。計測中に1件だけ観測
  (type→即 submit の直叩き 約1,500 回中 1 回・極端負荷下。入力欄の値は正しいのに
  `submitted=-` が初期値のまま = type ではなくタップ自体が落ちた)。type と違い
  「何が起きるべきだったか」をブリッジが知らないので、同じ読み返し方式は使えない。
  **2例目(2026-08-02・E2E-CMP/ios-xcuitest フル並列)**: `WebViewの中身を操作できること.S0010` の
  `tap("#btn_back")` 後に `#txt_screen_title` が "WebView" のまま(期待 "ホーム")。
  同シナリオ単独 3/3・同プロファイル フル 2/2 で再現せず。**xcuitest が画面ごと委譲している
  WebView 画面**で出た点が新しい(1例目は Android の入力画面)。
  **3・4例目は「別クラス」ではなく画面凍結だった(2026-08-05・決着)**: 同じ S0010 の**シーン1**
  (`launch` → `tap("#nav_webview")` → `textIs("#txt_screen_title") == "WebView"`)が
  10 周中 2 回 `actual "ホーム"` で落ちたので**安い再現条件を掴んだ**と考えたが、
  **どちらも画面が凍結したデバイス(-06)で起きていた**(上記「iOS シミュレータも『画面だけ死ぬ』」)。
  凍結機を再起動したうえで**同じ回し方で 35 周**回すと **35/35 全緑**(4台に分散)。
  0/35 の上界は約 9% なので、先の「2/10 = 20% 級」は棄却できる。
  **教訓**: 稀な事象の率を測る前に**環境要因を除く**。除かずに測ると、環境の率を
  そのクラスの率として記録してしまう。今は run 前トリアージが凍結機を弾くので母数が汚れない

  **凍結の一斉多発には発生条件の相関がある(2026-08-08・同日2回)**: どちらも
  「フル既定スイート(8並列10分超)完走直後の in-app フェーズ開始時」= 8台同時の
  terminate→launch+注入で描画負荷が同期する瞬間だった(1回目8台・2回目5台)。
  Android で対照実験済みの「複数台同時描画」凍結と同族とみて、**BridgeProvisioner の
  デバイス並列起動を「in-app の新規 launch を含むときだけ同時2台」に絞った**
  (start-device の同時2台ポリシーと同じ理屈。再利用だけの供給は従来どおり全並列)。
  凍結個体の症状は「除外されるほど重い」から「コールドラウンチ直後の tap 呑まれ・
  同一個体でのタップ無反応集中」まで幅がある — **失敗が1台に集中していたら
  まずこのクラスを疑い、その個体を shutdown/boot してから裁定する**

## FM が死んでいる run は「守りが効いていない run」(2026-08-20 に可視化)

FM の実呼び出しが全滅していると、**`screenLooksLike` は黙って素通りし、occlusion-guard(`exist` の既定
requireVisible)は OCR だけで判定する**(`OCROnlyVisibility`。OCR が判定できない形は素通り・
`ocrTextVisibilityCheck` が off なら全部素通り)。つまりその run の緑は
**「守りが効いた緑」ではない**し、赤は FM 起因かもしれない。**自己修復(ロケータの指紋照合)は
2026-09-15 に FM を呼ばなくなった**ため、この節の対象から外れた(→ MN-22)。

これは各シナリオの stderr には出ていたが、**run のまとめには出ていなかった**ため、赤を見るたびに
「自分の変更か FM か」を人が HEAD 対照で切り分けていた(2026-08-20 に何度も払った)。
いまは `fleetest run` のまとめに1行出る:

```
⚠️ FM unavailable: 3 scenario(s) ran with screenLooksLike skipped and the occlusion-guard judging
   from on-device OCR alone (…). Read this run's result with that in mind (confirm with: fleetest doctor --fm-only)
```

**合否は変えない**(FM と無関係な失敗を隠す方が危険)。数えるのは
「**呼び出しが1件以上あり、その全部が失敗**」のときだけ —— FM を使っていないだけの run で出すと、
警告の意味が薄れて誰も読まなくなる。

**この行だけでは足りない**(2026-09-03)。数えているのは「実際に FM を引いて全滅したシナリオ」なので、
**ブレーカが落ちて1回も呼ばずに素通りした run では 0 のまま**沈黙する。そこで、機械の死活台帳
(`FTCore.FMLiveness`)から**もう1行**出す ——「この機械で FM が死んでいる(どの経路が・なぜ)」。
根拠が別なので両方出す:

```
⚠️ FM is dead on this machine (vision): a green here is not a fully guarded green —
   screenLooksLike was skipped and the occlusion-guard judged from on-device OCR alone
   (text OCR cannot judge passes unchecked; with ocrTextVisibilityCheck off the guard passes through).
   vision: …
```

**FM のテキスト経路はもう実行時機能を1つも持たない**(自己修復が最後の利用者だった。
シナリオ下書き・命名コマンドは実行時ではないので対象外)ので、「テキスト経路が死んでいるので
自己修復を無効化する」という起動前警告は無くなった。残るのは視覚経路(occlusion-guard /
`screenLooksLike`)の死活警告だけ。同じ事実は **run 開始前**(`ProfileRunner.warnIfFMDegraded`)・
**run.json の `fmDead`**・**モニターの FM 行**(呼び出し0件でも ✕)・**`ft_status`** にも出る。
台帳の作り方と規律は CLAUDE.md の該当節。

**この行が出ている run では**: ①緑を「守りが効いた」と読まない ②赤は必ず HEAD 対照を取る
(同じ負荷条件で。docs/verification/ の flake の節)。

**ステップ単位では `notes` の `visibility-guard-skipped`**(2026-08-23)。occlusion-guard が FM に
訊いたのに判定が返らなかったステップに立つ(scenarios/*.json の `timeline[].notes` /
`failedSteps[].notes`)。run の1行より粒度が細かく、「どの exist が幾何だけで通ったか」まで追える。
**幾何の段(中心が画面外なら不可視)は FM が死んでいても効いている**ので、この注記が付いた緑は
「木に居て画面内」までは確かめた緑。
幾何の段の**陽性対照は `TestProjects/E2E-iOS/scenarios/_disabled/95_可視性の幾何.swift`**
(プロファイル `ios-fpc`。S0010 が `text visibility check failed (offscreen)` で落ちるのが正常。`_disabled/` に
あるので既定スイートでは1度も実行されない)。

## 「待ってから取り直す」を模すフェイクは**動く木**にする(2026-08-20)

割り込みを閉じた直後の取り直しを「整定を待つ」に変えた回、変異(整定を外して素の
`driver.snapshot()` に戻す)が**生き残った**。原因はテストのフェイクで、閉じるアニメーションを
**毎回同じ木**で模していた —— 整定は「同じ署名が2回」で成立するので、**静止した木では
待っても待たなくても同じ結果**になり、判定になっていなかった。

直し方は2つとも要る:
- **フェイクの木を動かす**(消えていくカードの frame をスナップショットごとにずらす)
- **長さを窓に入れる** —— 操作側のリトライ予算(3回)より**長く**、整定のポーリング上限
  (6回)より**短く**。短いと「どちらでも通る」、長いと「どちらでも落ちる」で、
  やはり判定にならない

一般化: **「待つ/待たない」の差は、待っている間に状態が変わるフェイクでしか出ない**。
整定・ポーリング・リトライを触るときは、フェイクが**時間とともに変わるか**を先に見る。
関連: 変異が生き残ったときの切り分け(フィルタ・先に落ちたテスト・変異式・テスト内容)。

## in-app ブリッジの A/B は「dylib が本当に入れ替わったか」を先に確かめる(2026-08-20)

**稼働中の in-app ブリッジは再利用される**ので、ソースを差し替えても**同じ dylib のまま**

## 旧版のブリッジとの A/B は「旧ソースを現行の版番号で」ビルドする(2026-10-10)

**旧版の APK・ランナーをそのまま入れても旧版では動かない**。`fleetest bridge up` は入っている版が期待する版
(`expectedBridgeVersionCode` / `bridgeProtocolVersion`)と違えば同梱の現行版へ入れ直す(`installBridgeIfNeeded`)。
2026-10-10、Pixel 4a で Android の v96 と v97 を比べたつもりが**両方 v97 で動いていて**「差が無い」と報告しかけた
(Emulator では旧版の `install -r` が格下げとして拒否された)。

- 旧ソースを一時的に戻し、**版番号は現行のまま**ビルドする(同じ版なので `bridge up` は入れ直さない)。ソースはすぐ戻す
- **どちらで動いたかを毎回ログで確かめる** —— 版ごとに違う欄を出す(例: Android は `FT_BRIDGE_TIMING=1` で
  ブリッジの所要の内訳 `settleTiming` が logcat に出る)。腕を切り替えたのに欄が変わらなければ、その測定は無効
- 実機へ APK を入れるときは Play Protect の照会(アプリを Google へ送るか)で止まる。素の `adb install` を打たず、

## in-app の整定が cap に張り付いているかを見る(2026-07-31)

`InAppSettle` は収束しても cap 打ち切りでも**同じ顔で返る**ので、常態的な張り付きは黙って
性能だけを食う(実測: Compose iOS の launch 直後 1〜2 アクションが毎回 2,500ms)。疑う手順:

1. `fleetest api run --project <P> --profile <inapp プロファイル> --scenario <1本>` の
   NDJSON で `actionMs` を見る。**cap 値(2500)に近い定数**なら張り付き。
   snapshotMs でも waitMs でもなく actionMs に出るのが目印
2. `InAppBridge/Sources/InAppSettle.swift` の打ち切り分岐に一時 `NSLog("FTSETTLE ...")` を入れ、
   層のクラス名・アニメーションキー・keyPath・delegate を出す(`InAppBridge/build.sh` で再ビルド)
3. `xcrun simctl spawn <udid> log stream --style compact --predicate 'eventMessage CONTAINS "FTSETTLE"'`
   を**プロファイルの全デバイスぶん**張ってから run(どの機に載るか選べないため)
4. 犯人が分かったら `layerAnimating` の除外に足す。**除外は狭く**(位置・不透明度・transform を
   除外すると本物の遷移待ちが壊れる)

**dylib は版を上げないと入れ替わらない**(`bridgeProtocolVersion`)。上げずに測ると旧 dylib の
数字を見ることになる。

## ブリッジの「誤った赤」を疑う手順(成功しているのに失敗と報告される)

**症状**: ステップは失敗するのに、直後にスナップショットを撮ると**期待どおりの状態になっている**。
2026-07-31 の Android WebView `type` がこれで、原因は a11y ノードのキャッシュを取り直さずに
読んでいたこと(値は入っていたが読みが古い)。同型は「キャッシュ・遅延イベント・整定の打ち切り」の
どれかを疑う。

1. **まずホスト側から状態を撮る**。失敗した直後に `/snapshot` を撃ち、期待値になっていれば
   誤った赤が確定する(「入っていない」のか「読めていない」のかはここで分かれる)
2. **シナリオ経由で追わない**。1 run に1回しか通らない操作は再現率が低すぎる
   (実測 111 run で 2 件 = 1.8%)。**ブリッジを直接叩くハーネス**をホストと同じ手順
   (snapshot → ref 解決 → 操作)で書き、全デバイス並列で数十回まわすと同じ事象が
   **20%** まで上がった。負荷は合成 CPU 負荷では足りず、別スイートの並走が要る
3. **ブリッジ側に一時診断を足す**(期限切れの瞬間に何が見えていたか: ノードの有無・text・
   focused・bounds・候補の全列挙)。**版を上げないと旧ブリッジが再利用されて意味がない**
4. 直したら**同じ負荷・同じ回数**で前後比較する(修正前の実測が無いと「効いた」と言えない)

**失敗レポートだけで誤った赤を確定できることがある**(2026-08-01・Android ネイティブ画面)。
レポートは**要素一覧(a11y)とスクリーンショット(ピクセル取得なので a11y を通らない)を両方**
載せるので、**この2つが食い違っていたら読みが古い**と即断できる(再現を待たなくてよい)。
さらに強い判定材料は**要素一覧の内部矛盾**: 同じアプリ state から描かれる2要素(例 echo と
入力欄の値)が同一フレームでは両立しない組み合わせで出ていたら、ツリーはキャッシュ混じり。
「タップが落ちた」仮説とはここで切り分けられる —— タップが落ちただけなら他の要素は新しいままのはず。

**この失敗クラスは WebView 限定ではない**: IME 等が前面にあるとネイティブ画面でも数秒古いツリーが
返る。逆向き(遷移前の状態を期待するアサーションが**誤って成功する**)は沈黙するので、
`notExist` や「クリア後の初期値」を見るステップが怪しく緑になっていないか疑うこと。

**全ノード refresh は既定にできない**(2026-08-01 実測)。`SnapshotBuilder.collect` で
`node.refresh()` を全ノードに広げると **snapshot 1回あたり +65ms**(アサーション中央値
6〜22ms → 43〜99ms)、scenario sum は **E2E-Android +43%**(208.3→297.3s)・E2E(Compose)+2.5%。
ノード数の多い View/XML SUT ほど重い。既定は WebView 内だけに留め、**ホストが期限切れで失敗と
決める直前の1回だけ** `/snapshot?refresh=1` を要求する。
