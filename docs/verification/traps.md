## 検証スクリプトそのものの罠

- **エラーを保存・表示するときは切り詰める前に入れ子を畳む**。`prefix(N)` で素の description を
  切ると**真因が構造的に落ちる**(最上位は「The operation couldn't be completed.」のような
  定型文で、原因は `NSUnderlyingError` / `NSMultipleUnderlyingErrors` の奥にある)。
  実害: FM の全滅原因が 300 文字の切り捨てで数日間まったく見えなかった(`FMHealth.describe` 参照)
- **pipefail 下で `cmd | head` を条件式・値の取得に使わない**。head が1行読んで先に閉じると
  上流が **SIGPIPE(141)** で死に、pipefail がそれを失敗として拾う。1行目が欲しいだけなら
  変数へ入れてからパラメータ展開で切る(`${out%%$'\n'*}`)。実害: `if x="$(xcodebuild -version | head -1)"`
  が正常な Xcode を `unusable` と判定し、受け手に無関係な license 同意を案内した(2026-07-29)。
  **矛盾する出力は誤判定の兆候**(このときは `xcode=unusable` と `xcode_first_launch=done` が同時に出ていた)
- **空の結果は成功と見分けがつかない —— 件数を必ず確かめる**(2026-08-03 に3回踏んだ)。
  実験や反復が**そもそも実行されていない**のに、出力は「失敗0」に見える形が3つあった:
  ①A/B で `fleetest` を差し替えたが実行の実体は `fleetest-scenarios-<project>`(→ どんな変更も差なし)/
  ②バックグラウンドの負荷ループが起動せず、**無負荷の測定を「負荷下」と報告**した/
  ③**未マッチの glob で `&&` の連鎖が切れ**、30回の反復が丸ごと走らなかったのに
  「30回中 回失敗」と出た。**判定に使う前に「何回走ったか」「生成物が在るか」を数える** ——
  `ls <出力>/*.log | wc -l` が期待値と一致するか、負荷を掛けたならそのログが実在するか。
  (計測基盤についての同じ規律は PT-4 にもある)
- **zsh の未マッチ glob はエラーになる**(bash と違い素通ししない)。`rm -f dir/*.log` は
  対象が無いと `no matches found` で失敗し、`&&` で繋いだ後続が**丸ごと実行されない**。
  使い捨ての作業ディレクトリは `rm -rf d && mkdir -p d` で作り直す(glob を書かない)
- **zsh は未クォート変数を単語分割しない**。`for x in "a b" "c d"; do set -- $x; ...` は
  bash の感覚だと 2 引数に割れるが zsh では割れず、`$1` に全体が入る。
  実害: SUT×プロファイルの再検証ループが全件「プロジェクトが見つかりません」で空振りした
- **合否を後続コマンドの exit code で潰さない**。`Scripts/e2e.sh > log; echo "EXIT=$?"` のように
  末尾へ何か足すと、**シェル全体の exit code は最後のコマンドのもの**になる。
  バックグラウンド実行の完了通知もそれを見るため「exit 0」と報告されるのに
  中身は `❌ E2E に失敗があります` という食い違いが起きる(2026-07-27 に実際に誤読した)。
  `$?` を表示したいなら**その値でそのまま終わる**(`exit "$?"`)か、ログの `❌` 行で判定する
- **E2E の実行中に `swift build` しない**。走っているランナーの実行ファイルを差し替えると
  プロセスが **SIGKILL** される(`Scripts/e2e.sh: ... Killed: 9`)。シナリオの失敗と紛らわしいので、
  検証中はビルドを挟まない(2026-07-27 に実際に踏み、Flutter の profile が丸ごと落ちた)
- **`log` は絶対パスで叩く**(`/usr/bin/log`)。shell 関数に食われて
  「too many arguments」になる。さらに**自分の述語文字列が `log` プロセス自身のログに出て
  偽の一致行になる**ので、必ずプロセス名まで確認する

## 調査用の計装は「恒久的な診断」として残る形で入れる(2026-08-04)

探索直後のタップずれは**計装を入れると消える**(probe の I/O がタイミングを変える)ため、
2026-08-03 の調査は 42 回を無駄にして止まっていた。今回は**ステップの注記**(メモリ上の
文字列を組み立ててレポートへ出すだけ・I/O なし)で計装したところ、1周目の失敗で
`the element is still reported outside its scroll container (3 re-resolve(s))` が出て機序が確定した。

学びは2つ:
- **計装の I/O はそれ自体が実験条件を変える**。タイミング由来の症状では、
  ファイル書き込み・ログ出力を足した時点で別の系を測っている
- **調査用に書いた計装は、そのまま診断として残す**。捨てる前提の計装は「次に落ちたとき
  また同じ物を書く」ことになる。今回の注記は修正後も残しており、**再発したときに
  第1機序か別機序かを注記の有無で見分けられる**

## 撃つ前に何を見たかは FT_BRIDGE_TRACE で採る(2026-10-20)

録画とランナーのログ(`.fleetest/bridge-<port>.log`)は「撃った操作」と「画面」は分かるが、**撃つ前にツールが木で見た位置**が
分からない。`FT_BRIDGE_TRACE=<id,id,...>` を付けた run は、シナリオのプロセスがブリッジ(XCUITest・in-app)へ送る要求を1件1行で
stderr へ出し、`results/runs/<月>/<runID>/events/<scenario>.ndjson` に `stream: "stderr"` の `bridgeTrace` として残る
(要求の時刻・所要・メソッドとパス・本文の先頭・status と、`/snapshot` なら指定した id の枠だけ。打鍵の文字列は文字数に置き換える。
定義は `FTBridgeClient/BridgeRequestTrace.swift`)。Android のブリッジへの要求は通らない。

- 使い方の実例: E2EX-CMP の無限スクロールの赤を `--broadcast` の 8 台 × 3 周で採り、赤 4 件と緑 20 件のタップ前後の
  木の位置を並べて形を確定した(直した経緯は MN-74.11)
- **木が言うことと画面が言うことを分ける**: 録画のクリップは `recordings/index.json` の `segments[].startedAt`(壁時計)から
  始まるので、bridgeTrace の `t` から引けばクリップ内の秒になる(シナリオの最初のイベントとクリップの頭の差は実測 0.01〜0.02 秒)。
  その時刻のフレームを AVFoundation(`AVAssetImageGenerator`)で取り出して見る。E2EX-CMP の無限スクロールの赤は、木の上では
  同じ「結果が空のまま」でも、録画では「タップが吸われた」と「タップは効いたのに木が変わらない」の2つに分かれた
  (前者は2回目の空打ちで直し、後者は Compose のタッチ範囲が削った枠による可視性検証の誤反転だった =
  docs/framework-differences.md の `TouchOverhangFrameRestore` の行)
- **I/O を足す計装なので、上の節の注意が効く**。この調査では記録ありの赤の率(24 回中 4 回)が記録なしの棚卸し(24 回中 5 回)と
  同程度だったが、タイミングが効く症状では毎回「記録ありでも同じ率で出るか」を先に見る

## 効果は「率」だけでなく「失敗の質」で見る(2026-08-04)

フレークの修正は試行回数を稼ぎにくく、**率だけでは有意差を出せない**(今回はスイート
8周で 3/6 → 2/8。この標本数では偶然と区別できない)。一方で**失敗したときの注記が
消えた**ことは機序レベルの証拠になった —— 修正前は失敗の2件に ghost 注記が付き、
修正後は 0 件になった(= その経路では落ちなくなった)。

**「何回落ちたか」ではなく「どの機序で落ちたか」を数える**。そのためには失敗時に機序が
分かる情報(注記)が要る = 上の節と対になっている。率で語れるだけの試行を回せるなら回すが、
回せないときに「有意でないから分からない」で止めない。

## 既存テストは無料の「全数当て」(2026-08-04)

新しい検知を入れたら既存資産の全数に当てて誤検知0を確かめる規律があるが、
**単体テスト群がその役割を果たすことがある**。今回、WebView の読み返しを入れた直後に
既存の `testDomInteropTypeFocusesByCoordinateThenTypesWithoutRef` が落ち、
「value を報告しない要素では毎回二重入力になる」という誤検知を捕まえた。

だから **自分の変更で既存テストが落ちたら、まず「テストの期待値が古い」ではなく
「自分の検知が誤検知している」を疑う**。今回は後者だった。

## 過去の実行データは「再現しなくても機構を確定できる」検体庫(2026-08-05)

再現待ちに入る前に、**手元に貯まっている実行データを全数集計する**。2026-08-05 の調査では
これだけで3テーマの機構が確定し、再現は1つも要らなかった。

**2つの供給源があり、用途が違う**:

| | 中身 | 向いている問い |
|---|---|---|
| `TestProjects/*/reports/*.md` | 全 run の手順・**失敗時の要素一覧とスクショ** | 「そのとき画面はどうなっていたか」= 機構の特定 |
| `TestProjects/*/results/runs/*/*/scenarios/*.json` | `profile`(= モード)・`timeline`(ステップ名・所要・status) | 「どのモードで何秒か・何回に1回落ちるか」= 率とコスト |

**レポートには mode が書かれていない**(device しか出ない)ので、モード差を見る集計は
必ず `results/runs` の `profile` を使うこと。逆に要素一覧は `results/runs` に無い。

実際に出た答え(いずれも n が大きいので推測が要らない):
- 失敗レポート 487 件を機械分類 → 「タップの空振り」が**3クラスに割れる**ことと、
  最大クラスの機構(容器の縁をまたぐ frame)が**同じ幾何で 11 件揃う**ことが分かった
- ステップ 422,343 件 → `activate 不発 → 合成タッチ`(検証不能なタップ)が in-app タップの **8.4%**、
  `did not settle (poll limit)` が **1,834 件**(ios-xcuitest のスクロール系に集中)
- 同 → `exist "WebView 見出し"` は **ios-xcuitest 2.96s / ios-inapp 3.04s / android 0.24s** =
  「モード差なし・iOS 側の床」が確定(**レポートだけで見ると SUT 差に見えて誤読する**)

**集計の注意**: レポートは1ディレクトリに数万件あるので `*.md` のグロブ展開は
`argument list too long` で落ちる。`grep -rl` / `pathlib.glob` を使う。

## フレークの集計は「調査由来の失敗」を除いてから読む(2026-08-04)

レポートを機械集計すると、**一時シナリオ(わざと失敗させる計測用)・開発中の失敗**が
上位を占める。今回の集計では上位5件のうち3件がそれで、そのまま読むと優先順位を誤る。
集計の前に次を外す: `99_`/`TMP_` 等の一時シナリオ・その日に実装していた機能のシナリオ・
既に原因が分かって修正済みのもの。**残ったものだけが「解くべきフレーク」**。
**run 横断で推移(良くなったか)を出すときは分母も揃える** —— run の本数・シナリオの集合・
標本数・デバイス構成の4つ。レシピは docs/results-json.md §フレークの推移を見る。

## 「届いていない」を推論で説明しない —— 生イベントを SUT 側で測る(2026-08-04)

ジェスチャが無反応のとき、**注入側の仕様から原因を推測すると外す**。2026-08-04 の
ダブルタップ/ピンチ調査では、推論と実測が2回とも食い違った:

| 推論 | 実測 | 実際の原因 |
|---|---|---|
| Compose に2打目が届いていない | **2打とも届いていた**(間隔 66ms) | **UP→DOWN が 0ms** = Compose の `doubleTapMinTimeMillis`(40ms)未満で捨てられていた |
| Flutter にピンチが届いていない | **2本指も移動も届いていた**(56 イベント) | **指の間隔が 8px→28px しか開かない** = Flutter のしきい値に届かない(Compose は比で見るので効く) |

やり方は単純で、**SUT に一時的なプローブを足して画面へ出す**(`ft_snapshot` / 失敗レポートの
要素一覧で読める)。値は「到達数・直前イベントからの時間差・同時ポインタ数・移動量」の4つで足りた:

- Compose: `pointerInput { awaitPointerEventScope { awaitPointerEvent(PointerEventPass.Initial) } }`
  で消費される前に数える(`changedToDown` / `changedToUp` と `uptimeMillis`)
- Flutter: `Listener(onPointerDown:onPointerMove:)` でポインタ id を集合に入れ、
  2点間距離の初期値と最大値を出す
- 読み出しは**わざと外れるアサーション**を1つ置く(失敗レポートが要素一覧を丸ごと出す)

**プローブは調査が終わったら必ず外す**(SUT の契約に無い要素が残ると別のシナリオの序数がズレる)。

## 同時刻クラスタは環境要因(kAXErrorAPIDisabled・2026-08-04)

iOS で `Error getting main window kAXErrorAPIDisabled`(500)が出ることがある。
**19件すべてが時刻の塊**だった(00:55:29〜34 に6件・別日に7件の塊)= **全レーンに一斉**なので、
シナリオやアプリの問題ではなく XCTest の a11y サーバ側の一時停止。数秒で復旧する。

**分布を見るまで個別のシナリオを疑わない**。集計は雑でよく、レポートの Timestamp を並べるだけで
「散発」か「塊」かは分かる(塊なら環境)。

対処(2026-08-04): **読み取り(snapshot/screenshot)だけ**待って撃ち直す(1・2・3 秒)。
**書き込みは撃ち直さない** —— 「撃つ前に落ちた」と断定できず、二重実行の方が高くつく
(`DriverError.isDefiniteDeliveryFailure` と同じ判断)。撃ち直したことは注記に残す。

## WebView の入力が黙って落ちる(domInterop・2026-08-04)

Compose/Flutter ホストの WebView(domInterop)の入力は「座標タップでフォーカス →
フォーカス中要素へ typeText」なので、**タップがフォーカスを立て損なうと打鍵が丸ごと落ちる**
(値は空のまま 200 が返り、後段の検証だけが落ちる)。E2E-CMP で 4/78。

対処: DOM は `value` を返せるので**読み返して1回だけ張り直す**。
**判定は「値が入力前から1文字も変わっていない」ときだけ**にする ——
「期待した文字列を含まない」で判定すると、入力を加工するフィールド(大文字化・書式化)で
**二重入力**になる(Android の `ACTION_SET_TEXT` で踏んだ二重追記と同じ型)。

## 決定は「根拠が消えたか」で見直す(2026-08-04)

2026-07-28 に「live / MCP は in-app ブリッジを使わない」と決めていた。根拠は
**`StepExecutor` を通らない `ft_*` は in-app だと `home` / `drag` / 座標 `press` が素の 501 になる**
という当時の事実で、決定そのものは正しかった。その後 `HybridFallbackDriver`(501 のときだけ
XCUITest へ回す)で根拠が消え、**決定だけが残っていた**。

決定の記録には理由が書いてあるので、**同じ領域を触るときは理由がまだ成立するかを見る**。
成立しなくなっていたら、決定を守るのではなくユーザーへ再判断を上げる(今回は上げて更新した)。
逆に「ユーザー決定・再提案しない」と書かれたものは根拠が消えても勝手に戻さない —— 判断の主体が違う。

## 検証に使う口と本番の口はモードまで揃える(2026-08-04)

シナリオ作成は「MCP(`ft_*`)で試す → シナリオに書く → 実行する」の流れだが、
**MCP は常に XCUITest・実行はプロファイルのモード**という差があった。結果、
Compose のダブルタップと Flutter のピンチだけ「MCP では無反応なのにシナリオでは通る」
という逆転が起きた。**このとき MCP の無反応は「できない」の証拠にならない**。

モードが変わると変わるのは成否だけではない: **snapshot の中身(要素の型・id の見え方)も変わる**。
探索で採ったセレクタが実行時に無い、という静かな崩れ方をする。だから
「同じデバイスで探索する」だけでなく **「同じモードで探索する」** までを原則にする
(実装は `MCPServer.iosDriver` が profile のモードに追従する。2026-08-04)。
**2026-10-11 に取り消した**: MCP の iOS は常に XCUITest(in-app の合成タッチが注入される前提で作られていないアプリで
効かないまま ok を返した。経緯は docs/design/ §MCP の iOS のモード)。「同じモードで探索する」は成立しない —— MCP で
無反応だったジェスチャは、シナリオで確かめる。

## プロトコルの既定実装は「実装漏れ」を黙って隠す(2026-08-04)

`AppDriver` は `drag` / 座標 `press` / `doubleTap` / `pinch` などに既定実装(501)を持つ。
ラッパードライバが1つ書き忘れても**コンパイルは通り**、包む相手が実装を持っているのに
「このブリッジでは未対応」を返す。**フォールバック先がこれを返すと、ホストからは
「どちらの経路でも 501」= 打つ手なしに見える**。

2026-08-04 に `AppAttachDriver` の座標長押しで実際に踏み、掃討したら `SystemUIDriver` にも
同じ穴があった(こちらは呼ばれていなかったので誰も気付いていなかった)。
**新しい操作を足したときの掃討は「今足したもの」だけでは足りない** ——
同じ性質(座標で完結する = 誰が受けても同じ)の**既存メソッドが全部揃っているか**まで見る。
再発は `DefaultImplementationForwardingTests`(ソース走査)が落とす。

## 「このフレームワークでは無理」は経路ごとに測り直す(2026-08-04)

in-app の合成タッチについて「**drag はジェスチャ認識器に受理されない**」という知見が
2026-07-22 以降あり、`press` / `swipe` が 501 な根拠にもなっていた。**これは UIKit/SwiftUI では
正しいが、自前描画のフレームワークには当てはまらなかった** —— Compose と Flutter は生タッチを
自分のアリーナで捌くため、同じ合成タッチでピンチが成立する(2026-08-04 実測)。

一般化した知見ほど「どの経路で測ったか」が落ちて広く適用されがちなので、**新しい操作を足すときは
フレームワーク × ブリッジのマスを実際に埋める**。このときの結果:

| iOS | SwiftUI/UIKit | Compose | Flutter | React Native |
|---|---|---|---|---|
| XCUITest | ダブルタップ ✅ / ピンチ ✅ | ダブルタップ ❌ / ピンチ ✅ | ダブルタップ ✅ / ピンチ ❌ | 未実測(想定: uikit 経路 = SwiftUI/UIKit と同じ ✅/✅) |
| in-app | 両方 ❌(合成タッチを受理しない) | 両方 ✅ | 両方 ✅ | 未実測(想定: uikit 経路 = in-app 501 → xcuitest フォールバック) |

**両者を足すと全マスが埋まる**ので、inapp モード(既定)は 501 フォールバックで全部通る
(MCP も 2026-08-04 から `profile` 指定で同じ合成を使っていたが、**2026-10-11 に MCP は XCUITest だけに戻した**。
`HybridFallbackDriver` は今はライブ操作だけが使う)。
埋まらないマス(xcuitest 単独・実機)は docs/commands.md に明記した。
**受理しない側で 200 を返さないこと**が要点で、in-app 側は uiFramework で判定して 501 を返す
(返さないと「成功したのに何も起きない」= 最悪の失敗モードになる)。

## 操作は ✅ なのに画面が変わらないとき

`tap` がエラーにならず成功として記録され、次の検証だけが「期待と違う」で落ちる形。
**ロケータの問題ではない**ので、セレクタを直そうとすると時間を溶かす。

**まず3つのクラスに分ける**(2026-08-05 に過去の失敗レポート 487 件を全数分類して整理した。
機構が違うので混ぜると追えない):

| クラス | 見分け方 | 状態 |
|---|---|---|
| **A. 座標が可視領域の外**(報告された frame が壊れている) | 失敗時の要素一覧で、対象の frame が容器の縁をまたぐ/外に居る。E2E-CMP S0110 の失敗 21 件中 **11 件**がこれ(`#row_30` が `y=206 h=26〜45`・容器の上端は 230 = **中心が容器の外**) | 機構は確定。**未対処**(下記「画面外要素の frame は信用できない」) |
| **B. ghost(容器の外に並ぶ子)** | ステップに `the element is still reported outside its scroll container` の注記が付く | 対策済み(再解決+追加スワイプ)。取りこぼしが 21 件中 2 件 |
| **C. 座標も正しく、イベントも受理され、アプリが反応しない** | A でも B でもない。注記も付かない | **真の未解明**。ただし混入していた環境要因が1つ判明(下記) |

**C を追う前に環境を疑うこと**(2026-08-05 の教訓): C だと思っていた失敗のうち、
**iOS シミュレータの画面凍結**(下記の節。真っ黒なのに a11y は健全でタップだけ届かない)が
混ざっていた。今は失敗レポートに blank frame 警告が出るので、まずそこを見る。

既知の原因は次のとおり。

1. **アプリが別プロセスの window に覆われている**(システムダイアログ・IME の案内・通知シェード)。
   アプリの a11y ツリーには他プロセスの window が出ないため、要素一覧は正常に見える。
   **2026-07-27 以降は失敗時に自動で警告が出る**(コンソールとレポート。
   `⚠️ アプリより手前に別の window があります: …`)。出ていたらこれが第一の容疑
2. **アプリ内メッセージ**(お知らせ・キャンペーンのモーダル)。**同一プロセスなので 1 の検出では
   捕まらない**。こちらは失敗メッセージに `(対象は #… に覆われています)` が付く(幾何判定・FM 不要)。
   繰り返し出るなら `irregularHandler` を宣言して自動で閉じさせる(../design/dsl-execution.md「割り込みハンドラ」)
3. **スクロール探索の直後**(下記の節)。こちらは修正済みだが、同じ症状の別原因として覚えておく
4. **座標が要素の外**(下記「画面外要素の frame は信用できない」)。報告された frame の中心が
   実際の可視領域の外にあり、タップが隙間や別の要素へ落ちる

**2026-08-05 以降は「飲まれたタップ」を失敗文言が名指しする**: 直前のタップの**直前に解決で
使った木**を覚えておき、失敗した検証が手元に持っている木と突き合わせて、**1ピクセルも変わって
いなければ** `(the preceding tap … did not change the screen at all; the interaction may have
been swallowed)` を添える(`StepExecutor.tapDiagnosisHint`)。
- **iOS では「別プロセスのアラートを出した」可能性も併記する**(`, or it raised a system alert …`)。
  iOS の木は in-app / XCUITest ともアプリのプロセスだけなので、権限の要求など SpringBoard の
  アラートを出したタップも「無変化」に見える(M1mini の E2E-iOS 16 S0010 で、アラートが待ちの
  5 秒に間に合わなかった赤を「飲まれた」と誤誘導した)。Android は権限ダイアログが木に載るので添えない
- **追加のスナップショットは撮らない**。実行中に I/O を足すと事象そのものが消える
  (下記「Compose の探索直後タップ」の heisenbug で 13 周回して再現しなかった)ため、
  これは設計要件であって最適化ではない
- **判定は変えない**(注記だけ)。「押しても画面が変わらないのが正しい」操作もあるため
- 署名には**ラベル・値・enabled・checked も入れる**。飲まれたタップの実例は
  `selected=-` のままか `selected=row_30` になるかの違いで、**座標は1ミリも動かない** ——
  `settledSignature` の署名(frame だけ)を流用すると黙って取りこぼす。逆にラベルの振れ
  (iOS の再利用セル)は「変わった」側に倒れるので、**誤って「無変化」と言うことはない**
- 記録は `select` では消さない(`tap → select → textIs` が失敗の定型)。画面を変える他の操作で消える
- **タップ点を手前の別要素が取っていた**ときは、無変化と同時に成立したときだけ名前も添える。
  単独で出さないのは、画面外要素の frame がクランプされるフレームワーク(下記)では
  **正常なタップでも普通に非 nil になる**ため
- **木が変わっていて、かつ対象があの後動いていたら移動量を出す**(2026-08-05 追加)。
  `(the target has moved (0,-100) since the preceding tap …)`。これが
  **「座標が古くなった」と「本当に無反応だった」を分ける唯一の材料** ——
  失敗時の幾何だけでは両者が同じ絵になり、実際に取り違えた(「掴んだ時点で壊れていた」と読んで
  探索側を直したが、10周回して**一度も発火しなかった**)。閾値は 8pt(整定の揺れで出さない床。
  実測の取りこぼしは 98pt 級)。対象が消えていたら黙る

実例: Gboard の「タッチペンを試してみる」が送信ボタンを覆い、03_テキスト入力(旧 05)が間欠失敗した
(抑止は `AndroidBridge.disableStylusHandwriting`)。**この手の教育用ポップアップは今後も増える**ので、
1 の警告が出たら SUT ではなくデバイス設定側を疑う。

**切り分けの定石(iOS)**: 同じシナリオを `ios-inapp` プロファイルでも回す。in-app は ref で、
xcuitest は座標でタップするので、**片方だけ落ちるならタップ経路の問題**、両方落ちるならアプリ側か
セレクタの問題と切り分けられる(スクロール直後のタップの機序特定で決め手になった)。

## iOS シミュレータも「画面だけ死ぬ」——a11y は健全・タップだけ届かない(2026-08-05 実測)

Android エミュレータの表示凍結([[emulator-display-freeze-wedge]])と**同じ病理が iOS でも起きる**。
2026-08-05 に E2E-CMP/ios-xcuitest の `-06` で観測:

- スクリーンショットは**全面真っ黒**。なのに **a11y ツリーは健全なホーム画面を返す**
  (要素・座標とも正常)。**タップだけが1つも届かない**(`tap("#nav_scroll")` が **9/9** 飲まれ、
  MCP から手で叩いても不発。**2回続けて叩いても不発** = 「容器が最初の1タッチを吸う」型ではない)
- 症状は「タップの空振り」に化ける。実際この日の失敗は
  `scrollTo "#row_40" element not found after 15 scroll(s)`(ホーム画面を 15 回スクロールしていた)や
  `textIs "#txt_screen_title" == "WebView" → actual "ホーム"` として記録された
- **コード変更とは無関係であることを同一デバイスの A/B で確認済み**(base 3/3・fix 6/6 とも失敗)。
  `simctl shutdown` → `boot` で回復した
- **ファイルサイズでは検出できない**(黒一色でも PNG 42KB)。判定は画素をサンプルする
  `BlankFrameDetector.isUniformBlank` だけが効く

**対処は2段(どちらも 2026-08-05)**:

1. **失敗時の検出**: 白/黒フレーム推定を **Android 限定から「実機以外」へ広げた**
   (`FTRuntime` の `inferFrozenFromBlankFrame`)。iOS でも
   「⚠️ The evidence screenshot is a blank frame (frozen device display)」がレポートに出て、
   既存の `deviceFrozen` 経路に乗る。**挙動変更**である —— 該当シナリオは**1回だけ再キュー**され
   (`MAX_FREEZE_RETRIES`)、ワーカーは離脱してブリッジを作り直す。再試行の上限に達したものは
   **`failed` ではなく `skipped`** として記録される(JUnit にもそう出る)。
   副作用は「失敗時のスクショが一様だと最大3回撮り直す(+7.5s)」だけで、成功パスには掛からない
2. **run 前のトリアージ**: `BlankWorkerTriage.excludeBlankScreenWorkers` を iOS ワーカーの
   合流直後に通す(Android の `excludeOrRepairBlankScreenWorkers` と同じ位置づけ)。
   恒常 blank(1.5s 間隔で2連続)なら**投入前に除外**し、復旧コマンドをログに出す。
   健全機は**1サンプルで返る**ので正常時の固定費はスクショ1枚

**iOS も回復させてから始める(2026-08-09 ユーザー指示・上の 2 を置き換え)**。
弾くだけだと、凍結が多発した run はレーンが半分になって走る。
`excludeBlankScreenWorkers` に `recover:` を渡し、**全機が戻るまで開始しない**:

- 回復の実体は `ProfileWorkerFactory.recoverFrozenIOSWorkers` = **`simctl shutdown` →
  `SimulatorBoot.ensureBooted`(`bootstatus -b` = Shutdown なら起動。機械全体の同時2台の枠もここで掛かる)**。**2台ずつ**戻す(一斉 boot は凍結の相関要因そのもので、start-device の
  「同時2台」と同じ理屈)
- **シミュレータを落とすとブリッジも死ぬ**ので、回復と `buildIOSWorkers` での張り直しは1セット。
  生きているブリッジは再利用されるため、実際に起動し直されるのは落とした機だけ
- **落とす前にその機のブリッジを止める**(2026-08-11。`BridgeLauncher.stopMatching(udid:)`)。
  掴んだまま `simctl shutdown` すると XCUITest ランナーの teardown を待って **約50秒**かかり
  (止めてからなら約5秒)、生き残ったランナーが再ブート後に再接続してくるので張り直しも遅い。
  **A/B 実測(3周とも一致)**: 現行 98.6 / 96.5 / 96.3s → 先に止める 34.6 / 34.6 / 33.9s = **−62s/回**。
  止めるのは**その udid のブリッジだけ**(他機・他セッションを巻き込まない)。
  順序は `FrozenIOSRecoveryTests` がソース走査で固定する
- 混在一覧(Android + iOS)を受けても **iOS だけ入れ替える**。素直に返り値で置き換えると
  `buildIOSWorkers` は iOS しか作らないので **Android のレーンが消える**
- `recoveryAttempts` = 2 まで試し、**戻らない個体だけレーンから外す**(「レーン上に凍結機を
  残さない」が要件)。全機戻れば除外0で開始する
- **iOS ワーカーの供給口は `ProfileSupplyLanes.ios` の1つ**(run / api run の全経路がそこを通る)。
  呼び手ごとに持っていた頃(3つ)は、2026-08-09 に1箇所だけ入れて `api run` 経由(拡張のモニターから走る経路)に
  穴を空けた。`BlankWorkerRecoveryWiringTests` が「呼び出し数と `recover:` の数が一致するか」と、呼び手に
  直呼びが戻っていないかを数えて検出する
- **コストは大きい**: 2026-08-09 の実測で、5台凍結した E2E-CMP/ios-inapp は供給に約 620 秒
  (凍結ゼロの同プロファイルは約 41 秒)。**弾くより遅いが、レーンは減らない**

**誤検知が狭い理由**: ブリッジのスクショは `XCUIScreen.main.screenshot()` = **画面全体**なので、
健全ならステータスバー(時計・電波)が写って一様にならない。誤検知するにはアプリが
ステータスバーを隠したうえで全面一様である必要がある(全画面動画・カメラプレビュー等)。

**この挙動は 2026-08-06 に「維持」で決着**(ユーザー決定)。2026-08-05 の Flutter/iOS 実行で
実際に発火し、凍結した `-07` からシナリオを `-04` へ振り直して合格・ワーカーも revive で復帰した
= 環境起因の失敗をテストの失敗に化けさせない効果が実データで確認できた。
**「警告のみに戻す」「同一ワーカーで2回続いたときだけ凍結扱いにする(誤検知を狭める)」は保留** ——
後者が守るのは「アプリが正当に全面一様の画面を出す」場合で、上記のとおり条件が狭い。
**利用者からその報告が出るまで実装しない**(再提案しない)。

## デバイス基盤の一過性エラーは「テストの失敗」と数えない(2026-08-06)

`kAXErrorAPIDisabled`(XCUITest の a11y 基盤が一時的に応答しない)は、**ブリッジ供給直後・
アプリ入れ替え直後**に**同時刻クラスタ**で出て、**再実行で必ず消える**。2026-08-05/06 のフル実行で
2回踏み(8件・6件)、そのたびに人間が「これは環境」と判定していた。

**判定を機械化した**(`RunOrchestrator.EnvironmentFault`)。既存の `deviceFrozen` /
`bridgeUnreachable` と同じ再キュー経路に載せるが、**ワーカーは離脱させない** ——
個体は健全で、ブリッジを作り直しても同じ確率で踏む。連続失敗の数にも入れない
(サーキットブレーカを環境ノイズで作動させない)。

**印を広げてはいけない**: 対象は「ドライバが返した基盤側のエラー」だけで、アサーション失敗の
文言(`element not found` 等)を足すと**本物の失敗が振り直され、最終的に skipped として
記録される**(赤が消える = 最悪の壊れ方)。`EnvironmentFaultTests` がこの境界を守る。
**振り直しても消えなければ従来どおり赤**(上限到達は `workerAnomalies` の `retryLimit` に残り、最後の失敗記録はそのまま残る。合成の skipped 記録には置き換えない)。

**配線の確認は陽性対照で**: 印に一時的に `element not found` を足し、確実に落ちるシナリオ
(`FT_CONTAINER_INFERENCE=off` + 飛び越し witness)で「振り直し → 上限到達 → 赤」を1回通してから
印を戻す。実際にこれで配線を確かめた。

## スクロール探索の「飛び越し」を決定的に再現する(2026-08-06)

探索は「木を撮る → 解決する → 1回スワイプ」の繰り返しなので、**スワイプの合間に一度も
木に出なかった要素は原理的に見つからない**。既定経路(`scrollFrame` 未指定)は刻みが
ブリッジ任せで、1回の移動が容器を超えると起きる。発生率は 0.8% しかなく効果を測れなかったので、
**決定的に再現する witness 画面**を SUT に置いた(E2E-CMP の「飛び越し」画面 =
`#list_jump` / `#jrow_01..12`。寸法の意味は E2EAppCMP/docs/ui-contract.md)。

**witness を作るのに3回失敗した。同じ轍を踏まないために**:

1. **容器を画面中央に置いてはいけない**。Android の既定スワイプは**画面 70% → 30%**
   (`AndroidRunner/.../BridgeRouter.java`)。容器が中央だと**指が乗らず1ピクセルも動かない** ——
   「飛び越している」ように見えて実際は何も起きていなかった(2回ぶんの実験が無駄になった)
2. **「移動量 > 容器 + 行の高さ」でないと穴が空かない**。容器を大きくすると連続する可視域が
   重なって全行が見えてしまう。逆に容器が小さすぎると①に反する。
   **画面の 20% 前後の容器を 70% 地点に置く**のが両立点
3. **iOS(Compose)では同じ画面が別の病理を出す** —— 可視域の外の行が木に残る(ghost)ので、
   飛び越しではなく「掴めるが撃つと飲まれる」になる。**Android が飛び越しの正**

## 端に着いたら探索を打ち切り、逆向きに拾い直す(2026-08-06)

上の witness を使って2つ入れた。**どちらも `containerInference` で切れる**。

- **打ち切り**(`unmovedRoundsToStopSearch = 2`): 木が2周続けて1文字も変わらなければ、
  上限まで振らずに失敗させる。**打ち切る直前に `settledSignature` で確かめる**
  (2026-08-06 に Flutter/Android で誤発火 —— a11y ツリーは遅れて公開されるので、
  動いている最中でも2周続けて同じ木が返る。整定待ちなら遅れと停止を区別できる。
  費用は打ち切る局面の1回だけ)。**8スワイプ 7.40s → 2スワイプ 2.05s**(実測)。
  理由文には**実際の回数**を出す(上限を名乗ると「8回も振ったのに」と読めてしまう)。
  **文言は2形に分ける**(`contentEverMoved`。2026-08-15 の外部評価): 動いた末の停止は
  `the scroll area reached its end`、1度も動かなかった回は `nothing moved at all during the search`。
  どちらも `raising maxSwipes will not help` まで言い切る —— 旧文言 `stopped early` は
  「途中で諦めた」としか読めず、**実際は iOS の設定アプリでリストの末尾に着いていた**回を
  欠陥と受け取らせ、maxSwipes を上げた無駄な再試行を誘っていた
- **逆走査**(`reverseSweep`): 端に着いても見つからないときだけ、**推測した容器の中を
  逆向きに細刻みで戻りながら**毎周解決を試す。**通常の送りには一切触らない**ので、
  2度撤回した「暗黙の座標化」(PT-3.19)の撤回理由に抵触しない。
  救えたときはステップ注記に `found by sweeping back after overshooting it` を出す(黙って救わない)

**実装で踏んだ罠**(いずれもデバイス上でしか出ない。観測はすべて Simulator / Emulator):

- **逆走査をスワイプでやると慣性で反対の端まで走る**(189px 指定が約 700px 走った)。
  ドラッグにしても **hintDrag の 0.3〜0.7s ではまだ速い** —— 距離ぶんの時間を必ず取る
  `slowDrag`(120px/s)にして初めて刻める
- **容器の推測は3段構え**が要る。①スワイプ点から当てるのは**不可**(始点比率はブリッジ側の値で
  ホストは知らない)②**中身が入れ替わった領域**(Android。飛び越すと2枚の木に共通の要素が
  1つも無いので「消えた/現れた」で見る)③**動いた要素の clip 元**(iOS は ghost で id 集合が
  変わらないぶん frame が動く)④**子がはみ出している clip 領域**(静止した木だけから採る最後の手段)
- **逆走査の直後は `settledSignature` まで待つ**。遅いドラッグでも離した後に滑り、
  掴んだ座標とタップの間で 176px ずれて隣の行を叩いた

## ghost へのタップ防御は「そのステップが探索したか」を条件にしてはいけない(2026-08-06)

iOS(Compose)は可視域の外に出た行を木に残し、frame は容器の外を指す。掴んだままタップすると
**容器の外を撃って画面が何も変わらないまま成功として記録**され、後段の検証だけが落ちる。

防御(`grabbedGhost`)は入っていたが、条件に **`searchSwiped`(そのステップ自身が探索した)**が
付いていたため、**`scrollTo` と `tap` を別ステップで書く自然な書き方では丸ごと素通り**していた。
さらに救済側は **`step.direction` を要求**しており、素の `tap`(向きを持たない)は
ghost を検出しておきながら**1本も送らずにそのままタップ**していた。両方外した
(戻す向きは `recoveryJump` / `recoveryDirection` が幾何から決められる)。

**縁にまたがった行は触る前に容器の中へ寄せる**(2026-08-06 に解決)。見えている部分を撃つだけでは
足りない —— Compose は focus 時に bringIntoView で内容を動かすので、離すまでに隣の行が指の下へ来る。

**2026-08-05 に撤回した「またぎも掴み直しの対象へ広げる」との違いは送り方だけ**:
あちらは全画面スワイプで行き過ぎて自傷した(S0110 が 2/10 → 5/10)。今回は
`recoveryJump`(容器の 40% 位置までの距離)+ `slowDrag`(フリングを出さない)なので行き過ぎない。
**同じ指標で測って裏を取った**:

| | 結果 |
|---|---|
| witness(飛び越し画面の S0020・タップまで検証) | **逐次 4/4 失敗 → 4/4 成功** |
| S0110(2026-08-05 に悪化した指標) | **32/32 成功**。しかも寄せは**発火している**(8本中5〜6回) |
| 性能(共通シナリオの sum・同一セッション) | ios-xcuitest **−0.6%** / Android は −13.2%(セッション変動)|

**対象は `tap` / `press` / `doubleTap` だけ**(`select` は掴むだけ・`type` は入力欄が動くと厄介)。
**完全に外(ghost)はこの経路で扱わない** —— あちらは掴み直し(`grabbedGhost`)の担当で、
救えなかった ghost に別機構を二重に当てない。

**負荷交絡に注意**: 同じ日に in-app が +4.2% に見えたが、**48 本すべてが一様に遅く**、
ホスト CPU 中央値が 31.4% → 43.9%(worker 1 → 3)だった。**全数が同じ向きに動いたら機構ではなく系を疑う**
(機構は特定の画面でしか発火しないので、内訳に偏りが出るはず)。

## 画面外要素の frame は信用できない —— XCUITest は容器の原点へクランプする(2026-08-05 実測)

**一時的な不整合ではなく、静止画面で常に成立する規則**。1回スナップショットを撮れば確認できる
(長時間の再現待ちは要らない)。E2E-iOS のスクロール画面(`UITableView`)を開いた直後の実採取:

```
[5]  table id=list_rows (16,270 370x395)     ← 容器は 270..665
[20] clickable "行 08" id=row_08 (16,662 …)   [21] staticText "行 08" (36,662 …)   ← 可視域内は親子一致
[22] clickable "行 09" id=row_09 (16,718 …)   [23] staticText "行 09" (16,270 …)   ← 子だけ容器の原点へ
[28] staticText "行 12" (16,270 330x56) … [56] staticText "行 40" (16,270 330x56)  ← 32 個が同一座標
```

- **可視域を外れた子孫は frame の原点が容器の原点にクランプされる**(サイズはそのまま)。
  親のセルは真の座標のまま返るので、**親子で矛盾したツリー**になる
- **セルが実体化していない行のラベルまでツリーに載る**(`row_12`〜`row_40`)。
  `cell.textLabel?.isAccessibilityElement = false` にしても消えない ——
  XCUITest の要素木は a11y ツリーそのものではない
- **実害はタップの空振りではなく「沈黙の誤タップ」**: クランプ先は先頭行の位置なので、
  `tap("行 15")` のようなラベル指定が **`row_01` をタップする**(2026-08-05 に実採取で再現。
  `ft_tap` した結果 `selected=row_01`)。`exist("行 15")` も画面外のまま真を返す =
  「exist は非スクロール(現在画面のみ判定)」の契約と食い違う
- 現状 E2E が踏んでいないのは、シナリオが**セル側(id 付き)**を指しているから。
  **利用者がラベルでタップを書くと普通に踏む**

**Compose iOS も同じクラスだが規則が違う**: あちらは縁をまたぐ行で
「原点はクリップ前・高さはクリップ後」の混成を返し、**中心が可視領域の外**に落ちる
(`#row_30` が `y=206 h=26〜45`・容器の上端は 230)。S0110 の失敗 21 件を分類すると
**またぎ 12 / 完全に外 7(うち ghost 注記あり2)/ 容器の中 2**。

**決着(2026-08-05・8並列で 160 サンプル)**: 失敗の**全部**でタップ座標が容器の外だった
(またぎ 26 / 完全に外 14)。しかも木は**1ピクセルも動いていない**(無変化の注記 17/20)
= **frame は安定していて、ただ間違っている**。だから:
- **整定を足しても無駄**(既に安定している) —— 触る直前に対象の静止を確かめる案は
  **fix 20/40 対 base 20/40 = 差ゼロ**で撤去した
- **送ると悪化**(動かすと座標がずれる) —— 掴み直しの対象をまたぎへ広げたら 2/10 → **5/10**
- **座標そのものを直すのが正解**: 中心が容器の外に落ちるときだけ
  **見えている部分(frame ∩ 容器)の中心を座標で撃つ**(`StepExecutor.visibleTapRect`)。
  交互 A/B(各40サンプル)で **base 18/40(45%)→ fix 5/40(12.5%)**、
  またぎクラスは **12 → 3**。残るのは「完全に外」= そもそも見えていない行を掴む形

**残りも決着(2026-08-05・8並列で さらに 176 サンプル)**。2段で消えた:
1. **救済は全画面スワイプで送っていた** —— ずれは 100pt 程度なのに1回が約1ページ動くので
   **行き過ぎて反対側へ出て往復する**(失敗 13 件は全部が救済を撃ち切り、tap 4.0s → 約8.0s、
   `#row_30` は容器の**上** y=116〜174 に戻っていた)。WebView のヒント跳躍と同じく
   **距離を測ってその分だけ**動かす(`recoveryJump` → `hintDrag`)。
   率では有意差が出なかった(4/40 対 7/40)が、**失敗の内訳が入れ替わった** ——
   「完全に外」5→0・「またぎ」2→0 で、残ったのは**容器のど真ん中**にある要素だけ
2. **救済で送った直後の1タッチを容器が吸っていた**。探索終端では空打ちドラッグで
   肩代わりしているのに**救済経路には無かった**。相関が決定的だった ——
   救済が走った 18 件のうち **4 件が失敗**、走らなかった 22 件は **0 件**(p≈0.03)。
   探索終端と同じ順序(肩代わり → 静止 → 掴み直し)を足すと **fix 0/48 対 base 8/48**(p≈0.006)

**通しの改善**: 45% → 12.5% → **0/48**。**回帰テストは S0110**(領域を指定しない探索)。

**⚠️ 事後の分類には注意**: 下の「またぎ 12/21」は失敗**時**の要素一覧から採ったもので、
「タップした瞬間の姿」ではない
(2026-08-05 に訂正)。**またぎは原因ではなく結果**のことがある —— 探索が掴んだ時点では
容器の中にあり、その後リストが動いて縁へずれた、でも同じ絵になる。
実際、下の修正を入れて S0110 を**スイート10周**回すと **8/10 通過・2/10 失敗(いずれもまたぎ)**で、
**修正は一度も発火していなかった**(`tap "#row_30"` の所要が10周とも 4.01〜4.11s = 追加スワイプ無し)。
= この screen では探索は**常に容器の中で**行を掴んでおり、ずれるのはその後。
**残りの本命は「掴んだ後に座標が古くなること」**(docs の計装記録でも FOUND y=347 → TAP y=249 と
98pt 動いていた)。iOS には Android の `bypassingCache` に当たる手が無いのが効いている可能性が高い。

**対処(2026-08-05・入れたが現状は潜在)**: `clippingAncestor` を**用途で2つに割った**。
旧実装は「祖先と交差しないこと」を条件にしていたため、**またいでいる行では nil に落ちて
viewport が画面全体になり**、「見えている」と誤判定して探索が止まっていた。
判定として正しいので残すが、**上のとおり現状の SUT では発火しない**(コスト0の保険。
同条件 A/B でスクロール系 39.3/39.7s 対 39.6/39.6s = 差なし)。

| 関数 | 条件 | 用途 |
|---|---|---|
| `clippingContainer` | 交差の有無を**問わない** | 見切れ判定の viewport。またぐ行を「見切れ」と判定して**もう1回送る** |
| `isOutsideContainer` | 容器と**交差しない**(完全に外) | ghost の掴み直し。またぐ行は ghost ではないので掴み直さない |

どちらも「同じ depth の兄弟が2つ以上その中に居る」ことを確かめてから容器を採る(叔父を掴んだ
ときに nil へ落とすため)。[[compose-ios-ax-frame-clamp]]

**対処(2026-08-05 実装)**: **ホスト側で解決候補から外す**(`ContainerGeometry.hasClampedCoordinates`)。
ブリッジ側で落とす案は採らなかった —— 要素集合が変わって `.型[n]` の序数・ref・`truncatedCount`
まで動くため。ホスト側なら候補の選び方だけが変わる。

**判定は症状ではなく機構で書く**。最初は「同じ場所に同 depth の要素が3つ以上」だけで書いたが、
**既存の単体テスト 13 件が落ちた** —— 同じ矩形を共有する兄弟自体は珍しくない。機構は
「**容器の原点にちょうど固定され、かつ容器より小さい**」なので、それを条件にする:

| 条件 | 何を守るか |
|---|---|
| 同一 frame(±0.5pt)が **3つ以上** | 親子2重で誤爆させない(`OcclusionSuspicion.isClampGhost` と同じ閾値) |
| **depth が同じ**(= 兄弟) | `homepage_container > app_bar > app_bar_container` のような**入れ子の連鎖**を残す(親子が同じ矩形を持つのは普通)。過去レポート 466 件へ当てて実際に引っかかった形 |
| 上位に**原点が一致し、より大きい**要素が居る | クランプ先が居ることの確認。居なければ「ただの重なり」と読む |
| 群が容器より**小さい** | 全面に重ねたオーバーレイ(容器と同じ大きさ)を残す |

**消したら必ず理由を書く**(`clampedStackHint`)。利用者には「ツリーには在るのに見つからない」と
しか見えないので、失敗文言に「N 個が同じ場所に積み上がっている / 先にスクロールして可視域へ入れる」
を添える。**黙って消すのが最悪**。

**当面の指針**: 位置に依存する判断(タップ座標・見切れ判定・覆い判定)は
**可視域内の要素の frame だけを信用する**。

## スクロールした直後のタップ(2026-07-27 修正済み)

スクロール探索(`scrollTo` / `tap(scroll:)`)の直後は、そのまま操作しても**別の要素を掴む(Android)**
**まったく効かない(iOS)**。`StepExecutor` の探索終端で2つの処置を**この順で**行って解消した。
利用者側の書き方は変わらない(回避策を覚える必要はない)。

1. **空打ちの極小ドラッグ(iOS のみ)**: Compose のスクロール容器は次の1タッチを消費してしまい、
   タップもプレスも効かない。クリックにならない 2pt ドラッグでその1回を肩代わりする
2. **静止待ち**: frame が連続2回同じになるまで待つ(最大 600ms・スワイプした周回だけ)

**`/tap` が古い ref の座標を撃っている率は `FT_STALE_TAP_PROBE=1` で測る**(保守者の測定スイッチ。XCUITest ランナーの ref の
`/tap` が撃つ直前に木を撮り直し、要素がもう控えた枠に居なかった回に注記 `stale-ref-at-tap`。断らずに撃つので判定は変わらず、
タップ1回ごとに撮り直しの費用(簡単な画面で実測 +21ms)を払い、撃つのもその分遅れる = 性能の測定と同時にしない。シナリオの子へ届くのは
`FT_` 接頭辞が子の環境の許可リスト(`ScenarioSandbox.inheritedEnvironmentPrefixes`)を通るからで、`e2ex.sh --on` の ssh の先へは
届かないので、ランナー機で直接 `FT_STALE_TAP_PROBE=1 Scripts/e2ex.sh …` と起こす)。

**空打ちが今も要るかは `FT_EMPTY_DRAG=off` で測る**(保守者の殺しスイッチ。2026-09-12 の計測:
止めて E2E-CMP / ios-xcuitest を3回回すと `S0080`(`selected=-`・注記 swallowed)と横向きの `S0020` が
3/3 で赤、E2E-Flutter は 2 回中 1 回 `S0080` が赤。単発の MCP witness(`scrollTo '#row_40'` → tap)では
吸われないので、**空打ちの要否は E2E の規模で判定する**)。

**木の形・型の名前からフレームワークを推定してはいけない**(同日の計測): Compose の XCUITest の木は「画面全体の
scrollView + 内側のリストは scroll 印の無い `other`」だが、実アプリのコーパス(iOS 22 画面)の
**10 画面(Safari の 7 画面・設定・写真・地図の経路)が同じ形**で、Flutter は容器が本物の scrollView
= UIKit と同じ形なのに空打ちが要る。型の名前も RN が Compose / Flutter と同じ顔ぶれ。誤検知は「行を押す」側に倒れる。
**使えるのは要素のクラス名だけ**(XCTest の非公開属性 5004 → `ElementInfo.axClass`。Compose / Flutter の要素は
`UIAccessibilityElement`、RN は `UIView`、SwiftUI は `NSObject`)—— 材料(.app/.ipa)と台帳の後の第3段として
掴んだ要素単位で使う(`AccessibilityClassHint`)。固定コーパス `Tests/Fixtures/AXClass/` が各フレームワークの値を
等号で固定する(Xcode の版で属性が変わったら落ちる = そのときは取れない側へ縮退する設計を確かめ直す)。

**iOS の空打ちを Android でやってはいけない**: Android では 2pt ドラッグが**クリックとして発火**し、
タップしていないのに行が選択される(= 二重実行)。`releasesScrollTouch` が唯一の分岐理由。

**空打ちは「対象が覆われていないとき」だけ打つ**(2026-07-27)。覆われている点を触ると
**覆っている側が反応する**。実害: E2E-iOS の `#txt_offscreen` はスクロール後に
**タブバーの帯(y 778〜840)の中**へ出るため、空打ちがタブバーに届いてホームタブへ切り替わり、
直後の `exist` が「要素が見つかりません」で **5/5 失敗**した(11:19 の空打ち導入から
E2E-iOS を回すまで気付かなかった)。**距離を伸ばしても・画面端から離しても直らない**
(ドライバの press→release はタップとして届く)。判定は
`StepExecutor.pointIsTakenByFrontElement`(**触る1点**が手前の別要素に入るか。
面積比の `OcclusionSuspicion.covering` では部分的な重なりを取りこぼし、並列実行の
フル E2E でだけ再発した)。

切り分けの記録(同じ実験を繰り返さないために):

| 試したこと | iOS の結果 | 分かること |
|---|---|---|
| `scrollTo` → `tap`(中間行) | ❌ `selected=-` | 現象 |
| `scrollTo` → `wait(2)` → `tap` | ❌ | **時間では解けない**(慣性・アニメーション待ちではない) |
| `scrollTo` → `tap` → `tap` | ✅ | **2回目は届く** = 1タッチが消費されている |
| `scrollTo` → `press` | ❌ | 別ジェスチャでも同じ |
| `scrollTo` → **固定ヘッダ**を `tap` | ✅ | タッチは配送されている。スクロール容器の中だけの問題 |
| **ios-inapp** プロファイル | ✅ 全て | in-app(ref)経路は無傷 = 座標の精度の問題ではない |
| ランナーで **XCUITest クエリ解決**して `element.tap()` | ❌ | **不採用**。届け方を変えても効かない |
| ランナーの整定待ちを 0.35→1.2s | ❌(揺れる) | **不採用**。1回の緑は雑音だった(なお 2026-07-30 にこの固定待ち自体を収束判定へ置換した。PT-3.8) |
| 「画面に収まるまで追加スワイプ」 | ❌ | **不採用**。frame は画面中央に完全表示でクランプではない |

- **既知の残: Android の `#row_25` 付近が確率的に落ちる**(`ロケータを解決できません` /
  スクロール探索自体の失敗)。**変更前から同じ**(ベースライン 3 回中 2 回で再現)なので本件とは別問題。
  フリング中に対象行がリサイクルされて消えるのが疑わしい

## `Scripts/e2e.sh`(fleetest 自身の E2E)

- SUT(`E2EAppCMP/` 他)の鮮度を見て必要なら再ビルドし、各プロファイルを順に回す。オプション:
  `--rebuild` / `--ios` / `--android` / `--cmp` / `--ios-native` / `--android-native` / `--flutter` / `--rn` /
  `--ios-xcuitest`(iOS を xcuitest モードで回す。既定は inapp モード。上記「1回の実行が見るのは…」節) /
  `--ios-inapp`(既定と同じモードで iOS のみ) /
  `--record`(録画パイプラインの整合チェック付き。詳細は下記「録画」節) /
  `--local`(各 run に `--runner local` = この Mac のデバイスだけ。E2EX を M1Ultra で同時に回すときの形) /
  `--align`(下記)
- **回帰の分担(ユーザー指示 2026-09-28)**: E2E はこの Mac(M2Ultra)で `Scripts/e2e.sh --local`、
  E2EX は `Scripts/e2ex.sh --on M1Ultra`(ssh でランナーのクローン `~/fleetest-runner/foundation-tester` に入り、
  **そこで SUT をビルドして**そこのデバイスで回す。残りの引数はそのまま渡す)を**同時に**起こす。向こうで動くのは
  align 済みのコミットなので commit → `Scripts/align.sh` → 実行の順。M1Ultra の道具(Flutter は
  ~/.local と ~/flutter、Homebrew の CocoaPods)は `~/.zprofile` の fleetest-tools ブロックの PATH にある
  (`zsh -lc` は `.zshrc` を読まない)
- **`--align`: リモートランナーの版ズレは「部分実行」ではなく「1本も走らない」**(2026-08-28)。
  複数機に跨るプロファイル(E2E-Android/android)は**開始前**の適合チェックで弾かれるので、
  手元を更新した直後のフルスイートはそのプロファイルのリモート担当ぶんが丸ごと欠ける
  (実際に 22 本中 14 本しか走らず、結果表には「1 of 14 failed」としか出ない)。
  `--align` を付けると実行前に `api remote-compat` を引き、**ランナーがこの clone の祖先
  (`remoteBehind`)のホストだけ** `fleetest remote align` する。**対象のホストは同時に揃える**
  (出力は機ごとのログへ分けて最後にまとめて出す。`Scripts/align.sh` と同じ形。1機ずつ待つと台数ぶん伸びる)。
  **既定では触らない** —— align はランナーの `.build` を差し替えるので、他人(や自分の別セッション)の
  run の下で走らせるとその run を SIGKILL で殺す(RR-18.3 規則2)。
  **向きを取り違えない**: `localBehind`(この clone が古い)・`diverged`(ブランチ作業)・
  未 push・toolchain 不一致・到達不能は**触らずに理由を1行出す**(align では直らない/直す側が逆)。
  判定の写しは `Scripts/e2e-align-plan.py` の1箇所だけで、祖先関係の計算は Swift 側
  (`FTRemote.RemoteCompat`)に任せる(2つ目の実装を作らない)。
  align が見るプロファイル集合は `planned_profiles`(実行ループの写し)なので、
  **実行後に実際に回した組と突き合わせて食い違いを警告する**(片方だけ直すと黙ってズレるため)
- **両OSを1プロファイルにまとめない**: platform 未指定シナリオは既定 platform のキューにしか入らず
  他方のワーカーが空回りする(DS-11.4)。SUT はネットワーク依存ゼロなのでバックエンド死活の
  切り分けは不要
- **フレームワーク差の退行は SUT を跨がないと出ない**。ブリッジのスナップショット/型写像
  (`SnapshotBuilder`・`BridgeRouter`)を触ったら SUT を絞らず全部回す。片方だけ通って
  もう片方が黙って空振りする類の退行が実際に出る(Compose の Button は `Cell`、View/XML は `Button` 等)
- **ディープリンクの URL スキームは SUT ごとに固有でなければならない**(2026-08-09)。
  iOS の E2E シミュレータには4つの iOS SUT が同居するため、共有スキームだと `openurl` の
  解決先が端末ごとに揺れる(実測で別アプリへ配送された)。`DeepLinkSchemeSyncTests` が
  契約(`E2EAppCMP/docs/ui-contract.md` §ディープリンク)との一致と SUT 間の重複を検出する

## SUT の Info.plist はコミットするソース —— URL スキーム等は直接編集する

iOS の SUT(E2EAppCMP / E2EAppIOS ほか)の `Info.plist` は `project.xcproj` と並ぶコミットするソースで、
ビルドでは書き換わらない。`DeepLinkSchemeSyncTests` が契約(`E2EAppCMP/docs/ui-contract.md`)との一致を守る。
Flutter / RN の SUT の `Info.plist` も同じ(ソース)。

## SpringBoard の確認アラートはアプリスコープのスナップショットに出ない(2026-08-09)

../design/dsl-syntax.md「openURL 後の SpringBoard 確認アラート自動了承」の実装対象。**システム UI が
アプリの上に載っていても、アプリスコープの木には1要素も現れない**(`com.apple.springboard` へ
attach したときだけ見える)。**「操作(タップ・入力)が効かないのに snapshot は正常」のときは、
木ではなく画面を撮る**(`xcrun simctl io <udid> screenshot`)。木だけを見ていると原因に
到達できない。

## E2E を同時に2つ走らせない(2026-08-09)

同じシミュレータ群で2つのスイート(サブエージェントの検証と自分の反復)を並行させたところ、
単独なら 22/22 緑のプロファイルが 16/22・11/22 失敗に崩れた。**フレーク判定の反復を始める前に、
他に実行中の run が無いことを確認する**(`ps aux | grep e2e.sh`)。サブエージェントにデバイス
検証を許可したら、その間は自分で回さない。

## デバイス上で説明がつかないときは、修正案より先に画面を撮る(2026-08-09)

RN のディープリンク不達を「JS 購読前の競合」と誤診し、ネイティブ側にリトライを入れて対処した。
真因は上記の SpringBoard 確認アラート(木に出ないため沈黙して見えた)で、**しかもそのリトライが
後で別のバグを生んだ**(戻る操作の直後に URL を再配送し、ホームへ戻った状態を上書きした)。
**誤った診断で入れた緩和策は、真因が判明した時点で外して再検証する**(直したつもりの層を
残したまま次の修正を重ねない)。
