# 検証: 検知・テスト・調べ方の規律

| 種別 | 範囲 | 読む場面 | 扱わないこと |
|---|---|---|---|
| 手順 | 検知の誤検知0・陽性対照・テストの破り方・計装と実採取・切り分けの進め方 | 検知やテストを足すとき・原因を調べるとき | 判定の規律(→ [judgment.md](judgment.md)) |

誤った結論を出さないための調べ方の規律。規律を見出しと冒頭に書き、事例は理由として短く添える。

## 「待ってから取り直す」を模すフェイクは**動く木**にする

割り込みを閉じた直後の取り直しを「整定を待つ」に変えた回、変異(整定を外して素の
`driver.snapshot()` に戻す)が**生き残った**。原因はテストのフェイクで、閉じるアニメーションを
**毎回同じ木**で模していた —— 整定は「同じ署名が2回」で成立するので、**静止した木では
待っても待たなくても同じ結果**になり、判定になっていなかった。

直し方は2つとも要る:
- **フェイクの木を動かす**(消えていくカードの frame をスナップショットごとにずらす)
- **長さを窓に入れる** —— 操作側のリトライ予算(3回)より**長く**、整定のポーリング上限
  (6回)より**短く**。短いと「どちらでも通る」、長いと「どちらでも落ちる」で、
  やはり判定にならない

一般化: **「待つ/待たない」の差は、待っている間に状態が変わるフェイクでしか出ない**。
整定・ポーリング・リトライを触るときは、フェイクが**時間とともに変わるか**を先に見る。
関連: 変異が生き残ったときの切り分け(フィルタ・先に落ちたテスト・変異式・テスト内容)。

## 私有 API の意味論は推測せず実採取する

CoreSimulator のような私有 API は、セレクタ名も引数の形もエラーの意味も**ヘッダが無い**。
推測で書くと、コンパイルは通るのに実行時に黙って誤動作する(objc_msgSend はシグネチャ違いを
検出しない)。**使う前に、その場で採る**:

1. **セレクタの実在と型エンコーディング**を `class_copyMethodList` / `method_getTypeEncoding` で
   採る。戻り値と out パラメータの有無はここで確定する
   (実例: `applicationIsInstalled:type:error:` の `type` は out パラメータで、
   知らずに引数を省くと引数の数が合わず落ちる)
2. **辞書キー等の定数は `nm -gU` でシンボルを探し、`dlsym` で実値を読む**
   (`SimDeviceLaunchApplicationKeyTerminateRunningProcess` = `"terminate_running_process"`)。
   実装でもリテラル直書きでなく dlsym で引けば Xcode 版差に強い
3. **エラーの意味論も採る**。「失敗した」だけでは足りず、**どの失敗か**を区別できるかを見る。
   実例: `applicationIsInstalled:` は「入っていない」も「判定できない」も `NO` を返し、
   前者だけが `NSPOSIXErrorDomain` code 3 を伴う。これを知らずに
   「`NO`+error は判定不能」と決め打ちしたら**未インストールの検出ごと壊れ**、
   逆に「`NO` は全部未インストール」なら端末が未 boot のときに嘘の失敗を出していた

**書き捨てのプローブで足りる**(`clang -fobjc-arc -framework Foundation`)。
ARC 下で out パラメータを受けるには `NSString * __unsafe_unretained *` が要る(素の `**` は
コンパイルエラー)。**採った事実は実装のコメントに数値・署名ごと残す** —— 次に Xcode が上がった
とき、何を採り直せばよいかがそこにしか無い。

## アプリの描画の時刻は SUT の描画プローブで採る

ツールの待ち(整定・応答)が画面の描画とどうずれるかは、**ツールの出力ではなくアプリ側の時刻**で測る
(自分の出力で外の性質を断定しない)。E2E の SUT には描画プローブが常備してあり、**有効にしない限り何もしない**。

| SUT | 有効にする | ログ(同じ場所)と時計 |
|---|---|---|
| iOS(E2EAppIOS・E2EAppCMP の iosApp・E2EAppRN の AppDelegate) | 起動の環境 `FT_RENDER_PROBE=1`(`simctl launch` は `SIMCTL_CHILD_FT_RENDER_PROBE=1`)。`2` は変わったレイヤーの持ち主のクラス名も出す詳細モード。環境を渡せない起動(in-app 注入)はアプリの `tmp/render-probe.on`(中身 `1` か `2`) | `tmp/render-probe.log`。`<CACurrentMediaTime> <レイヤー数>` = Simulator ではホストの `CLOCK_UPTIME_RAW` と同じ時計(Python 3.9 の `time.monotonic` は基準が違うので `clock_gettime(CLOCK_UPTIME_RAW)` で比べる) |
| Android(E2EAppAndroid・E2EAppCMP・E2EAppRN) | `adb shell run-as <pkg> touch files/render-probe.on`。release ビルドの RN は `/sdcard/Android/data/<pkg>/files/render-probe.on` | 目印と同じ場所の `render-probe.log`。壁時計の ms(ホストが `adb shell date +%s%3N` の往復が最短の回で差を測って揃える) |
| Flutter | iOS はアプリの tmp、Android は `run-as <pkg> touch cache/render-probe.on` | 同じ場所の `render-probe.log`。壁時計の ms |

- **目印ファイルは読んだら消える**(次の起動の1回だけ効く)。毎回の起動の前に置き直す。残る形だった間は、計測に使った端末で
  普段の起動・E2E でもプローブが回り続けていた(毎フレームの走査・書き込み = 性能の計測を乱す)
- 見ているもの: iOS = アプリがコミットしたレイヤー木(スクロールインジケータは除く。画面に出るのは次の vsync = 約 +16ms)、
  Android = View の描画(`OnDrawListener`。SurfaceView に描くものは見えない)、Flutter = フレームのコールバック
- 本体は SUT ごとに写しがある(iOS 3つ・Android 3つ)。直すときは全部を同じに直す(各ファイルの冒頭に写しの一覧)

## 「動き続ける画面」の対照はアニメーションで作らない —— E2E はアプリのアニメーションを止めて回す

実行プロファイルの既定(`enableAnimations` 無し = `AnimationPolicy` が無効化)では、Android は `animator_duration_scale` などを 0、
iOS は Reduce Motion をオンにして回す。**進捗バーの `tween`・回転インジケータ・Compose の `Animatable` は動かず一瞬で終わる**。
waitForSettle の時間切れの対照を E2EX の進捗の画面(2 秒の進捗バー + 回転インジケータ)で作ったら、両 OS で画面は本当に静止していて
「静止した」が正しい答えだった(実装の不具合ではなく対照の誤り)。

- 動き続ける画面が要る対照は、**この設定に左右されない動き**で作る —— スクロールの慣性(fling。iOS CMP 約 4 秒・Android 約 1.3 秒)。
  例: `TestProjects/E2E-CMP/scenarios/26_画面の静止を待つ.swift` の S0020
- 判定材料: 赤のはずが緑なら、まず端末のアニメーションの設定(`adb shell settings get global animator_duration_scale`)と、
  失敗時のスクリーンショットでその要素が最後の状態になっているかを見る

## ブリッジが「何を見ているか」は使い捨てのプローブ版で採る

a11y trait も Compose の役割マーカーもヘッダに無く、**推測で条件を書くと、緑のまま誤検出する**。
ブリッジは自前ビルドなので、**一時的に生の値を応答へ載せた版を焼いて1回読む**のが最短で確実。

- **Android**: `SnapshotBuilder.makeInfo` の `label` に `className` / `roleClassName` /
  `isVisibleToUser()` を連結する。**版を上げないと届かない** —— 稼働中の旧ブリッジが再利用されるので
  `build.sh` の `VERSION_CODE` を**捨て番(90 等)**にして `./build.sh --install`。
  ホスト(`expectedBridgeVersionCode`)は触らず、**`adb forward --list` で出たポートへ curl して直に読む**
  (`am instrument -w -e port 8123 … &` で自分で起動し直す)。
  `if (!node.isVisibleToUser()) return;` を外し `shouldInclude` を無効化すると**落とされた子まで**見える。
  戻すときは**捨て番から下げられない**(`INSTALL_FAILED_VERSION_DOWNGRADE`)ので、
  全機 `adb uninstall com.example.ftbridge` してから本番版を入れ直す
- **iOS(in-app)**: `InAppSnapshot.makeInfo` の `label` に `type(of:)` / `accessibilityTraits.rawValue` /
  `conforms(to: UITextInput.self)` を載せて `InAppBridge/build.sh`。注入は
  `SIMCTL_CHILD_DYLD_INSERT_LIBRARIES=<dylib> SIMCTL_CHILD_FT_PORT=<空きポート> xcrun simctl launch <udid> <bundleID>`。
  **アプリを変えれば同じ dylib でフレームワーク差がそのまま採れる**(Compose / Flutter / UIKit を1周)
- **採ったら必ず元へ戻してから**本番の条件を書く(プローブ版のまま指紋を貼り替えると
  `BridgeContractTests` が嘘の期待値で固まる)。バックアップは `git checkout` でなくファイルコピーで取る
- **採った数値は実装のコメントに残す**(traits の生値・実測した frame)。次に OS が上がったとき、
  何を採り直せばよいかがそこにしか無い

実例(2026-08-06): テキスト入力 trait が `1<<18` で Compose/Flutter 共通・分岐は `UITextInput` 準拠、
Compose の役割マーカーは画面端で**親と別の幅にクリップされる**(親 93px / 子 51px)。
どちらも推測では出せず、条件を1回で確定できた。

## 「回復したら公表を消す」は分岐ごとに書くと必ず片方を落とす

「回復したら公表を消す」処理は、**分岐ごとに書かず、関数の出口1箇所に置く**。「消し忘れを検出する」でなく「忘れられない形にする」。

実例: モニターの ❄️ が正常に描画しているタイルに出続けた。Android の回復は sleep/wake と guest restart の2段あるのに、共有ストアの消し込みが
sleep/wake の分岐にしか無く、guest restart で戻った機は run が終わるまで `.fleetest/frozen-<key>.json` に凍結が残った(モニターはそれを無条件に取り込む)。

- 切り分けの順序: 新しいモニターを別に起動したら誤検知ゼロ(= 表示・判定ではなく長時間動いているインスタンスの状態が原因)。
  次に配信抑制を疑って陽性対照(抑制下で1台を消灯 → 検知されるか)を通すと検知できたので抑制も除外され、公表経路にたどり着いた
- 直し方: 回復した機の `label` と `serial` を1つの記録(`repairedDevices`)にまとめ、消し込みは関数の出口1箇所だけに置いた。
  回復の分岐を足すときに「レーンに残す」だけ書いて「公表を消す」を忘れる、が型の上で起きない
- **残る弱点**: この配線を通るテストは無い(`excludeOrRepairBlankScreenWorkers` は AndroidHealthProbe の静的メソッドを直接呼ぶため差し替え口が無い)。
  「消し込みを外す」変異は生き残る。テストが担保しているのは `DeviceFrozenStore` の publish/clear/pid 判定までで、そこから先は構造で担保している

## 「画面が一様」は凍結の代理指標として弱い —— 初回描画待ちを凍結と誤認していた

**代理指標は「その症状が出る別の原因」を必ず持つ。分けたい2状態が同じ観測値を出さないかを先に確かめ、出すなら能動的に系を動かして応答を見る。**

実例: run 前トリアージは「一様なフレームが2連続なら凍結」で判定しており、フル E2E のたびに5〜10台を再起動していた。計測すると凍結と判定された 13台は
13台とも拍動が生きており、台数は描画の重さに比例した(E2E-iOS 0・E2E-RN 0・E2E-CMP 3・E2E-Flutter 10台=全機)。実体は**アプリが最初のフレームを描き終える前に判定していた**だけ
(サンプルは 1.5s × 2)。白画面の Android 機で HOME を押すとスクショが 24KB → 1.4MB になり、描画が生きていることも直接確かめた。

**拍動も代理指標として使えない**。「一様でも拍動(`displayIdleSeconds`)が生きていれば凍結としない」規則は、本物の wedge を故意に起こして観測すると、
画面が完全に固まっていても拍動が 0.001〜0.016s で回り続けた(拍動が測るのは「アプリが vsync を要求しているか」で「表示が進んだか」ではない)ので、本物を1件も検出できず撤回した。

- 現状: 拍動はホスト側の判定に一切使わない(`FrozenVerdict` に `displayIdleSeconds` 引数は無い)。判定材料は一様フレームと下記の能動プローブだけ。
  ブリッジの計装(`DisplayHeartbeat`)と DTO の `displayIdleSeconds` は、指紋ゲート(`BridgeContractTests`)の版上げ連鎖を避けるため**次のブリッジ変更に便乗して撤去する**(未着手)。
  `BridgeDTO.swift` の版履歴 64 は当時の記録として残す。**拍動を判定に使う前提で計器のコメントを書かない・採り直さない**
- **能動プローブ**: 黒画面には2種類あり、受動観測では原理的に分けられない。

  | 状態 | 受動観測 | 入力すると |
  |---|---|---|
  | 描画要求が無いだけ | 一様・拍動も生きている | **戻る**(凍結ではない) |
  | 本物の wedge | 同上 | 戻らない |

  run 前トリアージは「一様が約10秒続く → 画面を必ず変える入力を送る → それでも一様なら凍結」(`BlankWorkerTriage.observedVerdict` の `nudge`)。健全機には撃たない(一様でなければ1サンプルで抜ける)。
  一斉に force-stop/launch した直後に黒かった5台は、本物が1台で残り4台は HOME を押した瞬間に 15KB → 1.4MB へ戻った
- **プローブの副作用**: iOS は「別アプリを前面に出す」ため SUT が背面化し、in-app ブリッジが suspend してワーカーが離脱する(フル E2E で10件。うち9件は Flutter iOS)。
  **撃ったら SUT を前面へ戻す**
- 効果(フルスイート): 997.6s → 585.1s(−41%)・211/214 → 214/214。Flutter/ios-inapp-boost 単体は 387.0s → 98.9s

## 検知の「誤検知0」は、常に false を返す検出器と区別できない

検知は**陰性側(誤検知0)だけで確かめず、陽性対照(起こして検出されるか)を常設にする**。「誤検知0」は「検知が死んでいる」と同じ観測になる。

実例: モニターの凍結カウンタ(`Frozen: N`)は、実運用で一度も 1 以上にならないまま入っていた。当時の検証は3層あって、どれもこの欠陥を見られない構造だった:

| 検証 | 見ていたもの | なぜ通ったか |
|---|---|---|
| `MonitorFrozenDebounceTests` + 変異 4/4 | 判定構造体(純粋ロジック) | **呼び出し側が本番で到達しない**ことは範囲外 |
| 実デバイスで「10台すべてに frozen が乗り、60フレームで誤検知 0」 | NDJSON にフィールドが出ること | フィールドは判定器の出力と無関係に出る = **恒久 false の観測と同一** |
| `webviewFrozenIndicator.test.mjs` | `frozen:true` を与えたときの UI | 生成側を通らない |

真因は「配信を抑制中(タイルがストリーミング表示中)のデバイスはスクショ取得ごと飛ばす」ガードが
観測より手前にあったこと。実運用では**全デバイスが抑制対象**(iOS 10 + Android 8)なので、
検知は構造的に一度も走らない。

**規律**:
- **陰性側だけの確認で検知を入れない**。「誤検知0」は「検知が死んでいる」と同じ観測になる
- **意図的に起こせない事象には注入口を作る**(`FT_FAKE_FROZEN_KEYS` → `FrozenInjection`)。
  注入は**観測と公表の経路だけ**を通し、回復・除外のようなデバイスを触る動作は撃たない
- **陽性対照を常設テストにする**(`FrozenPositiveControlTests`: 注入 → run 前トリアージが
  `DeviceFrozenStore` へ公表 → モニターが凍結と言う → 注入を外すと消える)
- **呼び出し側の不変条件も純粋関数にして固定する**(`ApiMonitorCommand.capturePlan` =
  「抑制中でも観測は続く」。`MonitorFrozenWiringTests`)

実デバイスでの確認手順(この3つを通して初めて「動いた」と言える):

```bash
# ① 注入 → モニターがその機だけ frozen と言う

sleep 12 | FT_FAKE_FROZEN_KEYS=<UDID> .build/debug/fleetest api monitor \
  --project <p> --profile <run profile> --interval 2 | tail -1
# ② run が公表する(.fleetest/frozen-<UDID>.json に evidence:["injected"])

FT_FAKE_FROZEN_KEYS=<UDID> .build/debug/fleetest run --project <p> --profile <r> --scenario <s>
# ③ 公表だけを根拠にモニターが frozen と言う(注入なしでモニターを回す)

```

**モニターを `kill` で止めない**: NDJSON はブロックバッファリングされるので、SIGTERM で
落とすと**観測が丸ごと空になる**(実際に踏んだ)。`sleep N | fleetest api monitor …` にすると
**stdin EOF が終了指示**になり、自分で片付けて終わるのでバッファが flush される。

### FM の死を注入する

FM が死んだ状態でしか通らない経路が4つある —— **run 開始前の警告**
(`ProfileRunner.warnIfFMDegraded`)・**run.json の `fmDead`**・**まとめの1行**・
**モニターの FM 行**(グレーの線と `✕ text  ✕ vision`)。どれも**緑の run では1度も
実行されない**うえ、FM の間欠死は数分〜数時間で勝手に切り替わるので狙って作れない。
死活台帳(`FTCore.FMLiveness`)がそのまま注入口になる。

**① run の陽性対照**(警告・run.json・まとめを1本で通す):

```bash
DIR=/tmp/fm-inject && mkdir -p $DIR
# 鮮度の新しい dead を置く。プローブは「台帳が古いときだけ」撃つので、新しければ実呼び出しは

# 走らない。vision だけ / text だけ / 両方 で出し分けが変わるので、見たい形を書く

python3 -c "import json,time,pathlib;now=time.time();pathlib.Path('$DIR/fm-liveness.json').write_text(json.dumps({
  'text':  {'state':'alive','checkedAt':now,'source':'probe'},
  'vision':{'state':'dead', 'checkedAt':now,'source':'probe','error':'INJECTED'}}))"
chmod 500 $DIR   # ★ 読み取り専用にする
FT_FM_LIVENESS_DIR=$DIR .build/debug/fleetest run --project <p> --profile <r> --scenario <s>
```

**★ ディレクトリを読み取り専用にする**のが肝。しないと、**run 中の実 FM 成功が台帳を
`alive` で上書きして注入が消える**(ランナーの子プロセスは `FT_FM_LIVENESS_DIR` を継承する)。
台帳の書き込み失敗は握りつぶす契約なので、読み取り専用にしても run は壊れない。
run が `FMLiveness.freshSeconds`(120秒)を超えるなら、**別プロセスで 20 秒ごとに書き直す**
(書く瞬間だけ `chmod 700` → 書く → `chmod 500`)。

**② モニターの表示を目視する**(本物の VSCode パネルで見る唯一の方法):

```bash
# 本物の台帳へ新しい dead を書き続ける(20秒ごと)。プローブは古いときだけ撃つので

# 上書きされない。**止めれば60秒以内にプローブが実状態へ戻すので後片付けは要らない**

while :; do python3 -c "...上と同じ..." ~/.fleetest/fm-liveness.json; sleep 20; done
```

**注入した run は合否の判断に使わない**(FM を引くステップの挙動が変わる)。見るのは
警告・`run.json`・表示という**公表の経路だけ**で、これは `FT_FAKE_FROZEN_KEYS` と同じ規律。

## めったに撃たない経路は、緑を重ねても検証されない

「期限切れ直前だけ」「失敗したときだけ」しか通らない経路は、**フル E2E を何周回しても
一度も実行されない**ことがある。緑の回数は保証にならない。

実例: キャッシュを捨てて読み直す再試行(`/snapshot?refresh=1`)は URL 組み立てで
`?` が `%3F` にエスケープされ **404 で一度も成立していなかった**。単体テストは
フェイクドライバで「どちらのドライバへ流れたか」しか見ておらず配線を通らない。
E2E も、その経路が要る失敗(古い a11y を読む誤った赤)が出るまで沈黙した。
入れてから数時間・フル E2E 数百本を緑で通過している。

- **その経路を強制的に撃つ手段を用意する**(環境変数・テスト seam・専用の単体テスト)。
  今回は URL 組み立てを純粋関数へ切り出して直接検証した
- **「失敗時だけ動く安全網」を足したら、安全網自体が動くことを別に確かめる**。
  安全網は普段沈黙しているので、壊れていても誰も気付かない
- フェイクを使う単体テストは**配線(URL・ヘッダ・シリアライズ)を通らない**ことを意識する。
  そこが契約なら、契約の部分だけを純粋関数にして固める

### 陽性対照スイート(`Scripts/e2e-negative.sh`)

`_disabled/` の陽性対照(検知・門・クラッシュの記録を強制的に通すシナリオ)は、**回す運用を決めておかないと腐る**
(手で回す運用のあいだ 1度も回らず、97 の期待文言は実装と食い違い、Flutter/RN のクラッシュの指示は古い記録のままだった)。
一方、`e2e.sh` が既定で最後に回す運用はフル E2E を毎回約 10 分(本体 30 分の 3 割)延ばした。

**いまは既定で回さず、見ている部分が変わったときだけ推奨する**(ユーザー決定 2026-10-24。指紋照合
`heal-verify.sh`・FM 経路 `fm-verify.sh` も同じ扱い)。**回すのはユーザーの指示があるときだけ**
(`Scripts/e2e-negative.sh` を直接・または `Scripts/e2e.sh --negative`)。腐りの防ぎは推奨で担う:

- 監視対象は `Scripts/negative-controls.json` の `watches`(`common` = 陽性対照の全件・各 control の `watches` =

**見逃しの実例**: Android のネイティブのクラッシュ(Flutter の SIGSEGV)が `appCrash` に
載らず、失敗は「element not found」だけだった —— crash バッファには `Fatal signal 11` と `>>> <package> <<<` の
DEBUG ブロックが残るが、`AndroidAppProcessEvidence` は `FATAL EXCEPTION` しか見ていなかった。`nativeSignal` として
記録する。併せて DSL 側は crash バッファを時刻で絞らずに読んでいた(MCP は直近の launch 以降に絞っていた)ので、
シナリオの開始以降へ絞る(`AndroidAppProcessEvidenceQuery.scoped` を両方が通る)。**実害を対照で確かめた**:
「起動 → terminateApp → 要素を探して落ちる」だけの証人(このシナリオではクラッシュしない)を、crash バッファに
前の run の同じアプリの FATAL EXCEPTION が残る端末で回すと、HEAD は `appCrash: fatalException`(前の run の
PID を今の失敗に帰属)・直した版は空(`process not running` だけ)。表に `knownGap` を置くのは、記録されない事実を
⚠️ で出し続けるため —— 直ったら ❌ が表の更新を促す(今回それで外した)。

## 同じ機構を通る2経路で片方だけ失敗したら、機構でなく前提条件を疑う

interop WebView で「ref タップは効くのに座標タップが効かない」を座標のずれと誤診した。
ランナーのコードを読むと **ref タップも座標タップも同じ `coordinate(...).tap()`** で、
違うのは点の出どころだけだった。点が同じなら結果も同じはずなので、容疑は幾何ではなく
**その経路に入る前の状態**(attach・初期化・順序)に移る。実際の原因は直前の接続確認の不足だった。

- **まず両者の入力が本当に同じかをデバイス上で測る**(DOM と XCUITest の矩形を並べる。
  今回は `transform: translate(60px,0)` の要素も両方 `(76,477)` で一致し、座標は容疑から外れた)
- **次に機構が同一かをコードで確かめる**。同一なら差は状態にしかない
- この順序を踏まないと、正しい座標計算を「直す」方向へ時間を溶かす

## 切り分けは「実験系が効いているか」を先に確かめる

変更を入れて「差が出ない」「同じコードなのに結果が揺れる」ときは、仮説を疑う前に**実験系を疑う**。差が出ないことは、変更が無効だったことと実験が無効だったことを区別しない。
実例は Compose の探索不具合の調査で、実データの裏付けなしに3回誤った結論を出した。原因は2つの実験系の欠陥。

**① 差し替えたバイナリが実行されていない**

`StepExecutor`・ドライバ・セレクタ解決は `fleetest` ではなく **`fleetest-scenarios-<project>` サブプロセス**で動く(`RunOrchestrator.swift` 冒頭の契約)。
`swift build --product fleetest` して `.build/debug/fleetest` を差し替え `--skip-build` で回すと base と fix が同一のコードを実行するので、どんな変更も「差なし」に見える
(性能の A/B を誤って「退行なし」、修正案2件を誤って「no-op」と取り違えた)。

→ **陽性対照を先に通す**。マーカーファイルを書くだけの版をビルドして差し替え、実行してマーカーが出ることを確認してから本番の A/B に入る。手順は PT-4。

**② 観測値が前の run に汚染されている**

E2E アプリは選択状態や入力値を launch を跨いで永続する(だから `clearAppData` のシナリオがある)。検出器がそれを読むと壊れていても通る/直っていても落ちる。
実害: 「`scrollTo` が状態を書き換える」の報告が汚染と判明して撤回 → 正しい計装でやはり書き換えていたと確定、という往復。長く記録されていた
「狙った行ではなく数行先が選ばれる」も汚染由来の誤りだった(真の値は `selected=-`)。

→ **判定に使うシナリオは `clearAppData()` から始める**。とくに「操作していないのに値が入っている」形の検出器では必須。

**症状の記述が古いときは症状そのものを取り直す** —— 機構の説明も「画面外要素の frame をクランプ」と長く書かれていたが、実採取すると別物だった。

## 純粋関数が全部正しく緑でも、その入口に一度も入らなければ何も直っていない

純粋関数・単体テスト・変異テストが緑でも、**経路の手前で対象が弾かれていれば何も直っていない**。修正前に**詰みを再現するハーネスを先に用意し、ベースラインを取ってから直す**。

実例(実機ブリッジが起動し直されると `profile:` セッションが永久に詰む欠陥): 最初の修正は `isBound`(実機は listen を iproxy が引き継ぐのでランナー死後も true のまま残る)を
pid の生死で補強した。純粋関数は正しくテストも緑だったが、実機で撃つと直前と同じ "Cannot reach the driver" のままだった。
真因は手前で、`connectionLostHint` が `connections[key]`(表示用ラベル)の接頭辞で振り分けており、`profile:` 経路のラベル `"iPhone wave(実機) port 8144"` はどちらの接頭辞にも
一致せず、profile: のセッションは回復機構(`forgetConnection`)に一度も入っていなかった(DS-10「接続断からの回復は表示ラベルでなく記録で振り分ける」)。

既存の2節との違い:
- 「めったに撃たない経路は、緑を重ねても検証されない」 —— あちらは経路に一度も入らない。今回は経路には毎回入っていたが、中の振り分け条件が対象を素通りしていた
- 「切り分けは『実験系が効いているか』を先に確かめる」 —— あちらは実験系が壊れていた。今回は実験系も判定も正しく、経路の手前で対象が弾かれていた

ハーネスの形:
- fifo で MCP サーバの stdin を握り、**呼び出しの合間に**実機の XCUITest ランナーだけを kill する(iproxy は残す)。
  「listen は生きている(`isBound` == true)がランナーは死んでいる」という実機でしか起きない条件を確定的に作れる
- **修正前**は復帰の呼び出しが直前と**同一のエラー文**を返すことを確認してから直す(飛ばすと「直した」の基準が無い)
- **修正後**は「The XCUITest runner behind iPhone wave port 8144 exited」と名指ししたうえで、次の呼び出しが別ポートで起動し直して `ready: true` を返すことを確認する

## 陽性対照は「実装の誤り」だけでなく「設計と文言の嘘」も暴く

陽性対照は pass/fail でなく**出力の文言まで読む**。単体テストは「失敗文の主張がその回の観測と合っているか」を見ないので、主張と観測のズレは陽性対照でしか目に入らない。
**主張を含む文言を足したら、その主張が偽になる周回が無いかを設計で塞ぐ**。

実例: 要素数の上限で切り詰められた木から `notExist` が誤った成功を返す欠陥の最初の設計は「撮り直しは1アサーションにつき1回」の予算方式で、単体テスト14本・変異 14/14 とも緑だった。
陽性対照で、予算を使い切った2周目以降は既定上限(120)の木で判定するのに失敗文は「天井(400)でも切り詰められている」と名乗っていると分かった。
対策は、一度上限に当たったらその検証の残りを全部天井で撮る latch(判定に使う木が常に天井のものになるので、文言が構造的に嘘をつけない。撮影枚数も減る)。

**切り詰めの陽性対照はホスト側の一時パッチで作れる**: `StepExecutor` の snapshot 直前に `driver.raiseElementLimitOnNextSnapshot(1)` を1行入れるだけで、実ブリッジが 1 要素+truncated を返す盤面になる。
**ブリッジのソースには触らない**(触ると3ブリッジの指紋が動き、Android は版を上げると引き下げインストールができない = 戻せない)。
同型: 委譲 WebView の「中身が出ないまま待ちが尽きた」は `hasWebContent` を `false` 固定にする / RN の空打ちはプローブの戻り値を `nil` にする。どれもホスト側1行で、実ブリッジと実デバイスは本物のまま。

## 失敗の帰属は「HEAD での対照」で決める

変更の直後に出た失敗は、自分のせいと決めず、`git stash push -u` して **HEAD で同じシナリオを1本だけ回す**(stash → `swift build --product fleetest` → 1シナリオ → `git stash pop`。3〜4 分)。
「無関係だと思う」を根拠に報告するより安い。

- 実例: 4件の修正を積んだあと `Scripts/e2e.sh --ios-xcuitest --cmp` が 1/34 で落ちた。HEAD でも同じステップが同じ文言で落ちた。
  元からあった穴(WebView の入力欄を `#wv_input` だけで指しており、HTML id を a11y へ出さない xcuitest では解決できない。経路によって id と placeholder が入れ替わる)で、セレクタ側の修正まで繋がった
- **逆向きにも効く**: 「元からある失敗」と言い切る前に対照を取らないと、自分が壊した回帰を既存の不具合として見送る
- `git stash` は**未追跡ファイルごと**退避する(`-u`)。新規テストを置いたままだとビルドが食い違って対照にならない。戻したら `git status` の件数が退避前と一致することを確認する

## 単体テストが緑でも「実データで1回動かす」まで信用しない

単体テストは書いた本人の前提を共有しているので、前提そのものが誤っていると実装とテストが同じ誤りを持ったまま緑になる。
挙動を変えたら、単体テストの緑とは別に**最小構成で1回実行して出力を目で見る**(数十秒で、見つかるバグは中核であることが多い)。
特に「別の場所の副作用」「実際の文字列形式」「複数条件の混在」はテストの前提に取り込まれていて、テストでは出ない。

実例(LPT 投入順の実装 PT-3.7。単体テスト全通過のまま、実データを1回流すたびに別のバグが出た):

1. **ワーカー label のパース誤り**。`RunOrchestrator` のコメントが `例: "ios:8123"` のまま古く、実際の `ProfileWorkerFactory` の形は `"Pixel 9(Android 15)-01(android:emulator-5554)"`。
   デバイス名自体が `(` と `:` を含むため先頭 split が壊れていたが、テストも同じ誤った形式で書いていた。→ 生成と解析を `RunWorker.makeLabel` / `platform(fromLabel:)` に集約し、実形式での往復テストで固定
2. **`RunRecorder.begin` の副作用**。実行中の run のディレクトリが scanRecords の時点で既に存在し(中身は空)、履歴枠を1つ食っていた。副作用は別ファイルにあるのでコードを読むだけでは出ない
3. **単一 platform でしか試していなかった**。実績を `scenarioID` だけで集計していたため、同じシナリオを iOS/Android 両方で走らせる構成では中央値が両者の中間へ均されていた

## 自前 SUT に witness が無い形は、受け手の環境で取れたら台帳に書く

自前 SUT で代表できない形は、**SUT を増やす前に受け手の環境で取れないかを見る**。取れたら**どの環境で・いつ・何が緑になったか**をここに書く
(書かないと、次に同じ箇所を触る人が「witness が無い」と読んで作り直しにかかる)。受け手の報告は再現手順ごと控える(こちらでは再実行できないので、報告が唯一の記録になる)。

- 例: **OS で bundle ID が違うアプリ**は自前 SUT に1つも無い(5 SUT すべて ios/android 同一 ID)ので、「対象アプリを実行プロファイルから解決する」(`FTCore.ScenarioAppResolution`)の
  「同じコードが profile 切替で別の ID に解決される」部分は純粋関数のテストだけが担保していた。
  受け手の環境(OS ごとに別の bundle ID / package 名を持つアプリ)で埋まった(2026-08-19): `app:` を書かないシナリオで launchApp / appIs / removeApp / installApp / clearAppData
  すべてが実行プロファイル経由で解決され、両 OS で確認済み(`--profile android` は 8 シナリオ一括グリーン)
- SUT の bundle ID を片方だけ変える手もあったが、ビルド構成に触る割に得られるのは1形だけだった

## 修正の関門: 所見は再生できる形にしてから直す

探索・負荷の修正は、直した日のうちに取りこぼしと副作用を生む(10/31 の負荷の所見 19 件中 約 8 件)。前日までの手順の再生では
これを捕まえられない(10/31 の所見の机上の検証: 修正起因 14 件のうち前日までの再生で 4 件・同日の所見も元にすると 10 件)。
**再生は、後で回す資産ではなく修正の完了条件にする**。

- 誤った成功と回復の失敗を直すときは、`Scripts/replay-cases/` にケースを足す(形は同じフォルダの README)。
  **所見の手順に加えて、同じ故障・前提で経路だけ違う形**(MCP / DSL・ref あり / なし・別の SUT・別の OS)を `forms` に並べる。
  同じ手順だけでは机上の検出が半分に落ちる
- 足したケースは**対応する直しを外した版でも回して赤を確かめる**(`Scripts/replay.py --mcp <直しを外した fleetest-mcp>`。
  直しがブリッジの中なら古いブリッジで)。低率の形は緑の周回では判定できない。報告は率と 95% 上限で書く(0/10 の上限は約 26%)
- **赤を確かめられないケースは `redConfirmed` を付けず `redNote` に条件を書く**(緑の行に警告が出る)。高負荷でだけ出る形は、静かなマシンの緑を根拠にしない
- 確認は修正の担当と別の担当が、**そのコミットで**ケースを回す。USB・PIN・実機だけの故障はケースにせず、確認の手順を所見に書く
- 再生が捕まえるのは知っている形だけ。**探索は検出の主力として別に続ける**(同じ検証で、固定の課題と再生を足しても 69 件中 46 件は検出できない)

**固定の課題**(`Scripts/replay.py --suite baseline --record .fleetest/baseline.ndjson`)は修正の完了条件ではなく**回をまたぐ物差し**。検出の主力ではなく、誤った成功の率の推移を見るために使う。中身を変えない。行にはコミットとマシンの状態が付くので、**同じ負荷の回どうしで比べる**(la-F6 は load 70 以上でしか赤にならない)。

探索の手引きと所見の様式(`_work/` の brief.md)には次を必ず入れる:

```
## F<n>. <一行の主張>
- 重さ: 誤った成功 / 誤った失敗 / 文言 / クラッシュ / ハング / 回復不能 / その他
- 端末・アプリ・画面・そのときの負荷(Scripts/machine-state.py の出力)
- 再現(何回中何回): 撃った呼び出し → 応答の抜粋 → 別の手段で見た事実
- 期待:
- 根拠(分かれば): ファイル:行(推測は推測と書く)
- 直しとの関係: 直前の直しの退行 / 取りこぼし(同じ型の別の形)/ 既存 / 不明(コミットか所見 ID を添える)
```

**「直しとの関係」は収束の指標の元データ**(修正起因の割合)。10/30 午後の様式にあり、10/31 の様式で抜けて数えられなくなった。

## 新しい検知・警告は「既存資産の全数に当てて誤検知0」まで確認する

検知(警告・lint・修正提案)を新設したら、**単体テストが緑になった時点では半分**。
既存のシナリオ資産**全部**に当てて、誤検知が0件であることまで確認する。誤検知を出す検知は
オオカミ少年になり、**そのうち検知ごと無視される**ので、機能として死ぬ。

**単体テストでは出ない**。テストは書いた本人が想定した形しか試さないため
(「単体テストが緑でも実データで1回動かすまで信用しない」の系)。

実例(expectation のアサーション0検知を新設したとき)—— 単体テストは全部緑のまま、
既存213シナリオへ当てて**3件**ヒットした:

- 2件が**誤検知**。`expectation { android { notExist(…) } }` を iOS で回すと中身が実行されず
  0本に見える(E2E に実在する正当な書き方)。→ 実行しなかった条件ブロックを数え、
  1つでもあれば黙る抑止を追加
- 1件は**実バグ**。`appIs` が計数から漏れており、`verify { appIs(…) }` も**以前から**
  inconclusive になっていた。→ 同型の再発を落とすテストまで足した

**「データが無いとき」だけでなく「データが薄いとき」も試す**。`#id` の実在照合を足したとき、
「台帳が空なら黙る」は単体テストで確かめてあったが、**1画面だけ撮った台帳**で既存シナリオを回すと
**44/47 が誤警告**した(他画面の id を全部疑う)。空と満杯の間に、実運用でいちばん長く居る状態がある。
実データで1回動かすまで気付けなかった典型で、判定を「触る id の 2/3 以上が台帳に在るときだけ」へ
直して 44 → 2 件になった。

**OCR(occlusion-guard の Tier-2)の回帰は実 crop の固定コーパス**
(`Tests/Fixtures/OcclusionCrops/` の 3 枚 + `manifest.json`。`RegionTextCorpusTests` が
`swift test` で毎回走る):

- 固定するのは**言語集合ごとの読み取り**(日本語の集合には言語補正あり。2026-09-15 から)・**段ごとの
  読み取り**・**はしごが撃つ回数**の3つ。認識レベルを fast に落とす / 日本語の集合で言語補正を切る /
  拡大を止める / 言語規則を壊す、のいずれの変異もこの 3 枚が落とす
- **合成画像では代表できない**(6pt の合成文字は拡大すると悪化した = 実機の描画とは別物)。
  crop は実 run の measure モード(`FT_OCCLUSION_OCR=measure`)から採る
- Vision の**版は固定していない**ので、OS 更新で読みが変わればこのテストが落ちる(それが役目)
- **`RegionTextTests` / `RegionTextCorpusTests` が「読めるはず: []」で落ちたら、まず HEAD 対照**
  (`git stash push -u` → 同じテスト → `git stash pop`)。この Mac では Vision が**機械全体で数時間
  `[]` を返し続けて自然回復する**ことがある(2026-09-10。FM フラップと同じ ML 基盤)。自分の変更の
  せいに見えるが、HEAD でも同じ件数が落ちる
- **認識器の装置を変えると読みが変わる**(CPU に載せたら selected-row40 の ja+en ×3 が読めなくなった)。
  コーパスの `manifest.json` は**出荷する装置**(`RegionText.pickNonNeuralEngine`)の値で固定し、
  変えるときは装置ごとの差を `why` に書く

**OCR の近道が遅い/撃たれないときの診断**(2026-09-10 に組んだ計器。全部保守者向け・既定 OFF):

- `FT_OCR_HANG_SAMPLE=1` で run すると、シナリオ実行プロセスが `~/.fleetest/ocr-late/` に
  **コンパイルの顛末**(`compile-<pid>.json`: 所要・読めた行・ready になったか)と**諦めた読みの顛末**
  (`<pid>-<時刻>.json`: 本当の所要・段数・画素数)を書き、予算切れの後 3 秒たっても戻らない読みが
  あれば `/usr/bin/sample` で**自分のスタック**を `~/.fleetest/ocr-hang/` に落とす。
  **子の stderr は run のログには出ない**(親が `log` イベント → 疑似ステップへ畳む)ので、
  診断はファイルで採る
- `FT_OCR_BUDGET_MS=1` にすると近道が**必ず予算切れ**になり、諦めた読みの本当の所要が全件採れる
  (予算を広げて分布を見る用途にも同じ口)
- **単体テスト・素の CLI では再現しない**: xctest ホストは `com.apple.dt.xctest.tool` の、CLI は
  そのプロセス名のキャッシュを持っていてコンパイル済みに見える。**シナリオ実行プロセスの中で測る**
  (`fleetest run --scenario <1本>` に上の環境変数)。コールドにするには
  `~/Library/Caches/fleetest-scenarios-<project>/com.apple.e5rt.e5bundlecache` を消す
- 結果 JSON の読み方: `ocrMs`(OCR 段の所要)・`guardMs`(OCR + FM)・注記 `ocr-budget-exhausted`。
  1 プロセス内で `guardMs > 0` を並べて**最初の 1 件だけ桁違いに大きい**なら初期化の型
  (docs/results-json.md「TimelineStepRecord」)

**スナップショットの検知は dry-run では当てられない**(木が要る)。掃討は
**`Tests/Fixtures/RealAppSnapshots/` に固定した実アプリのスナップショット**へ当てる
(`SweepHarnessTests`。`swift test` で毎回走る):

- 画面ごとの検知件数を基準値と突き合わせる(`testDetectionCountsMatchTheBaseline`)
- タップ対象に対する警告率の上限 20%(`testWarningDensityStaysLow`)——
  **新しい検知が雑音になっていないかを自分で採点する**ための枠
- 採り直しは `FT_SWEEP_BASELINE=1 swift test --filter SweepHarnessTests/testPrintBaselines`
  (貼り付け用の1行と、**何が発火したかの明細**が出る)
- 別のコーパスを当てたいときは `FT_SWEEP_DIR=<dir>`(件数の照合はしない)

コーパスは `GET /snapshot` の生 JSON をブリッジから直接採る(手順は
`Tests/Fixtures/RealAppSnapshots/README.md`)。**Android(塗り順 `z` あり)/ iOS(`z` なし)/
自前 SUT(`disabled` の唯一の供給源)を必ず揃える** —— どれか欠けると、その経路の回帰が
素通しになる。**キーボード遮蔽(`keyboard` カウンタ)の供給源はキーボードを開いたまま採った
2枚**(`ios-maps_suggest_keyboard` / `and-maps_suggest_ime`。2026-08-08)—— `keyboardFrame` を
申告する新ブリッジ(iOS 版58 / Android 版53)でしか採れないので、採り直すときは版を確認する。
細帯(`sliver`)は現コーパスでは全画面 0 が基準(発火し始めたら誤検知をまず疑う)。
**`keyboard` / `sliver` は雑音密度ゲート(`warnedTappable`)に数えない** —— 画面の一時状態・
要素の細さであって恒常的な欠陥ではないため。keyboard 16 件の画面でも密度 20% を超えないのは
不整合ではなく設計。

**基準値を上げるのは、増えた分を1件ずつ見て真陽性だと確かめてから。**
黙って上げるとこの砦は現状の追認装置になる。

**必ず実アプリにも当てる。自前 SUT だけでは代表しない** —— 2026-08-06 に遮蔽・積み重なりの
警告を新設したときの掃討(6 構成 × 72 画面)は真陽性 34・誤検知 0 だったが、**同じ検知が
利用者の実アプリで5形の誤検知を出した**。2026-08-07 にも繰り返した: Google マップの
1セッションで誤検知3種類、同日の自前 SUT(3 SUT・44画面)は**0 件**。

**掃討ハーネスとコーパスはリポジトリへ固定する**(daf9712)。スクラッチパッドに置くと消える(同じセッション中に2回消えて採り直した)。
捨てるハーネスは単体テストが緑のまま実バグを出す(書き捨てた2回とも)。

**ハーネスの計数は production の関数を通すこと**: `disabled` の件数を `!e.enabled` と
自前で書いていたため、`RefGuard.disabledWarning` を壊しても素通しした(変異テストで発覚)。

引き継いでいる罠3つ(いずれも実害を出した):

- **1プロセスで通す**。`ft_launch` のセッションと直前の木を MCP が保持するので、
  1リクエスト1プロセスにすると照合も ghost 判定も全部壊れる
- **`ft_launch` の戻りは「投げた」であって「前面になった」ではない**。前面を確認してから
  進む。怠って**32画面すべて別アプリを読んだ**
- **ホーム画面で `back` を撃つとアプリを抜ける**。以降ずっと別アプリを読む。
  戻るのはサブ画面から1回だけ

### dry-run で全数に当てるレシピ(デバイス不要・1プロジェクト約15秒/49本)

構文・到達性・アサーション不足は**デバイス無しで判る**ので全数が安い(**セレクタの実在は
判らない** —— それはデバイス実行の仕事)。`--scenario` は**クラス名を渡すとそのクラス全体**を回す:

## 注記は「読んだ印象」でなく「まっさらなエージェントの手数」で足し引きする

注記・説明の類は、バグと違って**収束しない**(バグは初回12件 → 8〜11回目は実バグ0 → 直近は1〜2件に収束したが、注記は毎回3〜9件出続けた)。理由は構造的に2つ:

- **停止規則が無い**。「もっと分かりやすく言えたはず」は無限に出る。評価者(読んで違和感を探す側)が消費者と同一なので、必ず何か出る
- **加算しかない**。注記を足すほど出力が増え、次の監査で「雑音が多い」と指摘される面積が増える。実コストにもなった
  (iOS の律速がブリッジ(214ms)ではなく MCP 層の注記生成(13.6ms/要素)だった)

**対処は評価者を替える**。`Scripts/mcp-bench.sh` は、そのアプリを初めて触るエージェント(CLAUDE.md の無い作業ディレクトリ・fleetest の MCP だけ)に同じタスクを解かせ、
**完了率と ft_* の呼び出し回数**を測る。注記を1本落とした版と比べて手数が増えなければ、その注記は効いていない = 消してよい。**消すための根拠はこれ以外に作れない**。

判定の規律(詳細は Bench/README.md):

- **陽性対照を先に見る** —— 黙らせた run はサーバが起動時に stderr へ
  `FT_MCP_NOTES_OFF: silencing …` を出す(`bench.log` に残る)。これが無い run の A/B は無効。
  綴りを間違えた鍵は `NOT a note key (ignored)` で名指しされる
- **未完了の run を含む組は比較しない** —— 手数が少ないのは早々に諦めたからかもしれない
  (`bench-summary.mjs` の `compare` が構造的に弾く)
- **完了は成果物で判定する** —— 最終行の `RESULT:` をタスクの `expect` で照合する。
  「できました」という自己申告は使わない

## 注記の発火と出力コストはコーパス全数で台帳にする

`NoteCoverageTests` が `Tests/Fixtures/RealAppSnapshots/` の全数に `NoteCatalog` を当て、**注記ごとに「どの画面で発火したか」と「満額のバイト数」**を基準値と突き合わせる
(`SweepHarnessTests` は同じコーパスの RefGuard の幾何判定の件数を見る。層が別)。

`baseline` に発火した画面の名前をそのまま並べてあるので、少数のアーキタイプにしか並んでいない注記は、その形にだけ効いている疑いが目で見える。
分類の正は `NoteCoverageTests.archetypes`(接頭辞は OS を表すだけでアーキタイプは表さない)。

**「出ない」は「そのアプリがコーパスに無い」でしかないことがある。削除の根拠にする前に、必ずアーキタイプを足して測り直す。**
実例(2026-08-12 に地図以外を6枚足して測り直し): 「maps でしか出ない」と見えていた5本のうち3本はコーパスの偏りが作った幻で、19 枚の時点で削っていたら設定アプリとチャットで効いている注記を消していた。

| 注記 | 19 枚(map 14・ec 3・sut 2) | 25 枚(+ settings 2・chat/keypad/media/webview 各1) | 満額バイト |
|---|---|---|---|
| `duplicateIDsNote` | 12 枚 | 16 枚 / **5 アーキタイプ** | 15,057 |
| `ambiguousLabelsNote` | 15 枚 | 18 枚 / **6 アーキタイプ** | 10,015 |
| `unlabeledClickablesNote` | **map のみ** | map + **settings** | 4,031 |
| `truncatedLabelNote` | 4 枚 | 7 枚 / 5 アーキタイプ | 2,139 |
| `scrollFrameCandidates` | **map のみ** | map + **chat** | 1,852 |
| `keyboardCoverageNote` | **map のみ** | map + **chat** | 703 |
| `truncationNote` / `ghostNote` | **map のみ** | **map のみのまま**(各1画面) | 383 / 236 |
| `bulkExemptNote` / `sliverNote` | 0 枚 | **0 枚のまま** | — |

- 残った2本(`truncationNote`/`ghostNote`)は各1画面でしか出ないので、次に疑うならこちら
- 量の主因は上位2本(合計 25KB = 全体の6割)で、枚数を増やしても変わらない。どちらも「一意に指せるか」を言うもので 5〜6 アーキタイプで発火する = 汎用の側。**削るなら文面であって、対象ではない**
- 0 枚の2本は理由を確かめて `knownSilent` に登録してある(`bulkExemptNote` は全フィクスチャが `bulkExemptCount` を申告していない / `sliverNote` は縁で細帯に切れた操作可能要素が1件も無い =
  `SweepHarnessTests` の `sliver: 0` と一致)。**等号で照合する**ので、この免除表が「死んだ注記の置き場」になることはない(新しく黙った注記があれば落ちる)
- 採り直しは `FT_NOTE_COVERAGE=1 swift test --filter NoteCoverageTests`(貼り付け用の基準値・アーキタイプ別の内訳・1画面あたりのバイトが出る)

### アーキタイプを足すと検知の誤検知も出る

アーキタイプを足したら、幾何判定(`SweepHarnessTests`)の誤検知も測り直す。**自前 SUT の「4 SUT で誤検知0」は production を代表しない**。

実例: 実 web ページ6枚を足すと overlay が 14 件出た。全数検分で 10 件は誤検知: web の a11y は1つの文を run ごとの矩形で出し、
**折り返した run は前の run と同じ原点で2行ぶんの高さを持つ**(実測: staticText "A mobile app…"(16,332 254x23)と link "computer program"(16,332 328x51)は原点が一致し、後者が前者を完全に含む)。
iOS は z を持たないので後着が「手前」と読まれる(既知の「iOS に z が無い」型の一種)。雑音密度は 7/25 = **28%**(上限 30% のすぐ下)。残る4件は下部ツールバーがページ本文を覆う真陽性。
自前 SUT の4枚では1件も出ない形で、地図だけを深く掘っても出なかった。

## テストは「通ること」でなく「破ったら落ちること」を確認する

新しく書いたテストは、**production 側をわざと壊して落ちるか**を1回確かめる(変異テスト)。この確認だけで無力なテストが4件見つかった
(実例):

- TOOL_ROOT の照合が `fleetest-mobile` の**接頭辞一致**で、`fleetest-mobile-RENAMED` を素通し
- 時間集計のアサーションが「nil でないこと」止まりで、壁時計の計算を壊しても通る
- 走査 run 数の上限をテストが既定値のまま呼んでいて、上限を外しても差が出ない
- 同値の安定化を3要素で検証していて、比較器を壊しても偶然順序が保たれる

ソース走査テスト特有の無力化3種(OS/経路ごとに要求しないと片方を外す変異が生き残る・リテラル照合が引数の改行で落ちる・`if false` 型は見抜けない)は
この節末の「ソース走査テストにも同じ確認が要る」にまとめてある。

**やり方**: `Scripts/mutation-check.sh <mutations.json>` は **git worktree 並列**(ユーザー指示 2026-08-10)。変異の一覧(file / old / new / filter)を JSON で渡すと、
常設 worktree(リポジトリの隣の `<repo名>-mutwt/`。`MUT_JOBS` 本・既定4)へ**未コミットの
作業ツリーごと rsync** して変異を適用し、`swift test --filter` を並列に走らせて
OK(検出)/ SURVIVED(素通し)/ ERROR(適用失敗)の表を出す。
**本線のツリーには1バイトも書かない**ので、復元忘れ・「変異版バイナリのままデバイス検証」
(judgment.md「変異テストの後は製品バイナリを作り直す」)の型が構造的に起きない。
初回だけ worktree のコールドビルドで数分かかる(以後は増分)。
**worktree に運ぶのは git が無視していない物だけ**で、借りた worktree からは `.build` 以外の
無視物(前の変異のテストが残した results/・xcresult・SUT のビルド成果物)を毎回消す —— 放置すると
保持容量の掃除(本線の場所しか見ない)に映らないまま積もる(2026-09-16: 4 本で 65GB →
`Scripts/mutation-check.sh --purge` で 40.5GB 回収)。同じ worktree を2本で触らないよう
`<repo名>-mutwt/.mutation-check.lock` を取る(先客がいれば即座に断る)。
**filter には密閉されたテストだけを指定する** —— ホスト共有資源(`.fleetest/` 台帳・simctl/adb・
DiagnosticReports)に触るテストをプロセス並列で走らせると偽の失敗が出る(MN-4.9。ホスト共有資源の隔離)。
手で1件だけ確かめるときの旧手順(`cp` 退避 → 壊す → 実行 → 復元)も引き続き可。
**復元に `git checkout <file>` を使わない** —— そのファイルの**未コミットの変更が全部消える**
(変異を戻したつもりで、そのセッションの実装ごと巻き戻す。2026-08-03 に実際に踏んだ)。
検出できない変異が出たら
**テストを境界へ寄せる**(要素数を増やす・既定値でなく限界値で呼ぶ・観測可能な出力を assert する)。

**生き残りの最頻の型は「その節を1度も通らない入力しか書いていない」**。テストは呼ばれてもいるし緑でもあるので、フィルタや置き場所を疑っても何も出てこない。見るべきは
**変異した節に到達する前に、別のガードで落ちていないか**:

- 複数の条件を **and** で束ねた判定は、**片方だけが効く入力**を別に用意する。
  合成木の容器を画面いっぱいにしていたため「容器比」と「画面比」が同値になり、
  画面比を 0 にする変異を1つも殺せなかった(容器が画面の一部を占める木を足して解決)
- 絞り込みが**多段**なら、狙った段より前で落ちていないか確かめる。葉の判定は
  「scrollable でない」に加えて「容器より低い」も見ており、**容器と同じ高さの矩形を置いていた**
  ので前段で落ちて、後段を外す変異が素通しした
- **周期的・一様な入力は複数のガードに同時に当たる**。一様な並び(A,A,A…)は別のガードが
  先に落とすので、**そのガードだけが止めている形**(A,B,A,B… の周期)を別に用意する

**検出できないのが正しい場合もある**。Swift の `sorted(by:)` は仕様上は不安定だが実装は安定なので、
同値の安定化を外しても現在の挙動は変わらない(実測: 200要素・同値混在で順序保持)。この種の
「将来への保険」はコメントにその旨を書き、無理にテストを作らない。

**ソース走査テストにも同じ確認が要る**。走査は「文字列がそこにあるか」しか見ないので、書き方次第で無力になる:
見ないので、書き方次第で無力になる:

- **「分岐のどこかに1回あるか」で書くと、片方の OS/経路だけ外す変異を素通しする**
  (実測: iOS 実機監査の変異テストで `.ios` 側だけ呼び出しを落とした変異が生き残った)。
  `for platform in ["ios", "android"] { assert body.contains(...) }` のように
  **OS ごと・経路ごとに1本ずつ**要求する
- **リテラル照合は引数の改行で落ちる**(`resolve(\n    reported:` のような普通の折り返し)。
  **空白を潰してから照合する**(`components(separatedBy: .whitespacesAndNewlines).joined()`)——
  さもないと**配線ではなく整形を検査するテスト**になる(実際にこの形で落ちた)
- **ソース走査は `if false` 型の無効化までは見抜けない**(現実的な削除・呼び出し省略は捕まる)。
  「実行されないが文字列としては存在する」形の変異は走査の対象外と割り切る

## 拡張 webview のテストは jsdom にレイアウトが無い

`test/webview*.test.mjs` は実 HTML + 実バンドルを jsdom で動かすが、**jsdom はレイアウトを持たない**(`clientHeight`/`offsetHeight`/`getBoundingClientRect` は常に 0、
`offsetParent` は null)。「寸法を測って何かを決める」コードは分岐が1本しか通らず、緑でも無検証に近い。

- **再現の仕方**: 対象要素に `Object.defineProperty(el, 'clientHeight', { value: N, configurable: true })` で高さを与える
  (`webviewTileRelayout.test.mjs`。表示中=306 / `display:none` 相当=0 を切り替えてタブ往復を再現する)
- 実害: タイルの auto-fit がタブ復帰後に崩れるバグ(DS-12.5。非表示中に届く `devices` が `--tile-image-h` を潰す)は、表示中も非表示中も 0 で区別が付かず全ユニットテストが緑のまま残った
- レイアウト計算そのものは DOM 非依存の純関数へ切り出して単体テストする(`paneLayoutModel.js` ⇔ `paneLayoutModel.test.mjs`)。DOM 側テストは「実測して純関数へ渡す配線」だけ見る

## 排他は TSan で見る

共有状態のロック(`FTDriveCore.stateLock` / `FTRuntime.lock` [契約は DS-10] や `DeadlineTaskBox`)を触ったら **`swift test --sanitize=thread`** を通す。
**排他の正しさは目視レビューでは担保できず**、通常の `swift test` は緑のまま素通りする。

実例(レビューを通り抜けた競合を TSan が2件検出): ①`FTRuntime.shared.core` を tearDown が書き替える裏で違反スレッドが読む
②`RunOrchestrator.withDeadline` の満期 task 参照(「代入は同期区間で完了するのでレースしない」とコメントにあったが、`Task { }` の本体は囲みの同期区間と並行に開始し得る)。

**2つの罠**:
- **計装バイナリが `.build/debug` に残る**。TSan の後に E2E を回すと、シナリオが全部成功しても
  終了時に `Abort trap: 6` で落ちる(実害あり)。普通に `swift build` し直し
  `otool -L .build/debug/fleetest | grep -c tsan` が 0 になることを確認する
- **`Thread.sleep` のポーリング待ちは同期とみなされない**。実際には順序が付いていても
  `As if synchronized via sleep` 付きで報告されることがある(報告を読むときに見分ける)

## 調査用の計装は「恒久的な診断」として残る形で入れる

**計装の I/O はそれ自体が実験条件を変える**。タイミング由来の症状では、ファイル書き込み・ログ出力を足した時点で別の系を測っている。
**調査用に書いた計装は、そのまま診断として残す** —— 捨てる前提の計装は「次に落ちたときまた同じ物を書く」ことになる。

実例: 探索直後のタップずれは probe の I/O で消えて 42 回を無駄にした。ステップの**注記**(メモリ上の文字列を組み立ててレポートへ出すだけ・I/O なし)で計装すると、
1周目の失敗で `the element is still reported outside its scroll container (3 re-resolve(s))` が出て機序が確定した。
注記は修正後も残してあり、再発したとき第1機序か別機序かを注記の有無で見分けられる。

## 撃つ前に何を見たかは FT_BRIDGE_TRACE で採る

録画とランナーのログ(`.fleetest/bridge-<port>.log`)では「撃った操作」と「画面」は分かるが、**撃つ前にツールが木で見た位置**は分からない。
`FT_BRIDGE_TRACE=<id,id,...>` を付けた run は、シナリオのプロセスがブリッジ(XCUITest・in-app)へ送る要求を1件1行で stderr へ出し、
`results/runs/<月>/<runID>/events/<scenario>.ndjson` に `stream: "stderr"` の `bridgeTrace` として残る
(要求の時刻・所要・メソッドとパス・本文の先頭・status と、`/snapshot` なら指定した id の枠だけ。打鍵の文字列は文字数に置き換える。
定義は `FTBridgeClient/BridgeRequestTrace.swift`)。Android のブリッジへの要求は通らない。

- 実例: E2EX-CMP の無限スクロールの赤を `--broadcast` の 8 台 × 3 周で採り、赤 4 件と緑 20 件のタップ前後の木の位置を並べて形を確定した(MN-74.11)
- **木が言うことと画面が言うことを分ける**: 録画のクリップは `recordings/index.json` の `segments[].startedAt`(壁時計)から始まるので、
  bridgeTrace の `t` から引けばクリップ内の秒になる(シナリオの最初のイベントとクリップの頭の差は実測 0.01〜0.02 秒)。
  その時刻のフレームを AVFoundation(`AVAssetImageGenerator`)で取り出して見る。同じ「結果が空のまま」の木でも、録画では
  「タップが吸われた」(前者は2回目の空打ちで直した)と「タップは効いたのに木が変わらない」(Compose のタッチ範囲が削った枠による可視性検証の誤反転 =
  docs/framework-differences.md の `TouchOverhangFrameRestore` の行)の2つに分かれた
- **I/O を足す計装なので、上の節の注意が効く**。タイミングが効く症状では毎回「記録ありでも同じ率で出るか」を先に見る
  (この調査では記録ありの赤 24 回中 4 回、記録なしの棚卸し 24 回中 5 回で同程度)

## 既存テストは無料の「全数当て」

新しい検知を入れたら、単体テスト群が「全数当て」の役割を果たすことがある。**自分の変更で既存テストが落ちたら、まず「テストの期待値が古い」ではなく
「自分の検知が誤検知している」を疑う**。

実例: WebView の読み返しを入れた直後に `testDomInteropTypeFocusesByCoordinateThenTypesWithoutRef` が落ち、「value を報告しない要素では毎回二重入力になる」を捕まえた。

## 「届いていない」を推論で説明しない —— 生イベントを SUT 側で測る

ジェスチャが無反応のとき、**注入側の仕様から原因を推測すると外す**。SUT 側で生イベントを測る。

実例(ダブルタップ/ピンチ調査。推論と実測が2回とも食い違った):

| 推論 | 実測 | 実際の原因 |
|---|---|---|
| Compose に2打目が届いていない | **2打とも届いていた**(間隔 66ms) | **UP→DOWN が 0ms** = Compose の `doubleTapMinTimeMillis`(40ms)未満で捨てられていた |
| Flutter にピンチが届いていない | **2本指も移動も届いていた**(56 イベント) | **指の間隔が 8px→28px しか開かない** = Flutter のしきい値に届かない(Compose は比で見るので効く) |

- **SUT に一時的なプローブを足して画面へ出す**(`ft_snapshot` / 失敗レポートの要素一覧で読める)。値は「到達数・直前イベントからの時間差・同時ポインタ数・移動量」の4つで足りた
  - Compose: `pointerInput { awaitPointerEventScope { awaitPointerEvent(PointerEventPass.Initial) } }` で消費される前に数える(`changedToDown` / `changedToUp` と `uptimeMillis`)
  - Flutter: `Listener(onPointerDown:onPointerMove:)` でポインタ id を集合に入れ、2点間距離の初期値と最大値を出す
  - 読み出しは**わざと外れるアサーション**を1つ置く(失敗レポートが要素一覧を丸ごと出す)
- **プローブは調査が終わったら必ず外す**(SUT の契約に無い要素が残ると別のシナリオの序数がズレる)

## 決定は「根拠が消えたか」で見直す

決定の記録には理由が書いてあるので、**同じ領域を触るときは理由がまだ成立するかを見る**。成立しなくなっていたら、決定を守るのではなくユーザーへ再判断を上げる。
逆に「ユーザー決定・再提案しない」と書かれたものは根拠が消えても勝手に戻さない —— 判断の主体が違う。

実例: 「live / MCP は in-app ブリッジを使わない」(2026-07-28)の根拠は「`StepExecutor` を通らない `ft_*` は in-app だと `home` / `drag` / 座標 `press` が素の 501」で、
その後 `HybridFallbackDriver`(501 のときだけ XCUITest へ回す)で根拠が消えたのに決定だけが残っていた。再判断を上げて更新した。

## 検証に使う口と本番の口はモードまで揃える

シナリオ作成は「MCP(`ft_*`)で試す → シナリオに書く → 実行する」の流れだが、MCP は常に XCUITest・実行はプロファイルのモード、という差がある。
**MCP で無反応だったことは「できない」の証拠にならない** —— 無反応だったジェスチャは、シナリオ(プロファイルのモード)で確かめる。

- モードが変わると変わるのは成否だけではない。snapshot の中身(要素の型・id の見え方)も変わり、探索で採ったセレクタが実行時に無い、という静かな崩れ方をする
- 実例: Compose のダブルタップと Flutter のピンチは「MCP では無反応なのにシナリオでは通る」だった
- MCP の iOS を常に XCUITest にしている理由(in-app の合成タッチが注入される前提で作られていないアプリで、効かないまま ok を返した)は
  docs/design/bridge.md「MCP の iOS は常に XCUITest」

## プロトコルの既定実装は「実装漏れ」を黙って隠す

`AppDriver` は `drag` / 座標 `press` / `doubleTap` / `pinch` などに既定実装(501)を持つ。ラッパードライバが1つ書き忘れてもコンパイルは通り、
包む相手が実装を持っていても「未対応」を返す。フォールバック先がこれを返すと、ホストからは「どちらの経路でも 501」= 打つ手なしに見える。

- **新しい操作を足したときの掃討は「今足したもの」だけでは足りない** —— 同じ性質(座標で完結する = 誰が受けても同じ)の
  既存メソッドが全部揃っているかまで見る
- 実例: `AppAttachDriver` の座標長押しで踏み、掃討したら `SystemUIDriver` にも同じ穴があった(呼ばれていなかったので誰も気付かず)
- 再発は `DefaultImplementationForwardingTests`(ソース走査)が落とす

## 「このフレームワークでは無理」は経路ごとに測り直す

知見は「どの経路で測ったか」が落ちて広く適用されがちなので、**新しい操作を足すときはフレームワーク × ブリッジのマスを実際に埋める**。

実例: in-app の合成タッチは「drag はジェスチャ認識器に受理されない」と記録されていた(`press` / `swipe` が 501 な根拠にもなっていた)。
UIKit/SwiftUI では正しいが、Compose と Flutter は生タッチを自分のアリーナで捌くので、同じ合成タッチでピンチが成立した(2026-08-04 実測)。

| iOS | SwiftUI/UIKit | Compose | Flutter | React Native |
|---|---|---|---|---|
| XCUITest | ダブルタップ ✅ / ピンチ ✅ | ダブルタップ ❌ / ピンチ ✅ | ダブルタップ ✅ / ピンチ ❌ | 未実測(想定: uikit 経路 = SwiftUI/UIKit と同じ ✅/✅) |
| in-app | 両方 ❌(合成タッチを受理しない) | 両方 ✅ | 両方 ✅ | 未実測(想定: uikit 経路 = in-app 501 → xcuitest フォールバック) |

- 両者を足すと全マスが埋まるので、inapp-boost モード(既定)は 501 フォールバックで全部通る。MCP の iOS は XCUITest だけ。
  `HybridFallbackDriver` はライブ操作だけが使う。埋まらないマス(xcuitest 単独・実機)は docs/commands.md に明記
- **受理しない側で 200 を返さない**(返すと「成功したのに何も起きない」= 最悪の失敗モード)。in-app 側は uiFramework で判定して 501 を返す

## デバイス上で説明がつかないときは、修正案より先に画面を撮る

診断を入れる前に、**デバイスの画面を撮って木に出ない要素(SpringBoard の確認アラート等)が無いか**を見る。
木に出ないものは沈黙して見える。

実例: RN のディープリンク不達を「JS 購読前の競合」と誤診してネイティブ側にリトライを入れたが、真因は SpringBoard の確認アラートで、
しかもそのリトライが後で別のバグ(戻る操作の直後に URL を再配送してホームへ戻った状態を上書き)を生んだ。

**誤った診断で入れた緩和策は、真因が判明した時点で外して再検証する**(直したつもりの層を残したまま次の修正を重ねない)。

## スクロール探索の「飛び越し」を決定的に再現する

探索は「木を撮る → 解決する → 1回スワイプ」の繰り返しなので、**スワイプの合間に一度も
木に出なかった要素は原理的に見つからない**。既定経路(`scrollFrame` 未指定)は刻みが
ブリッジ任せで、1回の移動が容器を超えると起きる。発生率は 0.8% しかなく効果を測れなかったので、
**決定的に再現する witness 画面**を SUT に置いた(E2E-CMP の「飛び越し」画面 =
`#list_jump` / `#jrow_01..12`。寸法の意味は E2EAppCMP/docs/ui-contract.md)。

**witness を作るのに3回失敗した。同じ轍を踏まないために**:

1. **容器を画面中央に置いてはいけない**。Android の既定スワイプは**画面 70% → 30%**
   (`AndroidRunner/.../BridgeRouter.java`)。容器が中央だと**指が乗らず1ピクセルも動かない** ——
   「飛び越している」ように見えて実際は何も起きていなかった(2回ぶんの実験が無駄になった)
2. **「移動量 > 容器 + 行の高さ」でないと穴が空かない**。容器を大きくすると連続する可視域が
   重なって全行が見えてしまう。逆に容器が小さすぎると①に反する。
   **画面の 20% 前後の容器を 70% 地点に置く**のが両立点
3. **iOS(Compose)では同じ画面が別の病理を出す** —— 可視域の外の行が木に残る(ghost)ので、
   飛び越しではなく「掴めるが撃つと飲まれる」になる。**Android が飛び越しの正**

## 端に着いたら探索を打ち切り、逆向きに拾い直す

上の witness を使って2つ入れた。**どちらも `containerInference` で切れる**。

- **打ち切り**(`unmovedRoundsToStopSearch = 2`): 木が2周続けて1文字も変わらなければ、
  上限まで振らずに失敗させる。**打ち切る直前に `settledSignature` で確かめる**
  (2026-08-06 に Flutter/Android で誤発火 —— a11y ツリーは遅れて公開されるので、
  動いている最中でも2周続けて同じ木が返る。整定待ちなら遅れと停止を区別できる。
  費用は打ち切る局面の1回だけ)。**8スワイプ 7.40s → 2スワイプ 2.05s**(実測)。
  理由文には**実際の回数**を出す(上限を名乗ると「8回も振ったのに」と読めてしまう)。
  **文言は2形に分ける**(`contentEverMoved`。2026-08-15 の外部評価): 動いた末の停止は
  `the scroll area reached its end`、1度も動かなかった回は `nothing moved at all during the search`。
  どちらも `raising maxSwipes will not help` まで言い切る —— 旧文言 `stopped early` は
  「途中で諦めた」としか読めず、**実際は iOS の設定アプリでリストの末尾に着いていた**回を
  欠陥と受け取らせ、maxSwipes を上げた無駄な再試行を誘っていた
- **逆走査**(`reverseSweep`): 端に着いても見つからないときだけ、**推測した容器の中を
  逆向きに細刻みで戻りながら**毎周解決を試す。**通常の送りには一切触らない**ので、
  2度撤回した「暗黙の座標化」(PT-3.19)の撤回理由に抵触しない。
  救えたときはステップ注記に `found by sweeping back after overshooting it` を出す(黙って救わない)

**実装で踏んだ罠**(いずれもデバイス上でしか出ない。観測はすべて Simulator / Emulator):

- **逆走査をスワイプでやると慣性で反対の端まで走る**(189px 指定が約 700px 走った)。
  ドラッグにしても **hintDrag の 0.3〜0.7s ではまだ速い** —— 距離ぶんの時間を必ず取る
  `slowDrag`(120px/s)にして初めて刻める
- **容器の推測は3段構え**が要る。①スワイプ点から当てるのは**不可**(始点比率はブリッジ側の値で
  ホストは知らない)②**中身が入れ替わった領域**(Android。飛び越すと2枚の木に共通の要素が
  1つも無いので「消えた/現れた」で見る)③**動いた要素の clip 元**(iOS は ghost で id 集合が
  変わらないぶん frame が動く)④**子がはみ出している clip 領域**(静止した木だけから採る最後の手段)
- **逆走査の直後は `settledSignature` まで待つ**。遅いドラッグでも離した後に滑り、
  掴んだ座標とタップの間で 176px ずれて隣の行を叩いた

## ghost へのタップ防御は「そのステップが探索したか」を条件にしてはいけない

iOS(Compose)は可視域の外に出た行を木に残し、frame は容器の外を指す。掴んだままタップすると
**容器の外を撃って画面が何も変わらないまま成功として記録**され、後段の検証だけが落ちる。

防御(`grabbedGhost`)は入っていたが、条件に **`searchSwiped`(そのステップ自身が探索した)**が
付いていたため、**`scrollTo` と `tap` を別ステップで書く自然な書き方では丸ごと素通り**していた。
さらに救済側は **`step.direction` を要求**しており、素の `tap`(向きを持たない)は
ghost を検出しておきながら**1本も送らずにそのままタップ**していた。両方外した
(戻す向きは `recoveryJump` / `recoveryDirection` が幾何から決められる)。

**縁にまたがった行は触る前に容器の中へ寄せる**(2026-08-06 に解決)。見えている部分を撃つだけでは
足りない —— Compose は focus 時に bringIntoView で内容を動かすので、離すまでに隣の行が指の下へ来る。

## Android 凍結まわりの検証の罠

- **画面 OFF(KEYCODE_SLEEP)はフェイク凍結として万能ではない**: screencap は実凍結と同一の
  一様フレーム(<30KB)になるため **blank 検出・事前修復パスの検証には使える**(検出→sleep/wake
  修復→回復、が決定論的に再現する)。しかし **a11y 駆動(tap/type/textIs)は画面 OFF でも全て通る**
  (実測: シナリオ実行中に画面 OFF にしても 18/18 成功)ため、「シナリオ失敗→凍結判定→修復」の
  実行中経路は発火させられない。さらにシナリオの launch が画面を起こす過渡で別種の失敗が出る
  (注入アーティファクト。実凍結の症状ではない)。実行中修復パスの実発火はフェイクで強制できず、
  本番ログの「実行中の画面凍結を修復」で観測する
- **実凍結は事前修復が先に治すため「実行中だけ凍結」を意図的に作れない**(実凍結の誘発は
  8台並列 run の反復のみ。1台単独負荷・アイドルでは発生しない。PT-7)
- **凍結のホスト側証跡は `~/Library/Logs/fleetest/emulator/<AVD>.log`**(DeviceBooter が
  emulator stdout/stderr を保存。ブート毎 truncate)。根因の Metal エラー
  (`GLDRendererMetal command buffer completion error` / `IOGPUCommandQueueErrorDomain 518`)は
  ここにしか出ない(2026-07-25 実測)。凍結個体を調べるときはまずこのログを見る
- **エミュレータ操作は既定で emulator gRPC(EmulatorController)経由**(スクショ/キー・タッチ注入/
  停止等。実機・gRPC 失敗個体は自動で adb フォールバック。`Sources/FTAndroid/EmulatorControl.swift`)。
  gRPC 起因を疑うときは **`FT_EMULATOR_CONTROL=adb`** で全面 adb に切り替えて比較できる
  (gRPC を話すのは Swift だけ。拡張の凍結修復も `fleetest api repair-display` 経由でここを通るため、
  この環境変数1つで両方効く)。挙動差の切り分けはまずこれ。
  **iOS も同様に CoreSimulator 直叩きが既定**(DS-16.4)で、
  **`FT_SIMULATOR_CONTROL=simctl`** が殺しスイッチ。対象は**列挙だけでなく
  アプリ起動と未インストール検査も**(2026-08-02 拡張)なので、
  「launch がおかしい」ときもこれ1つで simctl 経路と比較できる
- **run が遅くなったら負荷トリアージを先に**: ① `top` で qemu の空転(劣化個体はアイドルでも
  ~73%/デバイス消費しホスト全体を遅くする)② run 同梱の `host-metrics.ndjson`(遅い run だけ CPU 飽和
  していれば環境要因)。Spotlight/mediaanalysisd のインデックスストームは CPU 数百%でも run を
  ほぼ遅くしない(M2 Ultra 実測)ので容疑から外してよい
- **guest reboot の完了判定は「1 でなくなる」→「1 になる」の2段で見る**: `adb reboot` 直後は
  まだ旧セッションが `sys.boot_completed=1` を返すため、いきなりブート待ちに入ると即成功して
  再判定が**凍結したままの旧画面**に当たる(run 前トリアージの実装 `ProfileWorkerFactory.rebootGuest`)。
  また再起動中は screencap 自体が失敗し、blank プローブは安全側の「非 blank」に倒れるので、
  **ブート完了を確認できない個体を blank 再判定に掛けてはいけない**(復帰と誤認する)
- **CPU 描画(swiftshader)フォールバックは emulator プロセスを再起動しないと戻らない**
  (`-gpu` は起動引数固定。ゲスト再起動・gRPC RESET では戻らない)。戻す経路はモニターの
  「GPUで再起動」「デバイスを全て起動」と、実行プロファイルの `recoverCpuFallbackToGpu`
  (DS-11)。**例外**: Wipe Data の再ブートは `startEmulator` の既定 `-gpu host` で
  起き上がるため、しきい値超過の個体は副作用で GPU に戻る(意図した復帰機能ではない)
- **凍結調査は両経路スイープで**(`adb screencap` サイズと gRPC スクショの画素一様判定を並記)。
  readback 白化と host キャプチャ黒は独立に壊れるため片経路だけでは誤診する。シナリオ成功率は
  表示層の劣化を映さない(凍結9/14台でも 18/18 成功する)。変種一覧・スケール上限・Metal エラー
  指標の正本は PT-7
