## 3. 既定待ち5秒のアサーションが 30〜113 秒かかり、120秒を跨いだ回だけ赤になる【大】

**再現**(1周目 E2E-CMP/ios-inapp): 6シナリオが `select` の
`the command timed out (120s)`(`failureKind: timeout`)で失敗。全て手元の8レーン、
リモート2機は0失敗。窓は 22:48:29〜22:50:57 で、**in-app ブリッジ8本を供給していた時間帯**
(`.fleetest/bridge-813*.inapp` の作成時刻 22:48:29〜22:50:04)と一致する。

失敗時の要素一覧には**探していた要素がそのまま写っている**
(例: `[4] staticText "selected=row_40" id=txt_row_selected`)= 要素は実在し、木が引けなかっただけ。

**素性**: 検証コマンドの既定待ちは `FlowStep.defaultWaitSeconds = 5` 秒。ところが
`StepExecutor+Assert` のポーリングは**期限を周回の合間でしか見ない**ので、1回の
`driver.snapshot()`(`BridgeClient.Timeout.session` = 45 秒)が伸びると 5 秒の予算を無視して
30〜100 秒進む。同じ窓で `select "#txt_row_selected"` が **104.9 秒かかって成功**した回もある
(同一症状の生存例)。**120 秒のコマンド上限を跨いだ回だけが赤**になるので、**赤は運次第**で、
同じ事象の大半は「緑だが 100 秒かかった」として黙って通っている。

FM のゲート待ちは原因ではない(この run の `fm.gateWait*` は 0)。

**記録の穴**: 残るのは `failureKind: timeout` と "the command timed out (120s)" **だけ**で、
「ブリッジが答えなかった」という事実が `notes` に載らない。今回は
ポートの割り当てとファイルの作成時刻から外形的に再構成するしかなかった。

**2・3周目では再現しない**(温まったフリートでは0件)。

## 4. `devices up` は1台も起動できなくても exit 0 で「✅ 完了」と言う【中】

**再現**: `fleetest devices up --project E2E-CMP --profile android` が
`❌ Pixel 9(Android 15)-03: the emulator exited before it registered with adb (status 1; ...)` を出したのに、
最終行は `✅ Device start-up sequence complete`・**exit code 0**。

**素性**: `DeviceBooter.bootItem` が `catch { log("❌ …") }` で握り、`bootAll` は Void を返し、
`DevicesCommand.Up.run` は無条件に ✅ を出す。

**同型(掃討)**: `ApiStartAllDevicesCommand` / `ApiRestartDevicesCommand` も個別の失敗を握って
`finished{ok:true}` を出す(後者の abstract は "exit code 1 when ok:false" と書いてあるが、
実際に ok:false になるのは device-not-found とプロファイル読み込み失敗だけ)。

規律「1台の失敗で全体を落とさない = **全滅のときだけ throw**」に照らすと、**全滅でも成功**は逸脱。
拡張側には「親の finished は ok:true のまま来るので中継された子の finished を見る」という
既知の注意書きが `vscode-fleetest/src/monitorDeviceLifecycle.ts` にあり、
**同じ穴の機械単位版は既に踏まれている**(今回はその台単位版)。

## 5. stale な AVD ロックでレーンが恒久的に死ぬ【中】

**再現**: `~/.android/avd/Pixel_9_Android_15_-03.avd/hardware-qemu.ini.lock` が前日から残存
(中身は pid 651。**その pid は再利用されて無関係の `cloudd` になっていた**)。
emulator は起動を拒否し、ログ(`~/Library/Logs/fleetest/emulator/<avd>.log`。**ツール自身が書いている**)に

```
FATAL | Running multiple emulators with the same AVD is an experimental feature.Please use -read-only flag ...
```

ところがツールの発話は `... Check the AVD name and <log>` で、**AVD 名は正しい**ので誤誘導。
手で lock を消したら即起動した(qemu プロセスは1つも無かった)。

**直す形**: 早期終了の経路で自分が書いたログの `FATAL`/`ERROR` 行をエラーに載せる。
多重起動の申告があり、**かつその AVD を握っているプロセスの実体が無い**ときだけ
`hardware-qemu.ini.lock` を消して1回だけ再試行する(`multiinstance.lock` は消さない)。
**生死は pid で見ない** —— 今回まさに pid 再利用で壊れた。
リポジトリの規律「台帳はプロセスの実体で掃除する」と同じ。

## 6. FM がブレーカで死んでいる run ほど `fmDead` が記録されない【中】

1周目の run は開始時点で FM が死んでいた(シナリオの errorLogs に
`Skipped 2 FM call(s) (circuit breaker open ...)`)のに、`run.json` の **`fmDead` は欄ごと不在**、
`scenarios/*.json` の `fm` は null。一方、run の**最中に**死んだ7本では正しく記録された。

**素性**: `RunRecorder` は閉じるとき `FMLiveness.current()`(鮮度 120 秒)を読む。
**ブレーカで落ちている間は誰も FM を呼ばない = 台帳が更新されない**ので、run が数分続くだけで
観測が古くなり「不明(欄ごと省略)」に落ちる。
`FMBreaker.isOpen` は mtime を1回読むだけの確実な事実なのに使っていない。
**「FM が死んだ run の緑」を仕分けるための欄が、まさにその場合にだけ黙る**。

## 7. ステップの内訳(snapshotMs / actionMs / waitMs)が結果 JSON に残らない【小】

`StepExecutor` は `StepTiming(durationMs:snapshotMs:actionMs:waitMs:)` を計測して
`ScenarioEvent` まで運んでいるのに、`RunRecord.TimelineStepRecord` は `durationMs` しか持たない。
§3 の「104 秒のうち何秒が snapshot か」を記録から言えない。
1ステップ3整数を足すだけで、遅いステップの仕分けが推測から観測になる。

## 8. 手法のメモ(次に同じことをやる人向け)

- **`--performance` を全周に付ける**とレーン数の変動が `measurementInvalid` で分かる(今回は0件 = 全周が計測に使える)
- **1周目は冷えたフリートの費用を含む**ので、比較は2周目以降で行う
- **同一 run 内に手元とリモートが居る構成は、機械固有の事象の対照がその場で取れる**
  (今回は FM の 60% 失敗が手元だけであることを、リモート2機の 0% と並べて即断できた)
- 遅いステップは `scenarios/*.json` の `timeline[].durationMs` を run 開始からの経過で並べると窓が見える
